## 二、OAuth 2.0 PKCE 完整流程

### 2.1 流程时序

```
1. 初始化
   → 创建 AuthCodeListener（OS 分配端口）

2. 生成 PKCE
   → Code Verifier: 43 字符 base64url 编码的随机 32 字节
   → Code Challenge: SHA256(verifier) base64url 编码

3. 构建认证 URL
   → 自动模式: http://localhost:{port}/callback（浏览器重定向）
   → 手动模式: https://platform.claude.com/oauth/code/callback（用户复制粘贴）

4. 等待认证码
   → 自动: AuthCodeListener.waitForAuthorization() 轮询 localhost
   → 手动: handleManualAuthCodeInput() 解析 Promise

5. Token 交换（client.exchangeCodeForTokens）
   → POST TOKEN_URL（含 code, state, code_verifier）
   → 服务器验证 PKCE 并返回 access/refresh tokens

6. 获取 Profile
   → getOauthProfileFromOauthToken() 丰富 Token 数据

7. 处理重定向
   → 自动: AuthCodeListener.handleSuccessRedirect() 发送浏览器到成功页
   → 手动: 无重定向

8. 清理
   → 关闭监听器和解析器
```

### 2.2 多环境 OAuth 配置

| 提供者 | 配置 | 用途 |
|--------|------|------|
| **Prod (Claude.ai/Console)** | `platform.claude.com`, `claude.ai` | 标准用户 |
| **Staging** | `staging.ant.dev` | 内部测试（ant-only） |
| **Local** | `localhost:3000/4000/8000` | 开发环境 |
| **FedStart Custom** | 允许列表 URL | PubSec/企业部署 |

## 三、Token 管理

### 3.1 Token 数据结构

```typescript
type OAuthTokens = {
  accessToken: string
  refreshToken: string
  expiresAt: number                    // Date.now() + expires_in * 1000
  scopes: string[]
  subscriptionType: 'max' | 'pro' | 'enterprise' | 'team' | null
  rateLimitTier: string | null
  profile?: OAuthProfileResponse
  tokenAccount?: {
    uuid: string
    emailAddress: string
    organizationUuid?: string
  }
}
```

### 3.2 Token 存储位置

| 存储 | 内容 | 安全性 |
|------|------|--------|
| **安全存储**（macOS Keychain/Linux pass） | accessToken, refreshToken | 高（系统级） |
| **全局配置** (~/.claude/config.json) | expiresAt, scopes, subscriptionType, rateLimitTier, tokenAccount | 中（文件级） |

### 3.3 Token 刷新机制

```
1. 检查过期: expiresAt < now + 5min 缓冲

2. POST TOKEN_URL
   → grant_type = 'refresh_token'
   → 请求特定作用域（默认 CLAUDE_AI_OAUTH_SCOPES）

3. 解析响应
   → access_token（必需）
   → refresh_token（可选 — 回退到旧的）
   → expires_in → 更新 expiresAt

4. Profile 获取（如未缓存则获取）
   → 优化：如果 config 中已有 profile 字段则跳过

5. 更新账户信息
   → displayName, billingType, accountCreatedAt 等

6. 返回新 OAuthTokens（合并订阅数据）
```

### 3.4 作用域扩展

```
后端允许超出初始授权的作用域扩展（ALLOWED_SCOPE_EXPANSIONS）
  → CLI 在刷新时请求完整 CLAUDE_AI_OAUTH_SCOPES
  → 支持仅推理 Token 提升为完整作用域
```

## 四、多 Provider 认证

### 4.1 认证来源优先级

```
1. CLAUDE_CODE_OAUTH_TOKEN           — 环境变量（托管会话）
2. CLAUDE_CODE_OAUTH_TOKEN_FILE_DESCRIPTOR — 安全管道
3. CCR_OAUTH_TOKEN_FILE              — CCR 子进程回退
4. apiKeyHelper                      — ~/.claude/settings.json 脚本
5. claude.ai OAuth token             — 安全存储
6. none
```

### 4.2 三方 Provider 支持

| Provider | 条件 | 认证方式 | 互斥 |
|----------|------|----------|------|
| **Anthropic 1P OAuth** | 默认 | OAuth 2.0 PKCE | — |
| **AWS Bedrock** | `CLAUDE_CODE_USE_BEDROCK=1` | IAM 凭证 | 与 OAuth 互斥 |
| **Google Vertex** | `CLAUDE_CODE_USE_VERTEX=1` | Google Cloud Auth | 与 OAuth 互斥 |
| **Azure Foundry** | `CLAUDE_CODE_USE_FOUNDRY=1` | Azure AD | 与 OAuth 互斥 |

### 4.3 API Key 管理

```
API Key 创建流程（client.createAndStoreApiKey）：
1. POST API_KEY_URL（Bearer {access_token}）
2. 服务器生成并返回 raw_key
3. 通过 saveApiKey() 保存到安全存储
4. 记录 tengu_oauth_api_key 事件

使用场景：
  → Console 用户：需要 API Key（Console 不使用 OAuth Token）
  → Claude.ai 用户：API Key 可选（可直接使用 OAuth Token）
  → 非交互式：SDK 调用者可能需要 API Key
```

### 4.4 安全验证

```typescript
// Token 过期验证
const bufferTime = 5 * 60 * 1000  // 5 分钟缓冲
isExpired = now + bufferTime >= expiresAt

// 作用域验证

// CSRF 防护（State 参数）
AuthCodeListener.validateAndRespond
  → state 必须匹配生成的 state
  → 不匹配时返回 400 错误
```

## 六、插件完整生命周期

### 6.1 发现与加载

```
发现来源：
1. 内置插件 — 保留名称，随 CLI 发布
2. 市场插件 — name@marketplace 格式
   → GitHub, NPM, git URL, git 子目录
   → 版本锁定：SHA 或 semver
3. 会话插件 — --plugin-dir CLI 标志（内联市场，会话作用域）

缓存策略：
1. 版本计算: SHA (git) 或 semver (marketplace)
2. 版本化路径: ~/.claude/plugins/cache/{marketplace}/{plugin}/{version}/
3. 遗留路径（回退）: ~/.claude/plugins/cache/{plugin-name}/
4. Seed 目录: BYOC 预填充缓存
5. ZIP 缓存: 可选的基于 zip 的缓存优化

加载流程（loadAllPlugins）：
1. 从所有设置作用域加载启用的插件列表
2. 对每个插件：
   a. 解析市场条目（获取/缓存）
   b. 下载/安装源（GitHub, NPM, git, 本地）
   c. 从 plugin.json 或 .claude-plugin/plugin.json 加载 manifest
   d. 用 PluginManifestSchema 验证 manifest
   e. 加载钩子配置
   f. 解析依赖（验证已启用）
   g. 检测/报告错误
3. 聚合已加载插件、错误和反向依赖
4. 返回 PluginLoadResult { enabled, disabled, errors }
```

### 6.2 安装流程

```
installPluginOp:
1. 解析插件标识符 (name@marketplace)
2. 查找市场条目
3. 检查策略（黑名单、严格允许列表）
4. 缓存插件（下载/提取到版本化路径）
5. 加载并验证 manifest
6. 检查反向依赖
7. 添加到指定作用域的设置
8. 记录 tengu_plugin_installed_cli 事件
```

### 6.3 更新流程

```
updatePluginOp:
1. 查找已安装插件（从 V2 数据或设置）
2. 获取新市场条目
3. 计算新版本
4. 如果版本不同：
   → 缓存新版本
   → 标记旧版本为孤立
   → 用新版本更新设置
5. 记录 tengu_plugin_updated 事件
```

### 6.4 卸载流程

```
uninstallPluginOp:
1. 在 V2 installed_plugins.json 中查找插件
2. 检查反向依赖（如果其他插件依赖则警告）
3. 从 V2 数据中移除安装
4. 删除插件缓存目录
5. 在所有设置作用域中禁用
6. 记录 tengu_plugin_uninstalled 事件
```

### 6.5 刷新机制

```
refreshActivePlugins:
1. 清除所有插件缓存
2. 重新加载所有插件（触发 loadAllPlugins）
3. 重建 MCP 连接
4. 更新 REPL 状态
```

### 8.3 隐私控制

**分析禁用条件**：
```
1. NODE_ENV === 'test'
2. CLAUDE_CODE_USE_BEDROCK=1（三方 Provider）
3. CLAUDE_CODE_USE_VERTEX=1（三方 Provider）
4. CLAUDE_CODE_USE_FOUNDRY=1（三方 Provider）
5. isTelemetryDisabled()（用户隐私设置）
```

**PII 处理**：
```
元数据类型安全 — 事件限制为 boolean | number | undefined
  → 无字符串：防止意外记录代码或文件路径

_PROTO_* 键 → 路由到特权 BQ 列（仅 1P 可见）
  → Datadog 传输前剥离

工具名称 → 编辑（mcp__ → mcp_tool）除非启用详细日志
文件路径 → 不直接记录
MCP 服务器名称 → 清理（除非官方或用户选择 OTEL_LOG_TOOL_DETAILS）

强制转换标记：
  AnalyticsMetadata_I_VERIFIED_THIS_IS_NOT_CODE_OR_FILEPATHS
    → 强制显式转换；记录意图
  AnalyticsMetadata_I_VERIFIED_THIS_IS_PII_TAGGED
    → 路由到特权列
```

## 九、事件传输架构

### 9.1 事件队列

```
1. Sink 附加前记录的事件 → 入队
2. attachAnalyticsSink() 调用 → 通过 queueMicrotask() 异步排空
3. 幂等：如果 Sink 已附加，为空操作
```

### 9.2 Datadog 传输

```
批处理策略：
  → 内存中批处理事件
  → 按定时器刷新（DEFAULT_FLUSH_INTERVAL_MS = 15s）
  → 或批满时刷新（MAX_BATCH_SIZE = 100）

传输：
  → POST https://http-intake.logs.us5.datadoghq.com/api/v2/logs
  → camelCase 转 snake_case
  → 标签字段: arch, clientType, model, platform, userType, version

过滤：
  → DATADOG_ALLOWED_EVENTS 白名单（基数控制）
```

### 9.3 第一方（1P）传输

```
基于 OTEL：
  → 构建 LoggerProvider + BatchLogRecordProcessor
  → 批配置来自 GrowthBook
  → 发射 LogRecord（含 event_name, event_id, attributes）

传输：
  → POST /api/event_logging/batch
  → 安全头认证
  → 属性: core_metadata, user_metadata, event_metadata

动态配置：
  → GrowthBook 标志控制批处理时序、大小、队列
```

### 9.4 采样配置

```typescript
// 每事件采样率
{
  [eventName]: {
    sample_rate: number  // 0-1
  }
}

// 不在配置中的事件 → 100% 记录
// sample_rate = 0 → 全部丢弃
// sample_rate = 1 → 全部记录
// 0 < rate < 1 → 随机采样（rate 添加到元数据）
```

## 十三、设计原则总结

| 原则 | 实现 |
|------|------|
| **多层认证** | 6 种认证来源优先级 + 4 个 Provider 互斥支持 |
| **安全存储** | 系统级 Keychain/pass + PKCE CSRF 防护 |
| **优雅降级** | Token 刷新 5 分钟缓冲 + 作用域扩展 |
| **插件隔离** | 版本化缓存路径 + 反向依赖检查 |
| **市场安全** | 官方保留名称 + 同形字防护 + 策略黑名单 |
