## 1. 这个文件在 skill 系统里的角色

`commands.ts` **不是 skill 模块的一部分**——它是整个 Claude Code 命令系统的"中央调度"，skill 只是它消费的若干来源之一。但它把 skill 系统的"对外接口"全集中在这一个文件里：

- **聚合**：把 file-based skill、plugin skill、bundled skill、built-in plugin skill、workflow command、内建 slash command 拼成一张总表
- **过滤**：按 `availability`、`isEnabled`、动态 skill 重新过滤
- **切视图**：从总表切出 `getCommands` / `getSkillToolCommands` / `getSlashCommandToolSkills` 三个视图给不同消费方
- **查找**：`findCommand` / `getCommand` / `hasCommand` 给上层用

打开 `restored-src/src/commands.ts`，准备并排读。

## 2. 第一段：内建命令清单（258-351 行）

这一段不是 skill 直接相关，但你需要先看一眼，因为后面所有"过滤"逻辑都要用到 `COMMANDS()` 这张表。

打开 `commands.ts:258-346`：

```ts
// 258
const COMMANDS = memoize((): Command[] => [
  addDir, advisor, agents, branch, btw, chrome, clear, color, compact, config,
  copy, desktop, context, contextNonInteractive, cost, diff, doctor, effort,
  exit, fast, files, heapDump, help, ide, init, keybindings, ...
  ...
  skills,    // ← 这是 /skills 菜单本身，不是 skill 列表！
  ...
])

// 348
export const builtInCommandNames = memoize(
  (): Set<string> =>
    new Set(COMMANDS().flatMap(_ => [_.name, ...(_.aliases ?? [])])),
)
```

**注意**：

- `COMMANDS()` 是函数（`memoize((): Command[] => [...])`），调用一次返回一张 commands 数组。memoize 让同一进程只计算一次。
- 第 300 行的 `skills` 是 `/skills` **菜单命令本身**——它是 `type: 'local-jsx'`，不是 skill。它会拿到当前命令表然后渲染 SkillsMenu 组件。**别和这一篇要讲的 skill 视图混淆**。
- 第 320-345 行有大量 `feature(...)` 守卫——KAIROS、BRIDGE_MODE、UDS_INBOX 等等。这些是按 feature flag 控制的内建命令，普通用户看不到。

`builtInCommandNames` 提供"哪些名字是内建的"——后面 `getCommands` 注入 dynamicSkills 时要用到（dynamicSkills 不能盖内建命令）。

#### 思考题

> `COMMANDS()` 用 memoize 包了，每次调用同一进程内只算一次。`getCommands(cwd)` 没 memoize，每次都重新过滤。这两个设计为什么不同？

（提示：内建命令清单是**进程恒定**的——同一进程跑不会变；而 `getCommands` 的过滤依赖 `availability`，auth 切换、feature flag 重置都会变。）

### 3.1 `getSkills(cwd)` — 拉四类来源（353-398）

打开 353 行：

```ts
async function getSkills(cwd: string): Promise<{
  skillDirCommands: Command[]
  pluginSkills: Command[]
  bundledSkills: Command[]
  builtinPluginSkills: Command[]
}> {
  try {
    const [skillDirCommands, pluginSkills] = await Promise.all([
      getSkillDirCommands(cwd).catch(err => {
        logError(toError(err))
        logForDebugging('Skill directory commands failed to load, continuing without them')
        return []
      }),
      getPluginSkills().catch(err => {
        logError(toError(err))
        logForDebugging('Plugin skills failed to load, continuing without them')
        return []
      }),
    ])
    const bundledSkills = getBundledSkills()
    const builtinPluginSkills = getBuiltinPluginSkillCommands()
    logForDebugging(`getSkills returning: ${skillDirCommands.length} ...`)
    return { skillDirCommands, pluginSkills, bundledSkills, builtinPluginSkills }
  } catch (err) {
    logError(toError(err))
    return { skillDirCommands: [], pluginSkills: [], bundledSkills: [], builtinPluginSkills: [] }
  }
}
```

#### 几个值得单独看的设计

**(a) 4 类来源的对应关系**

| 字段 | 来源 loader | 装载方式 | 是否异步 |
|---|---|---|---|
| `skillDirCommands` | `getSkillDirCommands` | 03 篇讲过：扫 `.claude/skills/` + `.claude/commands/` | 异步 |
| `pluginSkills` | `getPluginSkills` | plugin manifest 声明的 skill | 异步 |
| `bundledSkills` | `getBundledSkills` | `registerBundledSkill()` 注册的内存数组 | **同步** |
| `builtinPluginSkills` | `getBuiltinPluginSkillCommands` | built-in plugin 的 skill | **同步** |

后两者是同步函数，前两者是异步——**这是 `Promise.all` 只放了两个的原因**（同步函数放进去也不会加速）。

**(b) 两层 try-catch + 单路 `.catch`**

外层 `try { ... } catch (err)` 兜底返回空对象。

但内层每一路的 `.catch` 是更"细粒度"的：单路装载失败时不影响其它路——比如 plugin loader 挂了，file-based skill 还能正常进表。

外层 catch 注释（第 388 行）写："This should never happen since we catch at the Promise level, but defensive"——是防御性编程。

**(c) 每路失败都记 error，但是返回 `[]`**

这是 skill 系统的"软失败"哲学：**skill 不是核心功能，挂了不能拖整个 CLI**。这点和段 4 的 `getSlashCommandToolSkills` 的 try-catch 是一致策略。

#### 思考题

> 如果你把 `bundledSkills = getBundledSkills()` 这一行**也**塞进 `Promise.all`，比如 `Promise.all([..., Promise.resolve(getBundledSkills())])`，下面哪个会变？哪个不变？
> 1. 装载延迟
> 2. 失败隔离能力（bundled 同步抛异常时）
> 3. 代码清晰度

（提示：(1) 不变；(2) 同步抛异常会被 try 捕到外层 catch——所有 4 类都返回空，不再分路保留；(3) 一致排版可能更整齐，但语义实际更脆弱。）

### 3.2 `meetsAvailabilityRequirement(cmd)`（417-443）

```ts
export function meetsAvailabilityRequirement(cmd: Command): boolean {
  if (!cmd.availability) return true
  for (const a of cmd.availability) {
    switch (a) {
      case 'claude-ai':
        if (isClaudeAISubscriber()) return true
        break
      case 'console':
        if (
          !isClaudeAISubscriber() &&
          !isUsing3PServices() &&
          isFirstPartyAnthropicBaseUrl()
        ) return true
        break
    }
  }
  return false
}
```

注释 411-415 说得很到位：

```
Not memoized — auth state can change mid-session (e.g. after /login),
so this must be re-evaluated on every getCommands() call.
```

**这个函数被刻意排除在 memoize 之外**。auth 变了（用户 `/login` 切账号），过滤结果立即变。

skill 自己一般**不**声明 `availability`——skill 是用户/项目级的能力，不绑 auth provider。这个字段主要给内建命令用（比如 `/usage` 只对 console API 用户开放）。

### 3.3 `loadAllCommands(cwd)` — 总表组装（449-469）

```ts
const loadAllCommands = memoize(async (cwd: string): Promise<Command[]> => {
  const [
    { skillDirCommands, pluginSkills, bundledSkills, builtinPluginSkills },
    pluginCommands,
    workflowCommands,
  ] = await Promise.all([
    getSkills(cwd),
    getPluginCommands(),
    getWorkflowCommands ? getWorkflowCommands(cwd) : Promise.resolve([]),
  ])

  return [
    ...bundledSkills,
    ...builtinPluginSkills,
    ...skillDirCommands,
    ...workflowCommands,
    ...pluginCommands,
    ...pluginSkills,
    ...COMMANDS(),
  ]
})
```

#### 关键观察

**(a) memoize by cwd**

同一个 cwd 整个进程只跑一次。这是为什么 01 篇里 `initBundledSkills()` 必须在第一次 `getCommands()` 之前——一旦 `loadAllCommands` 拿到空 bundled 列表并 memoize，整个会话期间就回不来了。

**(b) 7 路并发**

注意拼接顺序：

```
bundled, builtinPlugin, skillDir, workflow, plugin commands, plugin skills, COMMANDS()
```

这个顺序决定了 `findCommand` 的命中优先级（`findCommand` 用 `.find`——第一个匹配赢）。

**为什么 bundled 排第一？**

bundled skill 是 Claude Code 自带、声誉最高的能力。如果用户写了一个同名 skill 想覆盖，结果是反的——bundled 赢。这是"内置 skill 不允许被影子化"的设计选择。

**为什么 plugin commands 在 plugin skills 前面？**

plugin commands 是 plugin 显式声明的 slash command，plugin skills 是约定目录扫出来的。plugin 作者写的 commands 优先级更高。

**(c) `pluginCommands` 和 `pluginSkills` 是不同的来源**

它们都来自 plugin，但分开装：

- `pluginCommands` 来自 plugin manifest 显式列的命令
- `pluginSkills` 来自 plugin 内 `skills/` 目录扫出的 skill

两者都通过 `loadPluginCommands.ts` 装载，但走不同的入口函数。

### 3.4 `getCommands(cwd)` — 对外的最终视图（476-517）

```ts
export async function getCommands(cwd: string): Promise<Command[]> {
  const allCommands = await loadAllCommands(cwd)
  const dynamicSkills = getDynamicSkills()

  // 基础命令（无动态 skill）
  const baseCommands = allCommands.filter(
    _ => meetsAvailabilityRequirement(_) && isCommandEnabled(_),
  )

  if (dynamicSkills.length === 0) {
    return baseCommands
  }

  // 动态 skill 去重 + availability 过滤
  const baseCommandNames = new Set(baseCommands.map(c => c.name))
  const uniqueDynamicSkills = dynamicSkills.filter(
    s =>
      !baseCommandNames.has(s.name) &&
      meetsAvailabilityRequirement(s) &&
      isCommandEnabled(s),
  )

  if (uniqueDynamicSkills.length === 0) {
    return baseCommands
  }

  // 找内建命令的边界，把 dynamicSkills 插在它前面
  const builtInNames = new Set(COMMANDS().map(c => c.name))
  const insertIndex = baseCommands.findIndex(c => builtInNames.has(c.name))

  if (insertIndex === -1) {
    return [...baseCommands, ...uniqueDynamicSkills]
  }

  return [
    ...baseCommands.slice(0, insertIndex),
    ...uniqueDynamicSkills,
    ...baseCommands.slice(insertIndex),
  ]
}
```

#### 这是 skill 系统对外的"出货口"。 关键点：

**(a) 三层处理**

```
loadAllCommands(cwd)        ← memoize，可能是空表（第一次跑）或缓存表
       │
       ▼
filter(availability + isEnabled)   ← 不 memoize，每次跑
       │
       ▼
插入 dynamicSkills (跳过名字冲突)   ← 在内建命令之前插入
```

**(b) dynamicSkills 单独拉，不进 memoize**

`getDynamicSkills()` 来自 `loadSkillsDir.ts`（03 篇段 4），每次 `getCommands()` 都现拉。

为什么不并进 `loadAllCommands` 里？

因为 dynamicSkills 是会**在会话过程中增长**的（FileRead/Write 触发新发现）。如果跟着 `loadAllCommands` 一起 memoize，新发现的 skill 永远进不了 `getCommands()`。

但是，**`loadAllCommands` 的缓存**对这一层是死的——加了新 dynamicSkills 后，要靠 `clearCommandMemoizationCaches` 清掉一些下游 memoize（看 3.6 节）。

**(c) 名字冲突 → 动态 skill 让步**（`494-498`）

```ts
const uniqueDynamicSkills = dynamicSkills.filter(
  s => !baseCommandNames.has(s.name) && ...
)
```

如果一个动态 skill 和基础命令同名（不管对方是 bundled、plugin、还是其它 skill），动态 skill 不进表。

这是合理的——dynamicSkills 是 lazy 发现的，名字冲突让对方赢更安全。

**(d) 动态 skill 插在内建命令之前**（`504-516`）

```ts
const insertIndex = baseCommands.findIndex(c => builtInNames.has(c.name))
return [
  ...baseCommands.slice(0, insertIndex),
  ...uniqueDynamicSkills,
  ...baseCommands.slice(insertIndex),
]
```

这是为什么动态 skill 名字虽然不能盖内建命令，**位置上仍然能"接近"内建命令**（被排在内建命令之前）。这影响 typeahead 顺序，但不影响 `findCommand`（因为已经按名字去重了）。

### 3.5 `getMcpSkillCommands(mcpCommands)`（547-559）

```ts
export function getMcpSkillCommands(
  mcpCommands: readonly Command[],
): readonly Command[] {
  if (feature('MCP_SKILLS')) {
    return mcpCommands.filter(
      cmd =>
        cmd.type === 'prompt' &&
        cmd.loadedFrom === 'mcp' &&
        !cmd.disableModelInvocation,
    )
  }
  return []
}
```

**MCP skill 走单独路径**。注释 543-546 解释：

```
Filter AppState.mcp.commands to MCP-provided skills (prompt-type,
model-invocable, loaded from MCP). These live outside getCommands() so
callers that need MCP skills in their skill index thread them through
separately.
```

为什么 MCP skill 不进 `getCommands()` 主流？因为 MCP commands 整体由 `AppState.mcp.commands` 管理（连接、断开、动态添加），生命周期不同步于 file-based skill。把它们一起塞进 memoize 总表会污染缓存。

`getMcpSkillCommands` 只是个"过滤器"——传入完整 MCP commands，过滤出 MCP **skill**（`loadedFrom === 'mcp'`）。注意 `disableModelInvocation` 在这里被过滤掉——MCP skill 默认是给模型用的，不能让模型调用就没意义。

`feature('MCP_SKILLS')` 是个总开关——MCP skill 能力可以整体关掉。

### 3.6 缓存失效函数（519-539）

```ts
// 519-532
export function clearCommandMemoizationCaches(): void {
  loadAllCommands.cache?.clear?.()
  getSkillToolCommands.cache?.clear?.()
  getSlashCommandToolSkills.cache?.clear?.()
  // getSkillIndex 是 EXPERIMENTAL_SKILL_SEARCH 那一层 memoize，外层
  // 必须显式清，不然内层清了但外层还把旧结果拿出来
  clearSkillIndexCache?.()
}

// 534-539
export function clearCommandsCache(): void {
  clearCommandMemoizationCaches()
  clearPluginCommandCache()
  clearPluginSkillsCache()
  clearSkillCaches()
}
```

**两个清理函数职责严格区分**：

| 函数 | 清谁 | 不清谁 | 用途 |
|---|---|---|---|
| `clearCommandMemoizationCaches` | `loadAllCommands` / `getSkillToolCommands` / `getSlashCommandToolSkills` / skillIndex | skill 装载本身的 cache、动态 skill 状态 | 动态 skill 新发现时——只刷视图，不重扫盘 |
| `clearCommandsCache` | 上面所有 + plugin commands + plugin skills + skill loader cache | （没有） | 全量 reset——比如 SIGUSR1 或 hot reload |

注释 527-530 解释了第二个细节：`clearSkillIndexCache` 是建在 `getSkillToolCommands/getCommands` 之上的**外层 memoize**，外层不清光清内层 = 外层永远拿旧结果。这是 lodash memoize 的常见陷阱——"双层 memoize 必须分开清"。

### 3.7 `getSkillToolCommands(cwd)` — 模型可调用 skill 视图（563-581）

```ts
// SkillTool shows ALL prompt-based commands that the model can invoke
// This includes both skills (from /skills/) and commands (from /commands/)
export const getSkillToolCommands = memoize(
  async (cwd: string): Promise<Command[]> => {
    const allCommands = await getCommands(cwd)
    return allCommands.filter(
      cmd =>
        cmd.type === 'prompt' &&
        !cmd.disableModelInvocation &&
        cmd.source !== 'builtin' &&
        // 自动放行的三类
        (cmd.loadedFrom === 'bundled' ||
          cmd.loadedFrom === 'skills' ||
          cmd.loadedFrom === 'commands_DEPRECATED' ||
          cmd.hasUserSpecifiedDescription ||
          cmd.whenToUse),
    )
  },
)
```

#### 这一段把"哪些 skill 能让模型通过 SkillTool 调用"的策略写成代码。

**5 道过滤门**：

1. `type === 'prompt'` — 必须是 prompt 型 command
2. `!disableModelInvocation` — 没有显式禁用模型调用
3. `source !== 'builtin'` — 不是内建 slash command（`/clear`、`/help` 这种）
4. **(自动放行 OR 显式描述 OR whenToUse)**

第 4 个是个 **OR 复合**：

- `bundled / skills / commands_DEPRECATED` — 三类自动放行（loader 会从 markdown 第一行抽 description）
- 其它情况（plugin / mcp）必须有 `hasUserSpecifiedDescription` 或 `whenToUse`

#### 为什么 plugin / MCP 要求显式描述？

注释 571-578 写：

```
Always include skills from /skills/ dirs, bundled skills, and legacy /commands/ entries
(they all get an auto-derived description from the first line if frontmatter is missing).
Plugin/MCP commands still require an explicit description to appear in the listing.
```

plugin / MCP 是**外部来源**，不像本地 file-based 那样作者随手写一句首行就足够——给模型看的列表如果有 description 不准的 skill，模型可能误调。所以**必须显式声明**才让进列表。

### 3.8 `getSlashCommandToolSkills(cwd)` — "skill 不是普通 slash" 视图（586-608）

```ts
// Filters commands to include only skills. Skills are commands that provide
// specialized capabilities for the model to use. They are identified by
// loadedFrom being 'skills', 'plugin', or 'bundled', or having
// disableModelInvocation set.
export const getSlashCommandToolSkills = memoize(
  async (cwd: string): Promise<Command[]> => {
    try {
      const allCommands = await getCommands(cwd)
      return allCommands.filter(
        cmd =>
          cmd.type === 'prompt' &&
          cmd.source !== 'builtin' &&
          (cmd.hasUserSpecifiedDescription || cmd.whenToUse) &&
          (cmd.loadedFrom === 'skills' ||
            cmd.loadedFrom === 'plugin' ||
            cmd.loadedFrom === 'bundled' ||
            cmd.disableModelInvocation),
      )
    } catch (error) {
      logError(toError(error))
      logForDebugging('Returning empty skills array due to load failure')
      return []
    }
  },
)
```

这个视图比 `getSkillToolCommands` 更严：

| 维度 | `getSkillToolCommands` | `getSlashCommandToolSkills` |
|---|---|---|
| `disableModelInvocation` | 必须 false | 必须有描述 OR `disableModelInvocation` |
| 描述要求 | 三类自动放行 | **必须有 description 或 whenToUse** |
| `loadedFrom` 范围 | bundled / skills / commands_DEPRECATED / 其它带描述 | **skills / plugin / bundled / disableModelInvocation** |

**关键点**：`getSlashCommandToolSkills` 不包括 `commands_DEPRECATED` 和 `mcp`，但**包括 disableModelInvocation 的 skill**——也就是"用户专属"的 skill 也算。

这个视图是给 **system prompt 看**的——告诉模型"这些是 skill，不是普通 slash command"。它进 attachment 系统的 `skill_listing`。

#### 三个视图的对比

整理一张终极对照表，把这一节读完留档：

| 视图 | 函数 | 主要消费方 | 主要排除 |
|---|---|---|---|
| 全表 | `getCommands(cwd)` | typeahead、`/help`、`findCommand` | (按 `availability + isEnabled` 过滤) |
| **模型可调用** | `getSkillToolCommands(cwd)` | `SkillTool` 自动调用列表 | builtin、`disableModelInvocation`、plugin/MCP 没描述的 |
| **skill 列表（system prompt）** | `getSlashCommandToolSkills(cwd)` | system prompt 注入、attachment 系统 | builtin、没描述的、`commands_DEPRECATED`、MCP（除非 `disableModelInvocation`） |
| `/skills` 菜单 | （在 `SkillsMenu.tsx` 里手写过滤） | `/skills` 菜单 UI | bundled、commands_DEPRECATED 之外 → 只展示 skills/plugin/mcp/legacy |

注意第四行——`/skills` 菜单**不**是从这三个视图拿的，**它有自己的过滤**。打开 `restored-src/src/components/skills/SkillsMenu.tsx:234-236`：

```ts
function _temp(cmd) {
  return cmd.type === "prompt" && (
    cmd.loadedFrom === "skills" ||
    cmd.loadedFrom === "commands_DEPRECATED" ||
    cmd.loadedFrom === "plugin" ||
    cmd.loadedFrom === "mcp"
  );
}
```

`/skills` 菜单展示 `skills / commands_DEPRECATED / plugin / mcp` 四类，**不展示 bundled、不展示 builtin plugin skill**。

为什么？因为 bundled 和 builtin plugin 是"出厂自带"，菜单展示它们会让用户混淆"自己装的"和"系统给的"。`/skills` 菜单回答的是"我装了哪些 skill"，不是"我能用哪些 skill"。

#### 思考题

> 一个 skill 同时设了 `disableModelInvocation: true` 和 `userInvocable: false`：
> 1. 它会出现在 `getCommands(cwd)` 里吗？
> 2. 出现在 `getSkillToolCommands` 里吗？
> 3. 出现在 `getSlashCommandToolSkills` 里吗？
> 4. 出现在 `/skills` 菜单吗？
> 5. 用户能 `/name` 调用吗？
> 6. 模型能用 SkillTool 调用吗？

（答：1 出现 — 仅按 availability/isEnabled 过滤；2 不出现 — `disableModelInvocation` 把它排除；3 出现 — 它满足 `disableModelInvocation` 这条 OR 分支；4 出现（如果 loadedFrom 命中四类之一）；5 不能 — `userInvocable: false`；6 不能 — `disableModelInvocation: true`。
**结论**：这种配置基本不可调用——可能仅作为 system prompt 提示存在，模型看到了名字但调不动。这是个非常诡异的状态，多半是配置错误。）

## 4. 第三段：findCommand 与一致性辅助（688-790 行）

这段很短，但很重要——用户输入 `/foo` 之后到底匹配哪个 command 取决于 `findCommand`。

### 4.1 `findCommand`（688-698）

```ts
export function findCommand(
  commandName: string,
  commands: Command[],
): Command | undefined {
  return commands.find(
    _ =>
      _.name === commandName ||
      getCommandName(_) === commandName ||
      _.aliases?.includes(commandName),
  )
}
```

三个匹配条件 OR：

1. `name` 严格相等
2. `userFacingName()` 相等（plugin skill 有 prefix-stripping 时用）
3. `aliases` 包含

**`.find` 是 `Array.prototype.find`——返回第一个匹配的**。所以：

- 命令在 commands 数组里的**位置决定优先级**
- `loadAllCommands` 拼接顺序就是优先级顺序：`bundled, builtinPlugin, skillDir, workflow, plugin, pluginSkills, COMMANDS()`

### 4.2 `getCommand`（704-719）

```ts
export function getCommand(commandName: string, commands: Command[]): Command {
  const command = findCommand(commandName, commands)
  if (!command) {
    throw ReferenceError(
      `Command ${commandName} not found. Available commands: ${...}`,
    )
  }
  return command
}
```

`find` 找不到就抛 ReferenceError，并把所有可用命令列出来。这是个 dev-friendly 错误——但要注意，错误信息里**会包含所有 skill 名字**，可能很长。

### 4.3 `formatDescriptionWithSource`（728-790）

这个函数把 `cmd.description` 包装成"带来源标签"的字符串。给 typeahead UI 展示用。

```ts
// 728-790 大致逻辑
export function formatDescriptionWithSource(cmd: Command): string {
  if (cmd.type !== 'prompt') {
    return cmd.description
  }
  if (cmd.kind === 'workflow') {
    return `${cmd.description} (workflow)`
  }
  if (cmd.source === 'plugin') {
    const pluginName = cmd.pluginInfo?.pluginManifest.name
    return pluginName ? `(${pluginName}) ${cmd.description}` : `${cmd.description} (plugin)`
  }
  if (cmd.source === 'builtin' || cmd.source === 'mcp') {
    return cmd.description
  }
  // 其它来源继续...
}
```

注释 723-727：

```
Use this in typeahead, help screens, and other places where users need to see
where a command comes from.
For model-facing prompts (like SkillTool), use cmd.description directly.
```

**给用户看带来源标签，给模型看不要标签**——避免污染 prompt。这是给"哪个文本给谁看"画的清晰边界。

## 6. 一个端到端 verify 例子的"在 commands.ts 里的旅行"

把 01 篇的 verify 接到这一篇上：

```
启动期：registerVerifySkill() 把 verify push 进 bundledSkills[]

第一次 getCommands(cwd) 调用时：
  loadAllCommands(cwd) 并发跑，verify 出现在 getBundledSkills() 返回值里
  loadAllCommands 把它放在拼接表的最前面（bundled 排第一）
  loadAllCommands 把整张表 memoize 住

每次 getCommands(cwd) 调用：
  从 memoize 拿 loadAllCommands 结果（包含 verify）
  filter by availability + isEnabled（verify 没设 availability，无 isEnabled，过）
  没动态 skill → 直接返回

用户敲 /verify：
  findCommand('verify', commands) 找到 verify（在表第一位）
  type === 'prompt' → 走 processPromptSlashCommand
  ...

用户打开 /skills 菜单：
  SkillsMenu 接收到 commands
  SkillsMenu._temp 过滤 loadedFrom in {skills, commands_DEPRECATED, plugin, mcp}
  verify 的 loadedFrom === 'bundled' → **不在菜单里**

模型通过 SkillTool 调用 verify：
  SkillTool 用 getSkillToolCommands(cwd) 拿可调用列表
  verify: type='prompt', !disableModelInvocation, source !== 'builtin',
          loadedFrom === 'bundled' → **在列表里**
  模型可以调
```

这条路径解释了原四篇文档里的那段疑问——"verify 不在 /skills 菜单里，但模型为什么能调"。
