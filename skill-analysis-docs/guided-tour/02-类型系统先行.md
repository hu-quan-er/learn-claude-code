## 2. 文件鸟瞰：5 块结构

先把整个文件的"骨架"扫一遍。从头到尾你会看到这五段：

```
types/command.ts (1-217 行)
│
├─ 1-14    import 段
│
├─ 16-23   LocalCommandResult
│            local 命令的返回值形状
│
├─ 25-57   PromptCommand           ← skill 用的就是这个
│            type: 'prompt'，包含 getPromptForCommand
│
├─ 59-105  LocalCommand 相关
│            LocalCommandCall / LocalCommandModule / LocalCommand
│
├─ 107-152 LocalJSXCommand 相关
│            LocalJSXCommandContext / OnDone / Call / Module
│
├─ 154-203 CommandBase
│            所有 Command 共享的元数据字段
│            （name, description, availability, kind, ...）
│
└─ 205-216 Command（联合）+ helper 函数
            export type Command = CommandBase & (PromptCommand | Local | LocalJSX)
            getCommandName / isCommandEnabled
```

最关键的是两段：

- **25-57** `PromptCommand`：决定了 skill 的运行时形状
- **154-203** `CommandBase`：决定了"这个 Command 怎么被发现、过滤、显示"

后面我们逐字段过一遍，但先记住一个核心结构：

```
type Command = CommandBase & (PromptCommand | LocalCommand | LocalJSXCommand)
```

**联合的判别字段是 `type: 'prompt' | 'local' | 'local-jsx'`**。所有 skill 都是 `type === 'prompt'`。

也就是说，TypeScript 层并没有 `Skill` 这个类型——skill 是 "`Command` 中 `type === 'prompt'` 且元数据满足某些条件" 的那一族。

## 3. 第一组：判别 type — `type` 和 `loadedFrom` 和 `source`

这三个字段非常容易混。我们一个一个拆。

### 3.1 `type`（25, 74-78, 144-152）

```ts
// 25
export type PromptCommand = {
  type: 'prompt'
  ...
}

// 74-78
type LocalCommand = {
  type: 'local'
  supportsNonInteractive: boolean
  load: () => Promise<LocalCommandModule>
}

// 144-152
type LocalJSXCommand = {
  type: 'local-jsx'
  load: () => Promise<LocalJSXCommandModule>
}
```

**`type` 是 TypeScript discriminated union 的判别器。** 它回答："这个 Command 跑起来的时候是什么形状？"

| `type` | 跑法 | 例子 |
|---|---|---|
| `'prompt'` | 把 prompt 注入到主会话，让模型继续 query | 所有 skill、`/init`、所有 file-based command |
| `'local'` | 调一个 `call(args, ctx) → text` 函数，结果作为 user message | `/clear`、`/cost`、`/help` |
| `'local-jsx'` | 调一个 `call(onDone, ctx, args) → React.ReactNode`，渲染交互 UI | `/skills` 菜单、`/login` 流程、`/permissions` 面板 |

**这是"Command 的执行模型"维度的判别。** skill 永远是 `'prompt'`。

#### 思考题

> 如果一个 skill 需要在执行前先弹个 UI 让用户做选择（比如 verify 让用户选要 verify 哪个 PR），它应该用 `type: 'prompt'` 还是 `type: 'local-jsx'`？还是两者结合？这种需求在当前架构下怎么实现？

（提示：看 `bundled/skillify.ts` 是怎么处理需要"问用户问题"的需求的——它没用 local-jsx，而是把"问问题"写进 SKILL_BODY 的 prompt 里，让模型自己问。）

### 3.2 `loadedFrom`（191-198）

```ts
loadedFrom?:
  | 'commands_DEPRECATED'
  | 'skills'
  | 'plugin'
  | 'managed'
  | 'bundled'
  | 'mcp'
```

**`loadedFrom` 回答："这个 Command 走的是哪条装载路径进来的？"**

把这六个值贴到 01 篇那张图上：

| 值 | 装载路径 |
|---|---|
| `'skills'` | `.claude/skills/<name>/SKILL.md` 或 `~/.claude/skills/<name>/SKILL.md` |
| `'commands_DEPRECATED'` | 旧式 `.claude/commands/*.md`（兼容路径） |
| `'plugin'` | plugin manifest 声明的 skill |
| `'managed'` | 受策略管理的全局 skill |
| `'bundled'` | `registerBundledSkill()` 内置（verify 走这条） |
| `'mcp'` | MCP server 的 `skill://` resource |

**这是"哪条 loader 把它装进来的"维度的判别。**

### 3.3 `source`（32）

```ts
source: SettingSource | 'builtin' | 'mcp' | 'plugin' | 'bundled'
```

`SettingSource` 来自 `utils/settings/constants.ts:7-22`：

```ts
export const SETTING_SOURCES = [
  'userSettings',     // 全局用户配置（~/.claude/）
  'projectSettings',  // 项目级（<repo>/.claude/）
  'localSettings',    // 项目本地（gitignored）
  'flagSettings',     // 来自 --settings CLI flag
  'policySettings',   // managed-settings.json / 远端策略
] as const
```

加上 PromptCommand 显式追加的四个，`source` 一共可能是这 9 个值之一：

```
'userSettings' | 'projectSettings' | 'localSettings' | 'flagSettings' | 'policySettings'
| 'builtin' | 'mcp' | 'plugin' | 'bundled'
```

**`source` 回答："这个 Command 的来源在哪个'信任域'里？"**

这是为了：

- UI 展示（"User"、"Project"、"Plugin"、"Built-in"）
- 信任策略判断（policy-only 模式下，只有 `policySettings` 来源能注册 hooks）
- 配置覆盖优先级

### 3.4 三个字段的对比与组合矩阵

为什么不能合并？因为它们各自承担**不同维度的判别**。看一个对比矩阵：

| 例子 | `type` | `loadedFrom` | `source` |
|---|---|---|---|
| bundled `verify` | `prompt` | `bundled` | `bundled` |
| 项目内 `.claude/skills/review/SKILL.md` | `prompt` | `skills` | `projectSettings` |
| 用户 `~/.claude/skills/review/SKILL.md` | `prompt` | `skills` | `userSettings` |
| 项目内 `.claude/commands/git/commit.md`（旧式） | `prompt` | `commands_DEPRECATED` | `projectSettings` |
| 受策略管理的 `.claude/skills/policy.md` | `prompt` | `skills` 或 `managed` | `policySettings` |
| MCP server 提供的 skill | `prompt` | `mcp` | `mcp` |
| 内置 `/clear` slash command | `local` | (无) | `builtin` |
| `/skills` 菜单（local-jsx） | `local-jsx` | (无) | `builtin` |

注意第 3 行和第 4 行：**同样是项目内 skill，`loadedFrom` 和 `source` 还可能不一致**。这正是原四篇文档 01 里那段"为什么这两个字段不能合并"的答案——它们解决了**正交的**两个问题：

- `loadedFrom`：是哪个 loader 装的？（决定**菜单展示**、SkillTool 过滤）
- `source`：信任域是什么？（决定**权限策略**、UI 标签）

**消费方对照表**（搜代码就能验证）：

| 消费方 | 看哪个字段 | 为什么 |
|---|---|---|
| `/skills` 菜单（`SkillsMenu.tsx`） | `loadedFrom` | 只展示用户视角的"非内置 skill"——bundled 不展示 |
| `getSkillToolCommands()`（`commands.ts:563-581`） | `source !== 'builtin'` + `loadedFrom in {bundled, skills, commands_DEPRECATED}` | 过滤"模型可调用的 prompt skill" |
| `getSlashCommandToolSkills()`（`commands.ts:586-608`） | `loadedFrom in {skills, plugin, bundled}` 或 `disableModelInvocation` | 提示模型"哪些是 skill 而非通用 slash command" |
| hook 注册策略检查 | `source` | `isSourceAdminTrusted(command.source)` 判断能否注册 hooks |

## 4. 第二组：可调用性 — `disableModelInvocation`、`userInvocable`、`isHidden`、`isEnabled`、`availability`

skill 的"可调用性"由 5 个字段共同决定。这一组容易写错，得逐个看。

### 4.1 `disableModelInvocation`（189）

```ts
disableModelInvocation?: boolean // Whether to disable this command from being invoked by models
```

`true` 时，**模型不能通过 `SkillTool` 调用**。SkillTool 的 `validateInput` 会拒绝。

典型用例：`/skillify`——用户可以主动发起，但模型不应该自己决定生成 skill。

### 4.2 `userInvocable`（190）

```ts
userInvocable?: boolean // Whether users can invoke this skill by typing /skill-name
```

`true` 时（默认 true），用户可以 `/skill-name` 直接调用。`false` 时，用户不能直接调用，但模型可以通过 SkillTool。

典型用例：某些只该让模型在特定上下文里调用的工具型 skill。

### 4.3 `isHidden`（182）

```ts
/** Defaults to false. Only set when the command should be hidden from typeahead/help. */
isHidden?: boolean
```

`true` 时，命令**不出现在 typeahead 自动补全里**，也不出现在 `/help`。

注意 `isHidden` 和 `userInvocable` 看起来类似，但**职责不同**：

- `userInvocable: false` → 用户敲 `/name` 也调不动（行为约束）
- `isHidden: true` → 命令不在补全里出现（UI 约束）

`bundledSkills.ts:95` 和 `loadPluginCommands.ts:321` 都写了：

```ts
isHidden: !(definition.userInvocable ?? true),
```

也就是说**默认情况下 `isHidden` 跟着 `userInvocable` 反向同步**——不允许用户调的就别在补全里出现，否则用户敲了又调不动只会困惑。

但这两个字段**仍然分开**，因为：

1. **bundled skill 可以只声明 `userInvocable: false`，让 `bundledSkills.ts` 自动算出 `isHidden`**——一处 source of truth。
2. **某些命令可能允许用户调但不在补全里出现**（比如内部诊断命令、deprecated 但仍然可用的命令），这种情况 `isHidden: true, userInvocable: true` 就有意义。
3. UI 层（`commandSuggestions.ts:36` 的 `.filter(cmd => !cmd.isHidden)`）只关心"展不展示"，不关心"能不能调"。

### 4.4 `isEnabled`（180）

```ts
/** Defaults to true. Only set when the command has conditional enablement (feature flags, env checks, etc). */
isEnabled?: () => boolean
```

注意它是**函数**而不是 boolean——每次 `isCommandEnabled(cmd)`（`214-216`）都会**实时调用**这个函数。

```ts
// 214-216
export function isCommandEnabled(cmd: CommandBase): boolean {
  return cmd.isEnabled?.() ?? true
}
```

`commands.ts:483-485` 用法：

```ts
const baseCommands = allCommands.filter(
  _ => meetsAvailabilityRequirement(_) && isCommandEnabled(_),
)
```

每次 `getCommands()` 都会重新过滤——这是为了让 feature flag 切换、环境变量变化能立即生效。

典型用例：

```ts
// bundled/loop.ts 大致
isEnabled: () => isKairosCronEnabled(),
```

### 4.5 `availability`（156-176）

```ts
export type CommandAvailability =
  | 'claude-ai'   // claude.ai OAuth subscriber
  | 'console'     // 直接 api.anthropic.com 用户
```

```ts
// 175-176
export type CommandBase = {
  availability?: CommandAvailability[]
  ...
}
```

`availability` 比 `isEnabled` 更"静态"——它声明这个 command **针对哪种 auth 类型可用**。看 `commands.ts:417-443` 的 `meetsAvailabilityRequirement`：

```ts
export function meetsAvailabilityRequirement(cmd: Command): boolean {
  if (!cmd.availability) return true
  for (const a of cmd.availability) {
    switch (a) {
      case 'claude-ai':
        if (isClaudeAISubscriber()) return true
        break
      case 'console':
        if (
          !isClaudeAISubscriber() &&
          !isUsing3PServices() &&
          isFirstPartyAnthropicBaseUrl()
        )
          return true
        break
    }
  }
  return false
}
```

注释 `159-167` 说得很清楚：

```
This is separate from `isEnabled()`:
  - `availability` = who can use this (auth/provider requirement, static)
  - `isEnabled()`  = is this turned on right now (GrowthBook, platform, env vars)
```

**典型例子**：`availability: ['claude-ai', 'console']` 会**对 Bedrock/Vertex/Foundry 用户隐藏**——因为这些 3P provider 的 API key 不能调 Anthropic 自己的 console-only 功能。

### 4.6 五个字段的总结对照表

| 字段 | 类型 | 谁来读 | 行为 vs UI | 静态 vs 动态 |
|---|---|---|---|---|
| `disableModelInvocation` | `boolean` | SkillTool.validateInput | 行为 | 静态 |
| `userInvocable` | `boolean` | processSlashCommand 用户输入分支 | 行为 | 静态 |
| `isHidden` | `boolean` | typeahead / `/help` UI | UI | 静态 |
| `isEnabled` | `() => boolean` | `getCommands()` 每次过滤 | 行为+UI | 动态 |
| `availability` | `string[]` | `meetsAvailabilityRequirement` | 行为+UI | 半静态（auth 切换会变） |

#### 思考题

> 如果你想做一个 skill：
> - 用户**能** `/skill-name` 调用
> - 但**不在 typeahead 补全里出现**（不希望用户偶然敲到）
> - 模型**不能**通过 SkillTool 调用
> - 只对 claude.ai 订阅用户启用
>
> 该如何设置 `disableModelInvocation`、`userInvocable`、`isHidden`、`availability`？

## 5. 第三组：执行行为修饰 — skill 真正"改变运行时"的字段

这一组字段是 skill **能改变本轮执行环境的"杠杆"**——它们才是 skill 区别于普通 prompt 模板的根本原因。

### 5.1 `allowedTools`（30）

```ts
allowedTools?: string[]
```

skill 生效后**为当前 turn 追加的工具权限**。

格式是 `parseToolListFromCLI` 能消化的字符串数组：

- `'Bash'`
- `'Bash(git:*)'`
- `'Read'`
- `'mcp__server__tool'`

**生效路径**：`processSlashCommand.tsx:889-898` 的 `additionalAllowedTools`，被包成 `command_permissions` attachment 注入到本 turn 的 always-allow rules。SkillTool 走 `contextModifier` 把这些规则合并到 `toolPermissionContext.alwaysAllowRules.command`。

### 5.2 `model`（31）和 `effort`（49）

```ts
model?: string
effort?: EffortValue
```

skill 可以**临时切换本轮使用的模型和 effort（思考预算）**。

- `model` 可以是 `'claude-opus-4-7'`、`'claude-sonnet-4-6'` 等
- `effort` 是个枚举（`EffortValue`），决定 max_thinking_budget

**生效路径**：

- 用户 slash 调用：`processSlashCommand.tsx:892` 返回 `{model: command.model, effort: command.effort}`，主循环消费
- 模型 SkillTool 调用：`SkillTool.ts` 的 `contextModifier` 调 `resolveSkillModelOverride()`

### 5.3 `context`（45）和 `agent`（48）

```ts
// 42-48
// Execution context: 'inline' (default) or 'fork' (run as sub-agent)
// 'inline' = skill content expands into the current conversation
// 'fork' = skill runs in a sub-agent with separate context and token budget
context?: 'inline' | 'fork'
agent?: string
```

- `context: 'inline'` 默认。skill 内容注入主会话。
- `context: 'fork'`。skill 运行在**子 agent** 里，有独立的 context window 和 token budget。

`agent` 只在 `context === 'fork'` 时使用，指定子 agent 类型（比如 `'Bash'`、`'general-purpose'`）。

**生效路径**：分两条——

- 用户 slash + fork：`prepareForkedCommandContext()` + `executeForkedSlashCommand()`
- 模型 SkillTool + fork：`SkillTool.ts:122 executeForkedSkill()`

第 06 篇会专门讲。

### 5.4 `hooks`（39）

```ts
// Hooks to register when this skill is invoked
hooks?: HooksSettings
```

skill 调用时注册的 lifecycle hooks（`PreToolUse`、`PostToolUse`、`UserPromptSubmit`、`Stop`、`ConfigChange` 等）。

**生效路径**：`processSlashCommand.tsx:870-873`：

```ts
const hooksAllowedForThisSkill = !isRestrictedToPluginOnly('hooks') || isSourceAdminTrusted(command.source);
if (command.hooks && hooksAllowedForThisSkill) {
  registerSkillHooks(...)
}
```

注意"不是所有 skill 都能注册 hooks"——`isRestrictedToPluginOnly('hooks')` 限制只有受信来源能注册。这是个安全门。

### 5.5 `paths`（51-52）

```ts
// Glob patterns for file paths this skill applies to
// When set, the skill is only visible after the model touches matching files
paths?: string[]
```

**`paths` 不是运行时过滤，是延迟曝光机制**。

skill 装载后，如果有 `paths`：

1. 进入 `conditionalSkills` 池，**不**进入 `getCommands()` 默认结果
2. 文件工具操作某个路径时，`activateConditionalSkillsForPaths()` 用 `ignore` 库（gitignore 风格）匹配
3. 命中才进入 `dynamicSkills`，下次 `getCommands()` 才拿得到

这是 file-based skill 的高级特性，第 07 篇专门讲。

### 5.6 `skillRoot`（41）

```ts
// Base directory for skill resources (used to set CLAUDE_PLUGIN_ROOT environment variable for skill hooks)
skillRoot?: string
```

skill 的"资源根目录"。用途：

- file-based skill：指向 `.claude/skills/<name>/` 目录
- bundled skill 带 files：指向 `getBundledSkillExtractDir(name)`
- plugin skill：指向 plugin 根目录

被 `getPromptForCommand` 用来替换 `${CLAUDE_SKILL_DIR}`、`${CLAUDE_PLUGIN_ROOT}`，也作为 hook 的环境变量基准。

### 5.7 `progressMessage`（27）和 `contentLength`（28）

```ts
progressMessage: string
contentLength: number
```

- `progressMessage`：skill 加载时给用户看的进度文案（"Running verify..."）
- `contentLength`：skill 内容长度（字符数），用于 token 估算

这两个是辅助字段，对核心理解 skill 不重要。

### 5.8 整组的总结表

| 字段 | 改变什么 | 生效阶段 |
|---|---|---|
| `allowedTools` | 本 turn 工具权限 | prompt 注入时 |
| `model` | 本轮 query 用的模型 | prompt 注入时 |
| `effort` | 本轮 thinking 预算 | prompt 注入时 |
| `context` / `agent` | 在主会话还是子 agent 跑 | 调度阶段 |
| `hooks` | 注册 lifecycle hooks | prompt 注入时 |
| `paths` | 是否进入可见 skill 集合 | 装载/动态发现阶段 |
| `skillRoot` | 资源定位的基准目录 | prompt 展开时（`${CLAUDE_SKILL_DIR}`） |

#### 思考题

> 一个 skill 同时声明了 `allowedTools: ['Bash']`、`model: 'claude-opus-4-7'`、`context: 'fork'`、`agent: 'general-purpose'`。
>
> 当模型通过 SkillTool 调用它时，下面三件事在哪个阶段发生？

> 2. 模型从当前模型切到 opus-4-7
> 3. 子 agent 被启动

## 6. 第四组：发现与展示 — `name`、`aliases`、`description`、`whenToUse`、`hasUserSpecifiedDescription`、`argumentHint`

这一组决定 skill 怎么被找到、怎么展示。

### 6.1 `name`（183）和 `aliases`（184）

```ts
name: string
aliases?: string[]
```

- `name` 是查找用的唯一键。`/verify` 就靠它找。
- `aliases` 是别名。比如 `aliases: ['v']` 让 `/v` 也能调到 verify。

不同 skill 的命名规则：

| 来源 | 命名规则 |
|---|---|
| `.claude/skills/review/SKILL.md` | `review`（取目录名） |
| `.claude/commands/git/commit.md` | `git:commit`（路径转命名空间） |
| `.claude/commands/release/SKILL.md` | `release`（目录式 skill 取目录名） |
| plugin `<plugin-name>:<skill>` | `my-plugin:review` |
| MCP `<server>:<skill>` | `database:query` |
| bundled | 由 `register*Skill` 显式给 |

### 6.2 `description`（177）和 `whenToUse`（187）

```ts
description: string
whenToUse?: string // From the "Skill" spec. Detailed usage scenarios for when to use this command
```

- `description` 简短描述，一行内
- `whenToUse` 详细使用场景，多行也行

**两个字段的设计目的不同**：

- `description` 给用户看（typeahead、`/help`）
- `whenToUse` 给**模型**看（让模型判断"我现在该不该用这个 skill"）

Plugin 和 MCP skill 必须有这两个之一才会进 `getSkillToolCommands` 列表（看 `commands.ts:573-578`）：

```ts
(cmd.loadedFrom === 'bundled' ||
  cmd.loadedFrom === 'skills' ||
  cmd.loadedFrom === 'commands_DEPRECATED' ||
  cmd.hasUserSpecifiedDescription ||
  cmd.whenToUse)
```

注意前三项是"自动放行"——bundled、本地 skill、legacy 不要求显式描述（loader 会自动从 markdown 第一行抽取作为 description）。但 plugin 和 MCP 因为来源不可控，**必须显式声明**。

### 6.3 `hasUserSpecifiedDescription`（178）

```ts
hasUserSpecifiedDescription?: boolean
```

`true` 表示"作者明确写了 description（不是 loader 自动从首行抽取的）"。

为什么要这个字段？因为 file-based skill 可能没写 frontmatter `description`，loader 会**降级**——用 markdown 正文第一行作为 description。这种情况下 `hasUserSpecifiedDescription = false`，UI 知道这是"猜的"，可能展示得保守一些；过滤逻辑也据此决定要不要要求显式描述。

bundled skill 永远是 `true`（看 `bundledSkills.ts:80`），plugin skill 由 frontmatter 决定。

### 6.4 `argumentHint`（186）

```ts
argumentHint?: string // Hint text for command arguments (displayed in gray after command)
```

补全器在 `/verify ` 之后展示的灰色提示。比如 `/loop ` 后面会展示 `5m /command`。

### 6.5 `version`（188）

```ts
version?: string // Version of the command/skill
```

skill 自己声明的版本号，主要用于 telemetry 和 hook 兼容性。

## 7. 第五组：杂项标志位 — `kind`、`immediate`、`isSensitive`、`isMcp`、`disableNonInteractive`

这些字段使用频率较低但都有具体用途。

### 7.1 `kind`（198）

```ts
kind?: 'workflow' // Distinguishes workflow-backed commands (badged in autocomplete)
```

只有一个值 `'workflow'`，用来标识"这是 WorkflowTool 创建的命令"。

`commands.ts:733` 的 `if (cmd.kind === 'workflow')` 和 `commandSuggestions.ts:273` 的 `cmd.kind === 'workflow'` 用来给 workflow 命令加特殊角标。

### 7.2 `immediate`（199）

```ts
immediate?: boolean // If true, command executes immediately without waiting for a stop point (bypasses queue)
```

主消息队列在等待"模型停下来"时，`immediate: true` 的命令可以**插队**立刻执行。

典型用例：用户敲 `/exit`、`/clear` 这类不能等的操作。skill 通常**不**用这个字段。

### 7.3 `isSensitive`（200）

```ts
isSensitive?: boolean // If true, args are redacted from the conversation history
```

`true` 时 args 在 conversation 持久化时会被脱敏（替换成 `***`）。

适合处理密码、token 这类敏感参数的命令。

### 7.4 `isMcp`（185）

```ts
isMcp?: boolean
```

MCP-backed 命令的标志。MCP skill 装载时设 `true`。

注意它和 `loadedFrom: 'mcp'` 看起来重复，但**职责不同**——`isMcp` 是给 prompt MCP 命令（`mcp__server__prompt`）用的，`loadedFrom: 'mcp'` 是给 MCP skill（`server:skill`）用的。两者命名空间不同。

### 7.5 `disableNonInteractive`（37）

```ts
disableNonInteractive?: boolean
```

`true` 时这个 prompt 命令**在非交互模式（CI、SDK programmatic）下不能用**。比如需要"用户回答问题"的 skill。

### 7.6 `userFacingName`（202）

```ts
/** Defaults to `name`. Only override when the displayed name differs (e.g. plugin prefix stripping). */
userFacingName?: () => string
```

显示用名字，不影响查找。helper 函数 `getCommandName(cmd)`（`209-211`）：

```ts
export function getCommandName(cmd: CommandBase): string {
  return cmd.userFacingName?.() ?? cmd.name
}
```

主要给 plugin skill 用——内部 name 是 `my-plugin:review`，UI 上想只展示 `review` 就用这个。
