### 3.2 `parseHooksFromFrontmatter`（136-153）和 `parseSkillPaths`（159-178）

两个小辅助：

```ts
// 136-153
function parseHooksFromFrontmatter(frontmatter, skillName) {
  if (!frontmatter.hooks) return undefined
  const result = HooksSchema().safeParse(frontmatter.hooks)
  if (!result.success) {
    logForDebugging(`Invalid hooks in skill '${skillName}': ${result.error.message}`)
    return undefined
  }
  return result.data
}
```

特点：**hooks 用 zod 严格 schema 校验**。校验失败不抛异常，记 debug log，返回 undefined——skill 仍然能加载，只是 hooks 不生效。这是个"软失败"设计。

```ts
// 159-178
function parseSkillPaths(frontmatter): string[] | undefined {
  if (!frontmatter.paths) return undefined
  const patterns = splitPathInFrontmatter(frontmatter.paths)
    .map(p => p.endsWith('/**') ? p.slice(0, -3) : p)
    .filter(p => p.length > 0)
  if (patterns.length === 0 || patterns.every(p => p === '**')) {
    return undefined
  }
  return patterns
}
```

两个细节：

1. **`/**` 后缀被删掉**——`ignore` 库语义上 `path` 已经包括"path 自己 + path 内一切"，写 `path/**` 会变成"只匹配 path 内部"，反而错。所以 loader 先归一化掉。
2. **如果所有 pattern 都是 `**`**（match-all），等价于"没有路径限制"，返回 undefined。这意味着写 `paths: '**'` 等于不写——避免无意义的"条件 skill"。

### 3.4 `createSkillCommand`（270-401）

这是字段对象 → `Command` 对象的最后一公里。**整个 file-based skill 装载链最终都收敛到这里**。

注意它的入参里有 5 个**不在 `parseSkillFrontmatterFields` 返回值里的**字段：

```ts

baseDir: string | undefined        // 调用方传入

paths: string[] | undefined        // 调用方传入（来自 parseSkillPaths，不在 parseSkillFrontmatterFields 里）

这种设计的含义：**`parseSkillFrontmatterFields` 只关心 frontmatter 内部能解析出来的字段**；`source / baseDir / loadedFrom / paths / skillName` 来自**装载上下文**——调用方知道这是从哪儿装的。

这种"内部字段"和"上下文字段"分开的设计，让 `parseSkillFrontmatterFields` 能被 file-based skill 和 MCP skill 共享（看段 5）——都解析 frontmatter，但 `source` 一个是 `'projectSettings'` 一个是 `'mcp'`。

#### `getPromptForCommand` 闭包是这文件最有趣的一段（344-399）

```ts
async getPromptForCommand(args, toolUseContext) {
  let finalContent = baseDir
    ? `Base directory for this skill: ${baseDir}\n\n${markdownContent}`
    : markdownContent

  finalContent = substituteArguments(finalContent, args, true, argumentNames)

  if (baseDir) {
    const skillDir = process.platform === 'win32' ? baseDir.replace(/\\/g, '/') : baseDir
    finalContent = finalContent.replace(/\$\{CLAUDE_SKILL_DIR\}/g, skillDir)
  }

  finalContent = finalContent.replace(/\$\{CLAUDE_SESSION_ID\}/g, getSessionId())

  // 关键安全门 ↓
  if (loadedFrom !== 'mcp') {
    finalContent = await executeShellCommandsInPrompt(
      finalContent,
      {
        ...toolUseContext,
        getAppState() {
          const appState = toolUseContext.getAppState()
          return {
            ...appState,
            toolPermissionContext: {
              ...appState.toolPermissionContext,
              alwaysAllowRules: {
                ...appState.toolPermissionContext.alwaysAllowRules,
                command: allowedTools,    // ← 这里把 skill 的 allowedTools
              },                          //   作为本次 shell 执行的临时 allow rules
            },
          }
        },
      },
      `/${skillName}`,
      shell,
    )
  }

  return [{ type: 'text', text: finalContent }]
}
```

**展开顺序**——这个顺序是设计过的：

1. 先注入 `Base directory for this skill: <dir>` 头部
2. 替换 `${args}` 类参数（`substituteArguments`）
3. 替换 `${CLAUDE_SKILL_DIR}`（baseDir 才替换）
4. 替换 `${CLAUDE_SESSION_ID}`
5. 执行 shell block（**只对非 MCP skill 执行**）
6. 包成 text content block 返回

注意 `loadedFrom !== 'mcp'` 这道门——MCP 是远程不可信来源，永远不能跑 inline shell。这是 skill 系统里**最硬的一道安全边界**之一。

注意 `getAppState()` 重写——它在 shell 执行的瞬间临时把 `allowedTools` 注入 `alwaysAllowRules.command`，让 shell block 能复用这些权限，而不是用全局 default。这是个非常局部、非常精巧的临时上下文 patching。

### 4.1 新式 loader：`loadSkillsFromSkillsDir`（407-480）

打开 407 行起读。这函数极简：

```
input:  basePath (一个 .claude/skills/ 目录), source (信任域)
output: SkillWithPath[]

1. fs.readdir(basePath)        ← 只读一层
2. 对每个 entry：
   - 如果不是目录或符号链接，跳过 (单独的 .md 文件不支持)
   - 拼出 <skillDir>/SKILL.md
   - 读文件
     - ENOENT 静默跳过
     - 其它 IO 错记 warn 日志
   - parseFrontmatter
   - parseSkillFrontmatterFields
   - parseSkillPaths
   - createSkillCommand({...parsed, baseDir: skillDir, loadedFrom: 'skills', source, paths})
3. 过滤掉 null
```

**关键约束**：第 425-428 行明确不支持单文件 skill：

```ts
if (!entry.isDirectory() && !entry.isSymbolicLink()) {
  // Single .md files are NOT supported in /skills/ directory
  return null
}
```

为什么？因为 skill 可能带 reference files（旁边的 `examples/`、`scripts/`），单文件无处放。强制目录格式让 skill 永远有自己的"工作目录"，这就是 `baseDir`/`skillRoot` 能稳定存在的前提。

### 4.2 旧式 loader：`loadSkillsFromCommandsDir`（566-623）

打开 566 行起读。这条线更复杂，因为它要兼容历史。

```

   ← 通用 markdown 装载器，在 markdownConfigLoader.ts
   ← 它会扫 .claude/commands/ 下的所有 .md（不限第一层），返回 MarkdownFile[]
2. transformSkillFiles(markdownFiles)  ← 关键合并步骤（493-521）

注意 `paths: undefined`——**legacy commands 不支持 conditional skills**。这是个保守选择：legacy 路径的兼容已经够复杂，不要再叠新特性。

#### `transformSkillFiles`（493-521）做了什么？

```ts
function transformSkillFiles(files: MarkdownFile[]): MarkdownFile[] {
  // 1. 按目录分组
  const filesByDir = new Map<string, MarkdownFile[]>()
  for (const file of files) {
    const dir = dirname(file.filePath)
    const dirFiles = filesByDir.get(dir) ?? []
    dirFiles.push(file)
    filesByDir.set(dir, dirFiles)
  }

  const result: MarkdownFile[] = []
  for (const [dir, dirFiles] of filesByDir) {
    const skillFiles = dirFiles.filter(f => isSkillFile(f.filePath))
    if (skillFiles.length > 0) {
      // 这个目录里有 SKILL.md，只保留 SKILL.md 一个
      const skillFile = skillFiles[0]!
      // 多个同名 SKILL.md 时记 warn
      result.push(skillFile)
    } else {
      // 这个目录里没有 SKILL.md，所有 .md 当独立命令保留
      result.push(...dirFiles)
    }
  }
  return result
}
```

**核心规则**：如果一个目录里**存在 `SKILL.md`**，那个目录被**当成 skill 容器**，目录里其它 markdown 文件被忽略。否则就是普通的 "每个 .md 一个命令" 旧式行为。

这个规则让作者能把旧式 `commands/release/prepare.md`、`commands/release/publish.md` 平滑迁移成 `commands/release/SKILL.md`——只要把 SKILL.md 加进去，其它文件**不需要删**就会自动被忽略。

#### 阶段 D：去重 + 条件分流（716-802）

```ts
// 拍平 + 拼接
const allSkillsWithPaths = [
  ...managedSkills, ...userSkills,
  ...projectSkillsNested.flat(),
  ...additionalSkillsNested.flat(),
  ...legacyCommands,
]

// 并发算 realpath
const fileIds = await Promise.all(
  allSkillsWithPaths.map(({ skill, filePath }) =>
    skill.type === 'prompt' ? getFileIdentity(filePath) : Promise.resolve(null)
  ),
)

// 同步去重（first-wins）
const seenFileIds = new Map<string, ...>()
const deduplicatedSkills: Command[] = []
for (let i = 0; i < allSkillsWithPaths.length; i++) {
  const fileId = fileIds[i]
  if (fileId === null || fileId === undefined) {
    deduplicatedSkills.push(skill)  // 没 realpath 的不参与去重
    continue
  }
  const existingSource = seenFileIds.get(fileId)
  if (existingSource !== undefined) {
    logForDebugging(`Skipping duplicate skill '${skill.name}' from ${skill.source} (same file already loaded from ${existingSource})`)
    continue
  }
  seenFileIds.set(fileId, skill.source)
  deduplicatedSkills.push(skill)
}

// 分流：unconditional vs conditional
const unconditionalSkills: Command[] = []
const newConditionalSkills: Command[] = []
for (const skill of deduplicatedSkills) {
  if (
    skill.type === 'prompt' &&
    skill.paths && skill.paths.length > 0 &&
    !activatedConditionalSkillNames.has(skill.name)
  ) {
    newConditionalSkills.push(skill)
  } else {
    unconditionalSkills.push(skill)
  }
}

for (const skill of newConditionalSkills) {
  conditionalSkills.set(skill.name, skill)
}

return unconditionalSkills
```

#### 关键设计观察

**(a) 顺序保留 + first-wins 去重**

`Promise.all` 完成后，**结果数组的位置和输入位置一一对应**——这是 JS spec 保证的。所以 5 路返回的相对顺序固定：managed → user → project → additional → legacy。然后 first-wins 去重。

也就是说，**managed 的 skill 优先级最高**（同一个 realpath 的文件谁先进谁赢）。这也是策略管理的语义体现：管理员定义的 skill 不会被用户 skill 覆盖。

**(b) `realpath` 失败的 skill 不参与去重**

第 748-751 行：

```ts
if (fileId === null || fileId === undefined) {
  deduplicatedSkills.push(skill)
  continue
}
```

为什么？因为 realpath 失败说明文件不可访问（可能是软链断了），但 skill 已经 parse 成功（说明读 markdown 时还是 OK 的）。这种"奇怪状态"下选择**保留 skill**——更宽松，不影响功能。

**(c) Conditional skills 不进 unconditional 表**

第 770-790 行把带 `paths` 的 skill 抽出来放进 `conditionalSkills` 池。**`getSkillDirCommands` 返回的是 `unconditionalSkills`，不含条件 skill**——这是"延迟曝光"机制的入口。

但已经被激活过的（`activatedConditionalSkillNames.has(name)`）不再视作 conditional——它们一旦激活就永久解锁本会话。这意味着 **conditional 状态在缓存清除后会回到"未激活"**——除非显式记录的 `activatedConditionalSkillNames` 不被清。看 806-811 的 `clearSkillCaches`：

```ts
export function clearSkillCaches() {
  getSkillDirCommands.cache?.clear?.()
  loadMarkdownFilesForSubdir.cache?.clear?.()
  conditionalSkills.clear()
  activatedConditionalSkillNames.clear()    // ← 也被清
}
```

**`clearSkillCaches` 把 `activatedConditionalSkillNames` 也清了**。这意味着热更新场景下，已激活的 conditional skill 在 reload 后**需要重新触发匹配**才会再次激活。后面 08 篇会回头讨论这点。

#### 思考题

> - `~/.claude/skills/review/SKILL.md`（userSettings）
> - `<project>/.claude/skills/review/SKILL.md`（projectSettings，是 symlink → 用户级 SKILL.md）

## 6. 段 4：动态发现与条件激活（817-1075 行）

这一段是 skill 系统的"产品化"那一块——让 skill 可以**和具体代码区域绑定**。第 07 篇会专门展开，这里先建框架。

### 6.1 模块级 state（820-829）

### 6.2 `discoverSkillDirsForPaths`（861-915）

被文件工具（FileRead/FileWrite/FileEdit）调用：

```

output: 新发现的 .claude/skills 目录列表（深度排序）

伪代码：

  currentDir = dirname(filePath)

    if 没检查过 skillDir:

      if skillDir exists:
        if 该 dir 不在 gitignore:

  // 走到 cwd 之上停（cwd 自己已经在启动期扫过了）
sort newDirs by depth desc
```

#### 关键安全门：gitignore 过滤（892-896）

```ts

防御 `node_modules/somepkg/.claude/skills/...` 这种路径"偷偷"被加载——别人 npm 包里夹带 skill，gitignore 已经声明不信任。

#### 思考题

> `dynamicSkillDirs` 把 hit 和 miss 都记进同一个 Set。这是有意为之的——为什么要记 miss？

### 6.3 `addSkillDirectories`（923-975）

调度器：把上面发现的目录批量装载，合并进 `dynamicSkills`。

```
input: dirs (已经过 discoverSkillDirsForPaths 排序，深度优先)

逻辑：
1. 检查 settings policy（projectSettings 必须开启，skills 不能 plugin-only）
2. Promise.all(loadSkillsFromSkillsDir for each dir)
3. **倒序**遍历：从浅往深 set 进 dynamicSkills
   → 深的覆盖浅的（map.set 后写赢）
4. emit 'skillsChanged' 信号
5. logEvent telemetry
```

注意第 944-951 行**反向遍历**：

```ts
for (let i = loadedSkills.length - 1; i >= 0; i--) {
  for (const { skill } of loadedSkills[i] ?? []) {
    if (skill.type === 'prompt') {
      dynamicSkills.set(skill.name, skill)
    }
  }

```

`dirs` 已经"深度降序"，所以倒序就是"浅度优先"，最后一次写入是深度最大的——**深 skill 赢**。这背后的语义是"距离当前文件最近的 skill 优先"。

### 6.4 `activateConditionalSkillsForPaths`（997-1058）

激活带 `paths` 的 skill：

```
input: filePaths, cwd
output: 新激活的 skill name[]

逻辑：
1. 如果 conditionalSkills 池空，return []
2. 对池里每个 skill：
   - 用 ignore 库（gitignore 风格）建匹配器
   - 对每个 filePath 算相对 cwd 路径
   - 跳过空、跳过 '..'-relative、跳过绝对路径
   - 命中即：
     - dynamicSkills.set(name, skill)
     - conditionalSkills.delete(name)
     - activatedConditionalSkillNames.add(name)
     - 加进 activated 列表
     - break（一个文件命中即可）
3. 如果有激活：emit signal + logEvent
```

注意第 1029-1039 行——**任何一个 filePath 命中就激活**，不要求所有路径都命中。语义是"只要碰到了相关代码区域就开"。

### 6.5 `getDynamicSkills`、`onDynamicSkillsLoaded`、`clearDynamicSkills`（981-1075）

三个工具：

- `getDynamicSkills`：返回当前所有动态 skill。`commands.ts:476-517` 的 `getCommands` 会调它。
- `onDynamicSkillsLoaded(callback)`：订阅 `skillsLoaded` 信号。**`commands.ts` 的 cache 失效就是订阅这个信号**——动态 skill 一变，cached commands 要重算。

## 7. 段 5：MCP builder 注册（1077-1086 行）

```ts
// 1077-1086
// Expose createSkillCommand + parseSkillFrontmatterFields to MCP skill
// discovery via a leaf registry module. See mcpSkillBuilders.ts for why this
// indirection exists (a literal dynamic import from mcpSkills.ts fans a single
// edge out into many cycle violations; a variable-specifier dynamic import
// passes dep-cruiser but fails to resolve in Bun-bundled binaries at runtime).
// eslint-disable-next-line custom-rules/no-top-level-side-effects -- write-once registration, idempotent
registerMCPSkillBuilders({
  createSkillCommand,
  parseSkillFrontmatterFields,
})
```

10 行解决一个**循环依赖**问题。

`mcpSkills.ts`（不在快照里）需要调用本文件的 `createSkillCommand` 和 `parseSkillFrontmatterFields`。如果 `mcpSkills.ts` 直接 import `loadSkillsDir.ts`，会形成循环——`loadSkillsDir.ts` 自己又依赖 `services/mcp` 那一摞。

解法：**反转控制**。`loadSkillsDir.ts` **主动**把这两个函数 push 给一个中间注册器（`mcpSkillBuilders.ts`），`mcpSkills.ts` 从注册器**拉**——这样依赖图变成 `loadSkillsDir → builders ← mcpSkills`，不再循环。

打开 `restored-src/src/skills/mcpSkillBuilders.ts` 看看（44 行）：

```ts
// 大致结构（mcpSkillBuilders.ts）
let builders: { createSkillCommand, parseSkillFrontmatterFields } | undefined

export function registerMCPSkillBuilders(b) { builders = b }
export function getMCPSkillBuilders() {
  if (!builders) throw new Error('not registered')
  return builders
}
```

注释 1078-1081 说有过两版尝试，最终选 leaf-registry 模式：

- 直接 `import` → 循环
- `await import('...')` 字面量 → dep-cruiser 仍然报循环
- variable-specifier dynamic import → dep-cruiser 通过但 Bun 打包后运行时找不到模块
- **leaf registry**（这一版）→ 静态依赖图 + 运行时控制反转，全部通过

这是大型 bundler 项目里非常常见的"绕循环"招数。记下来——后面读 `mcpSkillBuilders.ts` 时不会奇怪它为什么这么轻。
