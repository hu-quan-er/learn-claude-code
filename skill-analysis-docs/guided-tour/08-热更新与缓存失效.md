# 08. 热更新与缓存失效 — `skillChangeDetector.ts` + `useSkillsChange` + 三层 cache

> 这一篇做一件事：把"skill 文件被修改之后，运行中的 Claude Code 是怎么知道、怎么 reload、怎么通知 UI 和 attachment 系统"的完整代码路径走通。读完之后会清楚一件事——**热更新涉及三层 cache 的精细化失效**，每一层有自己的清理函数，乱清会出问题。
>
> 接 04 篇的两个清理函数（`clearCommandMemoizationCaches` 和 `clearCommandsCache`），接 03 篇的 `clearSkillCaches`，接 07 篇的"skill emit signal"。这一篇把它们串起来。

---

## 1. 这一篇覆盖的两条触发路径

skill 列表会在两种场景下"变"：

**触发 A：磁盘文件变化** — 用户编辑 `.claude/skills/foo/SKILL.md`、git pull 拉了新 skill、auto-update 装了新 plugin。

**触发 B：动态发现 / conditional 激活** — 07 篇讲过的 `addSkillDirectories` / `activateConditionalSkillsForPaths`。

两条路径走**不同**的 cache 清理函数——这正是这一篇要厘清的。

```
触发 A (磁盘文件变化)
       │
       ▼
chokidar watcher 监听到事件
       │
       ▼
handleChange → scheduleReload (debounce 300ms)
       │
       ▼
executeConfigChangeHooks('skills', path)   ← 给用户 hook 拦截机会
       │
   未拦截 ↓
       ▼
clearSkillCaches() + clearCommandsCache() + resetSentSkillNames()
       │
       ▼
skillsChanged.emit() → React UI 拿新 commands

触发 B (动态发现)
       │
       ▼
addSkillDirectories / activateConditionalSkillsForPaths 写入 dynamicSkills
       │
       ▼
skillsLoaded.emit()
       │
       ▼
onDynamicSkillsLoaded callback 跑
       │
       ▼
clearCommandMemoizationCaches()   ← ★ 注意：只清 memoize，不清 dynamicSkills
       │
       ▼
skillsChanged.emit() → React UI 拿新 commands
```

**关键差别**：触发 A 走 `clearCommandsCache`（深清），触发 B 走 `clearCommandMemoizationCaches`（浅清）。下面 4 节展开为什么。

## 2. 三层 cache 的层次结构

读 `skillChangeDetector.ts` 之前，先把三层 cache 的关系画清楚。

```
┌────────────────────────────────────────────────────────────┐
│ Layer 3: 命令视图缓存 (commands.ts)                        │
│   - loadAllCommands.cache (memoize by cwd)                │
│   - getSkillToolCommands.cache (memoize by cwd)           │
│   - getSlashCommandToolSkills.cache (memoize by cwd)      │
│   - clearSkillIndexCache (skillSearch 子系统)              │
│                                                            │
│   清理函数：clearCommandMemoizationCaches                  │
│   什么时候清：动态 skill 新增（dynamicSkills 变了）        │
└────────────────────────────────────────────────────────────┘
                          │
                          │ 这一层依赖：
                          ▼
┌────────────────────────────────────────────────────────────┐
│ Layer 2: 来源 loader 缓存                                  │
│   - getSkillDirCommands.cache (loadSkillsDir.ts)          │
│   - loadMarkdownFilesForSubdir.cache (markdownConfigLoader)│
│   - getPluginCommands.cache                               │
│   - getPluginSkills.cache                                 │
│                                                            │
│   清理函数：clearSkillCaches + clearPluginCommandCache +  │
│             clearPluginSkillsCache                         │
│   什么时候清：磁盘文件变化（要重新读 SKILL.md）           │
└────────────────────────────────────────────────────────────┘
                          │
                          │ 这一层维护：
                          ▼
┌────────────────────────────────────────────────────────────┐
│ Layer 1: 静态状态                                          │
│   - bundledSkills (内存数组)                              │
│   - dynamicSkillDirs / dynamicSkills / conditionalSkills  │
│     (Set + Map)                                           │
│   - activatedConditionalSkillNames                        │
│                                                            │
│   清理函数：clearBundledSkills (测试用) + clearSkillCaches │
│             也会清 conditionalSkills + activated          │
│   什么时候清：进程重启 / 完整 reset                       │
└────────────────────────────────────────────────────────────┘
```

#### 三层有依赖关系

- Layer 3 依赖 Layer 2 的输出（`getCommands` 调 `getSkillDirCommands`）
- Layer 2 依赖 Layer 1 的状态（`getSkillDirCommands` 写 `conditionalSkills`，读 `activatedConditionalSkillNames`）

#### 这是为什么"乱清"会出问题

**反例**：如果触发 B（动态发现）调用 `clearCommandsCache`（深清，会调 `clearSkillCaches`）：

1. `addSkillDirectories` 把新 skill 写入 `dynamicSkills`
2. `clearCommandsCache` 调 `clearSkillCaches`
3. `clearSkillCaches` 清 `conditionalSkills` 和 `activatedConditionalSkillNames`
4. `getSkillDirCommands.cache` 也被清——下次 `getCommands` 重扫盘
5. 重扫盘时，conditional skill 因为 `activatedConditionalSkillNames` 已被清空，**全部回到 conditionalSkills 池**
6. **dynamicSkills 里"被刚激活的 skill"对应的 conditional 元数据丢了**

但 `dynamicSkills` 自己**没被清**——所以问题更微妙：dynamicSkills 里有 skill X，但 conditionalSkills 池也有 skill X（重新装载产生），下次再激活时就是双写。

`clearCommandMemoizationCaches` 注释（commands.ts:519-522）就是讲这个：

```
Clears only the memoization caches for commands, WITHOUT clearing skill caches.
Use this when dynamic skills are added to invalidate cached command lists.
```

**触发 B 不能用深清**——这就是它走浅清的原因。

## 3. `skillChangeDetector.ts` 逐段精读

打开 `restored-src/src/utils/skills/skillChangeDetector.ts`。整个文件 312 行。

### 3.1 模块级常量与状态（27-71）

```ts
const FILE_STABILITY_THRESHOLD_MS = 1000      // 写入稳定阈值
const FILE_STABILITY_POLL_INTERVAL_MS = 500
const RELOAD_DEBOUNCE_MS = 300                // reload 去抖
const POLLING_INTERVAL_MS = 2000              // chokidar polling 间隔
const USE_POLLING = typeof Bun !== 'undefined'  // ★ Bun 强制用 polling

let watcher: FSWatcher | null = null
let reloadTimer: ReturnType<typeof setTimeout> | null = null
const pendingChangedPaths = new Set<string>()
let initialized = false
let disposed = false
let dynamicSkillsCallbackRegistered = false
let unregisterCleanup: (() => void) | null = null
const skillsChanged = createSignal()
```

#### 几个值得停下来看的常量

**(a) `USE_POLLING = typeof Bun !== 'undefined'`** 是非常重要的一行。

注释 51-61：

```
Bun's native fs.watch() has a PathWatcherManager deadlock (oven-sh/bun#27469,
#26385): closing a watcher on the main thread while the File Watcher thread
is delivering events can hang both threads in __ulock_wait2 forever. Chokidar
with depth: 2 on large skill trees (hundreds of subdirs) triggers this
reliably when a git operation touches many directories at once — chokidar
internally closes/reopens per-directory FSWatchers as dirs are added/removed.

Workaround: use stat() polling under Bun. No FSWatcher = no deadlock.
The fix is pending upstream; remove this once the Bun PR lands.
```

意思：**Claude Code 跑在 Bun runtime 时，原生 fs.watch 有死锁 bug，chokidar 自动启 polling 模式**——用 stat() 轮询代替 inotify/FSEvent。代价是延迟 + CPU 浪费，但不会死锁。

`POLLING_INTERVAL_MS = 2000` 给 polling 设了 2s 间隔——比 chokidar 默认 100ms 大 20 倍。skill 文件变化频率低，2s 延迟可接受。

**(b) `RELOAD_DEBOUNCE_MS = 300`**

注释 35-42：

```
Time in milliseconds to debounce rapid skill change events into a single
reload. Prevents cascading reloads when many skill files change at once
(e.g. during auto-update or when another session modifies skill directories).
Without this, each file change triggers a full clearSkillCaches() +
clearCommandsCache() + listener notification cycle, which can deadlock the
event loop when dozens of events fire in rapid succession.
```

git pull / auto-update / 跨 session 修改可能一秒内触发几十个文件事件。300ms debounce 把它们合成一次 reload。

**(c) `FILE_STABILITY_THRESHOLD_MS = 1000` 是 chokidar 自己的 awaitWriteFinish**

它和 `RELOAD_DEBOUNCE_MS` 不一样：

- `awaitWriteFinish.stabilityThreshold` 等**单个文件**写完（防止 chokidar 在文件还在写的时候就触发）
- `RELOAD_DEBOUNCE_MS` 等**多个文件**事件合并成一波

两者叠加：**单个 SKILL.md 编辑保存后，最坏要等 1.3s 才触发实际 reload**（1s 等 stable + 300ms debounce）。

#### 思考题

> `dynamicSkillsCallbackRegistered` 这个布尔为什么单独存在？为什么要确保只注册一次？

（提示：`onDynamicSkillsLoaded` 是 signal subscribe，多次注册会**多次回调**——同一个事件 emit 会跑 N 次 `clearCommandMemoizationCaches`。虽然冪等没副作用，但浪费 + 难调试。守卫确保唯一。）

### 3.2 `initialize`（85-141）— 启动时挂监听

```ts
export async function initialize(): Promise<void> {
  if (initialized || disposed) return
  initialized = true

  // 1. 注册动态 skill loaded callback
  if (!dynamicSkillsCallbackRegistered) {
    dynamicSkillsCallbackRegistered = true
    onDynamicSkillsLoaded(() => {
      clearCommandMemoizationCaches()         // ★ 浅清
      skillsChanged.emit()                    // 通知 React UI
    })
  }

  // 2. 拿要监听的目录
  const paths = await getWatchablePaths()
  if (paths.length === 0) return

  // 3. 启动 chokidar
  watcher = chokidar.watch(paths, {
    persistent: true,
    ignoreInitial: true,
    depth: 2,                                 // ★ 只下探 2 层（skill-name/SKILL.md）
    awaitWriteFinish: { stabilityThreshold: ..., pollInterval: ... },
    ignored: (path, stats) => {
      if (stats && !stats.isFile() && !stats.isDirectory()) return true
      return path.split(platformPath.sep).some(dir => dir === '.git')
    },
    ignorePermissionErrors: true,
    usePolling: USE_POLLING,
    interval: testOverrides?.chokidarInterval ?? POLLING_INTERVAL_MS,
    atomic: true,
  })

  watcher.on('add', handleChange)
  watcher.on('change', handleChange)
  watcher.on('unlink', handleChange)

  // 4. 注册 cleanup
  unregisterCleanup = registerCleanup(async () => {
    await dispose()
  })
}
```

#### 几个值得讨论的设计

**(a) 这个函数同时做两件事**

- 给"触发 B（动态发现）"挂回调（行 90-101）
- 给"触发 A（磁盘变化）"挂 chokidar（行 110-135）

两条路径都收敛到 `skillsChanged.emit()`——这是 detector 给外部的统一信号。

但**它们清的东西不同**：

| 触发 | 清理调用 |
|---|---|
| A: chokidar 监听到磁盘变化 | `clearSkillCaches() + clearCommandsCache() + resetSentSkillNames()`（在 `scheduleReload` 里） |
| B: dynamicSkillsLoaded | `clearCommandMemoizationCaches()` |

**(b) `depth: 2` 限制扫描深度**

skill 路径标准是 `<dir>/<skill-name>/SKILL.md` —— 两层。`depth: 2` 限制 chokidar 只下探到这一层，不递归到 skill 内的子目录。

**为什么这很重要？**

- 性能：用户级 `~/.claude/skills/` 下可能有几十个 skill，每个 skill 里可能有几十个文件（reference files、scripts 等）。如果 chokidar 全部监听，watcher 数量爆炸。
- 语义：skill 修改的判断单位就是 SKILL.md 的位置，更深的文件改动不需要触发 reload（它们在 SKILL.md 引用时才被读）。

**(c) `atomic: true`**

chokidar 的 atomic 模式合并"删 + 写"为一个 `change` 事件——很多编辑器（vim、IntelliJ）保存时是"先 mv 到临时再 rename 回来"，没有 atomic 会变成 `unlink` + `add` 两个事件，触发两次 reload。

**(d) `ignored` 函数过滤特殊文件**

socket、FIFO、device file 不能 watch（macOS 会 EOPNOTSUPP）；`.git/` 也排除——避免 git 操作触发 skill reload。

**(e) `registerCleanup` 优雅退出**

注册一个 cleanup 函数，进程退出时调 `dispose`。否则 chokidar watcher 不释放 → 进程不退出。

### 3.3 `getWatchablePaths`（171-235）— 决定监听哪几个目录

```ts
async function getWatchablePaths(): Promise<string[]> {
  const fs = getFsImplementation()
  const paths: string[] = []

  // 1. 用户 skills (~/.claude/skills)
  const userSkillsPath = getSkillsPath('userSettings', 'skills')
  if (userSkillsPath) try { await fs.stat(userSkillsPath); paths.push(...) } catch {}

  // 2. 用户 commands (~/.claude/commands)
  const userCommandsPath = getSkillsPath('userSettings', 'commands')
  ...

  // 3. 项目 skills (.claude/skills 相对当前 cwd)
  const projectSkillsPath = getSkillsPath('projectSettings', 'skills')
  if (projectSkillsPath) try {
    const absolutePath = platformPath.resolve(projectSkillsPath)  // ★ 转绝对
    await fs.stat(absolutePath)
    paths.push(absolutePath)
  } catch {}

  // 4. 项目 commands
  ...

  // 5. --add-dir 目录下的 .claude/skills
  for (const dir of getAdditionalDirectoriesForClaudeMd()) {
    const additionalSkillsPath = platformPath.join(dir, '.claude', 'skills')
    try { await fs.stat(additionalSkillsPath); paths.push(additionalSkillsPath) } catch {}
  }

  return paths
}
```

#### 几个观察

**(a) 不监听 managed (`policySettings`)**

注意没监听 `policySettings`。原因：策略管理目录由 IT 部署变化，不会运行时被用户改。也不该让用户的 skill watcher 触发 policy reload。

**(b) 不监听单个 cwd 之上的 `.claude/skills`**

03 篇讲过 `getProjectDirsUpToHome` 会从 cwd 一路向上扫到 git root——但这里只监听 cwd 自己的 `.claude/skills`，不监听父目录。

为什么？大概率父目录里有的 skill，cwd 也能继承（在装载时已经合并过）。监听父目录会让 monorepo 场景下相邻子项目的修改也触发当前会话 reload——噪音。

**(c) stat 失败就不加**

不存在的目录不监听。chokidar 监听不存在的路径不会报错（它会等目录被创建），但 detector 选择**只监听已存在的**。

副作用：用户**新建** `.claude/skills/` 目录（之前没有）时，detector 不会自动开始监听。需要重启 Claude Code（或者下次 init）。这是个小缺口。

### 3.4 `handleChange` + `scheduleReload`（237-279）— 真正的 reload 逻辑

```ts
function handleChange(path: string): void {
  logForDebugging(`Detected skill change: ${path}`)
  logEvent('tengu_skill_file_changed', { source: 'chokidar' })
  scheduleReload(path)
}

function scheduleReload(changedPath: string): void {
  pendingChangedPaths.add(changedPath)
  if (reloadTimer) clearTimeout(reloadTimer)
  reloadTimer = setTimeout(async () => {
    reloadTimer = null
    const paths = [...pendingChangedPaths]
    pendingChangedPaths.clear()

    // ★ 给用户的 ConfigChange hook 一次拦截机会
    const results = await executeConfigChangeHooks('skills', paths[0]!)
    if (hasBlockingResult(results)) {
      logForDebugging(`ConfigChange hook blocked skill reload (${paths.length} paths)`)
      return
    }

    // ★ 三件事
    clearSkillCaches()       // Layer 1+2: skill loader
    clearCommandsCache()     // Layer 2+3: 命令视图 + plugin
    resetSentSkillNames()    // attachments: 让 skill_listing 重新发

    skillsChanged.emit()
  }, testOverrides?.reloadDebounce ?? RELOAD_DEBOUNCE_MS)
}
```

#### 这一段是 hot reload 的核心

**(a) debounce 行为**

- 进来一个事件就 add path + reset timer
- 300ms 内每来一个事件都 reset timer
- 300ms 没新事件 → 触发实际 reload

效果：连续大量事件（git pull）只会触发**一次** reload。

**(b) `executeConfigChangeHooks('skills', paths[0])` 是用户拦截门**

用户可以在配置里写一个 ConfigChange hook：

```json
{
  "hooks": {
    "ConfigChange": [
      { "matcher": "skills", "hooks": [{ "type": "command", "command": "..." }] }
    ]
  }
}
```

hook 命令通过 `hasBlockingResult` 决定是否阻止 reload。

#### 用例

某些用户希望"我手动 `/reload` 才 reload，文件改了不要自动跑"——可以写个 ConfigChange hook 永远 block。

`paths[0]!` 这个 `!` 是 TS non-null assertion——如果 `pendingChangedPaths` 是空（不可能，因为 `add` 在前面），TS 会报错。注释 263-265 解释了为什么传第一个 path：

```
Fire ConfigChange hook once for the batch — the hook query is always
'skills' so firing per-path (which can be hundreds during a git
operation) just spams the hook matcher with identical queries. Pass the
first path as a representative; hooks can inspect all paths via the
skills directory if they need the full set.
```

**(c) 三件事的顺序**

```ts
clearSkillCaches()       // 1. 清 skill loader (Layer 1+2)
clearCommandsCache()     // 2. 清命令总线 (Layer 2+3)，内部又调 clearSkillCaches（幂等）
resetSentSkillNames()    // 3. 重置 attachment 已发名单
skillsChanged.emit()     // 4. 通知 React UI
```

`resetSentSkillNames()` 第三步——让 `skill_listing` attachment 在下次 turn 全量重发（07 篇讲过的 `sentSkillNames` set 被清）。这是必要的：skill 描述可能改了，模型需要看到新版描述。

`skillsChanged.emit()` 最后——React UI 拿到信号后会调 `getCommands(cwd)`，因为前面 cache 已经全清，一定拿到最新数据。

### 3.5 `dispose`（146-164）— 优雅退出

```ts
export function dispose(): Promise<void> {
  disposed = true
  if (unregisterCleanup) {
    unregisterCleanup()
    unregisterCleanup = null
  }
  let closePromise: Promise<void> = Promise.resolve()
  if (watcher) {
    closePromise = watcher.close()
    watcher = null
  }
  if (reloadTimer) {
    clearTimeout(reloadTimer)
    reloadTimer = null
  }
  pendingChangedPaths.clear()
  skillsChanged.clear()
  return closePromise
}
```

进程退出时跑：

1. 把 `disposed = true`，初始化函数失效
2. 反注册 cleanup（避免重复 dispose）
3. 关 chokidar watcher（异步，return 它的 promise）
4. 清 reload timer
5. 清待处理路径
6. 清信号订阅者

注意 5、6 是**主动清理**——避免 React 组件已经卸载但订阅还在引发 setState-on-unmounted。

## 4. UI 层消费：`useSkillsChange` Hook

打开 `restored-src/src/hooks/useSkillsChange.ts`。62 行。

```ts
export function useSkillsChange(
  cwd: string | undefined,
  onCommandsChange: (commands: Command[]) => void,
): void {
  // ★ skill 文件变化时：深清
  const handleChange = useCallback(async () => {
    if (!cwd) return
    try {
      clearCommandsCache()                    // 深清
      const commands = await getCommands(cwd)
      onCommandsChange(commands)
    } catch (error) {
      if (error instanceof Error) logError(error)
    }
  }, [cwd, onCommandsChange])

  useEffect(() => skillChangeDetector.subscribe(handleChange), [handleChange])

  // ★ GrowthBook 刷新时：浅清
  const handleGrowthBookRefresh = useCallback(async () => {
    if (!cwd) return
    try {
      clearCommandMemoizationCaches()         // 浅清
      const commands = await getCommands(cwd)
      onCommandsChange(commands)
    } catch (error) {
      if (error instanceof Error) logError(error)
    }
  }, [cwd, onCommandsChange])

  useEffect(() => onGrowthBookRefresh(handleGrowthBookRefresh), [handleGrowthBookRefresh])
}
```

#### 两个不同的失效路径

注释 13-22 写得很清楚：

```
Keep the commands list fresh across two triggers:

1. Skill file changes (watcher) — full cache clear + disk re-scan, since
   skill content changed on disk.
2. GrowthBook init/refresh — memo-only clear, since only `isEnabled()`
   predicates may have changed. Handles commands like /btw whose gate
   reads a flag that isn't in the disk cache yet on first session after
   a flag rename: getCommands() runs before GB init (main.tsx:2855 vs
   showSetupScreens at :3106), so the memoized list is baked with the
   default. Once init populates remoteEvalFeatureValues, re-filter.
```

**(1) 文件变化** → `clearCommandsCache`（深清）
   原因：skill 内容变了，必须重读磁盘。

**(2) GrowthBook 刷新** → `clearCommandMemoizationCaches`（浅清）
   原因：feature flag 变了，但 skill 文件没变。只需要重跑 `availability + isEnabled` 过滤。

#### 这里又一次出现"清的层次很关键"

如果 GrowthBook 刷新时调深清，会**重读所有 SKILL.md**——大量 IO，没必要。

如果文件变化时调浅清，会**用旧的 SKILL.md 内容**——文件改了没生效。

`useSkillsChange` 的设计是"按触发因素挑对应的清理深度"。

注释里还提到一个经典 bug：

> Handles commands like /btw whose gate reads a flag that isn't in the disk cache yet on first session after a flag rename: getCommands() runs before GB init...

GrowthBook init 在 `getCommands` 之后才有 flag 值。如果只清一次 cache，第一次过滤拿 default 值。GB init 完成后再次浅清，重新跑 `isEnabled()`——这次拿到正确 flag。这是个**双触发同步**的问题。

#### 思考题

> 如果用户**编辑了 SKILL.md** 同时 **GrowthBook 也刷新了**，两个回调都会跑。深清 + 浅清各一次，哪个先跑没保证。会不会出问题？

（答：不会。两个都最终调 `getCommands(cwd)`，深清结果包含浅清效果。即使顺序乱，第二次跑的结果一定正确——`getCommands` 不 memoize，每次都 fresh。性能上略浪费，但语义安全。）

## 5. 整条热更新链路的全景图

把第 3、4 节合起来：

```
用户编辑 ~/.claude/skills/foo/SKILL.md
         │
         │ 文件系统事件
         ▼
chokidar (USE_POLLING, depth:2, atomic, awaitWriteFinish 1s)
         │
         │ stable 之后
         ▼
handleChange(path)
   ├── logEvent('tengu_skill_file_changed')
   └── scheduleReload(path)
         │
         │ pendingChangedPaths.add(path)
         │ 重置 reloadTimer (300ms)
         │
         ▼ (debounce 300ms 静默后)
async reloadTimer callback:
   ├── paths = [...pendingChangedPaths]
   ├── pendingChangedPaths.clear()
   ├── await executeConfigChangeHooks('skills', paths[0])
   │     │
   │     ├ 用户 hook 命令跑
   │     └ hasBlockingResult? → 是 → return（用户阻止了 reload）
   │
   ├── clearSkillCaches()
   │     - getSkillDirCommands.cache.clear()
   │     - loadMarkdownFilesForSubdir.cache.clear()
   │     - conditionalSkills.clear()
   │     - activatedConditionalSkillNames.clear()
   │
   ├── clearCommandsCache()
   │     - clearCommandMemoizationCaches()
   │       · loadAllCommands.cache.clear()
   │       · getSkillToolCommands.cache.clear()
   │       · getSlashCommandToolSkills.cache.clear()
   │       · clearSkillIndexCache()
   │     - clearPluginCommandCache()
   │     - clearPluginSkillsCache()
   │     - clearSkillCaches() (幂等再清一次)
   │
   ├── resetSentSkillNames()
   │     attachments.ts 的 sentSkillNames map 全清
   │     下次 skill_listing attachment 全量发
   │
   └── skillsChanged.emit()
         │
         │ 订阅者：
         ▼
useSkillsChange.handleChange (React hook)
   ├── clearCommandsCache() (再清，幂等)
   ├── const commands = await getCommands(cwd)
   │     这次会重读磁盘，拿到新的 SKILL.md
   └── onCommandsChange(commands)
         │
         │ React state 更新
         ▼
REPL.tsx 重渲染 typeahead / SkillsMenu
```

模型的视角：

```
turn N: 用户修改 skill 文件
turn N: chokidar 检测到（最快也要 1.3s 后）
turn N: 实际 reload（cache 清、UI 更新）
turn N+1: skill_listing attachment 重新全量发给模型（resetSentSkillNames 让"已发"为空）
turn N+1: 模型看到新 skill 描述
```

**所以 hot reload 对模型来说有个不可避免的"延迟一个 turn"**——文件改了的瞬间，已经在飞的当前 turn 不会 retro-actively 拿到新 skill。这是合理的——会话连贯性比"立即一致"更重要。

## 6. 三层 cache 的清理矩阵

把整个文档要记住的清理逻辑做成一张矩阵：

| 触发 | 调用函数 | 清 Layer 1 | 清 Layer 2 | 清 Layer 3 | 副作用 |
|---|---|---|---|---|---|
| skill 文件改了 | `scheduleReload` callback | 部分（conditionalSkills + activated）| 全 | 全 | resetSentSkillNames，emit 信号 |
| 动态 skill 装载完成 | `onDynamicSkillsLoaded` callback | **不**清 | **不**清 | 全 | emit 信号 |
| GrowthBook 刷新 | `useSkillsChange.handleGrowthBookRefresh` | **不**清 | **不**清 | 全 | （只是重过滤） |
| 测试重置 | `clearBundledSkills` + `resetForTesting` | 全 | 全 | 全 | 全部 reset |

### 关键洞察

**深清比浅清的"破坏面"大**——它会清掉 conditionalSkills / activatedConditionalSkillNames。所以：

- **dynamicSkills 增加场景**只能用浅清，否则 conditional 状态会丢
- **磁盘文件变化场景**必须用深清，否则磁盘新内容读不到

这两条规则铭记于心，回头读 `commands.ts:519-539` 那两个清理函数就一目了然。

## 7. 一个容易踩的坑：`activatedConditionalSkillNames` 在深清时会丢

03 篇 + 07 篇都提过这点。这一篇把它在热更新里的影响讲完整。

### 场景

1. turn 1：用户读 `src/payments/foo.ts`
2. paths skill `payments-helper` 被 `activateConditionalSkillsForPaths` 激活
3. `activatedConditionalSkillNames.add('payments-helper')`
4. `dynamicSkills.set('payments-helper', skill)`
5. turn 1 末尾：`skill_listing` attachment 把 payments-helper 发给模型

6. turn 2：用户修改了**别的** SKILL.md（比如 `~/.claude/skills/foo/SKILL.md`）
7. chokidar 触发，1.3s 后 `scheduleReload` 跑
8. `clearSkillCaches()` 清掉 `activatedConditionalSkillNames` 和 `conditionalSkills`
9. **但 `dynamicSkills` 没被清** —— payments-helper 还在 dynamicSkills 里
10. `clearCommandsCache` 也清了 memoize 视图
11. `getCommands` 在下个 turn 重新跑：
    - `loadAllCommands` 重新装载磁盘 skill
    - `getSkillDirCommands` 把 payments-helper 当作 conditional skill **再次**抽走（因为 `activatedConditionalSkillNames` 被清了）
    - 但是 `getCommands` 拿 `dynamicSkills` 时 payments-helper 还在
12. 结果：payments-helper 在 dynamicSkills 里 + 在 conditionalSkills 池里 —— 一份重复

**这会产生什么问题？**

实际上**不会有用户可见 bug**——`getCommands` 用 `Set<name>` 去重（commands.ts:492-498）：

```ts
const baseCommandNames = new Set(baseCommands.map(c => c.name))
const uniqueDynamicSkills = dynamicSkills.filter(s => !baseCommandNames.has(s.name) && ...)
```

baseCommands 不包含 conditional pool 里的 skill（`getSkillDirCommands` 不返回它们）。所以 `uniqueDynamicSkills` 仍然包含 payments-helper。最终 commands 列表是对的——payments-helper 进得去。

**但**：

- `conditionalSkills.size` 永远 +1（payments-helper 仍在池里），下次模型读 `src/payments/foo.ts` 又会触发一次"激活"——但激活的是已经在 dynamicSkills 里的同名 skill，效果幂等。
- `tengu_dynamic_skills_changed` 的 telemetry 数据可能多算（"激活"了同一个 skill 多次）

这是个**轻量内存与 telemetry 噪音**，不是功能 bug。但读 03 篇段 3 阶段 D 的代码时你会发现这点设计的张力——`clearSkillCaches` 清 `activatedConditionalSkillNames` 是为了让 `getSkillDirCommands` 重新评估，但代价是 conditional 状态在每次深清后都"半失忆"。

#### 思考题

> 如果你想修复这个轻微的状态漂移（例如让 `clearSkillCaches` **不**清 `activatedConditionalSkillNames`），会不会引入新问题？比如热更新场景：用户从 SKILL.md 里**删掉了 paths frontmatter**，会发生什么？

（提示：如果不清，那 SKILL.md 改了 paths 字段后，`getSkillDirCommands` 会因为 `activatedConditionalSkillNames.has(name)` 仍然是 true，把它继续当作 unconditional——但用户已经把 paths 加回来了，期望的是"再次变 conditional"。所以**清是为了让 frontmatter 变化能够正向反映**，代价是丢已激活记忆。这是一个权衡，当前选择了"frontmatter 变化优先于会话记忆"。）

## 8. 这一篇你应该带走的几样东西

读到这里，你应该能回答：

1. 三层 cache 是哪三层？分别清谁？
   （Layer 1: 静态状态（bundled + dynamic）；Layer 2: loader cache；Layer 3: 命令视图 cache）
2. 触发 A（文件变化）和触发 B（动态发现）为什么用不同清理函数？
   （A 必须深清重读磁盘；B 必须浅清以保留 dynamicSkills 不丢）
3. `RELOAD_DEBOUNCE_MS = 300` 解决什么问题？
   （git pull 等批量操作触发几十个事件，避免每个都 reload）
4. `USE_POLLING = typeof Bun !== 'undefined'` 为什么？
   （Bun fs.watch 死锁 bug，stat polling 绕过）
5. `ConfigChange` hook 在 reload 流程的哪一步？做什么？
   （在 cache 清之前调；返回 blocking result 可以阻止 reload）
6. `resetSentSkillNames` 为什么必须在文件变化时调？
   （让 skill_listing attachment 全量重发——因为 description 可能改了）
7. hot reload 对模型可见的延迟最少多少？
   （awaitWriteFinish 1s + debounce 300ms + 下个 turn skill_listing 推送 = 至少 1.3s + 一个 turn）
8. `clearSkillCaches` 为什么会让"已激活的 conditional skill"回到"未激活"状态？带来什么副作用？
   （`activatedConditionalSkillNames.clear()` 让 `getSkillDirCommands` 认为它们仍是 conditional——下次需要路径再次命中才能激活；但 dynamicSkills 不清所以名字仍在 commands 列表里——状态漂移但不破坏功能）
