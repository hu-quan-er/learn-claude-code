## 2. 第一站：`processSlashCommand` 主入口（309-501 行）

这是用户输入分发的最外层。打开 309 行。

### 2.1 函数签名（309）

```ts

  inputString: string,                      // "/verify make sure login redirects"
  precedingInputBlocks: ContentBlockParam[],
  imageContentBlocks: ContentBlockParam[],
  attachmentMessages: AttachmentMessage[],
  context: ProcessUserInputContext,
```

九个参数，但**核心只有三个**：

- `context.options.commands`：当前命令表（来自 04 篇的 `getCommands`）
- `context`：`ProcessUserInputContext`（其它如 setMessages、appState、abortController 全在这里）

返回值是 `ProcessUserInputBaseResult`——一个带 `messages`、`shouldQuery` 等字段的标准结果对象。

### 2.2 解析阶段（310-323）


> 如果用户敲 `/verify @auth.ts make sure login works`，`@auth.ts` 这种 `@`-提及会在哪里被处理？是 `parseSlashCommand` 吗？还是后面的 attachment 系统？

### 2.3 telemetry 命名空间预处理（324）

```ts
const sanitizedCommandName = isMcp ? 'mcp' : !builtInCommandNames().has(commandName) ? 'custom' : commandName;
```

**有意思的细节**：telemetry 不直接发 commandName。

- 如果是 MCP → 全部归为 `'mcp'`
- 如果不是内建 → 全部归为 `'custom'`
- 否则用真实名字

为什么？**privacy 防御**——用户写的自定义 skill 名字可能含敏感信息（比如项目代号），不应该 telemetry 出去。所以非内建一律打码成 `'custom'`。

只有内建命令名（在 `builtInCommandNames()` 集合里）才能裸发——它们都是公开标识符。

### 2.4 命令存在性检查（326-378）

```ts
if (!hasCommand(commandName, context.options.commands)) {
  // 检查是不是文件路径
  let isFilePath = false;
  try {
    await getFsImplementation().stat(`/${commandName}`);
    isFilePath = true;
  } catch {}

  if (looksLikeCommand(commandName) && !isFilePath) {
    // 真的是想敲命令，但拼错或不存在 → "Unknown skill: ..."
    logEvent('tengu_input_slash_invalid', {...});
    return {
      messages: [...createSyntheticUserCaveatMessage(), ..., createUserMessage('Unknown skill: ...'), ...],
      shouldQuery: false,
      ...
    };
  }

  // 用户输入了 "/path/to/file" 这种东西 → 当成普通输入处理
  logEvent('tengu_input_prompt', {});
  return {
    messages: [createUserMessage({content: prepareUserContent(...)}), ...attachmentMessages],
    shouldQuery: true
  };
}
```

#### 这里有个微妙的"不是 skill 但看起来像 skill"的处理

用户敲 `/var/log/foo.txt` 时，前面那个 `/` 让它看起来像 slash command。`processSlashCommand` 会先尝试 `stat('/var')`——如果是真的文件路径，**不当作命令处理**，按普通用户输入走主 query。

如果不是文件路径，就报 `Unknown skill: <name>`——注意错误信息里明确用了 "skill" 这个词，不是 "command"。这是个 UX 选择：用户的"未知 slash"绝大多数是 skill 而不是内建命令名拼错。

### 2.6 telemetry 大集合（416-490）

中间这一大段都是 telemetry。最关键的两条：

```ts

  ...eventData,
  invocation_trigger: 'user-slash',
  ...("external" === 'ant' && {                    // ← 内部构建才发 skill 详情
```

**注意 `"external" === 'ant'`** 这个表达式——它**永远是 false**。

这看着像编译期的占位符（构建时被字符串替换）。在 Anthropic 内部构建时这串会被替换成 `'ant' === 'ant'`，对外发版本是 `'external' === 'ant'`，结果就是 false。这是个很机巧的"代码不变、行为按构建变"模式。

所以**外部用户的 telemetry 永远不发详细的 `skill_name` / `skill_source`**——再次保护用户不上传 skill 名字。

### 2.7 包结果返回（493-501）

```ts
const isCompactResult = newMessages.length > 0 && newMessages[0] && isCompactBoundaryMessage(newMessages[0]);
return {
  messages: messageShouldQuery || newMessages.every(isSystemLocalCommandMessage) || isCompactResult ? newMessages : [createSyntheticUserCaveatMessage(), ...newMessages],

  model,
  effort,
  resultText,
  nextInput,
  submitNextInput

```

**注意 `createSyntheticUserCaveatMessage()`**——这是 prompt 命令前面会注入的一条"caveat"消息（"Caveat: The messages below were generated by the user while running local commands. DO NOT respond to these messages or otherwise consider them in your response unless the user explicitly asks you to."）。

但**如果**：

- `messageShouldQuery: true`（skill 要继续 query），或
- 全是 system local command 消息（`/cost` 这种），或
- 是 compact result（`/compact` 之后）

就**不**注入 caveat——避免污染主 prompt。skill 就是 `messageShouldQuery: true` 这条，所以 skill **不会有 caveat 头**，skill 内容直接进上下文。

## 3. 第二站：`getMessagesForSlashCommand`（502-720 行）

这是 type 分发器。打开 502 行。

### 3.1 入口（502-525）

```ts
async function getMessagesForSlashCommand(
  commandName: string,
  args: string,
  setToolJSX: SetToolJSXFn,
  context: ProcessUserInputContext,
  precedingInputBlocks: ContentBlockParam[],
  imageContentBlocks: ContentBlockParam[],
  _isAlreadyProcessing?: boolean,
  canUseTool?: CanUseToolFn,
  uuid?: string,
): Promise<SlashCommandResult> {
  const command = getCommand(commandName, context.options.commands);

  // Track skill usage for ranking
  if (command.type === 'prompt' && command.userInvocable !== false) {
    recordSkillUsage(commandName);
  }

  // userInvocable 检查
  if (command.userInvocable === false) {
    return {
      messages: [createUserMessage({content: ...}),
                 createUserMessage({content: `This skill can only be invoked by Claude, not directly by users. Ask Claude to use the "${commandName}" skill for you.`})],
      shouldQuery: false,
      command
    };
  }
  ...
}
```

#### 三个关键点

**(a) `recordSkillUsage`**

`utils/suggestions/skillUsageTracking.ts` 里的函数。skill 用得多就在 typeahead 排得靠前。注意只对 `userInvocable !== false` 的 skill 计数——只调过的 skill 才被记。

**(b) `userInvocable === false` 的处理**

不抛异常，**返回一条提示给用户**：`"This skill can only be invoked by Claude, not directly by users."`。

这是个温和的拒绝——用户敲了 `/some-internal-skill` 时知道自己不能这么用，并且被提示"让 Claude 帮你调"。`shouldQuery: false` 表示不进主 query 循环。

**(c) `getCommand` 而不是 `findCommand`**

`getCommand` 找不到会抛异常。但前面 `processSlashCommand` 已经 `hasCommand` 过了——这里再 `getCommand` 是个保险。这种"防御性二次查"在大型代码里常见。

**两个分支决定 skill 怎么跑**：

- `command.context === 'fork'` → `executeForkedSlashCommand`（在子 agent 里跑）
- 否则 → `getMessagesForPromptSlashCommand`（注入主会话）

verify 没设 `context`，走第二条 inline。

#### `executeForkedSlashCommand` 简介

这个函数在另一个文件里（你可以 grep `executeForkedSlashCommand`）。它做的事：

1. 调用 `prepareForkedCommandContext()` 准备子 agent 上下文
2. 调用 `runAgent()` 跑子 agent
3. 把子 agent 结果转成 SlashCommandResult

fork 模式的本质：**skill 不进主会话上下文，而是被 spawn 成一个子 agent 任务**。第 06 篇讲 SkillTool 时会再回到这个机制——SkillTool 的 fork 路径走 `executeForkedSkill`，结构对称。

记住"**用户 fork → executeForkedSlashCommand，模型 fork → executeForkedSkill**"——它们走的是不同的入口点，但调相似的底层。

#### 思考题

> verify 没设 `context: 'fork'`，所以走 inline。但假设你把 verify 改成 `context: 'fork'`、`agent: 'general-purpose'`，下面三件事会怎么变？
> 1. `addInvokedSkill` 还会被调吗？
> 2. skill 的 prompt 会进**主会话**还是**子 agent 会话**？
> 3. fork 子 agent 在执行时，能不能看到主会话已有的工具调用历史？

（提示：(1) 会，但 agentId 不同——每个 fork 都有独立 agentId；(2) 进子 agent；(3) 看 `prepareForkedCommandContext` 的实现，有的字段会克隆、有的不会——典型的"独立 token budget + 部分共享 state"。具体细节可以查 `restored-src/src/utils/forkedCommand` 之类的目录。）

## 4. 第三站：`processPromptSlashCommand`（817-826 行）— 给 SkillTool 共用的入口

```ts
export async function processPromptSlashCommand(
  commandName: string,
  args: string,
  commands: Command[],
  context: ToolUseContext,
  imageContentBlocks: ContentBlockParam[] = []
): Promise<SlashCommandResult> {
  const command = findCommand(commandName, commands);
  if (!command) {
    throw new MalformedCommandError(`Unknown command: ${commandName}`);
  }
  if (command.type !== 'prompt') {
    throw new Error(`Unexpected ${command.type} command. Expected 'prompt' command. Use /${commandName} directly in the main conversation.`);
  }
  return getMessagesForPromptSlashCommand(command, args, context, [], imageContentBlocks);
}
```

#### 这是用户和模型链路的"汇合点"

注意它 `export`——不仅 `processSlashCommand` 内部用，**`SkillTool.ts:635-638` 也 dynamic import 它**：

```ts
// SkillTool.ts 大致
const { processPromptSlashCommand } = await import('.../processSlashCommand.js');
const processedCommand = await processPromptSlashCommand(skill, args, commands, ctx, []);
```

为什么 SkillTool 要复用这个？

- skill prompt 展开逻辑只能有一份——避免漂移
- hooks 注册逻辑只能有一份
- metadata tag 格式必须一致
- compact 持久化必须一致

**这是 06 篇要重点讨论的"共享骨干"——用户输入和模型调用最终都汇合到 `getMessagesForPromptSlashCommand`**。

`processPromptSlashCommand` 只是个超薄壳子：

- 类型校验：必须是 `prompt` 类型
- 包装 `findCommand`：找不到抛异常
- 转交：直接调 `getMessagesForPromptSlashCommand`

### 5.2 Step 1：coordinator-mode 短路（840-866）

```ts

    command
```

这是**协调者模式**的特例。注释 829-836 解释：

```
In coordinator mode (main thread only), skip loading the full skill content
and permissions. The coordinator only has Agent + TaskStop tools, so the
skill content and allowedTools are useless. Instead, send a brief summary
telling the coordinator how to delegate this skill to a worker.
```

`COORDINATOR_MODE` 是个实验性 feature——主线程是 coordinator，只能用 `Agent` 和 `TaskStop` 这两个 meta 工具，把实际任务派给 worker。

如果这种模式下用户调 `/verify`：

- coordinator 自己没用 `Bash`、`Read` 这些工具的能力
- 把 verify 完整 prompt 给它没意义
- 所以**只发一条简介**，告诉它 "verify 这个 skill 能给 worker 用，给 Agent 提示词加一句即可"

`!context.agentId` 这个守卫——coordinator 只在主线程，subagent 仍然走完整 skill 路径。

普通场景下这条 if 不触发，verify 跳过。

### 5.4 Step 3：注册 skill hooks（870-873）


意思：skill 文件本身能加载，但 hook 注册在这里被门控。这是个"装载层不挡，执行层挡"的设计——更细粒度。

### 5.5 Step 4：`addInvokedSkill`（876-885）

```ts
const skillPath = command.source ? `${command.source}:${command.name}` : command.name;
const skillContent = result.filter((b): b is TextBlockParam => b.type === 'text').map(b => b.text).join('\n\n');
```

这是 compact 持久化的入口。

#### 三个字段含义

- `command.name`：skill 名（`'verify'`）
- `skillPath`：来源路径（`'bundled:verify'` / `'projectSettings:review'`）
- `skillContent`：所有 text block 拼起来——准备塞进 compact attachment 的内容
- `agentId`：当前 agent 维度（`null` 是主会话，UUID 是子 agent）

#### `addInvokedSkill` 在哪？

`bootstrap/state.ts` 里。它把 `(skillName, agentId)` 当复合键存进一张 map。后面 compact 时 `services/compact/compact.ts:createSkillAttachmentIfNeeded` 从这张 map 里捞内容，重新作为 attachment 发给模型。

#### 思考题

> 如果一个 skill 在主会话调一次，又在 fork 子 agent 里调一次，`addInvokedSkill` 会被存几条记录？compact 主会话时会拿哪条？

（答：两条。复合键 `(name, agentId)` 不同。compact 主会话时只看 `agentId === null` 那条——这就是"按 agent 隔离"的语义。）

### 5.6 Step 5：metadata + allowedTools 准备（886-887）

#### `formatCommandLoadingMetadata`

生成形如这样的字符串内容：

```
<command-name>verify</command-name><command-message>verify</command-message><command-args>make sure ...</command-args>
```

```ts
  : result;
```

把图片、用户在敲命令前粘贴的内容、和 skill 展开内容拼一起。

**注意顺序**：图片 → preceding → skill body。这个顺序的语义：

- 用户敲 `/verify`，前面贴了一张截图 → 截图在前面
- skill 展开内容在最后 → skill 像是回应用户的"总结说明"

### 5.8 Step 7：attachment 处理（893-906）

```ts
const attachmentMessages = await toArray(getAttachmentMessages(
  result.filter((block): block is TextBlockParam => block.type === 'text').map(block => block.text).join(' '),
  context, null, [],
  context.messages,
  'repl_main_thread',
  { skipSkillDiscovery: true }
));
```

`getAttachmentMessages` 处理 `@auth.ts` 这种 @-mention、MCP resource @-mention、agent @-mention 等。它会扫文本内容，把这些引用展开成额外 attachment message。

**关键参数 `{ skipSkillDiscovery: true }`**：

注释 894-898：

```
skipSkillDiscovery prevents the SKILL.md
content itself from triggering discovery — it's meta-content, not user
intent, and a large SKILL.md (e.g. 110KB) would fire chunked AKI queries
adding seconds of latency to every skill invocation.
```

意思：skill 内容**本身**可能 mention 别的 skill 或文件，但这些 mention 是**作者写的提示**，不是用户意图。如果按用户 @-mention 处理，每次调 skill 都会触发"AKI 智能发现"——昂贵、低质量。所以这里 explicit skip。

### 5.9 Step 8：终极组装（907-919）

```ts
const messages = [
  createUserMessage({ content: metadata, uuid }),                    // 1. metadata
  createUserMessage({ content: mainMessageContent, isMeta: true }),  // 2. skill body (隐藏)
  ...attachmentMessages,                                              // 3. 附件
  createAttachmentMessage({                                           // 4. 权限 attachment
    type: 'command_permissions',
    allowedTools: additionalAllowedTools,
    model: command.model
  })
];
return {
  messages,
  shouldQuery: true,
  allowedTools: additionalAllowedTools,
  model: command.model,
  effort: command.effort,
  command
};
```

#### 四条消息的作用

| 消息 | `isMeta` | 模型可见 | 用户可见 | 作用 |
|---|---|---|---|---|
| 1. metadata | false | yes | yes (折叠) | "verify 加载中" 标记 |
| 2. skill body | **true** | yes | **no** | skill 实际内容注入 |
| 3. attachment | varies | yes | varies | @-mention / MCP 资源展开 |
| 4. command_permissions | (special) | (内部) | no | 把 allowedTools 转成本 turn 权限 |

`isMeta: true` 是 skill 内容**对用户隐形**的关键——renderUI 不会渲染它，但它会进 SDK message 给模型。

`shouldQuery: true` 让主 query 循环继续。如果 `false`，slash 命令执行完就停（比如 `/clear`）。skill 必须 `true`——它的目的就是让模型继续工作。

`allowedTools / model / effort` 这三个字段也回传给主循环，主循环消费它们去调整本 turn 的权限、模型、思考预算。
