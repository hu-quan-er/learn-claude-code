# 03 - 并行与串行调度

## 核心结论

`AgentTool` 自己声明 `isConcurrencySafe() === true`（`AgentTool.tsx:1273`）。在 `StreamingToolExecutor` 的调度规则下，这意味着：

- **一条 assistant message 里多个 `Agent` tool_use 块会并发执行**。
- 与同样 concurrency-safe 的工具（Read、Glob、Grep 等）之间也并发。
- 与 non-concurrent 的工具（Edit、Write、Bash 等大部分写动作）之间是"组切换"语义：要么全是 safe 的并发，要么独占一个非 safe 的。

模型实现"并行 spawn"的方式不是某种特殊参数，而是**直接在同一个 assistant message 中输出多个 `tool_use` block**。runtime 负责并发起跑、按到达顺序回填结果。

## StreamingToolExecutor 的调度规则

源码：`src/services/tools/StreamingToolExecutor.ts:40-150`。

```typescript
type TrackedTool = {
  id: string
  block: ToolUseBlock
  assistantMessage: AssistantMessage
  status: 'queued' | 'executing' | 'completed' | 'yielded'
  isConcurrencySafe: boolean
  ...
}

class StreamingToolExecutor {
  private tools: TrackedTool[] = []

  addTool(block: ToolUseBlock, assistantMessage: AssistantMessage): void {
    const toolDefinition = findToolByName(this.toolDefinitions, block.name)
    const parsedInput = toolDefinition.inputSchema.safeParse(block.input)
    const isConcurrencySafe = parsedInput?.success
      ? Boolean(toolDefinition.isConcurrencySafe(parsedInput.data))
      : false
    this.tools.push({ id, block, ..., status: 'queued', isConcurrencySafe, ... })
    void this.processQueue()
  }

  private canExecuteTool(isConcurrencySafe: boolean): boolean {
    const executingTools = this.tools.filter(t => t.status === 'executing')
    return (
      executingTools.length === 0 ||
      (isConcurrencySafe && executingTools.every(t => t.isConcurrencySafe))
    )
  }

  private async processQueue(): Promise<void> {
    for (const tool of this.tools) {
      if (tool.status !== 'queued') continue
      if (this.canExecuteTool(tool.isConcurrencySafe)) {
        await this.executeTool(tool)
      } else {
        if (!tool.isConcurrencySafe) break  // non-safe 必须按顺序，遇到不能跑就停
      }
    }
  }
}
```

可以提炼成 3 条规则：

| 当前 executing 状态 | 新 tool 是 safe | 新 tool 是 non-safe |
|----------------------|----------------|---------------------|
| 0 个在跑 | 立即起跑 | 立即起跑 |
| N 个 safe 在跑 | 立即起跑（并发） | 排队等 |
| 1 个 non-safe 在跑 | 排队等 | 排队等 |

所以"并发组"内全是 safe 的，"独占组"是一个 non-safe 的。两组之间 strict 切换。

## AgentTool 的 isConcurrencySafe / isReadOnly

```typescript
// AgentTool.tsx:1264-1276
isReadOnly() {
  return true   // delegates permission checks to its underlying tools
},
isConcurrencySafe() {
  return true
},
```

两个字段含义不同：

- `isConcurrencySafe` ←→ "和别人并行行不行"，决定调度。
- `isReadOnly` ←→ "工具本身是否需要权限确认"，决定权限层。

`AgentTool.isReadOnly() === true` 这个声明的意思是："Agent 工具本身不需要权限提示，权限交给内部 spawn 的子代理工具去处理"。这避免了"父 spawn 子前要先 ask 一次权限，子内部又要 ask 一次"的双确认体验。

## 模型如何"决定"并行

模型并行的物理表现：一条 assistant message 的 `content` 数组里多个 `tool_use` block：

```json
{
  "role": "assistant",
  "content": [
    { "type": "text", "text": "I'll run three searches in parallel." },
    {
      "type": "tool_use",
      "id": "toolu_1",
      "name": "Agent",
      "input": {
        "subagent_type": "Explore",
        "description": "Find DB migrations",
        "prompt": "Locate all database migration files..."
      }
    },
    {
      "type": "tool_use",
      "id": "toolu_2",
      "name": "Agent",
      "input": {
        "subagent_type": "Explore",
        "description": "Find API endpoints",
        "prompt": "Locate all API endpoint registrations..."
      }
    },
    {
      "type": "tool_use",
      "id": "toolu_3",
      "name": "Agent",
      "input": {
        "subagent_type": "Explore",
        "description": "Find logging config",
        "prompt": "Locate the global logging setup..."
      }
    }
  ]
}
```

`query.ts` 提取这 3 个 tool_use 后逐个调用 `streamingToolExecutor.addTool(block, ...)`：

```typescript
// query.ts
for (const toolBlock of msgToolUseBlocks) {
  streamingToolExecutor.addTool(toolBlock, message)
}
```

三个 Agent 工具都 safe，`canExecuteTool` 三次都通过，三个 `executeTool` 几乎同时进入 `runAgent()` 内部 query 循环。三个子代理各自独立跑 API call，谁先完成谁先把结果 yield 出来。`query.ts` 用 `getCompletedResults()` 不断 drain：

```typescript
// query.ts
for (const result of streamingToolExecutor.getCompletedResults()) {
  if (result.message) {
    yield result.message
    toolResults.push(...normalizeMessagesForAPI([result.message], tools).filter(_ => _.type === 'user'))
  }
}
```

返回顺序 ≠ 启动顺序，但**回到模型时按原 tool_use 顺序排列**（`StreamingToolExecutor` 内部 buffer 保证）。

### Agent 工具的 prompt 里也明确教模型并行

`AgentTool.tsx` 通过 `prompt.ts:271` 在工具描述里告诉模型：

```text
- If the user specifies that they want you to run agents "in parallel", you MUST send a single message with multiple Agent tool use content blocks. For example, if you need to launch both a build-validator agent and a test-runner agent in parallel, send a single message with both tool calls.
```

外加 pro 用户专属的鼓励语（`prompt.ts:247-249`）：

```text
- Launch multiple agents concurrently whenever possible, to maximize performance; to do that, use a single message with multiple tool uses
```

所以**模型主动并行**有 prompt 引导 + runtime 支持双向闭环。

## 串行依赖

模型在以下情况自然会"串行"，因为它没法在不知道前一个结果的情况下写出下一个 prompt：

```text
Round 1:
  父 assistant → Agent(Explore, "Find auth file")
  ↓
  tool_result: "Found in src/middleware/auth.ts:42"

Round 2:
  父 assistant → Agent(verification, "Verify the change to src/middleware/auth.ts:42 ...")
                                          ↑
                                依赖前一轮的结果
```

这种是**轮次级**串行，不是 `StreamingToolExecutor` 调度的串行。一条 assistant message 内 `tool_use` 是同步发出的，没办法表达"等 A 完了再 B"。

如果模型确实想表达"A 然后 B"，它必须分两个 turn 发，每轮一个 `tool_use`。这反而是模型"自我决定"的串行。

## 并发与 abortController 的关系

并发 spawn 的多个子代理各自有自己的 `agentAbortController`（`runAgent.ts:524-528`）：

```typescript
const agentAbortController = override?.abortController
  ? override.abortController
  : isAsync
    ? new AbortController()
    : toolUseContext.abortController
```

- **同步 spawn**：所有同步 spawn 的子代理共享父的 abortController。ESC 杀父 = 全部子代理也死。
- **async spawn**：每个 async 子代理新建独立 controller，父代理 ESC **不会**杀后台子代理（注释原文："background agents should survive when the user presses ESC to cancel the main thread"）。

所以同样是并行，sync 并行 vs async 并行的取消语义不一样：

| 场景 | ESC 父对话的效果 |
|------|------------------|
| 并行 3 个 sync Agent | 3 个子代理同时被取消 |
| 并行 3 个 async Agent | 3 个子代理继续跑；要单独 kill 用 chat:killAgents |

## sibling abort：一个工具失败时怎么办

`StreamingToolExecutor` 内还有一个 `siblingAbortController`（`StreamingToolExecutor.ts:48-61`）：

```typescript
this.siblingAbortController = createChildAbortController(toolUseContext.abortController)
```

这是父 abort 的子 controller。注释：

> Fires when a Bash tool errors so sibling subprocesses die immediately instead of running to completion. Aborting this does NOT abort the parent — query.ts won't end the turn.

也就是说：

- 父代理 abort（用户 ESC）→ siblingAbortController 也 abort
- 但 siblingAbortController abort 不会反向触发父 abort

具体到 Agent 工具：一条 message 里并发的 3 个 Bash 工具中有 1 个失败 → siblingAbortController 触发 → 另外 2 个 Bash 也立即终止。但同样并发的 Agent 子代理是否受这个影响，要看 Agent 内部 query 循环是不是用 sibling controller。源码里 `runAgent` 默认用的是 `toolUseContext.abortController`（同步）或新建 controller（async），所以 **sibling abort 主要影响 Bash 这类直接 subprocess 的工具，对 Agent 影响有限**。

## 并行 spawn 的现实约束

虽然 runtime 支持任意条数 Agent 工具并发，但实际有几道隐式上限：

1. **API rate limit**：每个子代理是一个独立的 API stream，N 个并发 = N 个并发 API connection。Anthropic API 有账户级 RPM/TPM 限制。
2. **prompt cache 利用率**：sync 并发的子代理各自有不同 system prompt（不同 agent 定义），不共享 cache。fork 并发的子代理共享父 prompt cache（参见 02 篇）。
3. **本地计算资源**：每个子代理是同进程内的 async 任务，但工具调用可能 spawn 子进程（Bash、grep 等），并发数高会饱和 CPU/IO。
4. **terminal UI 渲染**：并发太多时 `UI.tsx` 的 grouped tool use render 会变得难看。

源码层面没有硬上限，只有 prompt 层在 pro 用户那里**抑制**鼓励并发（参见 02 篇引用的 `getSubscriptionType() !== 'pro'` 分支）——pro 用户的 prompt 里没有"鼓励并发"那句话，因为 pro 用户的 rate limit 紧张，runtime 不主动推他并发。

## 工具维度 vs Agent 维度的 concurrency

容易混淆：

| 维度 | 实现位置 | 含义 |
|------|----------|------|
| 工具 `isConcurrencySafe` | 各工具自己声明 | "父代理同 turn 里我和别的工具能不能一起跑" |
| `runAgent` 内的并发 | runAgent.ts 内部的 query loop | "子代理自己的 turn 里再调多个 safe 工具能不能并发"——子代理也用 StreamingToolExecutor |
| 多 Agent spawn 并发 | 父的 StreamingToolExecutor 看到多个 Agent tool_use | "父调多个子代理能不能并发"——靠 AgentTool.isConcurrencySafe === true |

结论：调度规则是同一套，但在不同层各跑一份实例。

## 一个并发场景的完整轨迹

设父对话刚收到用户问："分别检查前端、后端、CI 的状态"。

```text
Round 1
─────────
Parent assistant:
  text: "I'll check all three in parallel."
  tool_use toolu_a: Agent(Explore, "Check frontend build status")
  tool_use toolu_b: Agent(Explore, "Check backend test status")
  tool_use toolu_c: Agent(Explore, "Check CI pipeline status")

query.ts 收到这 3 个 tool_use：
  streamingToolExecutor.addTool(a)
    → AgentTool.isConcurrencySafe(a.input) === true
    → executing 集为空 → canExecute → executeTool(a)
  streamingToolExecutor.addTool(b)
    → safe
    → executing = [a, safe] → canExecute → executeTool(b)
  streamingToolExecutor.addTool(c)
    → safe
    → executing = [a, b, safe] → canExecute → executeTool(c)

三个 runAgent() 内部 query 循环并发跑：
  Explore a 内部：先 Glob "frontend/**" → Read package.json → Bash "npm run build:check"
  Explore b 内部：先 Glob "backend/**" → Read pyproject.toml → Bash "pytest -k smoke"
  Explore c 内部：先 Read .github/workflows/*.yml → Bash "gh run list --limit 5"

每个子代理内部也用 StreamingToolExecutor 调度自己的工具（嵌套调度）。

子代理完成顺序（实际网络快慢决定）：
  c 先完成 → results buffer
  b 完成 → results buffer
  a 完成 → results buffer

drainResults 按 tool_use 顺序回填到父 assistant：
  user/tool_result(toolu_a, "frontend build OK ...")
  user/tool_result(toolu_b, "backend tests pass ...")
  user/tool_result(toolu_c, "CI: 2 failed, 3 passed ...")

Round 2
─────────
Parent assistant:
  text: "Frontend and backend are healthy. CI has 2 failing runs:
         <ci-1 failure> <ci-2 failure>. Want me to investigate?"
```

这一轮里父代理一次发起，三个子代理并发跑，时间 ≈ max(a, b, c) 而不是 a + b + c。

## 容易踩的点

1. **同步并发 ≠ 真并发**：并发的是 API request 和子代理内部循环，不是 OS 线程。本质是 JS event loop 的 `Promise.all` 风格调度。CPU bound 仍然串行。
2. **non-concurrent 工具在并发组中间会 break 队列**：`processQueue` 看到 non-safe 就 `break`，后面的 safe 工具也得等它跑完。所以模型混着发 `Edit + Agent + Agent` 时，第二个 Agent 要等 Edit 完。
3. **schema 校验失败 → isConcurrencySafe 默认 false**：`addTool` 里 `parsedInput.success === false` 时直接判定 non-safe，目的是稳妥（连参数都解析不了，不知道会发生什么）。
4. **子代理内部的并发是独立的**：父代理调度的是"开几个子代理"，子代理内部又有自己的 StreamingToolExecutor 调度自己的工具，两层互不干扰。
5. **fork 并发是最佳的**：fork 共享父 prompt cache，3 个并发 fork 的 cache hit 都很高；普通子代理 3 个并发是 3 份独立的 cache，cost 高很多。
