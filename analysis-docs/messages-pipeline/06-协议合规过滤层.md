# 06 协议合规过滤层

> normalize 后处理段有 5 个过滤器，每一个都对应一类 API 400 错误或训练数据问题。本篇逐个拆，让"为什么必须过滤"变得具体。

## 6.1 5 个过滤器对照表

| 过滤器 | 处理对象 | 触发原因 | 后果 |
|---|---|---|---|
| `filterOrphanedThinkingOnlyMessages` | 仅含 thinking block 的 assistant message | 流式分批 + compact 切片打断 | API 400 "thinking blocks cannot be modified" |
| `filterTrailingThinkingFromLastAssistant` | 最后一条 assistant 末尾的 thinking | 流式中断 / 模型最后输出是 thinking | API 400 不允许结尾是 thinking |
| `filterWhitespaceOnlyAssistantMessages` | 全空白 text block 的 assistant | 模型输出 "\n\n" 后用户中断 | API 400 "text content blocks must contain non-whitespace text" |
| `ensureNonEmptyAssistantContent` | content[] 为空的 assistant | 模型异常返回空数组 | API 400 "all messages must have non-empty content" |
| `sanitizeErrorToolResultContent` | is_error tool_result 含非 text block | 旧 transcript / image-in-error | API 400 "all content must be type text if is_error is true" |

加上一个不在 normalize 主循环但相关的：

| 过滤器 | 处理对象 | 触发原因 | 后果 |
|---|---|---|---|
| `stripSignatureBlocks` | thinking/redacted_thinking/connector_text | credential 切换后旧签名无效 | API 400 签名不匹配 |
| `validateImagesForAPI` | image block 尺寸 | 图像超过 5MB / 8000px | API 400 / 后续累积失败 |

每个都解决一个**具体的**API 错误。这一层的设计哲学是：**与其在生成消息时小心翼翼地避免每种错误，不如在最后一道闸门统一过滤**——让上游代码专注于"产生有意义的消息"。

## 6.2 `filterTrailingThinkingFromLastAssistant` —— 尾部 thinking 处理

### 6.2.1 实现

`messages.ts:4781-4828`：

```ts
function filterTrailingThinkingFromLastAssistant(
  messages: (UserMessage | AssistantMessage)[],
): (UserMessage | AssistantMessage)[] {
  const lastMessage = messages.at(-1)
  if (!lastMessage || lastMessage.type !== 'assistant') {
    return messages
  }

  const content = lastMessage.message.content
  const lastBlock = content.at(-1)
  if (!lastBlock || !isThinkingBlock(lastBlock)) {
    return messages
  }

  // Find last non-thinking block
  let lastValidIndex = content.length - 1
  while (lastValidIndex >= 0) {
    const block = content[lastValidIndex]
    if (!block || !isThinkingBlock(block)) {
      break
    }
    lastValidIndex--
  }

  logEvent('tengu_filtered_trailing_thinking_block', {
    messageUUID: lastMessage.uuid,
    blocksRemoved: content.length - lastValidIndex - 1,
    remainingBlocks: lastValidIndex + 1,
  })

  // Insert placeholder if all blocks were thinking
  const filteredContent =
    lastValidIndex < 0
      ? [{ type: 'text' as const, text: '[No message content]', citations: [] }]
      : content.slice(0, lastValidIndex + 1)

  const result = [...messages]
  result[messages.length - 1] = {
    ...lastMessage,
    message: { ...lastMessage.message, content: filteredContent },
  }
  return result
}
```

### 6.2.2 逻辑

只检查最后一条消息：

1. 如果不是 assistant，跳过；
2. 如果最后一个 block 不是 thinking，跳过；
3. 向前扫描，找最后一个非 thinking block；
4. 截掉尾部的所有 thinking；
5. 如果整条消息全是 thinking，插入占位 `'[No message content]'`。

### 6.2.3 为什么需要

API 协议规定：**assistant 消息不能以 thinking/redacted_thinking 结尾**。这是 thinking block 的协议约束——它必须被 text 或 tool_use 等"实际输出"封尾。

但流式过程可能产生末尾 thinking：

- 用户在 thinking 阶段就按 ESC 中断；
- 模型最后一段是 thinking 但没继续输出（罕见但发生过）；
- API 错误中途，留下了未完成的 thinking。

`logEvent` 上报 `tengu_filtered_trailing_thinking_block` 让数据团队跟踪触发频率。

### 6.2.4 边界：全 thinking 的处理

如果整条消息只有 thinking blocks，简单 slice 会得到空 content[]，API 又会因"empty content"报错。所以**插入占位文本** `'[No message content]'`——保持消息存在但合法。

## 6.3 `filterWhitespaceOnlyAssistantMessages` —— 全空白消息删除

### 6.3.1 实现

`messages.ts:4869-4919`：

```ts
export function filterWhitespaceOnlyAssistantMessages(
  messages: Message[],
): Message[] {
  let hasChanges = false

  const filtered = messages.filter(message => {
    if (message.type !== 'assistant') {
      return true
    }

    const content = message.message.content
    if (!Array.isArray(content) || content.length === 0) {
      return true
    }

    if (hasOnlyWhitespaceTextContent(content)) {
      hasChanges = true
      logEvent('tengu_filtered_whitespace_only_assistant', {
        messageUUID: message.uuid,
      })
      return false
    }

    return true
  })

  if (!hasChanges) {
    return messages
  }

  // Removing assistant messages may leave adjacent user messages that need
  // merging (the API requires alternating user/assistant roles).
  const merged: Message[] = []
  for (const message of filtered) {
    const prev = merged.at(-1)
    if (message.type === 'user' && prev?.type === 'user') {
      merged[merged.length - 1] = mergeUserMessages(prev, message)
    } else {
      merged.push(message)
    }
  }
  return merged
}
```

helper `hasOnlyWhitespaceTextContent`（`messages.ts:4835-4855`）：

```ts
function hasOnlyWhitespaceTextContent(
  content: Array<{ type: string; text?: string }>,
): boolean {
  if (content.length === 0) {
    return false
  }
  for (const block of content) {
    if (block.type !== 'text') {
      return false  // 有非 text block, 不算 whitespace-only
    }
    if (block.text !== undefined && block.text.trim() !== '') {
      return false  // 有非空 text, 不算 whitespace-only
    }
  }
  return true
}
```

### 6.3.2 逻辑

1. 遍历每条消息，找出"所有 block 都是 whitespace text"的 assistant；
2. 删除这些消息；
3. **删除后可能产生相邻 user message**，需要重新合并。

### 6.3.3 为什么需要

注释（`messages.ts:4858-4865`）：

> The API requires "text content blocks must contain non-whitespace text".
> This can happen when the model outputs whitespace (like "\n\n") before a thinking block, but the user cancels mid-stream, leaving only the whitespace text.
>
> This function removes such messages entirely rather than keeping a placeholder, since whitespace-only content has no semantic value.

具体场景：模型流式输出时，**先吐两个换行符，然后开始 thinking**。如果用户在 thinking 开始前按 ESC，最终累积出的消息是 `[text("\n\n")]`——只有空白文本，没有任何实际意义。

### 6.3.4 删除后重新合并

```ts
// Removing assistant messages may leave adjacent user messages that need
// merging (the API requires alternating user/assistant roles).
const merged: Message[] = []
for (const message of filtered) {
  const prev = merged.at(-1)
  if (message.type === 'user' && prev?.type === 'user') {
    merged[merged.length - 1] = mergeUserMessages(prev, message)
  } else {
    merged.push(message)
  }
}
```

API 要求**严格交替** user / assistant。删掉一个 assistant 后，原本被它隔开的两条 user 现在相邻——必须合并。这里再走一遍 `mergeUserMessages`。

这是**为什么 normalize 主循环外还有这层处理**——单 pass 合并不够，删除操作可能制造新的合并需求。

## 6.4 `ensureNonEmptyAssistantContent` —— 空 content 补占位

### 6.4.1 实现

`messages.ts:4933-4977`：

```ts
function ensureNonEmptyAssistantContent(
  messages: (UserMessage | AssistantMessage)[],
): (UserMessage | AssistantMessage)[] {
  if (messages.length === 0) {
    return messages
  }

  let hasChanges = false
  const result = messages.map((message, index) => {
    if (message.type !== 'assistant') {
      return message
    }

    // Skip the final message (allowed to be empty for prefill)
    if (index === messages.length - 1) {
      return message
    }

    const content = message.message.content
    if (Array.isArray(content) && content.length === 0) {
      hasChanges = true
      logEvent('tengu_fixed_empty_assistant_content', {
        messageUUID: message.uuid,
        messageIndex: index,
      })

      return {
        ...message,
        message: {
          ...message.message,
          content: [
            { type: 'text' as const, text: NO_CONTENT_MESSAGE, citations: [] },
          ],
        },
      }
    }

    return message
  })

  return hasChanges ? result : messages
}
```

### 6.4.2 逻辑

遍历每条 assistant 消息：

1. 如果是 final 消息（最后一条），**跳过**；
2. content[] 为空数组的，插入占位 text block。

### 6.4.3 为什么"最后一条"是例外

API 协议：

> all messages must have non-empty content **except for the optional final assistant message**

最后一条 assistant 允许 empty——这是 prefill 场景：上层想让模型从某个状态继续，发一个空 assistant 让 API 在它后面接着生成。这是合法用法。

非最后的 assistant 不能 empty——否则 400。所以这里只补占位"非最后"。

### 6.4.4 占位用 NO_CONTENT_MESSAGE

`NO_CONTENT_MESSAGE` 是个常量（在 messages.ts 早期定义，约值类似 `'[No content]'`）。被 createAssistantMessage / createUserMessage 在 content 为空时也用。这是个**项目内统一的空内容占位符**，让 transcript / API 都能看到一致字符串。

## 6.5 `filterOrphanedThinkingOnlyMessages` —— 孤立 thinking 消息

### 6.5.1 实现

`messages.ts:4991-5058`，分两遍扫描：

```ts
export function filterOrphanedThinkingOnlyMessages(
  messages: Message[],
): Message[] {
  // First pass: collect message.ids that have non-thinking content
  const messageIdsWithNonThinkingContent = new Set<string>()
  for (const msg of messages) {
    if (msg.type !== 'assistant') continue

    const content = msg.message.content
    if (!Array.isArray(content)) continue

    const hasNonThinking = content.some(
      block => block.type !== 'thinking' && block.type !== 'redacted_thinking',
    )
    if (hasNonThinking && msg.message.id) {
      messageIdsWithNonThinkingContent.add(msg.message.id)
    }
  }

  // Second pass: filter out thinking-only messages that are truly orphaned
  const filtered = messages.filter(msg => {
    if (msg.type !== 'assistant') {
      return true
    }

    const content = msg.message.content
    if (!Array.isArray(content) || content.length === 0) {
      return true
    }

    const allThinking = content.every(
      block => block.type === 'thinking' || block.type === 'redacted_thinking',
    )

    if (!allThinking) {
      return true
    }

    if (
      msg.message.id &&
      messageIdsWithNonThinkingContent.has(msg.message.id)
    ) {
      return true  // 有同 id 的消息含非 thinking, 保留待合并
    }

    logEvent('tengu_filtered_orphaned_thinking_message', {
      messageUUID: msg.uuid,
      messageId: msg.message.id,
      blockCount: content.length,
    })
    return false
  })

  return filtered
}
```

### 6.5.2 逻辑

1. **第一遍**：扫描全部消息，收集所有"含非 thinking 内容"的 message.id 集合；
2. **第二遍**：过滤——只在以下两个条件**同时**满足时删除消息：
   - 消息所有 block 都是 thinking；
   - 不存在同 message.id 的其他消息含非 thinking。

### 6.5.3 为什么需要

注释（`messages.ts:4979-4990`）：

> During streaming, each content block is yielded as a separate message with the same message.id. When messages are loaded for resume, interleaved user messages or attachments can prevent proper merging by message.id, leaving orphaned assistant messages that contain only thinking blocks. These cause "thinking blocks cannot be modified" API errors.

具体机制：

- 流式过程中，每个 content block 可能被作为**独立 message** yield 出来（同 message.id）；
- store 里这些消息可能被穿插的 user message / attachment 隔开；
- normalize 主循环里的"同 ID assistant 合并"扫描有边界——遇到非 assistant 非 tool_result 就停，所以可能漏合并；
- 留下来的孤立 thinking 消息发给 API 会触发 400。

### 6.5.4 "保留待合并"的细节

```ts
if (
  msg.message.id &&
  messageIdsWithNonThinkingContent.has(msg.message.id)
) {
  return true  // 保留
}
```

如果存在同 ID 的非 thinking 消息，**保留**这条 thinking——因为后续合并会把它们 merge 到一起，最终 message 里既有 thinking 又有其它 block，合法。

只有当**完全没有同 ID 的非 thinking 消息**时才删除——这种叫"孤立"。

## 6.6 `sanitizeErrorToolResultContent` —— is_error tool_result 强制 text-only

### 6.6.1 实现

`messages.ts:1884-1907`：

```ts
function sanitizeErrorToolResultContent(
  messages: (UserMessage | AssistantMessage)[],
): (UserMessage | AssistantMessage)[] {
  return messages.map(msg => {
    if (msg.type !== 'user') return msg
    const content = msg.message.content
    if (!Array.isArray(content)) return msg

    let changed = false
    const newContent = content.map(b => {
      if (b.type !== 'tool_result' || !b.is_error) return b
      const trContent = b.content
      if (!Array.isArray(trContent)) return b
      if (trContent.every(c => c.type === 'text')) return b
      changed = true
      const texts = trContent.filter(c => c.type === 'text').map(c => c.text)
      const textOnly: TextBlockParam[] =
        texts.length > 0 ? [{ type: 'text', text: texts.join('\n\n') }] : []
      return { ...b, content: textOnly }
    })
    if (!changed) return msg
    return { ...msg, message: { ...msg.message, content: newContent } }
  })
}
```

### 6.6.2 逻辑

只处理 user message 的 tool_result block：

- 不是 is_error → 跳过；
- content 是字符串 → 跳过（字符串本来就是 text）；
- content 是数组且全是 text → 跳过；
- content 是数组含非 text block → 提取所有 text、合并成单 text block、丢弃其它。

### 6.6.3 为什么需要

API 协议：**is_error 为 true 的 tool_result，content 只能是 text block**——不能有 image / search_result / 等。

但 Claude Code 的"队列命令"功能可能产生违反这条的情况：

- 用户在 BashTool 执行时排队了下一条命令；
- 排队命令包含粘贴板截图；
- BashTool 失败 → tool_result is_error=true，但 sibling smoosh 时把图像也塞进了 tool_result.content；
- → 400 错误，会让**之后每次 API 调用**都失败，对话变成"砖头"——/fork 也救不回来。

注释（`messages.ts:1876-1882`）：

> Strip non-text blocks from is_error tool_results — the API rejects the combination with "all content must be type text if is_error is true".
>
> Read-side guard for transcripts persisted before smooshIntoToolResult learned to filter on is_error. Without this a resumed session with one of these 400s on every call and can't be recovered by /fork. Adjacent text left behind by a stripped image is re-merged.

明确写出"这是 read-side guard"——保护 resume 场景。

### 6.6.4 设计判断：write-side fix + read-side guard

事实上 `smooshIntoToolResult` 现在已经知道在 is_error 上过滤非 text block（详见 [04](./04-合并smoosh与hoist三连击.md)）——所以**新产生的消息**不会有这个问题。

但**旧 transcript** 可能在那个 fix 之前持久化了违法消息。如果只在 write-side fix（smoosh 知道过滤），resume 旧 transcript 仍会 400。所以加 read-side guard：normalize 时再过一遍兜底。

这是**双重保险**：写入侧不再产生 + 读取侧仍能修复历史污染。任何修复"协议合法性"的代码都应该同时考虑历史数据。

## 6.7 `stripSignatureBlocks` —— credential 切换后清理签名

### 6.7.1 实现

`messages.ts:5066-5085`：

```ts
export function stripSignatureBlocks(messages: Message[]): Message[] {
  let changed = false
  const result = messages.map(msg => {
    if (msg.type !== 'assistant') return msg

    const content = msg.message.content
    if (!Array.isArray(content)) return msg

    const filtered = content.filter(block => {
      if (isThinkingBlock(block)) return false
      if (feature('CONNECTOR_TEXT')) {
        if (isConnectorTextBlock(block)) return false
      }
      return true
    })
    // ...
  })
}
```

### 6.7.2 逻辑

剥离 `thinking` / `redacted_thinking` / `connector_text` block——这些 block 带 cryptographic signature。

### 6.7.3 为什么需要

注释（`messages.ts:5060-5064`）：

> Their signatures are bound to the API key that generated them; after a credential change (e.g. /login) they're invalid and the API rejects them with a 400.

签名绑定到生成它们的 API key。`/login` 切换账号后，旧签名在新 key 下不被识别 → 400。

这个函数**不在 normalize 主循环里调用**——它在 credential 切换的特定时刻调一次，清理 store 里历史消息的签名 block。后续 normalize 看不到这些 block。

## 6.8 `validateImagesForAPI` —— 图像尺寸最终校验

`messages.ts:2367`：

```ts
validateImagesForAPI(sanitized)
```

normalize 主循环最后一行调用。具体实现在 `imageValidation.ts`（这里不展开），大致逻辑：扫描所有 user message 里的 image block，检查每张图：

- 文件大小 < 5 MB；
- 像素尺寸 < 8000 × 8000；
- 总像素数受请求级限制。

任一不满足 throw 对应的 `ImageSizeError` / `ImageResizeError`。上层捕获后：

1. 不发 API 请求；
2. 合成一个 syntheticApiErrorMessage 加进消息历史；
3. 下一轮 normalize 时通过 `errorToBlockTypes` + `stripTargets` 反向追溯到源 user message，剥离 image block；
4. 之后请求不再带这张图。

形成**闭环**：本轮 fail-fast → 下轮自动剥离。

## 6.9 过滤顺序的脆弱性（作者承认）

`messages.ts:2313-2320` 注释：

> Order matters: strip trailing thinking first, THEN filter whitespace-only messages. The reverse order has a bug: a message like `[text("\n\n"), thinking("...")]` survives the whitespace filter (has a non-text block), then thinking stripping removes the thinking block, leaving `[text("\n\n")]` — which the API rejects.
>
> These multi-pass normalizations are inherently fragile — each pass can create conditions a prior pass was meant to handle. Consider unifying into a single pass that cleans content, then validates in one shot.

作者明确说**这种多 pass 设计天然脆弱**。每个 pass 都可能制造其他 pass 处理的情况。建议未来合并成单 pass 清洗 + 单 pass 验证。

但目前仍然分开——为什么？

可能的原因：

- 每个 pass 单独可测；
- 每个 pass 有独立的 logEvent 上报，能跟踪具体哪一类错误更频繁；
- 合并代价大于现状收益（设计债，但暂时容忍）；
- 历史演化的产物：每个 pass 都是某次具体事故/A/B 加上的，移除它需要重新验证不会回归。

这条注释是个**诚实自批评**——让读者理解"这不是最优设计"。值得记下。

## 6.10 过滤层的设计判断回顾

### 1. 每个过滤器对应一个具体 API 400

不是"通用清洗"——而是按错误类型逐个加。这让代码意图清晰，也让 logEvent 上报有针对性指标。

### 2. logEvent 每个 pass 单独上报

`tengu_filtered_trailing_thinking_block` / `tengu_filtered_whitespace_only_assistant` / `tengu_fixed_empty_assistant_content` / `tengu_filtered_orphaned_thinking_message`——每种触发都有独立计数器。数据团队能看到"这周 whitespace-only 发生了 200 次"这种粒度。

### 3. 删除可能制造合并需求 → 内部再合并

`filterWhitespaceOnlyAssistantMessages` 删除后内部再调 `mergeUserMessages` 处理相邻 user。这种"自洽"设计避免上层调用方知道细节。

### 4. write-side fix + read-side guard 双保险

`sanitizeErrorToolResultContent` 体现这一思路——新数据不出错 + 旧数据能修复。这条经验适用于所有"协议合法性"修复。

### 5. 关键约束：保留 final assistant 的灵活性

`ensureNonEmptyAssistantContent` 跳过最后一条——因为 prefill 场景需要 empty 最终 assistant。这种"为合法用例留口子"的设计避免误伤。

### 6. 闭环错误处理：fail-fast + 自动剥离

`validateImagesForAPI` 抛错让本轮失败，但失败信息进消息历史，下轮 normalize 自动剥离问题源。错误是数据流的分支，不是异常路径。

### 7. 承认设计脆弱性，写下迁移建议

工业代码的成熟标志：在注释里承认现状不够好，并指出未来方向。

## 6.11 小结

- 5+2 个过滤器各对应一类具体 API 400 错误或训练数据问题；
- 主要的 5 个跑在 normalize 后处理段，顺序敏感（注释里明确警告反过来有 bug）；
- `stripSignatureBlocks` 在 credential 切换时调，不在 normalize 主循环里；
- `validateImagesForAPI` 是最终闸门，失败形成"本轮 fail-fast + 下轮自动剥离"的闭环；
- 删除消息可能制造合并需求——`filterWhitespaceOnlyAssistantMessages` 自己内部处理；
- 每个 pass 单独 logEvent 上报，让指标粒度细；
- 作者承认"多 pass 设计天然脆弱"，给出未来合并建议——工业代码罕见的诚实自批评。
