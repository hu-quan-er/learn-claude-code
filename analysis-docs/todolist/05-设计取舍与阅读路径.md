# 05 - 设计取舍与阅读路径

## V1 的优点

- 模型调用简单：一次传完整列表。
- 不需要磁盘、锁、ID、依赖关系。
- 非交互式和 SDK 场景足够轻量。
- transcript 扫描即可恢复最后状态。

## V1 的限制

- 无增量更新，最后一次 `tool_use` 覆盖全部状态。
- 无真实持久化，恢复依赖 transcript 中仍有 `TodoWrite` 输入。
- 无并发合并语义，不适合多个 agent 同时维护同一列表。
- 本地主交互 UI 基本不直接展示 V1 todo item。
- 全 completed 时 AppState 清空，但 tool output 仍返回原始 `todos`，存在一个“对外描述 vs 内部状态”的不一致。
- 全 completed 后如果从 transcript resume，恢复逻辑读取的是最后一次 `tool_use.input`，可能把 completed 列表重新放回 `AppState.todos`。

## V2 的改进

- 文件态任务适合交互式 CLI 的长会话。
- lock + high water mark 支持多进程 / swarm 并发。
- owner、依赖关系、metadata 支持团队协作。
- UI 有稳定的 external store，避免组件各自监听文件。
- hooks 可以阻止非法创建或完成，使任务状态成为可治理对象。

## V2 的成本

- 实现复杂度明显高于 V1。
- 状态分布到文件系统、watcher、AppState 展开视图、hooks、mailbox。
- reset / hide / watcher / fallback poll 引入更多时序边界。
- `TodoList` 名字仍残留在远程任务和历史文档里，阅读源码时容易和 V2 `Task` 混淆。

## 容易误解的点

| 误解 | 更准确的说法 |
|------|--------------|
| TodoList 是 Claude Code 自动解析用户需求生成的 | 任务列表来自模型返回的 `tool_use.input` |
| `TodoList` 类型就是用户在 CLI 里看到的任务列表 | 交互式 CLI 默认看到的是 V2 `Task` 文件系统 |
| `TaskCreate` 会自动开始任务 | `TaskCreate` 只创建 `pending`，开始执行要再调用 `TaskUpdate` |
| V1 可以 patch 单个 todo item | V1 每次必须提交完整 `todos` 数组 |
| tool result 是 assistant message | API 语义里 `tool_result` 是 `user` role content block |
| `shouldDefer: true` 代表工具不可用 | 它只表示 tool search 启用时可动态加载；标准模式仍可直接发送完整 schema |

## 最终总结

```text
V1 TodoWrite
  = 非交互式场景里的轻量 checklist
  = 模型提交完整数组
  = runtime 写 AppState
  = transcript 负责恢复

V2 Task tools
  = 交互式 CLI 的持久化任务系统
  = 模型创建和更新单个 task
  = runtime 写任务文件
  = watcher 驱动 UI 刷新

工具传递链路
  = Tool 对象转 API tools schema
  = 模型返回 assistant/tool_use
  = runtime 执行本地 call()
  = user/tool_result 回填下一轮上下文
```
