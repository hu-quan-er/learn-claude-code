# 上下文压缩与自动压缩机制

> Claude Code 上下文管理分析系列 - 第2篇
> 源码版本：claude-code 2.1.88

---

## 概述

当对话持续进行，上下文窗口逐渐被填满时，Claude Code 需要一套智能压缩机制来维持对话的连续性。本文分析 7 种压缩策略、自动压缩触发机制、级联回退链路、断路器保护，以及压缩边界标记与会话恢复。

---

## 1. 压缩策略总览

**文件**：`src/services/compact/`

```
┌──────────────────────────────────────────────────────────────────┐
│                      压缩策略层次（按代价递增）                    │
├──────────────────────────────────────────────────────────────────┤
│                                                                  │
│  ① Session Memory Compact    ← 最轻量，无 API 调用               │
│  ② Microcompact              ← 清除旧 tool result，无 API 调用   │
│  ③ Time-Based Microcompact   ← 基于时间间隔的 MC                 │
│  ④ Cached Microcompact       ← 通过 cache_edits 删除，保留缓存   │
│  ⑤ Snip Compact              ← 历史过滤                          │
│  ⑥ Partial Compact           ← 方向性部分摘要                    │
│  ⑦ Traditional Full Compact  ← API 全量摘要，代价最高             │
│                                                                  │
└──────────────────────────────────────────────────────────────────┘
```

## 2. 各策略详解

### 2.1 传统全量压缩（Traditional Full Compact）

**文件**：`src/services/compact/compact.ts`（第387行）

**核心函数**：`compactConversation()`

- **工作方式**：将整个对话历史发送给 Claude API，生成摘要替换原始消息
- **触发方式**：手动 `/compact` 命令 或 自动压缩阈值超标
- **输出 Token 预留**：20,000 tokens

**后置恢复资源预算**：

| 资源 | 预算 |
|------|------|
| 文件数 | 最多 5 个最近访问的文件 |
| 文件总 Token | 50K tokens |
| 每文件 Token | 5K tokens |
| 技能总 Token | 25K tokens |
| 每技能 Token | 5K tokens |

**PTL（Prompt Too Long）重试**：
- 遇到 413 错误时自动重试（最多 3 次）
- 每次重试截断最旧的 API 轮次组
- 记录 `tengu_compact_ptl_retry` 事件

### 2.2 Session Memory 压缩

**文件**：`src/services/compact/sessionMemoryCompact.ts`（第514行）

**核心函数**：`trySessionMemoryCompaction()`

- **策略**：使用预提取的会话记忆作为摘要，完全跳过 API 调用
- **在级联回退中的位置**：最先尝试，失败后才进入全量压缩

**配置参数**（第47-61行）：

| 参数 | 值 | 含义 |
|------|------|------|
| `minTokens` | 10,000 | 最少保留 Token 数 |
| `minTextBlockMessages` | 5 | 最少交互消息数 |
| `maxTokens` | 40,000 | 硬上限 |

**失败条件**（返回 null）：
- Feature flag `tengu_sm_compact` 未启用
- 会话记忆文件不存在
- 会话记忆匹配模板（空内容）
- 被摘要的消息 ID 在当前消息中不存在
- 压缩后 Token 计数仍超过 autoCompactThreshold

**边界调整**：`adjustIndexToPreserveAPIInvariants()`（第232行）
- 确保 `tool_use` / `tool_result` 对不被拆分
- 压缩后清除旧的 compact boundary 消息

### 2.3 Microcompact（微压缩）

**文件**：`src/services/compact/microCompact.ts`

**基本策略**：直接清除旧的工具结果内容，用标记替换：

```
[Old tool result content cleared]
```

**不调用 API**，仅修改本地消息内容。

### 2.4 Cached Microcompact（缓存微压缩）

**文件**：`src/services/compact/microCompact.ts`（第305-399行）

- **工作方式**：通过 API 的 `cache_edits` 机制删除工具结果，无需使整个缓存前缀失效
- **注册机制**：按用户消息分组跟踪工具结果（第313-330行）
- **选择逻辑**：`getToolResultsToDelete()` 从缓存 MC 模块获取待删除列表
- **输出**：`cache_edits` 块排队在 API 层发送（第336-338行）

```typescript
// cache_edits 块结构
{
  type: 'cache_edit',
  action: 'delete',
  tool_use_id: string
}
```

### 2.5 基于时间的 Microcompact

**函数**：`maybeTimeBasedMicrocompact()`（第446行）

**配置**（`timeBasedMCConfig.ts`）：

| 参数 | 值 | 含义 |
|------|------|------|
| `enabled` | boolean | 总开关 |
| `gapThresholdMinutes` | 60 | 触发时间间隔（缓存 TTL 必定已过期） |
| `keepRecent` | 5 | 保留最近 N 个工具结果 |

- **触发条件**：距上次 assistant 消息超过阈值（默认 60 分钟）
- **行为**：清除旧工具结果内容，保留缓存前缀免受过期影响
- **直接修改**消息内容（就地突变）

### 2.6 Snip Compact（片段压缩）

- **门控**：`HISTORY_SNIP` feature flag
- **机制**：在消息上注入 `[id:XXXXXX]` 标签，允许按 ID 过滤历史片段
- **Snip 工具运行时**必须启用

### 2.7 Partial Compact（部分压缩）

- **方向性**：可以只压缩对话的头部或中间部分
- **与全量压缩互补**：保留最近的上下文，只摘要较远的部分

## 3. 工具结果预算系统

### 3.1 单工具持久化

**文件**：`src/utils/toolResultStorage.ts`（第137-184行）

**阈值**：50,000 字符（默认，可通过 `tengu_satin_quoll` flag 覆盖）

**持久化流程**：

```
工具返回结果
    │
    ├── 结果大小 ≤ 阈值？ → 内联保留
    │
    └── 结果大小 > 阈值？
        │
        ├── 检查是否有非文本内容 → 有则返回错误
        ├── ensureToolResultsDir() 确保目录存在
        ├── 写入文件（flag: 'wx' 排他创建，避免重放覆盖）
        ├── 生成 2KB 预览
        └── 返回 {filepath, originalSize, isJson, preview, hasMore}
```

**存储路径**：`{projectDir}/{sessionId}/tool-results/{toolUseId}.{json|txt}`

**持久化输出标记**：

```xml
<persisted-output>
Output too large (SIZE). Full output saved to: FILEPATH

Preview (first 2KB):
PREVIEW_CONTENT
...
</persisted-output>
```

**特殊处理**：`tool.maxResultSizeChars = Infinity` 的工具（如 Read）永远不被持久化。

### 3.2 每消息聚合预算

**第769-909行**

| 参数 | 值 | 说明 |
|------|------|------|
| 默认限制 | 200,000 字符 | 每 API 级用户消息的聚合预算 |
| 覆盖来源 | `tengu_hawthorn_window` flag | GrowthBook 动态调整 |

**分组逻辑**（第600-639行）：
- 消息按 assistant message ID 边界分组
- 连续 user 消息（未被新 assistant ID 打断）合并到同一组
- Progress 消息不打断分组

**选择算法**（第675-692行）：

```
┌─────────────────────────────────────────────┐
│ 1. 收集所有工具结果                          │
│ 2. 分类：                                    │
│    • frozen（已见过）→ 永不修改（缓存稳定性） │
│    • fresh（新产生）→ 可选择持久化            │
│ 3. 按大小降序排列 fresh 结果                  │
│ 4. 从最大开始持久化，直到                     │
│    remaining(frozen + fresh) ≤ limit         │
│ 5. 已持久化的标记为 mustReapply              │
└─────────────────────────────────────────────┘
```

### 3.3 三态分类

| 状态 | 含义 | 行为 |
|------|------|------|
| **fresh** | 新产生的工具结果 | 可被选中持久化 |
| **frozen** | 已被看到过（在 seenIds 中） | 永不修改，保证缓存前缀稳定 |
| **mustReapply** | 之前被持久化的缓存预览 | 每轮重新应用 |

**状态跟踪**：
- `seenIds: Set<string>` — 所有已评估过的 tool_use_id
- `replacements: Map<string, string>` — tool_use_id → 预览字符串

**原子性保证**：非持久化候选者同步标记为 seen；持久化候选者在 await 完成后才标记 replacement。

### 3.4 空工具结果处理

**`isToolResultContentEmpty()`**（第250行）：

覆盖场景：`undefined`、`null`、空字符串、纯空白、空数组

**注入标记**（第287-295行）：
```typescript
if (isToolResultContentEmpty(content)) {
  logEvent('tengu_tool_empty_result', {toolName})
  return {
    ...toolResultBlock,
    content: `(${toolName} completed with no output)`
  }
}
```

**原因（inc-4586）**：模型在 tool_result 内容为空且位于提示末尾时会生成 `\n\nHuman: stop` 序列。

## 4. 自动压缩触发机制

### 4.1 有效上下文窗口

**文件**：`src/services/compact/autoCompact.ts`（第33-49行）

```
有效窗口 = 上下文窗口 - min(模型最大输出, 20,000)
```

可通过环境变量 `CLAUDE_CODE_AUTO_COMPACT_WINDOW` 覆盖。

### 4.2 自动压缩阈值

**`getAutoCompactThreshold()`**（第72-91行）：

```
autocompact 阈值 = 有效窗口 - 13,000 (AUTOCOMPACT_BUFFER_TOKENS)
```

**缓冲常量**：

| 常量 | 值 | 用途 |
|------|------|------|
| `AUTOCOMPACT_BUFFER_TOKENS` | 13,000 | 自动压缩缓冲 |
| `WARNING_THRESHOLD_BUFFER_TOKENS` | 20,000 | 警告阈值缓冲 |
| `ERROR_THRESHOLD_BUFFER_TOKENS` | 20,000 | 错误阈值缓冲 |
| `MANUAL_COMPACT_BUFFER_TOKENS` | 3,000 | 阻塞限制缓冲 |

可通过 `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` 环境变量覆盖。

### 4.3 触发条件：`shouldAutoCompact()`

**第160-239行**

```
┌────────────────────────────────────────────────┐
│ 前置检查（任一为真则跳过）：                     │
│ ├── DISABLE_COMPACT 环境变量                    │
│ ├── DISABLE_AUTO_COMPACT 环境变量               │
│ ├── autoCompactEnabled 用户配置                 │
│ ├── REACTIVE_COMPACT flag（抑制主动）           │
│ ├── CONTEXT_COLLAPSE flag（抑制主动）           │
│ └── querySource 为 session_memory/compact/      │
│     marble_origami（防死锁）                    │
├────────────────────────────────────────────────┤
│ Token 比较：                                    │
│ tokenCountWithEstimation(messages)              │
│   - snipTokensFreed                             │
│   >= autocompact_threshold                      │
│     → 触发自动压缩                              │
└────────────────────────────────────────────────┘
```

### 4.4 级联回退链路

**第287-350行**

```
Step 1: trySessionMemoryCompaction() [轻量级，无 API]
    │
    ├── 成功 → 返回 CompactionResult
    │
    └── 失败（null）
            │
            ▼
Step 2: compactConversation() [API 调用，较重]
    │
    ├── 成功 → 返回 CompactionResult
    │
    ├── PTL 错误 → 截断重试（最多 3 次）
    │
    └── 其他失败
            │
            ▼
Step 3: 错误处理
    ├── 递增 consecutiveFailures
    ├── >= MAX_CONSECUTIVE_AUTOCOMPACT_FAILURES (3)?
    │   ├── 是 → 停止重试，记录 circuit breaker 触发
    │   └── 否 → 下轮继续尝试
    └── 记录 warn 级别日志
```

### 4.5 断路器保护

**常量**：`MAX_CONSECUTIVE_AUTOCOMPACT_FAILURES = 3`（第70行）

**设计原因**：BQ 2026-03-10 数据显示 1,279 个会话有 50+ 次失败（最大 3,272 次），浪费约 250K API 调用/天。

**保护机制**：
- 连续 3 次失败后停止自动压缩尝试
- 防止 `prompt_too_long` (413) 和不可恢复的上下文溢出反复轰炸 API
- 手动 `/compact` 不受断路器限制

## 5. 压缩边界标记与会话恢复

### 5.1 边界消息结构

**文件**：`src/utils/messages.ts`（第4530-4612行）

**`createCompactBoundaryMessage()`**（第4530行）：

```typescript
{
  type: 'system',
  subtype: 'compact_boundary',
  content: 'Conversation compacted',
  uuid: randomUUID(),
  timestamp: ISO string,
  compactMetadata: {
    trigger: 'manual' | 'auto',
    preTokens: number,               // 压缩前 Token 计数
    userContext?: string,             // 自定义指令
    messagesSummarized?: number,      // 被摘要的消息数
    preCompactDiscoveredTools?: string[], // 摘要中使用的工具
    preservedSegment?: {              // 保留段（Session Memory 专用）
      headUuid: UUID,                 // 保留的第一条消息
      anchorUuid: UUID,               // 摘要的最后一条消息（重连点）
      tailUuid: UUID                  // 保留的最后一条消息
    }
  },
  logicalParentUuid?: UUID  // 最后一条压缩前消息
}
```

### 5.2 保留段重连算法

**文件**：`sessionStorage.ts`（第1860-1939行）

当会话恢复加载时：

```
Step 1: 验证 (第1875-1902行)
    ├── 从 tailUuid 通过 parentUuid 链向后遍历到 headUuid
    ├── 若遍历中断（UUID 在 transcript 中缺失）→ 优雅降级
    └── 记录 tengu_relink_walk_broken（验证失败时）

Step 2: 重连保留消息 (第1905-1919行)
    ├── head.parentUuid = anchorUuid（将保留消息连接到摘要）
    ├── 将 anchor 的其他子节点重定向到 tail（将 tail 拼接入链）
    └── 结果：Summary → 保留消息 → 剩余历史

Step 3: 清零陈旧 usage (第1920-1939行)
    ├── 清除保留消息的 input_tokens、output_tokens、cache tokens
    └── 防止恢复后 usage 仍为压缩前的 ~190K，立即重新触发 autocompact
```

### 5.3 边界发现

| 函数 | 作用 |
|------|------|
| `findLastCompactBoundaryIndex()` | 向后扫描查找最近的 compact boundary |
| `getMessagesAfterCompactBoundary()` | 返回边界之后的消息（启用 snip 时带过滤） |

## 7. Context Collapse 集成

**与自动压缩的关系**：

- **Feature gate**：`feature('CONTEXT_COLLAPSE')`
- **抑制自动压缩**（第215-223行）：
  - Context Collapse 启用时，主动自动压缩被抑制
  - 原因：Collapse 管理 90% commit / 95% blocking-spawn 流程
  - 自动压缩在 ~85%（13K 缓冲）会与 Collapse 竞争，破坏细粒度上下文
- **反应式回退**（第195行）：
  - `REACTIVE_COMPACT` flag 抑制主动但保留对 413 错误的反应式压缩
- **清理集成**（第179-182行）：
  - `marble_origami`（context agent）的 querySource 跳过自动压缩，防止死锁
  - `runPostCompactCleanup()` 调用 `resetContextCollapse()`

## 10. 架构要点总结

1. **代价递增的级联策略**：Session Memory（无 API）→ 全量压缩（API），最小化 API 开销
2. **确定性状态保证缓存稳定**：tool result 的 seenIds + replacements 一旦决定就冻结，保护提示缓存前缀跨轮次和恢复不变
3. **消息分组匹配真实负载**：工具结果按 `normalizeMessagesForAPI` 的合并结果分组，预算检查匹配实际传输格式
4. **保留段重连恢复**：compact boundary 包含 head/anchor/tail UUID，加载时重建逻辑链，实现部分消息裁剪
5. **断路器防止浪费**：连续 3 次失败后停止，防止不可恢复的上下文反复轰炸 API
6. **抑制协调**：自动压缩、反应式压缩与 Context Collapse 通过 feature gate 精心隔离，避免竞态条件
