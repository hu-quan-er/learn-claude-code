从用户输入到最终 API 请求，消息要经过一条完整的处理流水线。本文将前三篇涉及的各个子系统串联起来，分析端到端的消息处理编排、各阶段的触发顺序和依赖关系，以及整个上下文管理系统的协调机制。

## 3. 子系统协调矩阵

### 3.1 各子系统的触发时机

| 子系统 | 触发点 | 频率 |
|--------|--------|------|
| 消息归一化 | 每次 API 调用前 | 每轮 |
| 系统提示构建 | 会话初始化 / `/clear` | 一次 + 重置 |
| 用户上下文注入 | 每次 API 调用前 | 每轮 |
| 系统上下文注入 | 每次 API 调用前 | 每轮 |
| Token 计数 | 每次 API 调用前 | 每轮 |
| 工具结果预算 | 工具执行后 | 按需 |
| 时间微压缩 | API 调用前检查 | 超时触发 |
| 缓存微压缩 | API 调用时 | feature gate |
| Session Memory 压缩 | 自动压缩触发时 | 阈值触发 |
| 全量压缩 | SM 失败回退 / 手动 | 阈值触发 |
| 缓存中断检测 | API 响应后 | 每轮 |

### 3.2 Feature Gate 协调

多个子系统通过 feature flag 互斥或协调：

```
CONTEXT_COLLAPSE 启用时
    ├── 抑制主动 autocompact（避免竞争）
    ├── 保留反应式 compact（413 错误）
    └── marble_origami querySource 跳过 autocompact（防死锁）

REACTIVE_COMPACT 启用时
    ├── 抑制主动 autocompact
    └── 保留 413 反应式压缩

HISTORY_SNIP 启用时
    ├── 消息 ID 标签注入激活
    ├── Snip 工具运行时启用
    └── getMessagesAfterCompactBoundary() 带 snip 过滤

CACHED_MICROCOMPACT 启用时
    ├── cache_edits 逻辑激活
    ├── cacheEditingHeaderLatched 闩锁
    └── 与 microcompact 互补（非互斥）
```

### 3.3 错误处理与回退链

```
API 调用
    │
    ├── 成功 → 正常流程
    │
    ├── 413 Prompt Too Long
    │   ├── REACTIVE_COMPACT / CONTEXT_COLLAPSE 模式
    │   │   └── 触发反应式压缩
    │   └── 普通模式
    │       └── compact 重试（截断最旧轮次组，最多 3 次）
    │
    ├── 缓存中断检测
    │   ├── 客户端引起 → 记录具体变更原因
    │   ├── TTL 过期 → 记录时间间隔
    │   └── 服务端 → 记录疑似路由/驱逐
    │
    └── autocompact 连续失败
        └── 断路器：3 次后停止尝试
```

## 5. 缓存生命周期

### 5.1 单轮请求中的缓存交互

```
请求准备
    │
    ├── recordPromptState()
    │   └── 快照当前提示/工具/beta 哈希
    │
    ├── buildSystemPromptBlocks()
    │   └── 标记 cache_control + scope
    │
    ├── addCacheBreakpoints()
    │   ├── 添加 1 个 cache_control 标记（保护共享前缀）
    │   ├── 插入 cache_edits（如有）
    │   └── 添加 cache_reference（缓存前缀内的 tool_result）
    │
    ├── API 调用
    │   └── 服务端缓存匹配
    │       ├── 命中 → cache_read_input_tokens > 0
    │       └── 未命中 → cache_creation_input_tokens > 0
    │
    └── checkResponseForCacheBreak()
        ├── 比较本次 vs 上次的 cache_read_tokens
        ├── 下降 ≥ 5% 且 ≥ 2000 → 标记为中断
        └── 归因分析 + 遥测
```

### 5.2 跨轮次缓存维护

```
Turn 1: 初始请求
    └── cache_creation: 建立缓存前缀

Turn 2: 新消息追加
    ├── 系统提示 + 旧消息 → 缓存命中（cache_read）
    ├── 新消息 → cache_creation（扩展缓存）
    └── frozen tool results 保持不变 → 缓存稳定

Turn N: 工具结果积累
    ├── 超出预算的 fresh 结果 → 持久化为预览
    ├── 已持久化结果 → mustReapply（每轮重注入）
    └── 缓存前缀稳定性得到保证

Turn N+1: 缓存微压缩触发
    ├── cache_edits 删除旧 tool results
    ├── 缓存前缀不失效（编辑而非重建）
    └── cacheDeletionsPending = true（抑制误判中断）

Session 中期: TTL 过期
    ├── 5min / 1h TTL 到期
    ├── 下次请求 → cache_creation（重建）
    └── 检测为 TTL 过期（非客户端变更）
```

## 7. 关键设计模式总结

### 7.1 分层防御

上下文管理采用多层防御策略，从轻量到重量逐级升级：

```
Layer 0: 工具结果预算     ← 单工具粒度，实时执行
Layer 1: 微压缩            ← 旧结果清除，无 API 开销
Layer 2: 时间微压缩        ← 60min 超时触发
Layer 3: 缓存微压缩        ← cache_edits，保留缓存
Layer 4: Session Memory    ← 预提取摘要，无 API 调用
Layer 5: 全量压缩          ← API 摘要，代价最高
Layer 6: 断路器            ← 连续 3 次失败后放弃
Layer 7: 反应式压缩        ← 413 错误后的最后手段
```

### 7.2 缓存优先原则

整个系统围绕「最大化缓存命中」设计：
- **frozen 状态**：已见过的工具结果永不修改
- **闩锁 headers**：beta header 一旦发送就持续到 `/clear`
- **缓存编辑**：通过 `cache_edits` 删除而非重建
- **单标记策略**：每请求仅 1 个 `cache_control` 标记，优化页面驱逐
- **克隆防污染**：修改前克隆数组，防止共享引用破坏缓存

### 7.3 状态闩锁模式

多个组件使用「一旦启用就锁定」的模式：

| 组件 | 闩锁对象 | 清除时机 |
|------|----------|----------|
| TTL 资格 | `should1hCacheTTL` | 不清除（会话级） |
| AFK Mode Beta | `afkModeHeaderLatched` | `/clear` / `/compact` |
| Fast Mode Beta | `fastModeHeaderLatched` | `/clear` / `/compact` |
| Cache Editing Beta | `cacheEditingHeaderLatched` | `/clear` / `/compact` |

### 7.4 原子性保证

工具结果预算系统的状态更新保证原子性：
- 非持久化候选者：**同步**标记为 `seen`
- 持久化候选者：**await 完成后**才标记 `replacement`
- 防止中途失败导致状态不一致
