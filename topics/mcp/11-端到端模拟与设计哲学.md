## 11.6 设计哲学 1：协议合规但务实

Claude Code **严格按 MCP 规范实现**协议层（JSON-RPC 2.0 / capability negotiation / list_changed / elicitation）—— 同时**实用兼容 5 种非合规行为**：

| 非合规行为 | 来源 | Claude Code 适配 |
|----------|------|----------------|
| Slack 用 HTTP 200 + error body | Slack OAuth | `normalizeOAuthErrorBody` 改写 [Topic 07] |
| Slack `invalid_refresh_token` 替 `invalid_grant` | RFC 6749 | `NONSTANDARD_INVALID_GRANT_ALIASES` 映射 [Topic 07] |
| PHP IdP `expires_in` 字符串 | RFC 6749 | `z.coerce.number()` [Topic 07] |
| Server zip 含目录条目 | ZIP/Python zipfile | 过滤 `endsWith('/')` [Topic 08] |
| 非合规 RFC 7009 revoke | 多数 server | Bearer fallback retry [Topic 07] |

哲学：**协议是契约，不是宗教**。先让用户能用上 Slack/PHP-backed 服务，再坚持规范。注释里同时**说明 RFC 怎么规定 + 现实怎么走**——决策可追溯。

## 11.7 设计哲学 2：trust boundary 设在配置入口

7 种 scope 信任度不同 [Topic 01]：

```
信任高 ──────────────────────────────────── 信任低
enterprise → managed → user → project → local → dynamic → claudeai
```

- `enterprise/managed`：IT 管理员配的，可以连任意 server；
- `user`：用户全局配的，自己负责；
- `project/.mcp.json`：项目共享配的——**首次连接前必须用户批准**；
- `dynamic` (plugin)：plugin 注入的——marketplace 验证 + allowlist；
- `claudeai`：org 推送的——`user:mcp_servers` scope 必备。

`shouldAllowManagedMcpServersOnly` lockdown mode —— 企业可以**仅允许 managed**，连 user 配置都拒绝。

**威胁模型**：一旦 MCP server 连上，它的 tools 就是 model 的 attack surface。**信任 gate 在"是否连接"环节**——连上后内部基本信任。

[Kenneth's self-approve 评估](./09-channel抽象与elicitation.md#96-kenneth-的-self-approve-评估) 把这点说透：

> The trust boundary isn't the terminal — it's the allowlist.

## 11.8 设计哲学 3：fail-soft + observable

5 种 server state ([Topic 05]) 让**单个 server 失败不阻塞整体**：

- `pending` → connecting
- `connected` → 工作中
- `needs-auth` → 等用户
- `failed` → 不工作但不崩
- `disabled` → 用户手动关

启动时 `Promise.allSettled` 而不是 `Promise.all` —— **任一 server 失败不阻塞其它**。Phase 1 不等 Phase 2 [Topic 10]。

错误**全部进 analytics**：
- `tengu_mcp_oauth_flow_error` —— OAuth 失败原因 [Topic 07]
- `tengu_mcp_servers` —— 启动时 scope 分桶 [Topic 10]
- `tengu_mcp_channel_gate` —— channel 6 层 gate 哪层 skip [Topic 10]
- `tengu_mcp_list_changed` —— listChanged 前后 count
- `tengu_mcp_elicitation_shown/response` —— 表单交互
- `tengu_mcp_channel_message` —— 消息长度 + meta key 数

**软失败但要看见**——产品后端能知道用户卡哪。

## 11.9 设计哲学 4：性能投入在热路径

冷路径（一次启动）的 50-100ms 不优化，热路径（每个 LLM 请求）的 7.2% CPU 必须优化：

| 路径 | 调用频率 | 优化 |
|------|---------|------|
| OAuth metadata discovery | 启动 1 次 | 不优化 |
| Plugin manifest load | 启动 1 次 | lazy import @anthropic-ai/mcpb 700KB |
| `tokens()` SDK 调 | 每个 HTTP 请求 | 不 force keychain refresh，7.2% CPU 教训 [Topic 07] |
| `fetchToolsForClient` | listChanged 或 reload | memoizeWithLRU(20) [Topic 05] |
| `connectToServer` | 启动 + reconnect | memoize 整个函数 [Topic 05] |
| `prefetchAllMcpResources` | 启动 1 次 | 4-concurrent batch [Topic 05] |
| `updateServer` | 每个 server 状态变 | 16ms batch flush [Topic 10] |

哲学：**先 profile 再优化**。`tokens()` 7.2% CPU 的注释直接引用 PR #19436 —— **优化必须基于真实数据**。

## 11.10 设计哲学 5：注释承载决策

MCP 代码注释密度极高——典型样本：

`auth.ts:1543` 解释 `tokens()` 不 force refresh：

```
// Cross-process token changes (another CC instance refreshed or invalidated)
// are picked up via the keychain cache TTL (see macOsKeychainStorage.ts).
// In-process writes already invalidate the cache via storage.update().
// We do NOT clearKeychainCache() here — tokens() is called by the MCP SDK's
// _commonHeaders on every request, and forcing a cache miss would trigger
// a blocking spawnSync(`security find-generic-password`) 30-40x/sec.
// See CPU profile: spawnSync was 7.2% of total CPU after PR #19436.
```

5 个层次：

1. **WHAT**：不调 `clearKeychainCache()`；
2. **WHY**：跨进程同步走 TTL；
3. **HOW**：进程内通过 `storage.update()` invalidate；
4. **MEASUREMENT**：spawnSync 30-40x/sec → 7.2% CPU；
5. **PROVENANCE**：PR #19436。

`channelPermissions.ts:15-23` Kenneth 威胁模型；`auth.ts:251-254` 法律 trust 解释；`useManageMCPConnections.ts:792-801` 3 个 hazard 列举 ——**注释承载历史决策**，让未来的维护者**理解 why 而不仅是 what**。

## 11.11 设计哲学 6：UX 优先于纯技术

5 个 UX-driven 决策：

### 1. ID 字母表去掉 `l`

`channelPermissions.ts:78`：

```
const ID_ALPHABET = 'abcdefghijkmnopqrstuvwxyz'  // 没 l
```

字体里 l/1/I 混淆——25^5 比 26^5 少 18% 空间，但**用户不会打错**。

### 2. 脏词黑名单

防"yes fucky"短信给老板——技术上无影响、用户体验关键。

### 3. proactive refresh 300s

token 过期前 5min 主动刷——技术上"等 401 再 refresh"也对，但**用户会感受到延迟**。

### 4. unsigned exec bit fallback chmod

NFS/FUSE 不支持 chmod ——**继续解压不中断**。技术正确解是 throw，UX 正确解是 swallow。

### 5. 16ms batch update

无 batch UI 也对——但**每个 server 出现都重渲全列表 = jank**。

哲学：**正确的代码不够好，要照顾到具体用户场景**。

## 11.13 增量贡献 2：XAA Cross-App Access (SEP-990)

[Topic 07] 详述的 XAA 是**企业 SSO 的标准化提案**：

- IETF draft `id-jag` 实现；
- 与 RFC 8693 + 7523 + 9728 复合；
- 跨 MCP server 复用 IdP id_token；
- 4-step 交换协议；
- 引用 `~/code/mcp/conformance/examples/clients/typescript/everything-client.ts`——**有 conformance 测试**。

**MCP ext-auth SEP-990** 是 Claude Code 团队贡献给 MCP 标准的提案。

## 11.14 增量贡献 3：channel 协议

[Topic 09] 的 `notifications/claude/channel` 和 `notifications/claude/channel/permission` 命名空间——把 MCP server 升级为**双向交互式后台**。

`experimental['claude/channel']` capability 还在 MCP 协议的 `experimental` 命名空间——**实验性扩展**，未来可能纳入标准。

设计模式：
- 普通文本 vs 结构化权限 双 method 隔离；
- 防 "yes xxxxx" 文本意外触权限；
- 5-letter ID + 脏词黑名单 UX；
- 双 capability filter。

## 11.15 增量贡献 4：MCPB bundle 格式

[Topic 08] 的 `.mcpb` 是 Anthropic 独立设计的单文件分发格式：

- `@anthropic-ai/mcpb` npm 包；
- 兼容老 `.dxt`（Desktop Extension）；
- `manifest.json` + 服务器代码 + native binary；
- `user_config schema` 驱动配置 UI；
- `sensitive` 字段驱动存储分流（H1 #3617646 后强化）。

**为什么不用 npm 包**：

- MCPB 可包 native binary（chmod +x 保留）；
- 不依赖 npm 注册表；
- manifest 自描述 user_config UI；
- 单文件易分发（download + verify hash）。

## 11.16 增量贡献 5：CIMD (SEP-991)

[Topic 07] 的 CIMD（Client ID Metadata Document URL）：

- AS 用 URL 当 `client_id` 而不是 random string；
- 避开 DCR（千用户共享一个 URL）；
- 支持 FedStart 等多租户场景；
- 通过 `MCP_OAUTH_CLIENT_METADATA_URL` env 可 override。

**这是 OAuth 生态的开放提案**——和 SEP-990 一起属于 Claude Code 团队对 OAuth/MCP 标准的贡献。

## 11.18 几个隐性主题

读 11 篇后会发现 **6 个跨章节主题**：

### 1. memoize 是 first-class

`connectToServer`、`fetchToolsForClient`（LRU 20）、`fetchResourcesForClient`、`fetchCommandsForClient`、`fetchClaudeAIMcpConfigsIfEligible`（per-session）—— **几乎所有读路径都 memoize**。这不只是性能优化——是 **state 一致性的来源**：多处调用同一个 fn 看到的是同一份数据。

### 2. 同时维护"配置"和"运行时"两条信息

`McpServerConfig`（配置）+ `MCPServerConnection`（运行时）—— 同一个 server 在内存里有 2 个对象，[10.7](./10-连接管理与生命周期.md#10-7-pending-初始化--stale-清理) 显示 config 变了要主动 disconnect stale，这种"runtime ≠ config"的解耦让重连/重启逻辑简单。

### 3. AbortSignal 一以贯之

所有长操作都接受 abortSignal —— OAuth flow / connectToServer / XAA / tool call / elicitation。统一的取消语义让 `/clear` `/reload-plugins` `Esc` 这些用户动作能干净中断。

### 4. AppState 是最终 sink

无论 transport / auth / channel / elicitation，**最终都汇聚到 AppState**。中间所有 ref / Map / Promise 都是临时——consistency 单一来源是 AppState。

### 5. server.unref / timer.unref 防 pin event loop

OAuth callback server / reconnect timer / flush timer 全部 unref ——**用户 Esc / 关掉 UI 进程能立即退**，不被某个未完成的副作用卡住。

### 6. 注释引用 PR / Issue / incident ID

`PR #19436` (tokens CPU)、`PR #24454` (OAuth vs ingress)、`PR #28258` (step-up auth)、`H1 #3617646` (Telegram tokens)、`INC-3028` (2KB keychain)、`PR discussion 2956440848` (Kenneth threat model)、`#30337` (discoveryState bulky metadata) ——**决策可追溯到原始讨论**。

## 11.21 小结

- 5 个端到端场景演示 stdio / OAuth / channel / plugin schema flip / SDK MCP；
- 6 条设计哲学：
  1. 协议合规但务实（Slack/PHP 兼容）；
  2. trust boundary 设在配置入口（7-scope 信任阶梯）；
  3. fail-soft + observable（5-state + analytics）；
  4. 性能投入在热路径（`tokens()` 7.2% CPU）；
  5. 注释承载决策（WHY + measurement + PR ref）；
  6. UX 优先于纯技术（无 l / 脏词黑名单 / proactive refresh）；
- 5 处增量贡献：
  1. 8 transport 类型（InProcess / SdkControl / claudeai-proxy 独有）；
  2. XAA Cross-App Access (SEP-990) ID-JAG；
  3. channel 协议（`notifications/claude/channel`）；
  4. MCPB bundle 格式；
  5. CIMD URL-based client_id (SEP-991)；
- 6 个跨章节隐性主题：memoize / config-vs-runtime / AbortSignal / AppState sink / unref / 决策可追溯。

MCP 子系统 ≈ 16K 行代码，覆盖**协议实现 + 8 种 transport + 3 种认证 + plugin 集成 + channel 抽象 + React 状态管理** —— 是 Claude Code 中**最复杂的子系统**之一，也是它和外部世界连接的**主要接口**。
