# 00 总览与代码地图

## 0.1 MCP 协议是什么

**Model Context Protocol (MCP)** 是 Anthropic 提出的协议——让 LLM 工具的提供者和消费者解耦：

```
传统模式: 工具是 Claude Code 内置的 (FileRead/Bash/Edit...)
          模型只能用 Claude Code 提供的工具

MCP 模式:  工具由外部 MCP server 提供
          模型能用任何符合协议的 server 提供的工具
          server 可以是: 别的进程 / 远程 HTTP 服务 / SDK 嵌入 / Claude.ai 代理 / ...
```

**协议是规范，不是 SDK**——任何编程语言都能写 MCP server，Claude Code 这样的 client 能连任何 server。

### 5 种 capability

MCP server 可以提供 5 类能力：

| capability | 例子 | 含义 |
|------------|------|------|
| **tools** | `get_weather`, `query_db` | LLM 可调用的工具 |
| **resources** | `file://...`, `db://employees` | LLM 可读的资源（URL 寻址） |
| **prompts** | `/summarize`, `/translate` | 用户可触发的预定义 prompt（slash command 风格） |
| **elicitation** | "What's your API key?" | server **反向**询问用户输入 |
| **sampling** | server 让 client 帮忙调用 LLM | server 自己不会调 LLM，但能让 client 代它问 |

Claude Code 实现了前 4 种（sampling 较少使用）。

### 协议传输层

MCP 协议**只规定消息格式**（基于 JSON-RPC 2.0），不规定传输方式。Claude Code 实现了 **8 种 transport**：

```ts
// services/mcp/types.ts:23-26
export const TransportSchema = lazySchema(() =>
  z.enum(['stdio', 'sse', 'sse-ide', 'http', 'ws', 'sdk']),
)
```

加上 schema 里两个内部类型 `claudeai-proxy` 和 `ws-ide`，加上 `InProcessTransport`，共 **8 种**：

| transport | 用途 |
|-----------|------|
| `stdio` | 启动本地子进程，通过 stdin/stdout 通信 |
| `sse` | 远程 HTTP Server-Sent Events |
| `http` | 远程 HTTP 同步请求 |
| `ws` | 远程 WebSocket |
| `sse-ide` | IDE 扩展专用 SSE（VSCode 等） |
| `ws-ide` | IDE 扩展专用 WebSocket |
| `sdk` | SDK 调用方传入的 MCP server（Claude Code 作为库被嵌入时） |
| `claudeai-proxy` | Claude.ai 网页登录用户的 MCP 服务代理 |
| `InProcess` | Claude Code 内部进程内 MCP（如 vscode SDK） |

不同 transport 对应不同**部署场景**——Anthropic 想覆盖所有"MCP server 可能存在的地方"。

## 0.3 三套并行的认证体系

MCP 集成里最复杂的是认证——**3 套独立**实现：

### 1. 标准 OAuth PKCE (`auth.ts` 大部分)

为开源 MCP server 设计——任何符合 RFC 6749 / OAuth 2.0 + PKCE 的 server 都能接：

```
1. client 拿到 server's authServerMetadataUrl
2. 跳转浏览器 → 用户授权
3. 回调到 localhost:callbackPort
4. 拿 access_token + refresh_token
5. token 存在 keychain (macOS) / DPAPI (Windows)
6. 用 token 发请求
7. token 过期 → 用 refresh_token 刷新
```

### 2. Claude.ai 代理 (`claudeai.ts` 164 行 + `auth.ts` 部分)

Claude.ai 网页版用户的 MCP server 通过 Anthropic 的代理服务：

```
用户在 Claude.ai 已经登录了 → token 在浏览器 cookie 里
Claude Code 通过专门的 proxy URL 调用 MCP server
代理自动处理认证 → server 看到的是 Anthropic 提供的认证身份
```

### 3. xaa Cross-App Access (`xaa.ts` + `xaaIdpLogin.ts` 998 行)

ant 内部企业身份：

```
内部 IdP (Identity Provider) login → 拿到 xaa token
MCP server 内部支持 xaa → 用 token 直接调用
不走 OAuth，不走 Claude.ai
```

3 套各服务**不同群体**：
- OAuth → 开源生态
- Claude.ai proxy → Claude.ai 用户
- xaa → ant 内部用户

强行统一会牺牲灵活性——保持分开。

## 0.5 connectToServer 全景

整个 MCP 集成的"入口"是 `client.ts` 的 `connectToServer(config)`——给一个 server config，返回连上后的 client 对象（或失败 / 待认证状态）：

```
ScopedMcpServerConfig
        │
        ▼
┌──────────────────────────────────────────────┐
│ connectToServer (memoize 缓存)                │
│  - 根据 config.type 选 transport             │
│  - 创建 transport 实例                       │
│  - 初始化 Client                              │
│  - 协商 capabilities                          │
│  - 注册 channel notification handler         │
│  - 返回 ConnectedMCPServer 或失败状态        │
└────────────────────┬─────────────────────────┘
                     │
       ┌─────────────┼─────────────┐
       │             │             │
       ▼             ▼             ▼
   {connected}  {needs-auth}   {failed}
       │             │             │
       ▼             │             │
┌──────────────┐     │             │
│ fetchTools   │     │             │
│ fetchPrompts │     │             │
│ fetchResources│    │             │
└──────┬───────┘     │             │
       │             │             │
       ▼             ▼             ▼
   注册到 LLM     提示用户认证   UI 报错
   工具列表
```

具体的 connectToServer 实现 ~1100 行（client.ts:595-1700+），涵盖：

- 7 种 transport 分支（每种 client 初始化方式不同）；
- OAuth flow 整合（认证失败时挂起、跳浏览器、回调）；
- 错误处理与分类（network / timeout / protocol / auth）；
- memoize cache（避免同 server 多次连接）。

## 0.6 MCPServerConnection 状态机

每个 MCP server 在 React 状态里是一个 union type：

```ts
export type MCPServerConnection =
  | ConnectedMCPServer        // 连上了, 能用
  | FailedMCPServer           // 连接失败
  | NeedsAuthMCPServer        // 需要用户认证
  | PendingMCPServer          // 正在连接 / 正在 reconnect
  | DisabledMCPServer         // 用户禁用
```

状态机：

```
        DisabledMCPServer ──[enable]→ PendingMCPServer
                                          │
                                          ▼
        ┌─────────────────────────────────┴─────────────────┐
        │                                                    │
        ▼                                                    ▼
   {connected}                                          {needs-auth}
        │                                                    │
        │                                                    │
        │ ──[reconnect attempt]────────→ {pending}           │
        │                                                    │
        ▼                                                    ▼
   {failed}                                            {connected after oauth}
```

UI 渲染时根据状态显示不同——`needs-auth` 显示 "Connect via OAuth" 按钮，`failed` 显示 retry 按钮，等等。

## 0.7 8 种 transport × 5 种 capability 矩阵

不同 transport 支持的 capability 不完全一致：

| transport | tools | resources | prompts | elicitation | sampling |
|-----------|:-:|:-:|:-:|:-:|:-:|
| stdio | ✓ | ✓ | ✓ | ✓ | △ |
| sse | ✓ | ✓ | ✓ | ✓ | △ |
| http | ✓ | ✓ | ✓ | ✓ | △ |
| ws | ✓ | ✓ | ✓ | ✓ | △ |
| sse-ide | ✓ | ✓ | ✓ | ✓ | — |
| ws-ide | ✓ | ✓ | ✓ | ✓ | — |
| sdk | ✓ | ✓ | ✓ | — | — |
| claudeai-proxy | ✓ | △ | △ | △ | — |

- **✓** 完全支持；
- **△** 协议支持但 Claude Code 没用过 / 配置门控；
- **—** 不支持（如 IDE transport 跑在 IDE 进程里，不需要 sampling）。

实际上 **tools** 是最常用的——其它 capability 是 nice-to-have。

## 0.8 .mcpb bundle —— MCP server 的分发格式

`.mcpb` 文件是 MCP server 的**单文件分发格式**——把 server 二进制 + manifest + 依赖打包在一起：

```
example-server.mcpb (实际是 zip):
├── manifest.json     ← 服务器元数据 (name / version / entry / signature)
├── package/          ← server 代码 (Node 项目 / Python 项目 / 二进制)
│   ├── index.js
│   ├── package.json
│   └── ...
├── icon.png          ← UI 显示用
└── signature.sig     ← 数字签名 (官方 registry 服务签的)
```

用户操作：
- `claude mcp install ./my-server.mcpb` → 自动解压、验证签名、加进配置；
- 或者从 official registry 安装：`claude mcp install @anthropic/github-server`。

`mcpbHandler.ts` 968 行处理这些 logic。

## 0.9 几个隐性架构观察

读完 16K 行能抽出几条判断：

### 1. transport 是 8 种，但接口统一

`@modelcontextprotocol/sdk` 抽象了 `Transport` 接口。每种 Claude Code transport 实现这个接口，所有上层代码（client.ts）通过统一接口操作。**协议 / 传输分离**是 MCP 设计的核心。

### 2. 认证是异步状态机不是同步函数

`needs-auth` 是个**长期状态**——server 可能停在这个状态等用户去浏览器授权。Client 不阻塞等——返回 `NeedsAuthMCPServer`，UI 显示按钮，用户操作完后再 reconnect。

### 3. 名字规范化是必需的

MCP server 给的工具名可能含 `-` / `.` / 空格——不符合 JS identifier 规则。`normalization.ts` 把它们规范化（如 `my-tool` → `my_tool`），同时**记住**原名（`originalToolName`）供调用时反向映射。

### 4. mcp__server__tool 命名前缀和权限对齐

工具最终名字格式：`mcp__<server>__<tool>`（如 `mcp__github__create_issue`）。这让 Claude Code 的权限规则能精确控制——用户可以配 `Allow: mcp__github__*`（允许所有 github server 工具）。

### 5. 5 React UI 组件

MCP 集成不只是后端——`MCPServerMultiselectDialog` / `MCPServerApprovalDialog` / `MCPServerDesktopImportDialog` / `MCPReconnect` 等 React 组件让用户能交互管理 MCP server。

### 6. Claude Code 既是 MCP client 又能是 server

`entrypoints/mcp.ts` 让 Claude Code 作为 MCP server 跑——外部工具能通过 MCP 调 Claude Code 的工具（FileRead / Bash / 等）。"client ↔ server" 边界是模糊的。

### 7. instructions delta 是性能优化

MCP server 的 `instructions` 字段可能很长（几 KB）。`mcpInstructionsDelta.ts` 130 行实现**差量更新**——server 重新连接后，client 不重新发完整 instructions 到模型，而是发 diff。节省 token。

## 0.10 几个对比点

### vs swarm 专题的 IPC

| 维度 | swarm | MCP |
|------|-------|-----|
| IPC 介质 | 文件系统 (mailbox / lockfile) | 各种 transport (stdio / HTTP / ws / ...) |
| 协议格式 | 自定义 JSON (shutdown_request 等) | 标准 JSON-RPC 2.0 |
| 关系 | 平等 actor + 一个 lead | client 调 server (类 RPC) |
| 信任度 | 团队内部 | 外部 server (Unicode 清洗、签名验证) |

### vs bashtool 子进程

| 维度 | bashtool stdio | MCP stdio |
|------|--------------|-----------|
| 子进程是 | shell | MCP server |
| 通信 | stdin/stdout 纯文本 | JSON-RPC 帧 |
| 用途 | 用户给的命令 | 提供工具能力 |
| 生命周期 | 短期（命令完就退） | 长期（session 期间一直跑） |
