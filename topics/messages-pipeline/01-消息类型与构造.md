# 01 消息类型与构造

> 在能讨论 normalize 之前，先要理解：normalize 处理的输入到底是什么形状？本篇盘点 Claude Code 内部 `Message` 联合类型的 4 大主要类、构造函数族、以及 `SYNTHETIC_*` / `INTERRUPT_MESSAGE` / reject 措辞这些"看起来无聊但其实充满设计判断"的常量。

## 1.1 `Message` 联合类型概览

Claude Code 内部消息有 7 种 type：

| type | 用途 | 进 API 吗 | 进 UI 吗 | 进 transcript JSONL 吗 |
|---|---|:-:|:-:|:-:|
| `user` | 用户输入 / 工具结果 / attachment-after-normalize | ★ | ★ | ★ |
| `assistant` | 模型流式输出累积出的消息 / synthetic error | ★ | ★ | ★ |
| `attachment` | 系统注入的附件（未 normalize） | ✗（先转 user） | ✗（隐藏） | ★ |
| `progress` | 工具执行过程中的进度上报（如 BashTool 的 stdout 流） | ✗ | ★ | ✗ |
| `system` | 命令系统的事件（如 /slash 输出） | △（仅 `local_command` 子类） | ★ | ★ |
| `tombstone` | "撤回"标记，用于流式过程中撤销之前的消息 | ✗ | ✗ | ✗ |
| `tool_use_summary` | SDK 专用，给消费者看的工具调用摘要 | ✗ | ✗ | △ |

normalize 只处理前 4 种里"进 API"那一栏带 ★ 或 △ 的：user / assistant / attachment / system(local_command)。

下面分别讨论。

## 1.2 `UserMessage` 字段精读

`createUserMessage` 的签名是字段最丰富的（`messages.ts:460-523`）：

```ts
export function createUserMessage({
  content,
  isMeta,
  isVisibleInTranscriptOnly,
  isVirtual,
  isCompactSummary,
  summarizeMetadata,
  toolUseResult,
  mcpMeta,
  uuid,
  timestamp,
  imagePasteIds,
  sourceToolAssistantUUID,
  permissionMode,
  origin,
}: {
  content: string | ContentBlockParam[]
  isMeta?: true
  isVisibleInTranscriptOnly?: true
  isVirtual?: true
  isCompactSummary?: true
  toolUseResult?: unknown
  mcpMeta?: {
    _meta?: Record<string, unknown>
    structuredContent?: Record<string, unknown>
  }
  uuid?: UUID | string
  timestamp?: string
  imagePasteIds?: number[]
  sourceToolAssistantUUID?: UUID
  permissionMode?: PermissionMode
  summarizeMetadata?: {
    messagesSummarized: number
    userContext?: string
    direction?: PartialCompactDirection
  }
  origin?: MessageOrigin
}): UserMessage { ... }
```

每一个字段都对应一个具体的下游决策点：

| 字段 | 作用 | 影响 |
|---|---|---|
| `content` | 消息正文，string 或 ContentBlockParam[] | 发到 API 的核心数据 |
| `isMeta` | "这是系统元信息，不是真用户输入" | UI 默认隐藏；normalize 的 `error→strip-targets` 反向追溯只追到 isMeta user message |
| `isVisibleInTranscriptOnly` | 只在 transcript 模式显示 | 普通 UI 不渲染 |
| `isVirtual` | 显示用占位（如 REPL 内部模拟） | normalize 时直接 filter 掉，**永不进 API** |
| `isCompactSummary` | 这是压缩生成的摘要消息 | 后处理时用作 compact boundary |
| `summarizeMetadata` | 压缩元数据（被压缩了多少条、压缩方向） | 仅用于 UI 提示 |
| `toolUseResult` | 工具 Output 的原始 typed 形式 | UI 渲染 tool result；不进 API（API 拿 content 里的 tool_result） |
| `mcpMeta` | MCP 协议 metadata | 透传给 SDK 消费者，永不进模型 |
| `uuid` | 消息标识 | 配对 tool_use ↔ tool_result，[id:xxx] tag 用它派生 |
| `timestamp` | ISO 时间戳 | UI 显示 + transcript 排序 |
| `imagePasteIds` | 粘贴板图片 ID | 临时跟踪用，发完即用完 |
| `sourceToolAssistantUUID` | tool_result 类型消息：指向产生该工具调用的 assistant message uuid | UI 反向跳转 |
| `permissionMode` | 消息发出时的权限模式 | rewind 还原用 |
| `origin` | 消息出处 | `undefined`=人类键盘；其它=hook/command/sdk 等 |

构造时几乎所有字段都可选，最简形式：

```ts
createUserMessage({ content: "Hello" })
```

但实际场景里很少这么简单——见下文 1.6 的几种典型构造。

## 1.3 `AssistantMessage` 字段精读

`baseCreateAssistantMessage` 的签名（`messages.ts:355-409`）：

```ts
function baseCreateAssistantMessage({
  content,
  isApiErrorMessage = false,
  apiError,
  error,
  errorDetails,
  isVirtual,
  usage = {
    input_tokens: 0,
    output_tokens: 0,
    cache_creation_input_tokens: 0,
    cache_read_input_tokens: 0,
    server_tool_use: { web_search_requests: 0, web_fetch_requests: 0 },
    service_tier: null,
    cache_creation: {
      ephemeral_1h_input_tokens: 0,
      ephemeral_5m_input_tokens: 0,
    },
    inference_geo: null,
    iterations: null,
    speed: null,
  },
}: {
  content: BetaContentBlock[]
  isApiErrorMessage?: boolean
  apiError?: AssistantMessage['apiError']
  error?: SDKAssistantMessageError
  errorDetails?: string
  isVirtual?: true
  usage?: Usage
}): AssistantMessage {
  return {
    type: 'assistant',
    uuid: randomUUID(),
    timestamp: new Date().toISOString(),
    message: {
      id: randomUUID(),
      container: null,
      model: SYNTHETIC_MODEL,
      role: 'assistant',
      stop_reason: 'stop_sequence',
      stop_sequence: '',
      type: 'message',
      usage,
      content,
      context_management: null,
    },
    requestId: undefined,
    apiError,
    error,
    errorDetails,
    isApiErrorMessage,
    isVirtual,
  }
}
```

注意 `AssistantMessage` 比 `UserMessage` 字段更少——因为：

- 真正的 assistant 消息**不是用 `createAssistantMessage` 构造的**，而是从 SSE 流式事件累积出来的（见 [02](./02-流式事件与assistant增量构造.md)）；
- `createAssistantMessage` 主要服务于"合成 assistant 消息"场景：API 错误占位、tool result 中断后的伪 reply、resume 时补全占位等；
- 这些合成消息的 `model` 字段是 **`SYNTHETIC_MODEL = '<synthetic>'`**（line 300）——一个特殊标记，让下游知道"这不是真的模型输出"。

`isApiErrorMessage` + `model === SYNTHETIC_MODEL` 两个条件组合起来就是 `isSyntheticApiErrorMessage` 的判定（`messages.ts:321-329`）：

```ts
function isSyntheticApiErrorMessage(
  message: Message,
): message is AssistantMessage & { isApiErrorMessage: true } {
  return (
    message.type === 'assistant' &&
    message.isApiErrorMessage === true &&
    message.message.model === SYNTHETIC_MODEL
  )
}
```

normalize 主循环里**显式 filter 掉**这类消息（`messages.ts:2056-2074`）——它们是 UI/历史显示用的占位，不能发给 API（API 会因为"假 assistant 没真 tool_result 对应"报 400）。

## 1.4 `SYNTHETIC_*` 与 reject 措辞家族

这是 messages.ts 200-300 行密集出现的一类常量——**给模型读的固定措辞**。它们看起来无聊，但每一条都有具体设计判断。

### 1.4.1 中断系列

```ts
// messages.ts:207-209
export const INTERRUPT_MESSAGE = '[Request interrupted by user]'
export const INTERRUPT_MESSAGE_FOR_TOOL_USE =
  '[Request interrupted by user for tool use]'
```

两个版本，对应"用户在文本生成中按 ESC"和"用户在工具调用前点 deny"。区分两者让模型可以选择不同的恢复策略。

用法：`createUserInterruptionMessage({ toolUse: true })` 构造对应的 user message，下一轮发给模型。

### 1.4.2 取消 / 拒绝系列

```ts
// messages.ts:210-221
export const CANCEL_MESSAGE =
  "The user doesn't want to take this action right now. STOP what you are doing and wait for the user to tell you how to proceed."

export const REJECT_MESSAGE =
  "The user doesn't want to proceed with this tool use. The tool use was rejected (eg. if it was a file edit, the new_string was NOT written to the file). STOP what you are doing and wait for the user to tell you how to proceed."

export const REJECT_MESSAGE_WITH_REASON_PREFIX =
  "The user doesn't want to proceed with this tool use. The tool use was rejected (eg. if it was a file edit, the new_string was NOT written to the file). To tell you how to proceed, the user said:\n"

export const SUBAGENT_REJECT_MESSAGE =
  'Permission for this tool use was denied. The tool use was rejected (eg. if it was a file edit, the new_string was NOT written to the file). Try a different approach or report the limitation to complete your task.'

export const SUBAGENT_REJECT_MESSAGE_WITH_REASON_PREFIX =
  'Permission for this tool use was denied. The tool use was rejected (eg. if it was a file edit, the new_string was NOT written to the file). The user said:\n'

export const PLAN_REJECTION_PREFIX =
  'The agent proposed a plan that was rejected by the user. The user chose to stay in plan mode rather than proceed with implementation.\n\nRejected plan:\n'
```

值得注意的几个措辞设计：

#### 1. 显式说"new_string 没写入文件"

`REJECT_MESSAGE` / `SUBAGENT_REJECT_MESSAGE` 都明确告诉模型 **"the new_string was NOT written to the file"**。这是为什么？

因为模型有时候被 deny 之后会以为"虽然显示拒绝但还是写进去了"——这是一种 LLM 失误模式。措辞显式声明"操作没发生"，避免模型在后续生成里基于"假设已写入"的错误前提推理。

#### 2. 主代理 vs 子代理用不同措辞

主代理用 `REJECT_MESSAGE`（"用户拒绝了"），子代理用 `SUBAGENT_REJECT_MESSAGE`（"权限被拒了"）。两者语义不同：

- 用户拒绝 = 需要等用户告知怎么继续（STOP and wait）；
- 权限被拒 = 子代理应该 try a different approach（继续工作）。

子代理没有用户在旁边，所以不应该停下来"等用户告知"——它要么换条路、要么 report 失败回主代理。这是非常细的措辞设计。

#### 3. WITH_REASON_PREFIX 留尾巴

```
"...To tell you how to proceed, the user said:\n"
```

后面要拼用户的实际理由。`\n` 在末尾让用户的话独占一段，视觉上和模板文本分开。

### 1.4.3 否决建议（DENIAL_WORKAROUND_GUIDANCE）

`messages.ts:226-232`：

```ts
export const DENIAL_WORKAROUND_GUIDANCE =
  `IMPORTANT: You *may* attempt to accomplish this action using other tools that might naturally be used to accomplish this goal, ` +
  `e.g. using head instead of cat. But you *should not* attempt to work around this denial in malicious ways, ` +
  `e.g. do not use your ability to run tests to execute non-test actions. ` +
  `You should only try to work around this restriction in reasonable ways that do not attempt to bypass the intent behind this denial. ` +
  `If you believe this capability is essential to complete the user's request, STOP and explain to the user ` +
  `what you were trying to do and why you need this permission. Let the user decide how to proceed.`
```

这条措辞解决"被 deny 之后该怎么办"。核心三句：

1. **允许合理替代**：head 代替 cat 这种自然变形可以；
2. **禁止恶意绕过**：用 test runner 跑非 test 命令这种"绕规则"行为不行；
3. **必要时报告用户**：如果觉得这个权限确实必需，停下来告诉用户，让用户决定。

这一条措辞被 `AUTO_REJECT_MESSAGE(toolName)` 和 `DONT_ASK_REJECT_MESSAGE(toolName)` 复用。也被 `buildYoloRejectionMessage` 在 auto-mode 拒绝时复用。

### 1.4.4 `SYNTHETIC_MESSAGES` 集合

`messages.ts:300-308`：

```ts
export const SYNTHETIC_MODEL = '<synthetic>'

export const SYNTHETIC_MESSAGES = new Set([
  INTERRUPT_MESSAGE,
  INTERRUPT_MESSAGE_FOR_TOOL_USE,
  CANCEL_MESSAGE,
  REJECT_MESSAGE,
  NO_RESPONSE_REQUESTED,
])

export function isSyntheticMessage(message: Message): boolean {
  return (
    message.type !== 'progress' &&
    message.type !== 'attachment' &&
    message.type !== 'system' &&
    Array.isArray(message.message.content) &&
    message.message.content[0]?.type === 'text' &&
    SYNTHETIC_MESSAGES.has(message.message.content[0].text)
  )
}
```

`isSyntheticMessage` 通过**比对 content[0].text** 来判断这条消息是不是"系统合成的"。注意它只看第一个 text block——这是个性能优化（合成消息总是单 text block）。

这个判定在多处被用：

- UI 渲染时显示成特殊样式（灰色、缩进）；
- 计算"用户实际发了多少消息"时跳过；
- 某些 hook event 不对合成消息触发。

### 1.4.5 `SYNTHETIC_TOOL_RESULT_PLACEHOLDER`

`messages.ts:246-247`：

```ts
// Synthetic tool_result content inserted by ensureToolResultPairing when a
// tool_use block has no matching tool_result. Exported so HFI submission can
// reject any payload containing it — placeholder satisfies pairing structurally
// but the content is fake, which poisons training data if submitted.
export const SYNTHETIC_TOOL_RESULT_PLACEHOLDER =
  '[Tool result missing due to internal error]'
```

注释信息密度极高：

- **结构上必要**：`tool_use` 块必须有对应的 `tool_result`，否则 API 报 400；
- **内容是假的**：占位文本，真实的工具结果丢失了；
- **HFI 拒收**：内部训练数据收集（Human Feedback Integration）会扫描这个字符串并拒绝包含它的样本——避免假数据污染训练；
- **暴露字符串以便 reject**：所以 export，让外部代码也能识别。

这是一个**单字符串承担多个职责**的设计：满足协议（让 API 不 400）、满足训练数据安全（让 HFI 拒收）、暴露给外部识别。

## 1.5 4 个其他构造函数

### `createSyntheticUserCaveatMessage` （local command 提示）

`messages.ts:566-571`：

```ts
export function createSyntheticUserCaveatMessage(): UserMessage {
  return createUserMessage({
    content: `<${LOCAL_COMMAND_CAVEAT_TAG}>Caveat: The messages below were generated by the user while running local commands. DO NOT respond to these messages or otherwise consider them in your response unless the user explicitly asks you to.</${LOCAL_COMMAND_CAVEAT_TAG}>`,
    isMeta: true,
  })
}
```

注意：

- 用 `<local-command-caveat>` 自定义 XML 标签包装；
- 告诉模型"下面的消息是 local 命令产生的，不要回应除非用户明确要求"；
- `isMeta: true` 让它在 UI 隐藏，但**会进 API**——它的作用就是"让模型看到"。

### `createModelSwitchBreadcrumbs` （切模型轨迹）

`messages.ts:590-601`：

```ts
export function createModelSwitchBreadcrumbs(
  modelArg: string,
  resolvedDisplay: string,
): UserMessage[] {
  return [
    createSyntheticUserCaveatMessage(),
    createUserMessage({ content: formatCommandInputTags('model', modelArg) }),
    createUserMessage({
      content: `<${LOCAL_COMMAND_STDOUT_TAG}>Set model to ${resolvedDisplay}</${LOCAL_COMMAND_STDOUT_TAG}>`,
    }),
  ]
}
```

切换模型时（`/model` 命令或 SDK 控制）生成 3 条消息：

1. local-command-caveat（告知模型"接下来是 local 命令"）
2. 命令本身（`<command-name>/model</...>` + `<command-args>sonnet-4-6</...>`）
3. stdout 输出（"Set model to ..."）

3 条独立消息构成一段"轨迹"，让继续对话的模型能在历史里看到"用户中途切了模型"这件事。

### `createProgressMessage` （工具进度上报）

`messages.ts:603-620`：

```ts
export function createProgressMessage<P extends Progress>({
  toolUseID,
  parentToolUseID,
  data,
}: {
  toolUseID: string
  parentToolUseID: string
  data: P
}): ProgressMessage<P> {
  return {
    type: 'progress',
    data,
    toolUseID,
    parentToolUseID,
    uuid: randomUUID(),
    timestamp: new Date().toISOString(),
  }
}
```

`type: 'progress'`——这种消息只进 UI，**不进 API、不进 transcript**。它在工具执行过程中（如 Bash 长命令的中间 stdout）被产生，给用户实时反馈。`parentToolUseID` 让进度可以挂到嵌套子代理的某次工具调用上。

### `createToolResultStopMessage` （打断信号）

`messages.ts:622-631`：

```ts
export function createToolResultStopMessage(
  toolUseID: string,
): ToolResultBlockParam {
  return {
    type: 'tool_result',
    content: CANCEL_MESSAGE,
    is_error: true,
    tool_use_id: toolUseID,
  }
}
```

注意它返回的是 `ToolResultBlockParam`（一个 content block），不是 `Message`。它的用法：当用户中断了某个工具调用，需要给 API 发一个"假"tool_result 来配对那个 tool_use（否则下次 API 调用会 400）——这个就是那个假 tool_result，content 是 `CANCEL_MESSAGE`。

## 1.6 几种典型 user message 构造场景

把上面零件串起来，看几个实际场景：

### 场景 A：用户在 REPL 里输入一句话

```ts
createUserMessage({
  content: "fix the bug in foo.ts",
  origin: undefined,  // = 人类键盘
})
```

最简单的情况。`origin = undefined` 表示这是真用户输入。

### 场景 B：粘贴板含图片

```ts
createUserMessage({
  content: [
    { type: 'image', source: { type: 'base64', media_type: 'image/png', data: '...' } },
    { type: 'text', text: "explain this screenshot" }
  ],
  imagePasteIds: [42],
})
```

`imagePasteIds` 短暂跟踪粘贴板图片，让 UI 能在用户提交前预览/取消粘贴。

### 场景 C：工具结果

```ts
createUserMessage({
  content: [
    {
      type: 'tool_result',
      tool_use_id: 'toolu_abc',
      content: '<file content with line numbers>'
    }
  ],
  isMeta: false,                  // 工具结果不是 meta
  toolUseResult: { ... },          // 工具 Output 的原始 typed 形式
  sourceToolAssistantUUID: 'abc',  // 反向指针
})
```

注意 `content` 数组里只有一个 `tool_result` block。这是工具执行完后产生的"消息形式"——本质上是"用户角色，但内容是工具结果"。

### 场景 D：/slash 命令

```ts
[
  createSyntheticUserCaveatMessage(),
  createUserMessage({ content: formatCommandInputTags('compact', '') }),
  createUserMessage({ content: `<local-command-stdout>...</local-command-stdout>` }),
]
```

3 条消息构成 slash 命令的"对话轨迹"。

### 场景 E：被中断

```ts
createUserInterruptionMessage({ toolUse: true })
// 等价于
createUserMessage({
  content: [{ type: 'text', text: INTERRUPT_MESSAGE_FOR_TOOL_USE }]
})
```

用户在工具调用前按 ESC，生成这条消息让模型知道"用户中止了"。

### 场景 F：attachment 转 user（normalize 中）

attachment 类型消息会被 `normalizeAttachmentForAPI` 转成 1 条或多条 user message，比如 `relevant_memories` 转成：

```ts
wrapMessagesInSystemReminder([
  createUserMessage({
    content: `Relevant memories:\n\n${memoryContents}`,
    isMeta: true,
  })
])
```

`isMeta: true` 让它在 UI 隐藏，包装后是带 `<system-reminder>` 标签的 user message。详见 [07 attachment normalizer](./07-attachment-normalizer.md)。

## 1.7 一个常被忽略的细节：`message.message.content` vs `message.content`

Claude Code 的消息结构有两层：

```
UserMessage {
  type: 'user',
  uuid: ...,
  timestamp: ...,
  isMeta?: ...,
  // ... outer 字段（Claude Code 自己的）
  message: {                  ← 这一层是 SDK 类型 (BetaMessageParam)
    role: 'user',
    content: string | ContentBlockParam[]  ← 这一层是 API 发送的
  }
}
```

外层（`UserMessage` 自己）的字段是 Claude Code 内部用的（uuid / isMeta / origin / toolUseResult ...）。内层的 `message: { role, content }` 是 SDK 的 `BetaMessageParam` 类型，**是真正发给 API 的部分**。

normalize 的工作就是确保**外层的字段被正确转换/丢弃，内层的字段符合 API 协议**。后续几篇频繁出现 `msg.message.content`、`msg.message.content[i].type` 这种二级访问——记得这一层就好。

## 1.8 小结

- `Message` 联合类型有 7 种 type，normalize 主要处理 user/assistant/attachment/system(local_command)；
- `UserMessage` 14 个字段，每个对应一个具体下游决策；
- `AssistantMessage` 字段少——真消息从流式累积，构造函数主要给合成场景用；
- `SYNTHETIC_MODEL = '<synthetic>'` 是合成消息的标记，配合 `isApiErrorMessage` 让 normalize 能识别并 filter；
- reject 措辞家族（CANCEL/REJECT/SUBAGENT_REJECT/PLAN_REJECTION）字字斟酌：显式说"没写入文件"、区分主子代理、提供 reason prefix；
- `SYNTHETIC_TOOL_RESULT_PLACEHOLDER` 一个字符串承担"协议合规 + 训练数据安全 + 外部识别"三职责；
- 消息有内外两层（Claude Code 字段 + SDK BetaMessageParam）——`message.message.content` 是真正发 API 的部分。
