# 00 总览与全管线

## 0.1 这层在做什么

Claude Code 内部有两套"消息"概念：

- **内部消息**（`Message` 联合类型）：UI 显示用、JSONL 持久化用、resume 用。包含 `user` / `assistant` / `attachment` / `progress` / `system` / `tombstone` / `tool_use_summary` 七种 type，字段繁多（uuid、timestamp、isMeta、isVirtual、isCompactSummary、permissionMode、origin、imagePasteIds、toolUseResult ...）
- **API 消息**（Anthropic Messages API 的 `messages[]`）：只有 `user` 和 `assistant` 两种 role，每条 message 的 `content` 必须严格符合 SDK 的 `ContentBlockParam` 联合类型，且要满足一堆隐性约束（tool_use ↔ tool_result 必须配对、is_error 的 tool_result 只能是 text、tool_result 必须在 content[] 最前、相邻 text block 会被服务器合并、tool_reference 不能和别的 block 类型混在 tool_result.content 里 ……）。

**`messages.ts` 这一层就是把前者转换成后者的所有逻辑。**

它解决四类问题：

| 问题 | 例子 |
|---|---|
| **协议合规** | Bedrock 不支持连续两条 user message → 必须 merge；is_error tool_result 含图像 → 400 错误 → 必须过滤 |
| **训练数据安全** | 把 SR-text 和 tool_result 并置会让 wire 上出现 "Human:"，模型学到提前停止的模式 → smoosh |
| **prompt cache 友好** | 内容变动可能破坏 cache prefix → 一些字段（如 tool_use input）要保持稳定 |
| **历史漂移修复** | 旧 transcript 在新代码下可能含 image-in-error 等不再合法的状态 → resume 时清理 |

```
│                              │                                   │
│                              ▼                                   │
│   4. POST /v1/messages                                           │
│                              │                                   │
│                              ▼                                   │

│                              │                                   │
│                              ▼                                   │
│   6. 边解析边累积出 AssistantMessage → 进入 store               │
│                              │                                   │
│                              ▼                                   │
│   7. 工具执行 → 产出新 tool_result user message → 进入 store    │
│                              │                                   │
│                              └──→ 下一轮回到第 1 步              │
└──────────────────────────────────────────────────────────────────┘
```

**重点判断**：

1. **normalize 不修改 store 里的 message**——它返回的是新数组，原 `messages` 不动。这让 normalize 可以反复跑（实际也确实如此：每一轮 API 调用都会 normalize 一次完整历史）；
2. **normalize 不做异步 IO**——只是纯数据变换。所以再贵也只是 CPU 开销；
3. **normalize 的输入包含 `tools` 参数**——这是因为部分变换依赖工具是否注册（如 `stripUnavailableToolReferences`）；
4. **normalize 处理的是历史全量**——不是增量。每轮重新 normalize 整个 message 数组。

## 0.4 七个核心区段速览

### A. 消息构造族（350-650）

提供 4 类 Message 的构造函数：

- `createUserMessage(content, ...flags)`：构造 user 消息。注意 11 个可选字段（isMeta / isVirtual / isCompactSummary / sourceToolAssistantUUID 等），每一个都对应"消息是怎么产生的、要不要发给 API、要不要进 transcript"等下游决策；
- `createAssistantMessage`：构造 assistant 消息。但**真正的 assistant 消息是从 SSE 流式累积出来的**，这里主要给 synthetic 场景用（API error message、合成的占位）；
- `createToolResultStopMessage`：构造打断信号的 tool_result，content 为 `CANCEL_MESSAGE`、`is_error: true`；
- `createSyntheticUserCaveatMessage`：构造 `<local-command-caveat>` 包装的提示。

详细在 **[01 消息类型与构造](./01-消息类型与构造.md)**。

### B. 流式事件分发（2930-3094）

`handleMessageFromStream` 是 SSE 流的中央调度。它接收：

- `stream_request_start` → onSetStreamMode('requesting')
- `message_start` → 上报 ttftMs
- `content_block_start` → 根据 content_block.type 分流（thinking / text / tool_use / server_tool_use / 等）
- `content_block_delta` → 4 类 delta（text / input_json / thinking / signature）
- `content_block_stop` / `message_delta` / `message_stop` → 状态机推进

边接收边构造，同时支持外部回调 `onStreamingToolUses` / `onStreamingThinking` / `onStreamingText` 让 UI 实时显示。

详细在 **[02 流式事件与 assistant 增量构造](./02-流式事件与assistant增量构造.md)**。

### C. normalize 主循环（1989-2370）

`normalizeMessagesForAPI(messages, tools)`：

1. 先 `reorderAttachmentsForAPI` 把 attachment 上浮；
2. 过滤 progress / system / virtual / synthetic-error 消息；
3. 构建 error→strip-targets 映射（PDF 太大、图像太大、请求太大 → 反向追溯到源头 user message，标记要剥离哪些 block type）；
4. 主 switch 按 `message.type` 分发到 user / assistant / attachment / system 四个 case；
5. 完成后做一系列 pass：thinking 过滤、whitespace 过滤、ensureNonEmpty、merge、smoosh、sanitize、validate。

详细在 **[03 normalize 主循环与三路分发](./03-normalize主循环与三路分发.md)**。

### D. 合并 smoosh hoist（2372-2598）

层级嵌套的合并族：

```
mergeAdjacentUserMessages    (顶层: 走一遍消息数组合并相邻 user)
   ↓ calls
mergeUserMessages            (合并两个 user message)
   ↓ calls
mergeUserContentBlocks       (合并两个 content[] 数组)
   ↓ calls smoosh? 
smooshIntoToolResult         (把非 tool_result block 折叠进 tool_result.content)
hoistToolResults             (把 tool_result 移到 content[] 最前)
joinTextAtSeam               (text-text 接缝处插 \n)
```

每一层做一件具体的事，且大多对应一个具体的 A/B 实验或事故修复。

详细在 **[04 合并 smoosh 与 hoist 三连击](./04-合并smoosh与hoist三连击.md)**。

### E. tool_reference 协议边界（1933-1988、normalize 主循环 2139-2185）

`tool_reference` 是 tool-search beta 引入的特殊 content block。它有一个**协议层的副作用**：服务器把它渲染成 `<functions>...</functions>` 标签，和系统提示里 tools section 的标签同名，导致模型看到 tool_reference 在 prompt 末尾时会以约 10% 概率采样到停止序列。

解决方案有两套，按 feature gate 切换：

- **预防方式**（gate OFF）：在含 tool_reference 的 user message content 末尾**注入** `TOOL_REFERENCE_TURN_BOUNDARY` 文本（看起来像 `\n\nHuman: ...`）作为边界 sibling，让 Anthropic 服务器把它解析成新的 user turn 起点；
- **重定位方式**（gate ON）：用 `relocateToolReferenceSiblings` 把 text sibling 从 tool_reference 消息**搬到下一条**没有 tool_reference 的 user message，避开协议陷阱。

详细在 **[05 tool_reference 与协议边界事故](./05-tool_reference与协议边界事故.md)**。

### F. 协议合规过滤族（4800-5050）

5 个 filter 各对应一类 API 400 错误或训练数据问题：

| 过滤器 | 防御对象 |
|---|---|
| `filterOrphanedThinkingOnlyMessages` | 仅含 thinking block 的 assistant 消息（compact 后可能产生）→ 400 |
| `filterTrailingThinkingFromLastAssistant` | 最后一条 assistant 末尾的 thinking → API 不接受 thinking 在结尾 |
| `filterWhitespaceOnlyAssistantMessages` | 全空白的 assistant 消息 → 训练数据噪声 + 可能 400 |
| `ensureNonEmptyAssistantContent` | content[] 为空 → 400 |
| `sanitizeErrorToolResultContent` | is_error tool_result 含 non-text block → 400 |

详细在 **[06 协议合规过滤层](./06-协议合规过滤层.md)**。

### G. attachment normalizer（3453-4800）

一个超长 switch，把 25+ 种 attachment 类型转换成 user message 列表。覆盖的 attachment 类型大致分四类：

- **状态注入**：`directory` / `git_status` / `env` / 当前 cwd / 当前时间
- **记忆/计划**：`relevant_memories` / `plan_mode` / `todo` / `nested_memory`
- **协作**：`team_context` / `teammate_mailbox` / `agent_mention`
- **能力声明**：`skill_discovery` / `bagel_console`（旧）

详细在 **[07 attachment normalizer](./07-attachment-normalizer.md)**。

## 0.5 一个反直觉的事实：normalize 是幂等的（几乎）

normalize 的几个关键设计：

- 输入是 `Message[]`，输出是 `(UserMessage | AssistantMessage)[]`；
- `ensureSystemReminderWrap` 做 `startsWith('<system-reminder>')` 判定，已包过的不重复包；
- `smooshIntoToolResult` 在已经被 smoosh 过的输入上是 no-op；
- `relocateToolReferenceSiblings` 在已经 relocate 过的（源 text 已被清空）上是 no-op；
- `appendMessageTagToUserMessage` 在已经有 [id:] tag 的消息上是 no-op。

**这意味着**：normalize 可以反复跑、可以串联跑、可以在不同条件下跑而不破坏结果。这是非常稳健的设计——上层不需要担心"normalize 被多次调用会出错"。

但是**几乎**——有两种情况是状态依赖的：

1. **uuid 重新生成**：`createUserMessage`/`createAssistantMessage` 内部用 `randomUUID()`，所以 normalize 输出里如果有新构造的消息（如 attachment 转 user），它的 uuid 每次都不同。这就是为什么 `normalizeMessagesForAPI` 返回值**不能持久化**回 store——必须每次重算；
2. **feature gate 切换**：`tengu_chair_sermon` / `tengu_toolref_defer_j8m` 等 gate 在不同环境下值不同，导致 normalize 结果会变。
