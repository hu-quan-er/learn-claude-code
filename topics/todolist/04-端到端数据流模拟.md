# 04 - 端到端数据流模拟

先明确一个关键点：**todolist 不是 Claude Code 自动从用户文本里解析出来的**。Claude Code 做的是：

1. 在系统提示和工具列表里告诉模型“你可以用任务工具跟踪进度”。
2. 模型自己决定是否调用 `TodoWrite` 或 `TaskCreate` / `TaskUpdate`。
3. 工具执行器只负责校验、落状态、返回 `tool_result`。
4. 下一轮请求构建时，系统可能通过 reminder 或文件态 UI 把状态再带回来。

也就是说，todolist 的“产生者”是 assistant 的 `tool_use.input`；Claude Code 是执行和持久化这个输入的 runtime。

## 模拟一：V1 TodoWrite 非交互式会话

假设当前是 SDK / `--print` 这类非交互式会话：

```text
getIsNonInteractiveSession() = true
isTodoV2Enabled() = false
可用任务工具 = TodoWrite
sessionId = sess-001
AppState.todos = {}
```

用户输入：

```text
请帮我实现登录页，包含表单、校验、提交 API，并运行测试。
```

### 第 1 步：模型决定创建 TodoList

系统提示和 `TodoWriteTool/prompt.ts` 都告诉模型：复杂多步骤任务、用户要求测试时应该使用 TodoList。于是模型生成工具调用：

```json
{
  "type": "tool_use",
  "id": "toolu_v1_001",
  "name": "TodoWrite",
  "input": {
    "todos": [
      {
        "content": "Implement login form UI",
        "activeForm": "Implementing login form UI",
        "status": "in_progress"
      },
      {
        "content": "Add client-side validation",
        "activeForm": "Adding client-side validation",
        "status": "pending"
      },
      {
        "content": "Wire login submit API",
        "activeForm": "Wiring login submit API",
        "status": "pending"
      },
      {
        "content": "Run tests for login flow",
        "activeForm": "Running tests for login flow",
        "status": "pending"
      }
    ]
  }
}
```

### 第 2 步：TodoWriteTool 写入 AppState

`TodoWriteTool.call()` 执行：

```typescript
const todoKey = context.agentId ?? getSessionId() // sess-001
const oldTodos = appState.todos[todoKey] ?? []    // []
const allDone = todos.every(t => t.status === 'completed') // false
const newTodos = allDone ? [] : todos
```

写入后：

```json
{
  "todos": {
    "sess-001": [
      { "content": "Implement login form UI", "activeForm": "Implementing login form UI", "status": "in_progress" },
      { "content": "Add client-side validation", "activeForm": "Adding client-side validation", "status": "pending" },
      { "content": "Wire login submit API", "activeForm": "Wiring login submit API", "status": "pending" },
      { "content": "Run tests for login flow", "activeForm": "Running tests for login flow", "status": "pending" }
    ]
  }
}
```

工具返回给模型：

```json
{
  "role": "user",
  "content": [
    {
      "type": "tool_result",
      "tool_use_id": "toolu_v1_001",
      "content": "Todos have been modified successfully. Ensure that you continue to use the todo list to track your progress. Please proceed with the current tasks if applicable"
    }
  ]
}
```

### 第 3 步：模型完成第一项后更新

V1 的更新不是 patch，而是完整替换。模型不能说“把第 1 项改成 completed”，它必须再次提交完整列表：

```json
{
  "type": "tool_use",
  "id": "toolu_v1_002",
  "name": "TodoWrite",
  "input": {
    "todos": [
      {
        "content": "Implement login form UI",
        "activeForm": "Implementing login form UI",
        "status": "completed"
      },
      {
        "content": "Add client-side validation",
        "activeForm": "Adding client-side validation",
        "status": "in_progress"
      },
      {
        "content": "Wire login submit API",
        "activeForm": "Wiring login submit API",
        "status": "pending"
      },
      {
        "content": "Run tests for login flow",
        "activeForm": "Running tests for login flow",
        "status": "pending"
      }
    ]
  }
}
```

写入后，`AppState.todos["sess-001"]` 被整个替换为新数组。这里没有 item ID，也没有合并逻辑，最终状态完全取决于最后一次 `TodoWrite` 的输入。

### 第 4 步：全部完成时的特殊清理

最后模型可能提交：

```json
{
  "todos": [
    { "content": "Implement login form UI", "activeForm": "Implementing login form UI", "status": "completed" },
    { "content": "Add client-side validation", "activeForm": "Adding client-side validation", "status": "completed" },
    { "content": "Wire login submit API", "activeForm": "Wiring login submit API", "status": "completed" },
    { "content": "Run tests for login flow", "activeForm": "Running tests for login flow", "status": "completed" }
  ]
}
```

此时：

```typescript
allDone = true
newTodos = []
```

运行时保存的是：

```json
{
  "todos": {
    "sess-001": []
  }
}
```

但工具输出里的 `newTodos` 仍然是模型传入的 completed 列表。这是 V1 的一个不一致点：

| 位置 | 最终值 |
|------|--------|
| `AppState.todos["sess-001"]` | `[]` |
| tool result `newTodos` | 全部 completed 的原始列表 |
| transcript 中的 `tool_use.input` | 全部 completed 的原始列表 |

如果之后从 transcript resume，`sessionRestore.ts` 会读取最后一次 `TodoWrite.input.todos`，而不是读取运行时曾经清空后的 `AppState`。

### 第 5 步：很久没更新时的 reminder

如果后续 10 个 assistant turn 都没有再调用 `TodoWrite`，并且距离上次 reminder 也超过 10 个 assistant turn：

```text
turnsSinceLastTodoWrite >= 10
turnsSinceLastReminder >= 10
```

`attachments.ts` 会创建：

```json
{
  "type": "todo_reminder",
  "content": "AppState.todos[sess-001]",
  "itemCount": "AppState.todos[sess-001].length"
}
```

如果任务尚未全部完成，这里通常是当前列表长度；如果之前已经触发全 completed 清理，这里就是 `0`。`messages.ts` 再把它转成隐藏的 meta reminder 放进下一轮模型上下文，提醒模型“TodoWrite 很久没用了，如果相关就更新一下”。这不是用户可见消息。

## 模拟二：V2 Task tools 交互式 CLI

现在换成正常交互式 REPL：

```text
getIsNonInteractiveSession() = false
isTodoV2Enabled() = true
可用任务工具 = TaskCreate / TaskUpdate / TaskGet / TaskList
taskListId = getSessionId() = sess-002
任务目录 = ~/.claude/tasks/sess-002/
```

同样的用户输入：

```text
请帮我实现登录页，包含表单、校验、提交 API，并运行测试。
```

### 第 1 步：模型创建任务文件

模型会调用 `TaskCreate`。每次调用创建一个 `pending` 任务：

```json
{
  "type": "tool_use",
  "id": "toolu_create_1",
  "name": "TaskCreate",
  "input": {
    "subject": "Implement login form UI",
    "description": "Create the login page form fields and layout",
    "activeForm": "Implementing login form UI"
  }
}
```

`TaskCreateTool.call()` 内部执行：

```text
createTask(getTaskListId(), taskData)
  → ensureTaskListLockFile()
  → lockfile.lock()
  → findHighestTaskId()
  → id = highest + 1
  → writeFile("1.json")
  → notifyTasksUpdated()
```

生成的文件类似：

```json
{
  "id": "1",
  "subject": "Implement login form UI",
  "description": "Create the login page form fields and layout",
  "activeForm": "Implementing login form UI",
  "status": "pending",
  "blocks": [],
  "blockedBy": []
}
```

模型继续创建其它任务后，目录可能变成：

```text
~/.claude/tasks/sess-002/
├── .lock
├── 1.json  Implement login form UI
├── 2.json  Add client-side validation
├── 3.json  Wire login submit API
└── 4.json  Run tests for login flow
```

和 V1 最大的区别是：V2 的每个任务都有稳定 ID，后续更新用 ID 定位。

### 第 2 步：模型把当前任务标成 in_progress

`TaskCreate` 只创建 `pending`。开始做第 1 项时，模型调用：

```json
{
  "type": "tool_use",
  "id": "toolu_update_1",
  "name": "TaskUpdate",
  "input": {
    "taskId": "1",
    "status": "in_progress"
  }
}
```

`TaskUpdateTool` 读取 `1.json`，合并更新并写回：

```json
{
  "id": "1",
  "subject": "Implement login form UI",
  "description": "Create the login page form fields and layout",
  "activeForm": "Implementing login form UI",
  "status": "in_progress",
  "blocks": [],
  "blockedBy": []
}
```

然后触发：

```text
notifyTasksUpdated()
  → useTasksV2 store 收到通知
  → listTasks(taskListId)
  → TaskListV2 重新渲染
```

终端 UI 看到的列表大致是：

```text
▪ Implement login form UI
□ Add client-side validation
□ Wire login submit API
□ Run tests for login flow
```

注意：源码层面没有强制“只能有一个 `in_progress`”。这是 prompt 约束和模型行为约定，不是 `TaskUpdateTool` 的硬校验。

### 第 3 步：完成一个任务并推进下一个任务

第 1 项完成后：

```json
{
  "type": "tool_use",
  "id": "toolu_update_2",
  "name": "TaskUpdate",
  "input": {
    "taskId": "1",
    "status": "completed"
  }
}
```

`TaskUpdateTool` 在真正写入前会执行 TaskCompleted hooks：

```text
executeTaskCompletedHooks(...)
  → 如果返回 blockingError，则拒绝完成
  → 否则 updateTask(..., { status: "completed" })
```

然后模型再调用：

```json
{
  "type": "tool_use",
  "id": "toolu_update_3",
  "name": "TaskUpdate",
  "input": {
    "taskId": "2",
    "status": "in_progress"
  }
}
```

UI 变成：

```text
✓ Implement login form UI
▪ Add client-side validation
□ Wire login submit API
□ Run tests for login flow
```

### 第 4 步：加入依赖和 owner

V2 可以表达 V1 没有的关系。例如测试必须等 API 接好：

```json
{
  "type": "tool_use",
  "id": "toolu_update_4",
  "name": "TaskUpdate",
  "input": {
    "taskId": "4",
    "addBlockedBy": ["3"]
  }
}
```

内部会调用：

```text
blockTask(taskListId, blockerId = "3", blockedId = "4")
```

结果是：

```json
{
  "file": "3.json",
  "id": "3",
  "blocks": ["4"]
}
```

```json
{
  "file": "4.json",
  "id": "4",
  "blockedBy": ["3"]
}
```

如果在 swarm 模式里把任务分配给 teammate：

```json
{
  "type": "tool_use",
  "id": "toolu_update_5",
  "name": "TaskUpdate",
  "input": {
    "taskId": "3",
    "owner": "frontend-worker"
  }
}
```

`TaskUpdateTool` 会把 owner 写入任务文件，并向对应 mailbox 写一条 `task_assignment`。这就是 V2 能服务多 agent 协作的原因。

### 第 5 步：全部完成后自动隐藏

当所有任务都变成 completed：

```text
TaskListV2 仍短暂显示完成状态
useTasksV2 检测到 all completed
  → 设置 5 秒 hide timer
  → 5 秒后再次 listTasks 确认仍然全部 completed
  → resetTaskList(taskListId)
  → 删除任务 json 文件
  → 写 .highwatermark 防止 ID 复用
  → hidden = true
```

最终：

```text
~/.claude/tasks/sess-002/
├── .lock
└── .highwatermark
```

UI 不再显示任务列表。下次再创建任务时，ID 会从 high water mark 后继续增长，而不是重新使用旧 ID。

## 两条模拟的本质差异

| 问题 | V1 TodoWrite | V2 Task tools |
|------|--------------|---------------|
| Todo 从哪来 | 模型一次提交完整 `todos` 数组 | 模型调用 `TaskCreate` 逐个创建 |
| 如何更新 | 再次提交完整数组，覆盖旧数组 | `TaskUpdate(taskId, fields)` 增量更新文件 |
| 状态主存储 | `AppState.todos[todoKey]` | `~/.claude/tasks/{taskListId}/{id}.json` |
| 是否有 ID | 没有 | 有 |
| 是否能表达依赖 | 不能 | `blocks` / `blockedBy` |
| 是否适合多 agent | 较弱，按 agentId 隔离 | 更强，可共享 taskListId、owner、mailbox |
| UI 来源 | 主要用于远程进度和 reminder | `useTasksV2` 文件监听后渲染 |
| 完成后清理 | 全 completed 时 AppState 写 `[]` | 全 completed 5 秒后 reset 文件列表 |
