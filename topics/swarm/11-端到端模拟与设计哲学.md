# 11 端到端模拟与设计哲学

> 收尾。先用一次完整的"team-lead 派 3 个 teammate 协作完成 task"推演把前 10 篇所有机制串成一条线，再总结 swarm 系统的设计哲学。

## 11.1 端到端推演：3-teammate 协作完成任务

### 场景

用户对 lead 说："Build a TypeScript SDK for our API. I want a researcher to study the API docs, a coder to implement, and a reviewer to check."

### T0：用户输入

Lead Claude Code 收到用户输入。Lead 模型看到任务，决定 spawn 一个团队。

### T1：TeamCreate

Lead 模型调 `TeamCreate({team_name: "sdk-build", description: "..."})`：

```ts
// TeamCreateTool.call() 执行:
const finalTeamName = generateUniqueTeamName("sdk-build")  // 假设没冲突 → "sdk-build"
const leadAgentId = formatAgentId(TEAM_LEAD_NAME, "sdk-build")
// → "team-lead@sdk-build"

// 写 ~/.claude/teams/sdk-build/config.json:
{
  "name": "sdk-build",
  "description": "Build TypeScript SDK",
  "createdAt": 1719857234234,
  "leadAgentId": "team-lead@sdk-build",
  "leadSessionId": "abc-uuid",
  "members": [
    {
      "agentId": "team-lead@sdk-build",
      "name": "team-lead",
      "agentType": "team-lead",
      "model": "claude-sonnet-4-6",
      "joinedAt": 1719857234234,
      "tmuxPaneId": "",
      "cwd": "/Users/me/project",
      "subscriptions": []
    }
  ]
}

// 创建 task list 目录:
// ~/.claude/tasks/sdk-build/

// AppState.teamContext = { teamName: "sdk-build", leadAgentId: "team-lead@sdk-build", ... }
```

### T2：TaskCreate × 3

Lead 调 TaskCreate 3 次创建 3 个 task：

```
TaskCreate({subject: "Research API docs and create design doc", owner: "researcher"})
TaskCreate({subject: "Implement TypeScript SDK", owner: "coder", blockedBy: [task#1]})
TaskCreate({subject: "Review SDK code", owner: "reviewer", blockedBy: [task#2]})
```

3 个 task 写到 `~/.claude/tasks/sdk-build/{1,2,3}.json`。

### T3：spawn 3 个 teammate

Lead 调 `Agent(team_name: "sdk-build", name: "researcher", prompt: "Research the API")`等 3 次（或一次 `Promise.all`）：

```ts
// AgentTool 在 team_name 提供时复用 spawnTeammate(config)

// handleSpawn 入口判断:
isInProcessEnabled() === true  // 假设用户在普通终端跑
→ handleSpawnInProcess
```

3 个 spawn 路径并发：

```ts
const results = await Promise.all([
  spawnTeammate({ name: "researcher", prompt: "...", teamName: "sdk-build", color: "red" }),
  spawnTeammate({ name: "coder", prompt: "...", teamName: "sdk-build", color: "blue" }),
  spawnTeammate({ name: "reviewer", prompt: "...", teamName: "sdk-build", color: "green" }),
])
```

每个 handleSpawnInProcess 内部：
1. `generateUniqueTeammateName`（同时三个名字都唯一 → 直接用）；
2. **append member 到 team config**（lockfile 保证并发安全）；
3. `spawnInProcessTeammate`：创建 TeammateContext + AbortController + InProcessTeammateTaskState；
4. `startInProcessTeammate`（fire-and-forget）：runner 在后台启动。

3 秒内 3 个 teammate 都 spawn 完毕。team config.json 现在有 4 个 member（lead + 3 teammate）。

### T4：teammate 启动并 claim 任务

每个 teammate 的 runner 启动：

```ts
// inProcessRunner.runInProcessTeammate
// (在 runWithTeammateContext context 内)

// 1. tryClaimNextTask("abc-uuid", "researcher"):
//    - listTasks → 3 个 task
//    - findAvailableTask: task#1 (无 blockedBy, pending) → 可认领
//    - claimTask(taskListId, 1, "researcher") → success
//    - updateTask: status = 'in_progress'
//    - return formatted prompt

// 2. while loop iteration 1:
//    - currentPrompt = wrappedInitialPrompt + claimed task prompt
//    - runAgent(...)  ← 这里跑模型 + 工具调用
```

3 个 teammate 各自 claim：
- researcher → task#1（无依赖）
- coder → 试图 claim 但 task#2 blockedBy task#1（未完成）→ idle 等
- reviewer → 同样 idle 等

researcher 开始工作。

### T5：researcher 工作 + 跨 teammate 通信

researcher 模型决定要读 API docs 文件——调 `FileRead` 工具。

```ts
// inProcessRunner 内的 canUseTool 被调用 (createInProcessCanUseTool)
// → 通过 permissionSync 把请求 forward 给 lead

// Worker side:
const reqId = generateRequestId()
await writePermissionRequest({
  id: reqId,
  workerId: "researcher@sdk-build",
  workerName: "researcher",
  teamName: "sdk-build",
  toolName: "FileRead",
  input: { file_path: "/path/to/api.md" },
  // ...
})
// 同时通过 mailbox 发 doorbell
await sendPermissionRequestViaMailbox(...)
// 然后 pollForResponse(reqId) 阻塞等...
```

### T6：lead 收到 permission_request

Lead 的 attachment surfacer 在下一轮 query loop 注入 mailbox 消息：

```
<teammate-message teammate_id="researcher">
{"type":"permission_request","request_id":"...","tool_name":"FileRead",...}
</teammate-message>
```

Lead 模型看到这条消息。但**lead 模型不直接决策**——Claude Code 的协议是 lead 模型把消息透传给用户（通过 UI 弹 ToolUseConfirm 对话框）。

`leaderPermissionBridge` 让 inProcessRunner 调到 REPL 的 `setToolUseConfirmQueue`——把 permission_request 加进对话框队列。

UI 显示："researcher wants to FileRead /path/to/api.md — Allow / Deny / Always Allow?"

用户点 Allow。

### T7：lead 写 resolved

REPL 处理用户响应：

```ts
await resolvePermission(reqId, {
  decision: 'approved',
  resolvedBy: 'leader',
  // updatedInput, permissionUpdates 都是空
})
// → 写 resolved/req.json
// → 删 pending/req.json
```

### T8：researcher 拿到 response

researcher 的 `pollForResponse` 轮询 `resolved/` 目录——500ms 内发现新文件，读取，返回：

```ts
return { decision: 'approved', updatedInput: undefined, permissionUpdates: undefined }
```

researcher 的 canUseTool 返回 `{ behavior: 'allow' }`——FileRead 真正执行，读到 API docs。

researcher 模型继续工作——写 design doc。

### T9：researcher 完成 turn

researcher 完成一轮工作（读、思考、写 design doc）。runner 进入 idle 状态：

```ts
// 5c. 更新 task.isIdle = true
updateTaskState(taskId, t => ({ ..., isIdle: true }), setAppState)

// 5e. 发 idle_notification 给 lead
await sendIdleNotification("researcher", "red", "sdk-build", {
  idleReason: 'available',
  summary: "Created design.md with API analysis",
  completedTaskId: "1",
  completedStatus: 'resolved',
})

// 5f. waitForNextPromptOrShutdown - 阻塞等下个事件
```

researcher 的 task#1 现在 status='completed'。

### T10：lead 收到 idle_notification

Lead 下一轮 query loop 看到：

```
<teammate-message teammate_id="researcher" summary="Created design.md with API analysis">
{"type":"idle_notification","from":"researcher","idleReason":"available","completedTaskId":"1","completedStatus":"resolved",...}
</teammate-message>
```

UI 显示 spinner 旁边一行 "researcher: idle"（[06 协议消息](./06-协议消息状态机.md) 提过 IdleNotification 的 UI 处理）。

Lead 模型看到 task#1 done → coder 现在可以开始（task#2 不再 blocked）。

### T11：coder 自动 claim task#2

coder 一直在 idle loop 里轮询。`tryClaimNextTask` 在每轮 500ms 后试着 claim：

```
轮询 1 (500ms 前): task#2 blockedBy task#1 (in_progress) → 不能 claim
轮询 2 (现在): task#2 blockedBy task#1 (completed) → 可以 claim!
```

coder claim task#2，开始 implement。

**注意**：没人显式告诉 coder 开工——它自己通过 task list 状态自动 claim。这是**异步协调**的核心——没有"lead 派活到 coder"的显式动作，coder 自己感知任务可用。

### T12：coder 工作几个 turn

coder 跑很多个 turn——每次 turn 之间 send idle_notification + wait for new prompt。

实际上 coder 在**同一个 turn** 内做完所有 implementation（理想情况）——但即使分多 turn 也没关系，task list 一直存在。

coder 完成 task#2 → idle_notification → lead 看到。

### T13：reviewer 自动 claim task#3

同样自动——reviewer 在 idle loop 里看到 task#2 完成 → claim task#3 → 开始 review。

### T14：reviewer 发现问题 → 给 coder 发消息

reviewer 看 coder 写的代码，发现一个 bug。调用 SendMessage：

```ts
await sendMessage({
  to: "coder",
  summary: "found bug in auth.ts",
  message: "Line 42 has a typo: `aithenticate` should be `authenticate`",
})
```

**这是 peer-to-peer 消息**——不通过 lead 转发。reviewer 直接写到 coder 的 inbox。

```ts
// SendMessageTool.call:
await writeToMailbox("coder", {
  text: "Line 42 has a typo: ...",
  from: "reviewer",
  color: "green",
  summary: "found bug in auth.ts",
}, "sdk-build")
```

### T15：coder 收到消息

coder 在 idle loop 里**等下一个 prompt**——`waitForNextPromptOrShutdown` 看到 mailbox 有未读消息。

返回 `{ kind: 'next_prompt', prompt: formatAsTeammateMessage(...) }`。

coder 进入 new turn，prompt 是 reviewer 的消息。模型理解需要修 typo，调 FileEdit 修改 auth.ts。

修完后 coder send idle_notification + 给 reviewer 发"done" 消息。

### T16：reviewer 拿到 "done" 通知

reviewer 在 idle loop 收到 coder 的"done"消息——重新检查代码，确认 typo 已修。

reviewer 决定 task#3 完成，调 TaskUpdate(task#3, {status: 'completed'}).

reviewer send idle_notification 给 lead，说 "All tasks completed".

### T17：lead 看到所有 task done

Lead 看到 reviewer 的 idle_notification：

```
{"type":"idle_notification","summary":"All tasks completed","completedTaskId":"3","completedStatus":"resolved"}
```

Lead 模型查看 task list——3 个都 done。决定 shutdown 团队：

### T18：lead 发 shutdown_request × 3

Lead 调 SendMessage 给每个 teammate：

```ts
await sendMessage({
  to: "researcher",
  message: { type: "shutdown_request", reason: "All tasks done" }
})
// 同样给 coder, reviewer
```

实际上调 `sendShutdownRequestToMailbox(name)` 是更标准的方式。

3 个 shutdown_request 写到对应 inbox。

### T19：teammate 收到 shutdown 决定 approve

每个 teammate 在 idle loop 里收到 `shutdown_request`：

```ts
const shutdownReq = isShutdownRequest(msg.text)
if (shutdownReq) {
  // 决定是否 approve
  // researcher 的任务已完成 → approve
  await sendMessage({
    to: "team-lead",
    message: {
      type: "shutdown_response",
      request_id: shutdownReq.requestId,
      approve: true,
    }
  })
  // SendMessageTool 内部 trigger gracefulShutdown
  // → 进程退出 (in-process: AbortController.abort())
}
```

3 个 teammate 各自 approve、各自退出。

### T20：lead 等所有 teammate idle 后 TeamDelete

Lead 调 `waitForTeammatesToBecomeIdle` 等所有 teammate task status = 'completed'/'killed'：

```ts
// (实际上 in-process teammate approve shutdown 后 task status → 'completed')
await waitForTeammatesToBecomeIdle(setAppState, appState)
// 全部 idle 后:
await TeamDelete()
// → cleanupTeamDirectories ('sdk-build')
// → 删除 ~/.claude/teams/sdk-build/
// → 删除 ~/.claude/tasks/sdk-build/
// → AppState.teamContext = undefined
```

团队结束。Lead 报告用户："SDK build complete. All 3 tasks done."

## 11.2 推演总结：20 个步骤、~5 分钟实际时间

完整流程 20 步，实际墙钟时间 ~5 分钟（取决于 task 复杂度）：

```
T0  用户输入             (0s)
T1  TeamCreate           (1s)
T2  TaskCreate × 3       (3s)
T3  spawn 3 teammate     (5s)
T4  teammate claim task  (5.5s)
T5  researcher 跑工具    (10s, FileRead permission flow)
T6  lead 收 permission   (10.5s)
T7  lead 写 resolved     (12s, 用户点 allow)
T8  researcher 拿到      (12.5s)
T9  researcher 完成 task#1 (60s)
T10 lead 收 idle         (60.5s)
T11 coder claim task#2   (61s)
T12 coder 工作           (180s)
T13 reviewer claim task#3 (181s)
T14 reviewer DM coder    (200s, 发现 bug)
T15 coder 收到、修复     (210s)
T16 reviewer 确认        (220s)
T17 lead 看到 all done    (220.5s)
T18 lead 发 shutdown × 3 (221s)
T19 teammate approve     (222s)
T20 TeamDelete           (225s)

合计 ~225s ≈ 3.75 min
```

## 11.3 关键观察

### 1. 没有显式"派活"动作

researcher 完成 task#1 后，**coder 自己感知**到 task#2 可以开始——通过 task list 的 blockedBy 关系。

如果是同步派活模式：lead 必须显式调 SendMessage("coder", "start task#2")。这增加 lead 的协调负担。

异步感知模式让 lead 只需要"创建任务"——teammate 自己流转。

### 2. peer-to-peer 通信

reviewer 给 coder 发消息**不通过 lead 转发**——直接写 coder inbox。

这避免 lead 成为单点瓶颈——peer 之间能直接交流。

### 3. permission flow 全程透明

researcher 跑 FileRead 时：
- researcher 自己不知道权限决策在哪里发生；
- lead 看到 mailbox notification 但模型不决策；
- 用户在 UI 弹窗里看到、决定；
- 整个流程对 researcher 模型透明——它只看到工具调用成功或失败。

**关注点分离**——每个角色只看到自己关心的。

### 4. idle/active 状态自动维护

每个 turn 结束 task.isIdle = true、下个 turn 开始前重置——状态自动维护，不需要外部干预。

### 5. shutdown 是 graceful 不是 kill

lead 不能直接 kill teammate——发 shutdown_request 让 teammate 自己决定。teammate 可能在 mid-task 拒绝。

只有 TeamDelete 强制清理目录时才会强制 kill 剩下的 teammate。**协议优先于强制**。

### 6. team config 是单一权威源

所有 spawn / shutdown 都更新 team config——任何时候读这个文件能知道团队完整状态。

lockfile 保证并发更新一致——多个 spawn 同时改 members 数组不会丢数据。

### 7. file system 是协调介质

mailbox（inbox 文件）、permission（pending/resolved 文件）、task list（task json）、team config（config.json）——全部走文件系统。

**没有进程间通信库**（gRPC / 消息队列 / etc）。文件系统 + lockfile = 标准 unix 工具。简洁、可观察、可 resume。

代价：延迟（轮询 500ms）。但人类级交互场景下完全够用。

## 11.4 设计哲学：actor model vs RPC model

总结 swarm 系统体现的设计哲学：

### 1. teammate 是 actor 不是 function

actor 长期运行、有 mailbox、并发处理消息。function 短期调用、同步返回值、调用方阻塞等。

| 维度 | actor (swarm teammate) | function (sub-agent) |
|------|------------------------|---------------------|
| 生命周期 | 长 | 短 |
| 状态 | 有，跨调用持久 | 无（每次新建） |
| 通信 | 异步 message | 同步 RPC |
| 调用方 | 不阻塞等待 | 阻塞等返回 |
| 多个并发 | 自然并发 | 显式 Promise.all |

actor 模型适合"长期协作"，function 模型适合"一次性请求"。Claude Code 两者都有——AgentTool 走 function 模式、swarm 走 actor 模式。

### 2. 协议而不是 API

swarm 的"协议消息"（shutdown_request / plan_approval / permission）是**自描述的 JSON 状态机**——不是 RPC API。

API：调用方调 `terminateTeammate()`，被调方立刻终止。
协议：调用方写 `{type: 'shutdown_request', requestId}`，被调方读、决策、可能 approve 或 reject。

协议的**异步性 + 协商性**让 teammate 有自主权——不是简单的"被动执行命令"。

### 3. file-based IPC

mailbox / permissionSync 都是文件——而不是 socket / pipe / shared memory。

文件协议的优势：
- 跨进程跨终端可用；
- 不需要服务进程；
- 可 resume（重启后状态仍在）；
- 可审计（事后看文件能 reconstruct 历史）；
- 用 lockfile 处理并发——标准工具。

代价：延迟（轮询）+ 文件 IO 开销。**简洁性优先于性能**。

### 4. 中心化协调 + 去中心化执行

**lead 是协调者**：UI / 权限决策 / 团队管理。
**teammate 是执行者**：独立跑自己的工作，peer-to-peer 通信。

这种**hybrid 模型**结合 hierarchy 和 mesh 的优势：
- hierarchy 让用户体验简单（一个 lead 对话窗口）；
- mesh 让 teammate 不需要全部消息走 lead（避免瓶颈）。

### 5. 多 backend 共享接口

`TeammateExecutor` 接口让上层不关心底下是 tmux / iTerm2 / in-process。换 backend 不改业务代码。

这种 strategy pattern 在新型系统里很少见——但在 swarm 这种"多用户环境"下必要（用户在不同 terminal 环境）。

### 6. AsyncLocalStorage 让 in-process 成为可能

没有 AsyncLocalStorage，同进程多 teammate 不可能（globals 互相覆盖）。

Node 18+ 的这个特性是 in-process swarm 的**技术基础**——这种新 API 在 LLM agent 系统中找到了完美用例。

### 7. graceful 优先于 forceful

shutdown_request 让 teammate 自己决定（可 reject）；plan_approval 让 worker wait response；permission forward 给 lead 决策。

**没有"调用方强制被调方做事"** —— 每个角色都有自主权。这种**协议化的尊重**避免 race condition 和 partial state。

代价：发起方必须**容忍等待和拒绝**。但这是 distributed system 的现实——异步通信不能假设瞬时响应。

### 8. 中心化身份 + 分布式状态

- **身份**集中：team config 单一权威源；
- **状态**分散：每个 teammate 自己持有 mailbox / task / context；

这种**身份 vs 状态**的解耦让 add/remove teammate 不影响其它 teammate 状态——只更新 team config 即可。

### 9. 自动化协调

task list 的 blockedBy 自动让依赖管理工作 —— teammate 自己感知任务可用。

不需要 lead 显式派活，不需要每个 teammate 主动询问 lead "我下一步干啥"。

这种**emergent coordination** 是 actor 模型的核心优势——任务通过环境（task list 文件状态）自然流转。

### 10. 文件系统作为协调介质

整个 swarm 用文件系统作为协调中心——而不是任何专门的 broker / database / framework。

理由：
- Unix 哲学；
- 跨进程跨终端开箱即用；
- 用户机器永远有；
- 标准工具（lockfile / mtime）够用；
- 调试简单（cat 文件就能看到状态）；
- 可 resume / replay。

这种**用最简单工具构建复杂系统**的设计是 Claude Code 整体审美的体现。

## 11.5 关键设计取舍

整个 swarm 的关键取舍可以浓缩成几对：

| 选择 | 优先什么 | 代价 |
|------|---------|------|
| file-based IPC | 简洁、跨进程、可 resume | 轮询延迟 |
| graceful shutdown | 自主权、避免 partial state | 拒绝可能性、wait 等待 |
| AsyncLocalStorage in-process | 不依赖 tmux/iTerm2 | 同进程 teammate 间无 OS 隔离 |
| 中心化 lead 权限决策 | UI 统一、共享 rules | 单点延迟（permission 必走 lead） |
| 中心化 team config | 单一权威源 | lockfile 并发瓶颈 |
| peer-to-peer 消息 | 不通过 lead 中转 | 没有 lead 监督（peer DM 不被审查） |
| 轮询 (500ms) 而非事件驱动 | 简洁 | 平均 250ms 延迟 |
| 显式 mode（auto/tmux/in-process） | 用户可控 | 用户得知道 mode 区别 |

每个选择都有具体的理由——不是"看起来酷"，而是"实际场景下平衡 trade-off"。

## 11.6 与其它专题的最终关系

swarm 在 Claude Code 系统里的位置：

```
┌─────────────────────────────────────────────────────────────┐
│ User (一个用户)                                              │
└────────────────────┬────────────────────────────────────────┘
                     │
        ┌────────────▼────────────┐
        │   Lead Claude Code      │  (REPL / UI / 单点交互)
        │  • UI 渲染              │
        │  • 权限对话框           │
        │  • Lead 模型决策         │
        │  • TeamCreate / Delete  │
        └────┬──────────────┬─────┘
             │              │
   ┌─────────▼───┐  ┌───────▼──────┐
   │ Sub-agent   │  │ Swarm        │  ← 不同模式
   │ (AgentTool) │  │ Teammates    │
   │             │  │              │
   │ • function  │  │ • actors     │
   │ • RPC       │  │ • async msg  │
   │ • sync      │  │ • mailbox    │
   └─────────────┘  └──────┬───────┘
                           │
                  ┌────────┼────────┐
                  ▼        ▼        ▼
              ┌──────┐ ┌──────┐ ┌──────┐
              │teammate│ │teammate│ │teammate│
              │  A    │ │  B   │ │  C   │
              └──────┘ └──────┘ └──────┘

底下用到的子系统:
  - [agent] AgentTool 派发（spawnMultiAgent 复用）
  - [messages-pipeline] teammate_mailbox / team_context attachment
  - [prompt-injection] <teammate-message> 标签防混淆
  - [bashtool] worker 工具权限走 leader (permission sync)
  - [todolist] task list 共享与 V2 任务管理
  - [overview 09] memory 的 team scope
  - [skill] teammate 也能用 skill (但 skill 不跨 teammate 共享)
```

Swarm 是 **agent 系统之上的协调层** —— 复用 agent / messages-pipeline / prompt-injection / bashtool / todolist 等基础设施，加上**团队管理 + 异步通信 + 中心化协调**让多个 Claude 实例长期协作。

## 11.8 收尾思考

读完 swarm 专题，最有价值的几条总结：

### 1. actor model 在 LLM agent 系统的应用

Claude Code 的 swarm 是少有的**production-ready 的 LLM actor system**。它体现：
- LLM 可以作为长期运行的 actor（不只是请求-响应）；
- 异步消息可以替代同步函数调用；
- 多 LLM 可以协调任务（通过 task list 自动流转）；
- file-based IPC 在 LLM 场景下足够。

### 2. AsyncLocalStorage 让 in-process 隔离成为基础设施

Node 18+ 的这个特性可能是 LLM agent 系统最大的赋能 API——让"一个进程多个 agent"从不可能变成 339 行代码（InProcessBackend）。

未来 LLM agent 系统大概率都会用这个 pattern。

### 3. 协议优于 API

shutdown / plan_approval / permission 都不是 simple RPC——而是 request/response 状态机。让 teammate 有 **拒绝权和决策权**。

这种**协议化交互**比 simple function calling 更适合 LLM agent—— LLM 本身就有判断能力，不该被简单"调用"。

### 4. 文件系统是最简协调介质

用 lockfile + JSON 文件做协调，避免引入 broker / database。**Unix 哲学在 LLM agent 系统的复兴**——简单工具组合能解决复杂问题。

### 5. 关注点分离的极致

- backend 不知道协议；
- 协议不知道 backend；
- runner 不知道 mailbox 内部结构；
- mailbox 不知道协议消息含义；
- permission sync 不知道 mailbox doorbell 实现；
- 每一层只关心自己的责任。

10K 行代码的复杂性主要来自**协调多个独立子系统**，而不是任何单一子系统的复杂度。每个子系统都相对简单（200-1500 行）。

### 6. 显式 + 注释承载历史

每个 feature 注释里能看到：
- 为什么这样设计；
- 替代方案为什么被否决；
- 历史 bug 或 trade-off；
- 与其它系统的协议契约。

这种**自描述的代码**是工业级 LLM 项目的标志——大型协作开发的必要条件。
