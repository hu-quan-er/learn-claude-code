# 06 协议消息状态机

> teammate 之间的"自由聊天"里嵌入了一套**显式状态机**——`shutdown_request` 必须配对 `shutdown_approved`/`rejected`、`plan_approval_request` 必须配对 `plan_approval_response`、`request_id` echo 让请求和响应能 match。本篇拆这套"嵌在自由文本里的协议"。

## 6.1 为什么需要嵌入式协议

回顾 [05 消息系统](./05-消息系统与SendMessage.md)：mailbox 里的消息字段是 `text: string`——纯文本。teammate 之间大部分通信确实是自由文本（"我做完了"、"帮我检查 X"）。

但有些场景需要**结构化交互**：

- **shutdown**：leader 要求 teammate 关闭——teammate 可能在 mid-turn 不能立刻退，需要 approve/reject 协议；
- **plan approval**：teammate 在 plan mode 下生成了 plan，需要 leader 批准才能 implement——必须 wait response；
- **permission request**：worker 想跑工具但本地没权限决策——必须 wait leader response。

这些场景需要 **request/response 配对**——但 mailbox 只是 string 列表。怎么办？

Claude Code 的解法：**把 JSON 协议消息嵌入到 message.text 字符串里**。reader 通过 `try-parse + schema validate` 检测出哪些消息是协议消息。

## 6.2 5 对 request/response 协议消息

`teammateMailbox.ts` 定义了 5 对协议消息（部分对在 5.12 节列过）：

| 配对 | 发起方 | request | response（如有） |
|------|--------|---------|-----------------|
| shutdown | leader | `shutdown_request` | `shutdown_approved` 或 `shutdown_rejected` |
| plan approval | worker | `plan_approval_request` | `plan_approval_response` |
| permission | worker | `permission_request` | `permission_response` |
| sandbox permission | worker | `sandbox_permission_request` | `sandbox_permission_response` |
| idle notification | worker | `idle_notification` | (无 response) |

注意 5 对里有 3 对**双向**——必须 wait response 才能完成动作。idle_notification 是单向的。

## 6.3 shutdown 状态机详解

### 数据 schema

```ts
// teammateMailbox.ts:720-768
export const ShutdownRequestMessageSchema = lazySchema(() =>
  z.object({
    type: z.literal('shutdown_request'),
    requestId: z.string(),
    from: z.string(),
    reason: z.string().optional(),
    timestamp: z.string(),
  }),
)

export const ShutdownApprovedMessageSchema = lazySchema(() =>
  z.object({
    type: z.literal('shutdown_approved'),
    requestId: z.string(),
    from: z.string(),
    timestamp: z.string(),
    paneId: z.string().optional(),       // 让 leader 知道哪个 pane 要清理
    backendType: z.string().optional(),  // 让 leader 知道用哪个 backend kill
  }),
)

export const ShutdownRejectedMessageSchema = lazySchema(() =>
  z.object({
    type: z.literal('shutdown_rejected'),
    requestId: z.string(),
    from: z.string(),
    reason: z.string(),       // reject 必须给理由 (require!)
    timestamp: z.string(),
  }),
)
```

注意 `reason` 在 `request` 是可选、在 `rejected` 是**必需**。设计语义：

- request 不一定有理由（"我们做完了"是普通退场）；
- reject 必须给理由（teammate 拒绝必须解释为什么）。

## 6.4 SendMessageTool 对 shutdown_response 的特殊处理

`SendMessageTool.ts:520+` 是工具实现。处理 shutdown_response 时**不仅仅是发消息**——还要触发 teammate 自己的 gracefulShutdown。

伪代码（从代码片段推断）：

```ts
// SendMessageTool 收到 input:
// { to: 'team-lead', message: { type: 'shutdown_response', request_id, approve: true } }

if (message is shutdown_response && approve === true) {
  // 1. 把 shutdown_response 送到 lead 的 inbox
  await writeToMailbox('team-lead', { text: JSON.stringify(message), ... })

  // 2. 立刻触发自己的 gracefulShutdown
  await gracefulShutdown()
  // 进程退出, 这一调用不返回
}

if (message is shutdown_response && approve === false) {
  // 1. 把 shutdown_response (reject) 送到 lead 的 inbox
  await writeToMailbox('team-lead', { text: JSON.stringify(message), ... })

  // 2. 不退出, 继续工作
}
```

这种 **"工具调用副作用与消息发送绑定"** 的设计让协议状态机变得简单——模型只要按 prompt 教育的方式发消息，gracefulShutdown 自动发生。

`SendMessageTool/prompt.ts` 里教育模型：

```
Approving shutdown terminates your process. Rejecting plan sends the teammate back to revise. Don't originate shutdown_request unless asked. Don't send structured JSON status messages — use TaskUpdate.
```

明确告诉模型 approve = 进程终止——这不是 hint，是**协议规则**。

## 6.5 request_id —— 状态机的 join key

每个 request 有 `requestId` / `request_id` 字段（schema 里是 camelCase，input 里是 snake_case），response 必须 echo 同一个值。

### 生成

`teammateMailbox.ts:842`：

```ts
const requestId = generateRequestId('shutdown', targetName)
```

`generateRequestId('shutdown', 'researcher')` 返回类似 `shutdown-researcher-1719857234234-abc123`——含类型、目标、时间戳、随机后缀。

### 用途

| 用途 | 谁用 |
|------|------|
| 配对 request/response | leader / worker |
| 去重重复 response | leader |
| 关联日志条目 | analytics / debugging |
| 防 race condition（多个并发请求） | 协议层 |

### 为什么不用 lock + 顺序

替代设计：让 leader 一次只发一个 shutdown request、等 response 再发下一个——这样不需要 requestId。

但实际上 leader 可能**同时**给多个 teammate 发 shutdown（如 TeamDelete 前清理）——三个 teammate 各收一个 request。response 可能乱序回来。**requestId 让乱序仍能正确配对**。

## 6.6 plan_approval 状态机

```ts
// teammateMailbox.ts:684-715
export const PlanApprovalRequestMessageSchema = lazySchema(() =>
  z.object({
    type: z.literal('plan_approval_request'),
    from: z.string(),
    timestamp: z.string(),
    planFilePath: z.string(),        // plan 文件路径
    planContent: z.string(),         // plan 全文
    requestId: z.string(),
  }),
)

export const PlanApprovalResponseMessageSchema = lazySchema(() =>
  z.object({
    type: z.literal('plan_approval_response'),
    requestId: z.string(),
    approved: z.boolean(),
    feedback: z.string().optional(),       // 提反馈让 teammate 改进
    timestamp: z.string(),
    permissionMode: PermissionModeSchema().optional(),  // 批准后切换的 permission mode
  }),
)
```

注意 `request` 字段名是 `approved`（schema 里），但 `SendMessageTool.StructuredMessage` 里是 `approve`（用户输入字段）：

```ts
z.object({
  type: z.literal('plan_approval_response'),
  request_id: z.string(),
  approve: semanticBoolean(),     // ← 输入用 approve
  feedback: z.string().optional(),
})
```

这是**输入接口 vs 内部 schema 不一致**——`SendMessageTool` 收到 `{approve: true}` 后内部转成 `{approved: true}`。

为什么？因为模型输入用 `approve`（更直观），内部 schema 用 `approved`（更正确）。SendMessageTool 做个适配。

### plan_approval 流程

```
状态: TEAMMATE IN PLAN MODE (生成了 plan)
                          │
                          ▼
        ┌──────────────────────────────────────┐
        │ Teammate 发 plan_approval_request:    │
        │ - planFilePath: ~/.claude/plans/...   │
        │ - planContent: full plan text         │
        │ - requestId                            │
        └────────────────┬─────────────────────┘
                         │
                         ▼
              Leader inbox 收到
                         │
                         ▼
        ┌──────────────────────────────────────┐
        │ Lead 模型看到 plan_approval_request   │
        │ + plan 内容                            │
        │ + UI 可能弹 dialog 给用户决定          │
        └────────────────┬─────────────────────┘
                         │
        ┌────────────────┴────────────────┐
        ▼                                 ▼
    用户批准                         用户拒绝 / 要修改
        │                                 │
        ▼                                 ▼
   Lead 发 plan_approval_response:   Lead 发 plan_approval_response:
   { approve: true,                  { approve: false,
     permissionMode: 'auto' }          feedback: '加错误处理' }
        │                                 │
        ▼                                 ▼
   Teammate 收到 → 退出 plan mode    Teammate 收到 → 修改 plan, 再次请求
   开始 implement                     循环直到 approved

```

`permissionMode` 字段是个**有趣的副效应通道**——leader 批准 plan 时可以**同时切换** teammate 的 permission mode。例如批准 plan 后从 `default` 切到 `auto`（无需后续每个工具问），让 teammate 一气呵成实现。

## 6.7 isXxx 解析器函数

`teammateMailbox.ts:868-948` 提供 5 个判定函数：

```ts
export function isShutdownRequest(messageText: string): ShutdownRequestMessage | null {
  try {
    const result = ShutdownRequestMessageSchema().safeParse(jsonParse(messageText))
    if (result.success) return result.data
  } catch {}
  return null
}

export function isShutdownApproved(messageText: string): ShutdownApprovedMessage | null { ... }
export function isShutdownRejected(messageText: string): ShutdownRejectedMessage | null { ... }
export function isPlanApprovalRequest(messageText: string): PlanApprovalRequestMessage | null { ... }
export function isPlanApprovalResponse(messageText: string): PlanApprovalResponseMessage | null { ... }
```

每个函数：

1. `jsonParse(messageText)`——失败返回 null（不是 JSON）；
2. `Schema.safeParse(parsed)`——校验是不是符合 schema；
3. 通过 → 返回类型化的对象；不通过 → 返回 null。

**双重检查**：JSON parse + schema validate。这避免误把"恰好是 JSON 但不是协议消息"的内容当协议处理。

用法：

```ts
// 接收方扫描 mailbox 时:
for (const msg of unreadMessages) {
  const shutdownReq = isShutdownRequest(msg.text)
  if (shutdownReq) {
    handleShutdownRequest(shutdownReq)
    continue
  }

  const planReq = isPlanApprovalRequest(msg.text)
  if (planReq) {
    handlePlanApprovalRequest(planReq)
    continue
  }

  // ... 其它类型
  // 否则当作普通文本消息处理
}
```

这是**enum-by-shape** 模式——多个独立 isXxx 判定，第一个匹配的处理掉。

## 6.8 sendShutdownRequestToMailbox —— 可复用的发送 helper

`teammateMailbox.ts:831-863`：

```ts
export async function sendShutdownRequestToMailbox(
  targetName: string,
  teamName?: string,
  reason?: string,
): Promise<{ requestId: string; target: string }> {
  const resolvedTeamName = teamName || getTeamName()
  const senderName = getAgentName() || TEAM_LEAD_NAME
  const requestId = generateRequestId('shutdown', targetName)

  const shutdownMessage = createShutdownRequestMessage({
    requestId,
    from: senderName,
    reason,
  })

  await writeToMailbox(
    targetName,
    {
      from: senderName,
      text: jsonStringify(shutdownMessage),
      timestamp: new Date().toISOString(),
      color: getTeammateColor(),
    },
    resolvedTeamName,
  )

  return { requestId, target: targetName }
}
```

注释说："This is the core logic extracted for reuse by both the tool and UI components."

**让 tool 和 UI 都能调**——SendMessageTool 调它；UI 上"shutdown"按钮也调它。统一入口让 shutdown 发起的行为一致。

注意 `senderName = getAgentName() || TEAM_LEAD_NAME`——如果当前是 teammate（`getAgentName()` 返回 'researcher' 等），用 agent name；否则当 lead 发的（用 `TEAM_LEAD_NAME`）。

## 6.9 collapseTeammateShutdowns —— UI 折叠多个 shutdown

当 lead 同时 shutdown 多个 teammate 时（如 TeamDelete），UI 会收到多个 `task_status: completed` attachment。一个一个显示会刷屏。

`utils/collapseTeammateShutdowns.ts` 实现 UI 折叠：

```ts
function isTeammateShutdownAttachment(msg: RenderableMessage): msg is AttachmentMessage {
  return (
    msg.type === 'attachment' &&
    msg.attachment.type === 'task_status' &&
    msg.attachment.taskType === 'in_process_teammate' &&
    msg.attachment.status === 'completed'
  )
}

export function collapseTeammateShutdowns(messages: RenderableMessage[]): RenderableMessage[] {
  const result: RenderableMessage[] = []
  let i = 0
  while (i < messages.length) {
    const msg = messages[i]!
    if (isTeammateShutdownAttachment(msg)) {
      let count = 0
      while (i < messages.length && isTeammateShutdownAttachment(messages[i]!)) {
        count++
        i++
      }
      if (count === 1) {
        result.push(msg)
      } else {
        result.push({
          type: 'attachment',
          uuid: msg.uuid,
          timestamp: msg.timestamp,
          attachment: { type: 'teammate_shutdown_batch', count },
        })
      }
    } else {
      result.push(msg)
      i++
    }
  }
  return result
}
```

55 行函数做一件事：**连续的 shutdown 状态变化合并成一条 `teammate_shutdown_batch` attachment**。

UI 渲染：
- 单条：`researcher: idle (shutdown)`
- 多条：`3 teammates shutdown`

这是**UI 层的 message collapsing**——和 [messages-pipeline 04 smoosh](../messages-pipeline/04-合并smoosh与hoist三连击.md) 是同一类思路：相邻同类消息合并避免噪声。区别：

- smoosh 在 API 层（防模型学到坏 pattern）；
- collapseTeammateShutdowns 在 UI 层（防用户看到刷屏）。

## 6.10 协议消息字段的 4 个一致性原则

读 5 对协议消息的 schema，可以提炼字段命名规则：

| 字段 | 含义 | 始终存在 |
|------|------|---------|
| `type` | 消息类型字面值（discriminator） | ✓ |
| `requestId` | request 标识 | request + response 都必有 |
| `from` | 发送者 | ✓ |
| `timestamp` | ISO 时间戳 | ✓ |
| `reason` | 解释（可选 / 必需） | shutdown_request 可选、shutdown_rejected 必需 |
| `approve` / `approved` | 决策 | response 必有 |
| 其它扩展字段 | 类型特定 | 按需 |

**`type` + `requestId` + `from` + `timestamp` 是 4 个基础字段**——所有协议消息都有。这种统一**让通用 helper（如日志、UI 渲染）能处理任何协议消息**而不需要类型特定逻辑。

## 6.11 协议消息的 5 个设计判断

读完整套协议，可以抽出 5 条经验：

### 1. 嵌入 JSON 而不是扩展 schema

mailbox 的 `text: string` 字段不变——协议消息用 JSON.stringify 嵌入。这避免：
- mailbox schema 频繁演化（每加一种协议消息要改 mailbox 字段）；
- 跨进程兼容性问题（schema 版本不一致时读不出新字段）。

代价：reader 要 try-parse 检测。但提供了 isXxx helper 封装。

### 2. 每个协议消息独立 schema

5 对 = 10 个独立 schema。没有共享 base 类（虽然有 4 个共同字段）。理由：

- 每种消息的字段约束不同（`reason` 在 reject 是必需、在 request 可选）；
- Zod schema 不易做强继承；
- 显式重复让每个 schema 自包含、可单独阅读。

工程权衡——DRY vs explicit。这里选了 explicit。

### 3. requestId 让乱序响应能配对

不假设串行——允许 leader 并发发多个 request、worker 同样能并发处理。requestId 作为 join key。

### 4. 副效应字段嵌入响应消息

`plan_approval_response` 带 `permissionMode` —— 批准 plan 同时切换权限模式。这种**piggyback** 副效应让一次响应做多件事——避免后续再发一个独立消息。

### 5. UI 层 collapsing 防刷屏

UI 显示和 API 表达分离。API 层产生 N 个独立 shutdown 状态变化、UI 层 collapse 成一条。

## 6.12 整体协议流程对比

把 3 种 request/response 协议放一起看相似性：

```
┌──── shutdown (leader 发起) ────────────────────────────┐
│ Leader → Worker: shutdown_request                       │
│ Worker → Leader: shutdown_approved / shutdown_rejected  │
└─────────────────────────────────────────────────────────┘

┌──── plan_approval (worker 发起) ────────────────────────┐
│ Worker → Leader: plan_approval_request                  │
│ Leader → Worker: plan_approval_response (approved: T/F) │
└─────────────────────────────────────────────────────────┘

┌──── permission (worker 发起) ───────────────────────────┐
│ Worker → Leader: permission_request                     │
│ Leader → Worker: permission_response (subtype: success/error) │
└─────────────────────────────────────────────────────────┘
```

3 个模式一致：

1. **request 含 `requestId`**；
2. **response echo 同 `requestId`**；
3. **request/response 异步、不必立即响应**（leader 可能在弹用户对话框）；
4. **state 转换在 response 处理时发生**（不在 request 发出时）。

这是个**典型的 actor-based async RPC** 模式。

## 6.14 小结

- 协议消息嵌入到 mailbox 的 `text: string` 里——避免 mailbox schema 频繁演化；
- 5 对协议：shutdown / plan_approval / permission / sandbox_permission / idle_notification；
- 每对 request 含 `requestId`，response echo 让乱序配对；
- shutdown_response approve 时 SendMessage 工具内部 trigger gracefulShutdown——副作用与发送绑定；
- plan_approval_response 可携带 `permissionMode` 让一次响应做多件事（piggyback）；
- isXxx 函数用 JSON parse + Zod schema 双重检查；
- `sendShutdownRequestToMailbox` 是 tool 和 UI 共享的发送 helper；
- `collapseTeammateShutdowns` 在 UI 层合并连续 shutdown 通知防刷屏；
- 4 基础字段（type / requestId / from / timestamp）让通用 helper 能处理所有协议消息；
- 整体是 actor-based async RPC——request 异步、response 携带 state 转换、不假设立即响应。
