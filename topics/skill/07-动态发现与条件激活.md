# 07. 动态发现与条件激活 — skill 怎么"在用过程中长出来"

> 这一篇做一件事：把"skill 不仅是启动期一次性装的、还能在会话过程中动态出现"这套机制的全部代码路径走通。
>
> 接 03 篇段 4：03 篇讲了 `discoverSkillDirsForPaths` / `addSkillDirectories` / `activateConditionalSkillsForPaths` 这三个函数本身。这一篇讲它们**被谁调用、为什么要分开、新发现的 skill 怎么通知模型**。

---

## 1. 为什么要"动态发现"

回想 03 篇段 3 的 `getSkillDirCommands`——它用 `getProjectDirsUpToHome('skills', cwd)` 从 cwd 一路向上扫到 git root。

但**它不向下扫**。这是个有意的设计：

- 一个大型 monorepo 可能有几十个子项目，每个子项目都有自己的 `.claude/skills/`
- 启动时把所有子项目的 skill 全装进来 → 启动慢 + skill 列表过长 + 浪费 token budget
- 用户大概率只工作在某一个子项目里

所以装载层只装"当前 cwd 视角能看到的"。**子目录的 skill 等到模型真的"深入"那个子目录时再装**——这就是动态发现。

类比：think of it as lazy loading by directory locality。

```
project/
├── .claude/skills/         ← 启动期加载
│   └── shared-skill/
├── frontend/
│   └── .claude/skills/     ← 不会启动期加载
│       └── ui-skill/        ← 模型读 frontend/foo.tsx 时才发现
└── backend/
    └── .claude/skills/     ← 同上
        └── api-skill/       ← 模型读 backend/bar.ts 时才发现
```

## 2. 三个函数三种职责

打开 `restored-src/src/skills/loadSkillsDir.ts:817-1075`。这一段有三类机制：

```
┌─────────────────────────────────────────────────────────┐
│ 机制 A：自动目录发现                                    │
│   (子目录有 .claude/skills/ → 自动装载)                │
│                                                         │
│   触发：FileRead/Write/Edit 工具调用                   │
│   函数：discoverSkillDirsForPaths + addSkillDirectories │
│   状态：dynamicSkillDirs (Set)                         │
│         dynamicSkills (Map<name, Command>)             │
└─────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────┐
│ 机制 B：条件 skill 激活                                 │
│   (paths frontmatter 命中 → 暴露)                       │
│                                                         │
│   触发：FileRead/Write/Edit 工具调用                   │
│   函数：activateConditionalSkillsForPaths               │
│   状态：conditionalSkills (Map，待激活池)              │
│         activatedConditionalSkillNames (Set)           │
│         dynamicSkills (Map，激活后归这里)              │
└─────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────┐
│ 机制 C：通知模型新 skill 出现                           │
│   (skill_listing attachment 增量推送)                  │
│                                                         │
│   触发：每次 query turn 准备消息时                     │
│   函数：getSkillListingAttachments                     │
│   状态：sentSkillNames (按 agent 记录已发名单)         │
└─────────────────────────────────────────────────────────┘
```

A 和 B 是**怎么发现新 skill**，C 是**发现之后怎么让模型知道**。

## 3. 机制 A：自动目录发现

### 3.1 谁在调？三个文件工具

打开 `restored-src/src/tools/FileReadTool/FileReadTool.ts:575-591`：

```ts
// Discover skills from this file's path (fire-and-forget, non-blocking)
// Skip in simple mode - no skills available
const cwd = getCwd()
if (!isEnvTruthy(process.env.CLAUDE_CODE_SIMPLE)) {
  const newSkillDirs = await discoverSkillDirsForPaths([fullFilePath], cwd)
  if (newSkillDirs.length > 0) {
    // Store discovered dirs for attachment display
    for (const dir of newSkillDirs) {
      context.dynamicSkillDirTriggers?.add(dir)
    }
    // Don't await - let skill loading happen in the background
    addSkillDirectories(newSkillDirs).catch(() => {})
  }

  // Activate conditional skills whose path patterns match this file
  activateConditionalSkillsForPaths([fullFilePath], cwd)
}
```

`FileWriteTool.ts:234-245` 和 `FileEditTool.ts:408-422` 几乎一样的代码。

#### 这一段值得停下来看的几个点

**(a) `await discoverSkillDirsForPaths` 是同步的，但 `addSkillDirectories` 是 fire-and-forget**

```ts
const newSkillDirs = await discoverSkillDirsForPaths(...)   // 等
if (newSkillDirs.length > 0) {
  addSkillDirectories(newSkillDirs).catch(() => {})         // 不等
}
activateConditionalSkillsForPaths(...)                       // 同步
```

为什么这样？

- `discoverSkillDirsForPaths` 只做 stat 和 gitignore check，便宜
- `addSkillDirectories` 真正读 markdown 文件 + parse frontmatter + 进 `dynamicSkills`，慢
- 如果 await `addSkillDirectories`，每次 FileRead 都会阻塞——**但用户当前 turn 的 FileRead 不需要看到新 skill**（skill 在下一 turn 才会通过 attachment 通知模型）

所以**让 skill 装载在背景跑**，不阻塞当前文件操作。

**(b) `.catch(() => {})` 静默失败**

第 586 行 `.catch(() => {})` 一句把所有错都吞了。

这是合理的——skill 装载失败不该让 FileRead 也失败。FileRead 的核心职责是读文件，skill 是副作用。`addSkillDirectories` 内部已经记 logEvent / logError，不需要外层再处理。

**(c) `dynamicSkillDirTriggers` 是给 attachment UI 用的**

第 583 行把发现的目录写进 `context.dynamicSkillDirTriggers`。这个 Set 后续被 attachment 系统用来构造 UI 提示——"在 frontend/foo.tsx 附近发现了新 skill"。和实际装载分开。

**(d) `CLAUDE_CODE_SIMPLE` 守卫**

simple 模式（极简启动）里跳过整个 skill discovery。simple mode 是 SDK 嵌入场景的优化——调用方明确不要 skill。

#### 思考题

> 模型在一个 turn 里连续 Read 了 frontend/a.tsx、frontend/b.tsx、backend/c.ts。`discoverSkillDirsForPaths` 会被调几次？发现的目录会不会重复？

（提示：每次 FileRead 都调一次，每次只传一个路径。同一个目录会被多次"问"——但 `dynamicSkillDirs` Set 在第一次时就记下，第二次起 stat 都跳过。所以 stat 的开销只在第一次发生。）

### 3.2 `discoverSkillDirsForPaths` 的核心逻辑（loadSkillsDir.ts:861-915）

```ts
export async function discoverSkillDirsForPaths(
  filePaths: string[],
  cwd: string,
): Promise<string[]> {
  const fs = getFsImplementation()
  const resolvedCwd = cwd.endsWith(pathSep) ? cwd.slice(0, -1) : cwd
  const newDirs: string[] = []

  for (const filePath of filePaths) {
    let currentDir = dirname(filePath)

    // 关键守卫：startsWith(cwd + sep)
    while (currentDir.startsWith(resolvedCwd + pathSep)) {
      const skillDir = join(currentDir, '.claude', 'skills')

      if (!dynamicSkillDirs.has(skillDir)) {
        dynamicSkillDirs.add(skillDir)        // hit & miss 都记
        try {
          await fs.stat(skillDir)
          if (await isPathGitignored(currentDir, resolvedCwd)) {
            logForDebugging(`[skills] Skipped gitignored skills dir: ${skillDir}`)
            continue
          }
          newDirs.push(skillDir)
        } catch {
          // dir 不存在 — 已经 add 进 Set，下次跳过
        }
      }

      const parent = dirname(currentDir)
      if (parent === currentDir) break
      currentDir = parent
    }
  }

  return newDirs.sort((a, b) => b.split(pathSep).length - a.split(pathSep).length)
}
```

#### 三个关键设计点

**(a) "向上走但不到 cwd 自身"**

```
while (currentDir.startsWith(resolvedCwd + pathSep)) { ... }
```

注意 `+ pathSep`——这让 `cwd` 自己不进循环。原因：cwd 级 `.claude/skills/` 已经在启动期被 `getSkillDirCommands` 装过。这里只发现**子目录**的 skill。

如果是 `cwd.startsWith(resolvedCwd)` 没加 sep，会有 prefix 误匹配——比如 cwd 是 `/project`，`/project-backup/foo` 也会误命中。加 sep 是必要的边界保护。

**(b) `dynamicSkillDirs` 同时记 hit 和 miss**

```ts
if (!dynamicSkillDirs.has(skillDir)) {
  dynamicSkillDirs.add(skillDir)     // 先 add，再判断 stat
  try { await fs.stat(skillDir) ... }
  catch { /* miss 已经 add */ }
}
```

**很关键的优化**：绝大多数子目录**没有** `.claude/skills/`。如果不记 miss，每次 FileRead 都会重新 stat 一遍——浪费。

记下来之后，第二次同一目录直接 `if (!has) → false`，跳过整个 try。

**(c) gitignore 安全门**

第 892 行 `isPathGitignored(currentDir, resolvedCwd)`——发现 `.claude/skills/` 之后还要检查它的**包含目录是否被 gitignore**。

为什么？典型场景：`node_modules/some-pkg/.claude/skills/`。攻击者发布一个 npm 包夹带 skill，用户 npm install 后 skill 就出现在文件树里。但 `node_modules` 是 gitignored 的——这一道门挡住这种"供应链注入"。

注释 887-891：

```
Skills dir exists. Before loading, check if the containing dir
is gitignored — blocks e.g. node_modules/pkg/.claude/skills from
loading silently. `git check-ignore` handles nested .gitignore,
.git/info/exclude, and global gitignore. Fails open outside a
git repo (exit 128 → false); the invocation-time trust dialog
is the actual security boundary.
```

注意"fails open"——不在 git 仓库时（比如 `/tmp/ad-hoc/`）这个检查直接通过，不阻断。这是合理的——非 git 环境下 gitignore 概念不适用。

**(d) 深度优先排序**

```ts
return newDirs.sort((a, b) => b.split(pathSep).length - a.split(pathSep).length)
```

返回值按路径深度降序排——深的在前。原因看 3.3 节 `addSkillDirectories` 的反向遍历。

### 3.3 `addSkillDirectories` 的"深度覆盖"语义（loadSkillsDir.ts:923-975）

```ts
export async function addSkillDirectories(dirs: string[]): Promise<void> {
  if (!isSettingSourceEnabled('projectSettings') || isRestrictedToPluginOnly('skills')) {
    return
  }
  if (dirs.length === 0) return

  const previousSkillNamesForLogging = new Set(dynamicSkills.keys())

  const loadedSkills = await Promise.all(
    dirs.map(dir => loadSkillsFromSkillsDir(dir, 'projectSettings')),
  )

  // ★ 反向遍历：浅度优先 set，深度后写赢
  for (let i = loadedSkills.length - 1; i >= 0; i--) {
    for (const { skill } of loadedSkills[i] ?? []) {
      if (skill.type === 'prompt') {
        dynamicSkills.set(skill.name, skill)
      }
    }
  }

  // telemetry + emit signal
  if (newSkillCount > 0) {
    if (addedSkills.length > 0) {
      logEvent('tengu_dynamic_skills_changed', {...})
    }
  }
  skillsLoaded.emit()
}
```

#### "深度优先排序 + 反向遍历"的含义

- 入参 `dirs` 已经按深度降序（最深在 `[0]`）
- 反向遍历从 `[length-1]`（最浅）开始
- `Map.set(name, skill)` 后写覆盖前写——**最深的 skill 最后写赢**

效果：**距离当前文件最近的 skill 优先**。

例：

```
模型读 /project/frontend/components/Button.tsx
discoverSkillDirsForPaths 返回（深度降序）：
  [0] /project/frontend/components/.claude/skills
  [1] /project/frontend/.claude/skills

反向遍历：
  i=1: 装 /project/frontend/.claude/skills 里所有 skill
  i=0: 装 /project/frontend/components/.claude/skills 里所有 skill
       ← 同名 skill 在这里覆盖了 i=1 的版本

最终：components 里的 skill 赢。
```

这是合理的——skill 越靠近当前操作的文件，作者越有针对性。

#### 思考题

> 为什么 `addSkillDirectories` 在 `Promise.all` 之前用 `dirs.length === 0` 提前返回？这个 fast path 在多大概率下命中？

（答：调用方 `FileReadTool.ts:579-580` 已经做了 `if (newSkillDirs.length > 0)` 守卫，不会传空数组进来。但 `addSkillDirectories` 是 export 的、可能被其它路径调用，自带这层保护是 defensive。fast path 几乎不命中——但也不贵。）

## 4. 机制 B：条件 skill 激活

### 4.1 conditional skills 的"两阶段"语义

03 篇段 3 阶段 D 已经讲过 `getSkillDirCommands` 在装载结束时**把带 `paths` 的 skill 抽走放进 `conditionalSkills` 池**。

回顾这段（loadSkillsDir.ts:771-795）：

```ts
const unconditionalSkills: Command[] = []
const newConditionalSkills: Command[] = []
for (const skill of deduplicatedSkills) {
  if (
    skill.type === 'prompt' &&
    skill.paths && skill.paths.length > 0 &&
    !activatedConditionalSkillNames.has(skill.name)   // ← 已激活的不再当 conditional
  ) {
    newConditionalSkills.push(skill)
  } else {
    unconditionalSkills.push(skill)
  }
}

for (const skill of newConditionalSkills) {
  conditionalSkills.set(skill.name, skill)
}

return unconditionalSkills    // ★ 返回值不含 conditional skill
```

**两阶段语义**：

```
阶段 1：装载完成时
  conditional skill 进 conditionalSkills 池（map）
  getSkillDirCommands 不返回它们
  → 模型看不到，用户不能 /name 调用

阶段 2：文件路径命中
  activateConditionalSkillsForPaths 把它从池里搬到 dynamicSkills
  → 进 getCommands 结果
  → 进 SkillTool 列表
  → 通过 attachment 通知模型
```

### 4.2 `activateConditionalSkillsForPaths`（997-1058）

```ts
export function activateConditionalSkillsForPaths(
  filePaths: string[],
  cwd: string,
): string[] {
  if (conditionalSkills.size === 0) return []

  const activated: string[] = []

  for (const [name, skill] of conditionalSkills) {
    if (skill.type !== 'prompt' || !skill.paths || skill.paths.length === 0) continue

    const skillIgnore = ignore().add(skill.paths)

    for (const filePath of filePaths) {
      const relativePath = isAbsolute(filePath) ? relative(cwd, filePath) : filePath

      // ignore() 限制：不能空字符串、不能 '..'-relative、不能绝对
      if (!relativePath || relativePath.startsWith('..') || isAbsolute(relativePath)) {
        continue
      }

      if (skillIgnore.ignores(relativePath)) {
        dynamicSkills.set(name, skill)
        conditionalSkills.delete(name)
        activatedConditionalSkillNames.add(name)
        activated.push(name)
        logForDebugging(`[skills] Activated conditional skill '${name}' (matched path: ${relativePath})`)
        break    // ★ 一个文件命中即可
      }
    }
  }

  if (activated.length > 0) {
    logEvent('tengu_dynamic_skills_changed', { source: 'conditional_paths', ... })
    skillsLoaded.emit()
  }

  return activated
}
```

#### 关键点

**(a) 用 `ignore` 库，不是 minimatch**

为什么？因为 `ignore` 库实现的是 **gitignore 风格**——它和 CLAUDE.md 条件规则、`.claude/agents/*.md` 的 `paths` 字段、各种文件匹配场景**复用同一套语义**。

gitignore 风格和 minimatch 在几个地方不同：

- `path/` 等于 `path`（包括 path 自己 + 内部所有）
- `**/foo` 在任意层级匹配
- 否定规则 `!foo` 反向

skill 作者用熟悉的 gitignore 语法就能写匹配规则。

**(b) 文件路径相对化**

```ts
const relativePath = isAbsolute(filePath) ? relative(cwd, filePath) : filePath
```

`paths` 模式是相对 cwd 的。把绝对文件路径转相对——`/project/frontend/foo.tsx` → `frontend/foo.tsx`。

**三道异常守卫**：

- 空字符串：`relative()` 可能返回空（filePath === cwd）
- `..`-relative：文件在 cwd 之外（不该匹配 cwd-relative pattern）
- 绝对路径：Windows 跨盘符 `relative()` 会保留绝对（这是 Windows 特性）

`ignore` 库对这三种输入会**抛异常**，所以提前过滤。

**(c) 一旦命中就 break**

只要某个 filePath 命中，激活整个 skill，跳出 inner loop。语义："只要碰到了相关代码区域，就开"——而不是要求**所有**文件都命中。

**(d) `activatedConditionalSkillNames` 永久记**

第 1033 行 `activatedConditionalSkillNames.add(name)` 把激活过的 skill 名字记进永久 Set。这个 Set 在 03 篇段 3 阶段 D 起作用——`getSkillDirCommands` 不会再把它当 conditional 抽走。

也就是说：**conditional skill 一旦激活，本会话内永远是 unconditional**。即使后续操作的文件不再匹配 paths，skill 也不会"取消激活"——一向激活。

#### 思考题

> conditional skill 写：
> ```yaml
> paths: 'src/payments/**'
> ```
> 模型读了 `src/payments/charge.ts` → 激活。然后模型读 `src/users/user.ts`。
> 这时 skill 还在 dynamicSkills 里吗？为什么？是好设计还是坏设计？

（答：在。`activateConditionalSkillsForPaths` 不做反向"取消激活"。这是**有意的**——skill 进入了上下文，模型已经看到 skill 内容并可能基于它做了决策；硬把 skill 从 prompt 里挪走会让会话不连贯。但代价是 skill 列表只增不减，长会话里可能膨胀。设计上选择"会话内 sticky"。）

### 4.3 `activatedConditionalSkillNames` 在 cache clear 时被清

## 5. 机制 C：通知模型新 skill 出现

skill 装进 `dynamicSkills` 之后，模型怎么知道？

`getCommands(cwd)` 会自动包含 dynamicSkills（04 篇 3.4 节讲过），但 `getCommands` 只是给 SkillTool 当"可调用列表"用——模型不会主动遍历它。**模型必须看到 skill 描述出现在 prompt 里，才会知道"我可以用这个 skill"。**

这就是 `skill_listing` attachment 的作用。

### 5.1 `skill_listing` 的增量推送（utils/attachments.ts 部分）

打开 `restored-src/src/utils/attachments.ts:2680-2751`。函数是 `getSkillListingAttachments`：

```ts
let sent = sentSkillNames.get(agentKey)
if (!sent) {
  sent = new Set()
  sentSkillNames.set(agentKey, sent)
}

// resume 短路（略）

// ★ 找还没发过的 skill
const newSkills = allCommands.filter(cmd => !sent.has(cmd.name))

if (newSkills.length === 0) return []

const isInitial = sent.size === 0

// 标记已发
for (const cmd of newSkills) {
  sent.add(cmd.name)
}

// 按预算裁剪
const contextWindowTokens = getContextWindowForModel(...)
const content = formatCommandsWithinBudget(newSkills, contextWindowTokens)

return [{ type: 'skill_listing', content, skillCount, isInitial }]
```

#### 关键设计

**(a) `sentSkillNames` 按 agent 分组**

每个 agent (含主会话和 fork 子 agent) 有自己的 sent set。fork 子 agent 不受主会话已发列表影响——它要看到完整 listing 一次。

**(b) 增量推送：只发新增**

`filter(cmd => !sent.has(cmd.name))` —— 已发过的 skill 不再发。

第一次（`isInitial = true`）发整个列表；后续 turn 只发**这一 turn 新发现的**。

**(c) `formatCommandsWithinBudget` 控制 token 预算**

打开 `tools/SkillTool/prompt.ts:70` 看 `formatCommandsWithinBudget`——它会按上下文窗口的某个百分比预算，决定能塞多少 skill 描述。超预算会优先保留 description（不带 `whenToUse`），最坏情况下只发 name + 简短 description。

这是为什么 03 篇 2.3 节那个 `estimateSkillFrontmatterTokens` 函数存在——它给这里提供 token 估算。

### 5.2 attachment 触发的时机

`utils/attachments.ts:875` 那一行：

```ts
maybe('skill_listing', () => getSkillListingAttachments(context)),
```

`maybe` 是 attachment 生产管道的一部分。每次主 query 准备消息时都会跑一遍——所以**每个 turn 都有机会发 attachment**。

```
turn N：
  1. 模型 FileRead frontend/foo.tsx
  2. discoverSkillDirsForPaths 发现 frontend/.claude/skills
  3. addSkillDirectories 在背景装载
  4. activateConditionalSkillsForPaths 激活若干条件 skill
  5. dynamicSkills 增加
  6. skillsLoaded.emit() → onDynamicSkillsLoaded 回调 → clearCommandMemoizationCaches
  7. 当前 turn 模型继续干活（看不到新 skill）

turn N+1：
  1. 准备 messages 时 maybe('skill_listing') 跑
  2. getCommands(cwd) 返回新 dynamicSkills
  3. getSkillListingAttachments 发现 newSkills 非空
  4. 拼一条 skill_listing attachment 发给模型
  5. 模型这一 turn 看到新 skill 名 + 描述
```

#### 思考题

> turn N 模型 FileRead 触发了新 skill。`addSkillDirectories` 是 fire-and-forget 的——如果它还在跑、turn N+1 已经开始准备 messages，会发生什么？

（答：可能漏发。`addSkillDirectories` 还在装载时，`getCommands(cwd)` 看不到那些 skill，attachment 也就不会发。但下下个 turn (N+2) 一定会发——signal 会触发 cache 失效，`getCommands` 在 N+2 准备时拿到完整列表。所以新 skill **可能延迟一个 turn 才告诉模型**。这是性能权衡——避免阻塞 FileRead。）

## 7. 这些机制带来的产品语义

回头看一遍，这三套机制实际上构造了**skill 系统的"产品化"行为**：

1. **skill 跟代码区域绑定**
   - frontend 子项目的 skill 只在模型工作 frontend 时出现
   - backend 同理
   - 不污染对方的 skill 列表

2. **skill 跟代码主题绑定**（paths 条件）
   - `paths: 'src/payments/**'` 让 payments 相关 skill 只在碰到支付代码时暴露
   - 长会话不会被无关 skill 噪音化

3. **skill 列表对模型按需"长出来"**
   - 模型每个 turn 只看到**新增的** skill listing
   - 已经知道的不再重复发——节省 token

4. **跨 agent 隔离**
   - 每个 agent 有自己的 sentSkillNames
   - fork 子 agent 看到完整 listing 一次

5. **安全边界**
   - gitignore 守卫挡 node_modules 注入
   - conditional skill 在被激活前对模型不可见

6. **失败软化**
   - skill 装载失败不阻塞 FileRead
   - skill 错过一个 turn 通知，下个 turn 还会发

## 8. 这一篇你应该带走的几样东西

读到这里，你应该能回答：

1. 为什么动态发现要分 `discoverSkillDirsForPaths` 和 `addSkillDirectories` 两步？
   （前者便宜（stat + gitignore），可以 await；后者贵（解析 markdown），fire-and-forget）
2. `dynamicSkillDirs` Set 同时记 hit 和 miss 是为什么？
   （绝大多数子目录没 skill，记 miss 避免重复 stat）
3. conditional skill 的"两阶段"是什么？
   （装载阶段：进 conditionalSkills 池；激活阶段：路径命中时进 dynamicSkills）
4. 一旦激活的 conditional skill 会被"取消激活"吗？
   （不会——activatedConditionalSkillNames 永久记。但 `clearSkillCaches` 会清。）
5. `skill_listing` attachment 是按什么逻辑发的？
   （按 agent 维度记 sentSkillNames，每 turn 只发新增 skill；按 token budget 裁剪）
6. 为什么要把 `addSkillDirectories` 改成 fire-and-forget？带来什么副作用？
   （不阻塞 FileRead；副作用是新 skill 可能延迟一个 turn 才被通知到模型）
7. gitignore 守卫挡的是什么场景？
   （node_modules 等 third-party 包夹带 .claude/skills 的供应链注入）
8. `addSkillDirectories` 反向遍历是为什么？
   （深度优先覆盖——子目录 skill 比父目录 skill 优先）
