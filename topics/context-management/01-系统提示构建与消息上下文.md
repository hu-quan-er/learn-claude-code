# 系统提示构建与消息上下文

> Claude Code 上下文管理分析系列 - 第1篇
> 源码版本：claude-code 2.1.88

---

## 概述

Claude Code 的系统提示不是一段静态文本，而是一个由多种来源动态组装的复合结构。本文分析系统提示的构建流程、消息上下文注入机制、消息归一化流水线，以及 Token 计数子系统。

## 1. 系统提示构建架构

### 1.1 顶层入口：`buildEffectiveSystemPrompt()`

**文件**：`src/utils/systemPrompt.ts`（第41-123行）

系统提示遵循严格的优先级层次，从高到低：

```
┌─────────────────────────────────────────────────┐
│  1. overrideSystemPrompt                        │  ← 最高优先级，完全替换（如 loop 模式）
│     若存在 → 直接返回，跳过所有其他提示          │
├─────────────────────────────────────────────────┤
│  2. coordinatorSystemPrompt                     │  ← 协调器模式下使用
├─────────────────────────────────────────────────┤
│  3. agentSystemPrompt                           │  ← Agent 定义的提示
│     • proactive 模式 → 追加到默认提示末尾        │
│     • 非 proactive → 替换默认提示                │
├─────────────────────────────────────────────────┤
│  4. customSystemPrompt                          │  ← --system-prompt 参数指定
├─────────────────────────────────────────────────┤
│  5. defaultSystemPrompt                         │  ← 标准 Claude Code 提示
└─────────────────────────────────────────────────┘
  + appendSystemPrompt 始终追加到末尾（除 override 场景）
```

**核心签名**：

```typescript
export function buildEffectiveSystemPrompt({
  mainThreadAgentDefinition,
  toolUseContext,
  customSystemPrompt,
  defaultSystemPrompt,
  appendSystemPrompt,
  overrideSystemPrompt,
}: {...}): SystemPrompt
```

### 1.2 提示段落系统：Memoized vs. Volatile

**文件**：`src/constants/systemPromptSections.ts`（第1-69行）

系统提示被拆分为独立的「段落」(Section)，每个段落有两种缓存策略：

| 类型 | 创建函数 | 行为 | 典型场景 |
|------|----------|------|----------|
| **Memoized** | `systemPromptSection(name, computeFn)` | 首次计算后缓存，直到 `/clear` 或 `/compact` | 大多数静态段落 |
| **Volatile** | `DANGEROUS_uncachedSystemPromptSection(name, computeFn, reason)` | 每轮重新计算 | MCP 服务器指令等动态内容 |

Volatile 段落会打破提示缓存（prompt cache），因此必须提供 `reason` 说明为何需要不缓存。例如：

> `"MCP servers connect/disconnect between turns"`

**段落解析 API**：

```typescript
export async function resolveSystemPromptSections(
  sections: SystemPromptSection[]
): Promise<(string | null)[]>
```

缓存存储在 `getSystemPromptSectionCache()` 中，由 `src/bootstrap/state.ts` 管理。

### 1.3 默认系统提示的完整构成：`getSystemPrompt()`

**文件**：`src/constants/prompts.ts`（第444-577行）

最终的系统提示是一个字符串数组，各段落以 `\n\n` 拼接。构成如下：

**静态段落（可缓存）**：

| 段落 | 函数 | 内容 |
|------|------|------|
| 角色介绍 | `getSimpleIntroSection()` | Claude Code 的基本角色定义 |
| 系统说明 | `getSimpleSystemSection()` | 工具执行、权限模式、系统标签 |
| 任务指导 | `getSimpleDoingTasksSection()` | 任务处理方式的详细指导 |
| 行动说明 | `getActionsSection()` | 可执行行动描述 |
| 工具使用 | `getUsingYourToolsSection()` | 工具使用模式与最佳实践 |
| 语气风格 | `getSimpleToneAndStyleSection()` | 沟通风格指导 |

**全局缓存边界标记**：

```typescript
SYSTEM_PROMPT_DYNAMIC_BOUNDARY = '__SYSTEM_PROMPT_DYNAMIC_BOUNDARY__'
```

当 `shouldUseGlobalCacheScope()` 为真时，此标记将静态内容与动态内容分隔：
- 标记之前的内容可使用 `scope: 'global'`（全局缓存作用域）
- 标记之后的内容标记为 `scope: null`（无全局缓存）

**动态段落（Memoized 或 Volatile）**：

| 段落名 | 缓存类型 | 内容 |
|--------|----------|------|
| `session_guidance` | Memoized | 技能工具命令、启用的工具列表 |
| `memory` | Memoized | 通过 `loadMemoryPrompt()` 加载记忆文件 |
| `ant_model_override` | Memoized | Ant 专属模型覆盖配置 |
| `env_info_simple` | Memoized | 环境信息 |
| `language` | Memoized | 用户语言偏好 |
| `output_style` | Memoized | 自定义输出风格 |
| `mcp_instructions` | **Volatile** | MCP 服务器指令（动态连接/断开） |
| `scratchpad` | Memoized | 暂存目录指令 |
| `frc` | Memoized | 函数结果清除段落 |
| `summarize_tool_results` | Memoized | 工具结果摘要指导 |
| `token_budget` | Memoized | "+500k" 等预算指令 |
| `brief` | Memoized | KAIROS/BRIEF 特性指导 |

## 2. 上下文构建：User Context 与 System Context

### 2.1 系统上下文：`getSystemContext()`

**文件**：`src/context.ts`（第116-150行）

```typescript
// 返回类型
{ gitStatus?: string, cacheBreaker?: string }
```

- **Memoized 异步函数**，只计算一次
- 计算 Git 状态：分支名、主分支、Git 用户、工作区状态、最近提交
- **截断限制**：最大 2000 字符（超出时输出警告）
- 在 CCR（远程模式）下跳过
- 通过 `appendSystemContext()` 追加到系统提示末尾

### 2.2 用户上下文：`getUserContext()`

**文件**：`src/context.ts`（第155-189行）

```typescript
// 返回类型
{ claudeMd?: string, currentDate: string }
```

- **Memoized 异步函数**
- 加载 CLAUDE.md 文件（自动发现或通过 `--add-dir` 显式指定）
- `--bare` 模式跳过自动发现
- 可通过 `CLAUDE_CODE_DISABLE_CLAUDE_MDS` 环境变量禁用
- 通过 `prependUserContext()` 作为 `<system-reminder>` 用户消息注入

### 2.3 上下文注入到 API 的方式

**文件**：`src/utils/api.ts`

| 函数 | 位置 | 方式 |
|------|------|------|
| `appendSystemContext()` | 第437-447行 | 将 git status 等键值对追加到系统提示末尾 |
| `prependUserContext()` | 第449-474行 | 作为 `<system-reminder>` 标签的用户消息预置到消息列表最前 |

`prependUserContext` 注入的消息标记为 `isMeta: true`（内部内容，非用户输入），空上下文时跳过注入。

## 3. 消息归一化流水线

### 3.1 核心函数：`normalizeMessagesForAPI()`

**文件**：`src/utils/messages.ts`（第1989-2370行）

```typescript
export function normalizeMessagesForAPI(
  messages: Message[],
  tools: Tools = [],
): (UserMessage | AssistantMessage)[]
```

此函数对消息执行 **13+ 遍处理**，确保消息格式满足 API 要求。

### 3.2 完整处理流水线

```
原始消息数组
    │
    ├── Pass 1: 附件重排序 + 虚拟消息过滤
    │   ├── reorderAttachmentsForAPI()：将附件上浮到 tool_result 或 assistant 消息之前
    │   └── 过滤 isVirtual=true 的消息（REPL 内部工具调用，仅用于显示）
    │
    ├── Pass 2: 错误驱动的媒体剥离
    │   ├── 构建 error_text → block_types 映射表
    │   ├── 从错误消息向前回溯找到前置用户消息
    │   └── 剥离导致 "too large" 错误的图片/PDF，防止重发
    │
    ├── Pass 3-5: 消息类型过滤与处理
    │   ├── 过滤：progress 消息、非本地命令系统消息、合成 API 错误
    │   │
    │   ├── System → 转为 user 消息，与前置 user 消息合并
    │   │
    │   ├── User → 归一化工具搜索字段
    │   │   ├── 剥离 tool_reference 块（tool search 未启用时）
    │   │   ├── 剥离不可用工具的引用（tool search 启用时）
    │   │   ├── 注入 TOOL_REFERENCE_TURN_BOUNDARY（防止停止序列采样）
    │   │   └── 合并连续 user 消息（Bedrock 要求；1P API 自动合并）
    │   │
    │   ├── Assistant → 归一化工具输入，按 message.id 合并
    │   │   ├── normalizeToolInputForAPI()：剥离 plan/extra 字段
    │   │   ├── 剥离 caller 字段（tool search 未启用时）
    │   │   └── 回溯查找同 ID 的前置 assistant 消息并合并
    │   │
    │   └── Attachment → 归一化后与前置 user 消息合并
    │       ├── normalizeAttachmentForAPI()
    │       └── 可选包裹 system-reminder（由 feature flag 控制）
    │
    ├── Pass 6: Tool Reference 兄弟节点重定位
    │   └── 门控：tengu_toolref_defer_j8m feature flag
    │
    ├── Pass 7: 孤立 Thinking-Only 消息过滤
    │   └── 过滤仅含 thinking 块的 assistant 消息（无 text/tool_use）
    │
    ├── Pass 8: 末尾 Thinking 剥离
    │   └── 从最后一条 assistant 消息剥离 thinking 块
    │
    ├── Pass 9: 空白消息过滤
    │   └── 移除仅含空白文本的 assistant 消息
    │
    ├── Pass 10: 非空内容保证
    │   └── ensureNonEmptyAssistantContent()：空 assistant 消息添加占位符
    │
    ├── Pass 11: System Reminder 合并
    │   ├── 门控：tengu_chair_sermon feature flag
    │   ├── mergeAdjacentUserMessages()
    │   └── smooshSystemReminderSiblings()：将 <system-reminder> 折入相邻 tool_result
    │
    ├── Pass 12: 错误 Tool Result 清理
    │   └── sanitizeErrorToolResultContent()：移除错误 tool_result 中的图片
    │
    ├── Pass 13: 消息 ID 标签注入
    │   ├── 门控：HISTORY_SNIP feature flag + 非测试模式
    │   └── 在 user 消息末尾追加 [id:XXXXXX]（从 UUID 派生）
    │
    └── Pass 14: 图片验证
        └── validateImagesForAPI()：确保所有图片在 API 大小限制内
```

### 3.3 关键辅助函数

**消息合并**：

| 函数 | 作用 |
|------|------|
| `mergeUserMessages()` | 合并两条连续 user 消息，保留非 meta 消息的 UUID |
| `mergeAssistantMessages()` | 合并同 ID 的 assistant 消息内容 |
| `mergeUserMessagesAndToolResults()` | 合并 user 消息与 tool_result，将 result 前置 |
| `mergeAdjacentUserMessages()` | 扫描并合并所有相邻 user 消息对 |

**内容组织**：

| 函数 | 作用 |
|------|------|
| `hoistToolResults()` | 将所有 `tool_result` 块移到内容数组前端（API 要求） |
| `normalizeUserTextContent()` | 确保 content 为块数组格式 |

## 4. Token 计数子系统

### 4.1 精确计数：API 原生方法

**文件**：`src/services/tokenEstimation.ts`（第140-201行）

```typescript
async function countMessagesTokensWithAPI(
  messages: Anthropic.Beta.Messages.BetaMessageParam[],
  tools: Anthropic.Beta.Messages.BetaToolUnion[],
): Promise<number | null>
```

- 使用 API 的 `beta.messages.countTokens()` 端点
- 自动检测 thinking 块并在计数请求中启用 thinking
- 发送前剥离 tool search beta 字段（caller, tool_reference）
- Bedrock 提供商回退到专用实现
- Vertex 过滤部分会导致 400 错误的 beta
- 通过 VCR 缓存结果（确定性重放）

### 4.2 Haiku 模型回退：`countTokensViaHaikuFallback()`

**第251-325行**：当 API 计数不可用时，使用轻量模型估算

| 场景 | 使用模型 |
|------|----------|
| 默认（1P） | Haiku 4.5（支持 thinking） |
| Vertex 全局区域 | Sonnet（Haiku 不可用） |
| Bedrock + thinking | Sonnet（Haiku 3.5 不支持 thinking） |
| Vertex + thinking | Sonnet（Haiku 3.5 不支持 thinking） |

约束参数：
- `max_tokens = 2048`（TOKEN_COUNT_MAX_TOKENS）
- `thinking.budget_tokens = 1024`（检测到 thinking 时）

### 4.3 粗略估算

**`roughTokenCountEstimation()`**（第203-208行）：

```typescript
export function roughTokenCountEstimation(
  content: string,
  bytesPerToken: number = 4,
): number {
  return Math.round(content.length / bytesPerToken)
}
```

**文件类型特化比率** via `bytesPerTokenForFileType()`（第215-224行）：

| 文件类型 | 比率 | 原因 |
|----------|------|------|
| JSON / JSONL / JSONC | 2 bytes/token | 大量单字符 token：`{`, `}`, `:`, `,`, `"` |
| 默认 | 4 bytes/token | 英文经验均值 |

**块级别估算** via `roughTokenCountEstimationForBlock()`（第391-435行）：

| 块类型 | 估算方式 |
|--------|----------|
| `text` | `roughTokenCountEstimation()` |
| `image` / `document` | 固定 2000 tokens |
| `tool_result` | 递归估算内容 |
| `tool_use` | 估算 name + JSON.stringify(input) |
| `thinking` / `redacted_thinking` | 估算 text/data |
| 其他（如 mcp_tool_use） | JSON.stringify 后估算 |

### 4.4 混合 Token 计数：`tokenCountWithEstimation()`

**文件**：`src/utils/tokens.ts`（第226-261行）

这是上下文大小判断的**规范函数**：

```typescript
export function tokenCountWithEstimation(
  messages: readonly Message[]
): number {
  // 1. 找到最后一条有 usage 的 assistant 消息
  let lastUsage = getTokenCountFromUsage(lastMessage.usage)
  
  // 2. 回溯到同 message.id 的第一个兄弟（并行工具调用）
  let i = indexOfLastMessageWithSameId
  
  // 3. 返回 usage + 新消息的粗略估算
  return lastUsage + roughTokenCountEstimationForMessages(messages.slice(i + 1))
}
```

**关键设计**：回溯查找并行工具调用的所有兄弟消息，确保交错的 tool_result 不被遗漏，防止低估。

### 4.5 Token 使用量提取

**`getTokenCountFromUsage()`**（第46-53行）：

```typescript
export function getTokenCountFromUsage(usage: Usage): number {
  return (
    usage.input_tokens +
    (usage.cache_creation_input_tokens ?? 0) +
    (usage.cache_read_input_tokens ?? 0) +
    usage.output_tokens
  )
}
```

**`finalContextTokensFromLastResponse()`**（第79-112行）：
- 检查 `usage.iterations` 数组（服务端工具循环）
- 使用最后一次迭代：`input_tokens + output_tokens`（不含缓存）
- 与服务端 `renderer.py:292` 公式匹配

## 5. 上下文窗口管理

### 5.1 上下文窗口大小

**文件**：`src/utils/context.ts`（第51-98行）

**默认值**：`MODEL_CONTEXT_WINDOW_DEFAULT = 200,000`

**解析优先级**（首个匹配生效）：

```
1. 环境变量覆盖（Ant 专属）：CLAUDE_CODE_MAX_CONTEXT_TOKENS
2. 客户端 [1m] 后缀：显式启用 1M 上下文
3. 模型能力数据：modelCapabilities
4. 1M 禁用检查：is1mContextDisabled() → 限制到 200K
5. Beta 头：CONTEXT_1M_BETA_HEADER + modelSupports1M()
6. Sonnet 1M 实验：GrowthBook A/B 测试
7. Ant 模型覆盖：内部配置
8. 默认：200,000 tokens
```

**支持 1M 的模型**：Sonnet 4.x（所有版本）、Opus 4.6

### 5.2 最大输出 Token

**`getModelMaxOutputTokens()`**（第149-210行）：

| 模型 | 默认输出 | 上限 |
|------|----------|------|
| Opus 4.6 | 64K | 128K |
| Sonnet 4.6 | 32K | 128K |
| Opus 4.5 / Sonnet 4.x / Haiku 4.x | 32K | 64K |
| Opus 4.1 / Opus 4 | 32K | 32K |
| Claude 3 系列 | 4K-8K | — |

**槽位预留优化**：
- `CAPPED_DEFAULT_MAX_TOKENS = 8,000`（较小请求的上限）
- `ESCALATED_MAX_TOKENS = 64,000`（首次重试时提升）
- BQ 数据显示 p99 输出为 4,911 tokens；32K/64K 默认值过度预留 8-16 倍
- 加帽策略减少过度预留；仅 1% 请求需要提升到 64K

### 5.3 有效上下文窗口计算

**文件**：`src/services/compact/autoCompact.ts`（第33-49行）

```typescript
export function getEffectiveContextWindowSize(model: string): number {
  const reservedTokensForSummary = Math.min(
    getMaxOutputTokensForModel(model),
    MAX_OUTPUT_TOKENS_FOR_SUMMARY,  // 20,000
  )
  let contextWindow = getContextWindowForModel(model, getSdkBetas())
  return contextWindow - reservedTokensForSummary
}
```

**公式**：

```
有效窗口 = 上下文窗口 - min(模型最大输出, 20,000)
```

**示例**（Opus 4.6 + 1M）：

```
max_context   = 1,000,000
reserved      = min(64,000, 20,000) = 20,000
effective     = 1,000,000 - 20,000 = 980,000 tokens
```

## 6. Query 流水线中的集成

**文件**：`src/query.ts`（第181-400+行）

在 Query 循环中，系统提示与上下文的集成步骤：

```
1. normalizeMessagesForAPI(messages, tools)    ← 13+ 遍消息转换
       │

       │

```
