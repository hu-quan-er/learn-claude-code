# 提示缓存与内容替换机制

> Claude Code 上下文管理分析系列 - 第3篇
> 源码版本：claude-code 2.1.88

---

## 概述

Claude Code 的提示缓存（Prompt Caching）系统通过精细的哈希指纹、双 TTL 管理和缓存编辑机制，最大化缓存命中率以降低延迟和成本。内容替换系统则负责将超大工具结果卸载到磁盘，同时维护缓存前缀的稳定性。

## 1. 提示缓存架构

### 1.1 双阶段缓存中断检测

**文件**：`src/services/api/promptCacheBreakDetection.ts`

缓存中断检测分两个阶段：

```
┌─────────────────────────────────────────────┐
│  Phase 1: 预调用状态记录                      │
│  recordPromptState()                         │
│  ├── 计算 systemHash（不含 cache_control）    │
│  ├── 计算 toolsHash（工具 schema 哈希）       │
│  ├── 计算 cacheControlHash（含 cache_control）│
│  ├── 计算 perToolHashes（逐工具 schema 哈希） │
│  └── 存储到 previousStateBySource Map        │
├─────────────────────────────────────────────┤
│  Phase 2: 后调用验证                          │
│  checkResponseForCacheBreak()                │
│  ├── 检测 token 下降 ≥ 5% 且 ≥ 2000          │
│  ├── 区分客户端/服务端/TTL 过期               │
│  └── 记录遥测 + 写入 diff 文件               │
└─────────────────────────────────────────────┘
```

### 1.2 预调用状态快照

**`recordPromptState()`**（第247行）

**哈希类型**：

| 哈希 | 计算方式 | 检测目标 |
|------|----------|----------|
| `systemHash` | 系统提示文本（不含 cache_control） | 提示文本变更 |
| `toolsHash` | 所有工具 schema | 工具定义变更 |
| `cacheControlHash` | 系统提示（含 cache_control） | scope/TTL 翻转（global↔org, 1h↔5m） |
| `perToolHashes` | 逐个工具的 schema 哈希 | 定位具体哪个工具发生变化 |

**状态存储**（`PreviousState` 类型，第28-69行）：
- 按 `querySource` 维度存储在 `previousStateBySource` Map 中
- 上限 `MAX_TRACKED_SOURCES = 10`（防止子 agent 无限增长）
- 存储调用计数、待处理变更、缓存读取 token 基线
- `cacheDeletionsPending` 标志：标记由 cached microcompact 触发的预期缓存下降

**变更检测**（`PendingChanges` 类型，第71-99行）：

三态分类字段：
- `systemPromptChanged` — 提示文本变更
- `toolSchemasChanged` — 全量 schema 变更
- `cacheControlChanged` — 仅 scope/TTL 翻转
- `changedToolSchemas` / `addedTools` / `removedTools` — 逐工具追踪
- 还追踪：beta headers、effort 值、auto-mode 状态、overage 状态

### 1.3 后调用缓存中断检测

**`checkResponseForCacheBreak()`**（第437行）

**检测公式**：

```typescript
const tokenDrop = prevCacheRead - cacheReadTokens
// 非中断条件：
if (cacheReadTokens >= prevCacheRead * 0.95 || tokenDrop < MIN_CACHE_MISS_TOKENS) {
  // 不算中断
}
// MIN_CACHE_MISS_TOKENS = 2,000
```

**中断分类**：

```
缓存中断
    │
    ├── 客户端引起
    │   ├── systemPromptChanged
    │   ├── toolSchemasChanged
    │   ├── modelChanged
    │   ├── cacheControlChanged
    │   └── betaHeadersChanged
    │
    ├── TTL 过期
    │   └── 时间间隔 > CACHE_TTL（5min 或 1h），无提示变更
    │
    └── 服务端原因
        └── 时间间隔 < 5min，提示未变 → 路由/驱逐问题
```

**调试支持**：`writeCacheBreakDiff()`（第708行）将 diff 文件写入磁盘。

## 2. TTL 管理

### 2.1 双 TTL 系统

**文件**：`src/services/api/claude.ts`

**`should1hCacheTTL()`**（第393行）：

| TTL | 适用场景 |
|-----|----------|
| **5 分钟**（默认） | 普通用户，无显式 TTL |
| **1 小时** | Ant + 订阅用户（未超额） |

**1 小时 TTL 资格判定**：

```
1. 用户类型检查：Ant 或订阅用户（非 overage）
   → 在 bootstrap state 中闩锁（latch）
   
2. GrowthBook 白名单模式匹配：
   allowlist.some(pattern =>
     pattern.endsWith('*')
       ? querySource.startsWith(pattern.slice(0, -1))
       : querySource === pattern
   )
   
3. 白名单示例：["repl_main_thread*", "sdk", "agent:*"]

4. 缓存在 STATE 中，确保会话稳定性
   → 防止 GrowthBook 中途更新翻转 TTL
```

**Bedrock 特例**：通过 `ENABLE_PROMPT_CACHING_1H_BEDROCK` 环境变量启用 1h TTL。

### 2.2 Cache Control 块应用

**`getCacheControl()`**（第358行）：

```typescript
{
  type: 'ephemeral',
  ttl?: '1h',      // 仅 should1hCacheTTL() 为 true 时
  scope?: 'global'  // 仅 useGlobalCacheScope() 为 true 时
}
```

## 3. 缓存断点与作用域管理

### 3.1 系统提示缓存

**`buildSystemPromptBlocks()`**（第3213行）：
- 将系统提示拆分为按缓存作用域划分的块
- 仅当 `enablePromptCaching && block.cacheScope !== null` 时应用 cache_control
- Global vs org scope 由 `skipGlobalCacheForSystemPrompt` flag 控制

### 3.2 消息级缓存标记

**`addCacheBreakpoints()`**（第3063行）：

**关键约束**：每个请求恰好 **1 个** cache_control 标记（优化 Mycro 的页面驱逐）。

**标记位置**：
- 正常写入：`messages.length - 1`（最后一条消息）
- Fire-and-forget fork（`skipCacheWrite=true`）：`messages.length - 2`（倒数第二条）

**设计原理**：保护共享前缀点；未保护的尾部被 page_manager 释放。

### 3.3 Tool Result 缓存引用

**第3164-3207行**：

- 在缓存前缀内（最后一个 cache_control 标记之前）添加
- 格式：`cache_reference: block.tool_use_id`
- **克隆 content 数组**防止就地修改污染复用的块

## 5. 内容替换状态机

### 5.1 大型工具结果持久化

**文件**：`src/utils/toolResultStorage.ts`

**持久化阈值逻辑**（`getPersistenceThreshold()`，第55行）：

```typescript
// GrowthBook 覆盖映射（Flag: tengu_satin_quoll）
// 硬退出：tool.maxResultSizeChars = Infinity → 跳过持久化
// 正常：min(declaredMax, DEFAULT_MAX_RESULT_SIZE_CHARS)
// 默认：50,000 字符
```

**目录结构**：
```
{projectDir}/{sessionId}/tool-results/
    ├── {toolUseId-1}.json
    ├── {toolUseId-2}.txt
    └── ...
```

**持久化流程**（`persistToolResult()`，第137行）：

1. 检查非文本内容（存在则返回错误）
2. `ensureToolResultsDir()` 确保目录存在
3. 以 `flag: 'wx'`（排他创建）写入，重放时跳过
4. 生成 2KB 预览（`PREVIEW_SIZE_BYTES = 2,000`）
5. 返回 `{filepath, originalSize, isJson, preview, hasMore}`

### 5.2 三态分类系统

```
工具结果状态
    │
    ├── fresh（新鲜）
    │   ├── 首次出现的工具结果
    │   ├── 可被选中持久化
    │   └── 按大小降序排列，最大优先
    │
    ├── frozen（冻结）
    │   ├── 已在 seenIds 中
    │   ├── 永不修改
    │   └── 保证缓存前缀跨轮次稳定
    │
    └── mustReapply（必须重应用）
        ├── 之前被持久化产生的预览
        ├── 存储在 replacements Map 中
        └── 每轮重新应用到消息中
```

### 5.3 预算选择算法

```
输入: 一组工具结果（frozen + fresh）
限制: 200K 字符（默认）

1. frozen 结果大小固定不变
2. fresh 结果按大小降序排列
3. 循环：
   while (frozen_total + remaining_fresh_total > limit):
       persit(largest_fresh)  // 持久化最大的
       fresh_total -= largest_fresh.size
       fresh_total += preview.size  // 加回预览大小
4. 非持久化候选同步标记 seen
5. 持久化候选 await 后标记 replacement
```

## 6. 闩锁式 Beta Header（会话稳定性模式）

### 6.1 设计模式

**原则**：一旦首次发送某个 beta header，在会话剩余时间内持续发送。

**被闩锁的 Headers**：

| Header | 触发条件 |
|--------|----------|
| `AFK_MODE_BETA_HEADER` | Auto mode 首次激活 |
| `FAST_MODE_BETA_HEADER` | Fast mode 首次使用 |
| `CACHE_EDITING_BETA_HEADER` | Cached MC 首次启用 |
| `THINKING_CLEAR_BETA_HEADER` | Thinking clear 首次使用 |

**设计原因**：防止会话中途切换导致 ~50-70K 已缓存 token 失效。

**清除时机**：`/clear` 和 `/compact` 命令调用 `clearBetaHeaderLatches()`。

### 6.2 消息数组修改安全

**模式**：修改前克隆数组，防止就地突变污染共享引用。

```typescript
// claude.ts 第628行
return {
  role: 'user',
  content: Array.isArray(message.message.content)
    ? [...message.message.content]  // 克隆
    : message.message.content,
}
```

**原因**：多次调用 `addCacheBreakpoints` 或插入 `cache_edits` 块会污染共享数组引用。

## 7. 媒体项剥离

### 7.1 超限媒体清理

**`stripExcessMediaItems()`**（`claude.ts` 第956行）：

```typescript
export function stripExcessMediaItems(
  messages: (UserMessage | AssistantMessage)[],
  limit: number = API_MAX_MEDIA_PER_REQUEST  // 100
): (UserMessage | AssistantMessage)[]
```

**算法**：

```
1. 统计所有消息中的媒体块总数（images + documents）
2. 计算超额：toRemove = totalCount - limit
3. 无超额 → 原样返回
4. 从最旧消息开始裁剪：
   优先级 1：tool_result 内的媒体块
   优先级 2：顶级媒体块
5. 有状态 toRemove 计数器递减
```

## 11. 架构要点总结

1. **双阶段检测**：预调用指纹捕获 + 后调用 token 分析，区分客户端变更、TTL 过期和服务端驱逐
2. **闩锁保护缓存投资**：Beta header 一旦发送就持续到 `/clear`，避免 50-70K 缓存 token 意外失效
3. **三态分类保证稳定性**：frozen/fresh/mustReapply 确保已决定的持久化决策跨轮次不变
4. **最大优先选择算法**：在预算内从最大结果开始持久化，最大化内联保留的小结果数量
5. **缓存编辑避免失效**：通过 `cache_edits` 删除旧工具结果，无需重建整个缓存前缀
6. **克隆防污染**：所有可能被多次处理的消息数组在修改前克隆，防止共享引用导致的副作用
