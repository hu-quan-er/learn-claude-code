# 08. 设计哲学 — 从 7 个 model 看 claude-code 的思考方式

> 这一篇做一件事：把前 7 篇散见的设计选择**系统化**——总结成 12 条可复用的设计原则。每条配前 7 篇里的具体例证。读完之后，你写自己的 agent CLI 或大型 TS 项目时，能直接套这些原则，**而不是抽象地"借鉴 claude-code"**。

## 1. 这 12 条不是发明，是被反复使用的

下面每条都不是 claude-code 独有——大部分是工业界 TS / TypeScript 项目的成熟模式。但 claude-code **把它们用得彻底、用得一致**——值得作为 reference 看。

阅读建议：每条读完，问自己"我自己代码里能不能用？哪里能用？"

## 2. 原则 1：用 discriminated union 替代继承

### 2.1 现象

7 个 model 几乎都用 union + `type` 字段判别。

| Model | union 形态 |
|---|---|
| Command | `Command = CommandBase & (PromptCommand \| LocalCommand \| LocalJSXCommand)`，type: 'prompt' / 'local' / 'local-jsx' |
| Message | 6 大类 union，type: 'user' / 'assistant' / 'system' / 'attachment' / 'progress' / 'tombstone' |
| SystemMessage | 14 种 subtype |
| Attachment | 30+ 种 type |
| PermissionDecision | allow / deny / ask 三态，behavior 字段判别 |
| PermissionResult | PermissionDecision \| passthrough |
| PermissionUpdate | 6 种 type（addRules / replaceRules / ...） |
| PermissionDecisionReason | 11 种 type |
| HookCallback / HookCommand | type: 'callback' / 'command' |
| HookJSONOutput | sync \| async |
| `hookSpecificOutput` | 13 种 hookEventName 特化 |
| PluginError | 30+ 种 type |

### 2.2 为什么这比继承好

```ts
// 继承（OOP 风格）
abstract class Command {
  abstract execute(): Result
}
class PromptCommand extends Command { ... }
class LocalCommand extends Command { ... }
class LocalJSXCommand extends Command { ... }

// vs

// Discriminated union (TypeScript 风格)
type Command = { type: 'prompt'; getPromptForCommand: ... }
             | { type: 'local'; load: () => Promise<...> }
             | { type: 'local-jsx'; load: () => Promise<...> }

if (cmd.type === 'prompt') {
  // TS 自动 narrow 到 PromptCommand
  cmd.getPromptForCommand(...)
}
```

#### 优势

1. **没有运行时 polymorphism overhead**——纯类型，编译期消除
2. **新 case 强制处理**——`switch` 上的 exhaustive check 让漏 case 编译报错
3. **可与 plain object 互操作**——JSON serialize/deserialize 直接还原类型
4. **不需要构造函数**——任何符合形状的对象都是合法值

### 2.3 适用场景

任何"这玩意儿有 N 种类型，每种类型字段不同"的建模。**默认选 discriminated union 而不是继承**，除非真的有共享行为（方法）需要 inherited。

## 3. 原则 2：可见性 / 可调用性 / 启用性是独立维度

### 3.1 现象

Command（02 篇 3.3 节）有 5 个独立字段管"可见 / 可调用 / 启用"：

| 字段 | 维度 |
|---|---|
| `disableModelInvocation` | 模型能否调用（行为） |
| `userInvocable` | 用户能否调用（行为） |
| `isHidden` | 在 typeahead 显示？（UI） |
| `isEnabled` | 当前启用？（动态函数） |
| `availability` | 哪种 auth 可用？（半静态） |

类似的现象在 Hook（`internal: boolean`）、Plugin（`enabled?: boolean` / `isAvailable?`）、Tool（`isReadOnly` / `isDestructive` / `isConcurrencySafe` / `isOpenWorld`）。

### 3.2 为什么不合并

合并会 force 错误的耦合。比如 `userInvocable: false` 和 `isHidden: true` 通常一起出现——但**允许独立**让"deprecated 但还能用 / 在补全里隐藏"等场景能精确建模。

### 3.3 适用场景

每发现一个 boolean 字段时问：

- 这个布尔的"true 含义"和现有某字段是否完全一样？
- 是否存在两者**意图不同**的场景？

如果存在"通常一起、但偶尔分开"——**用两个字段**。冗余比强耦合好。

## 4. 原则 3：来源（source / loadedFrom）是 first-class 元数据

### 4.1 现象

```
Command:
  source: SettingSource | 'builtin' | 'mcp' | 'plugin' | 'bundled'
  loadedFrom: 'commands_DEPRECATED' | 'skills' | 'plugin' | 'managed' | 'bundled' | 'mcp'

PermissionRule:
  source: PermissionRuleSource (8 种)

PluginError:
  source: string                      // 几乎每个 error 都有

Plugin:
  source: string
  repository: string
```

来源不是被遗忘的元数据——它是**驱动决策的核心字段**：

- `source` 决定信任级别（admin trusted / user / 远程不可信）
- `source` 决定 UI 标签（`(Plugin) ...` / `(MCP) ...`）
- `source` 决定权限策略（plugin-only 模式下哪些能注册 hooks）
- `loadedFrom` 决定菜单分组（`/skills` 菜单按它分组）
- `loadedFrom` 决定可见性过滤（bundled 不进 `/skills`）

### 4.2 为什么这么重要

在 plugin / MCP 这种**多源 + 安全要求高**的系统里，**来源决定一切信任决策**。把它建模成 first-class 字段而不是"埋在配置里某个深层 path"——任何代码读到对象都能立即决策。

### 4.3 适用场景

任何"对象可能来自多个不同来源、来源影响信任 / UI / 行为"的系统。**第一个该加的字段就是 source**——别等到 bug 后才追加。

## 5. 原则 4：内部 / 外部 API 严格区分

### 5.1 现象

```ts
// types/permissions.ts
ExternalPermissionMode = 'acceptEdits' | 'bypassPermissions' | 'default' | 'dontAsk' | 'plan'
InternalPermissionMode = ExternalPermissionMode | 'auto' | 'bubble'

// settings 里只能写 External 的；运行时类型是 Internal
```

```ts
// hooks.ts
export const HOOK_EVENTS = [...] as const  // SDK 暴露
const ALWAYS_EMITTED_HOOK_EVENTS = ['SessionStart', 'Setup'] as const  // 内部
```

```ts
// tool.ts buildTool defaults
isConcurrencySafe: () => false,  // 内部默认；但 type 上声明为 required
```

### 5.2 为什么

外部 API 是稳定契约——改了破坏用户。内部状态是实现细节——可以自由演化。把它们用类型层**显式分开**让重构安全。

### 5.3 适用场景

任何 SDK / Plugin 系统里。**前缀化** `External / Internal` 让阅读者立刻知道契约边界。

## 6. 原则 5：用 zod schema 作为 SDK / config 的真理之源

### 6.1 现象

Hook 系统：

```ts
export const syncHookResponseSchema = lazySchema(() => z.object({...}))
type SchemaHookJSONOutput = z.infer<ReturnType<typeof hookJSONOutputSchema>>

// 编译期断言：zod schema 推导出的类型 必须 等于 SDK 类型
type _assertSDKTypesMatch = Assert<IsEqual<SchemaHookJSONOutput, HookJSONOutput>>
```

类似的：`promptRequestSchema`、`permissionUpdateSchema`、`HooksSchema` 等。

### 6.2 为什么 schema-first

zod schema 同时是：

- **runtime validator**——hook 命令 stdout 解析
- **TS 类型推导源**——`z.infer<...>`
- **JSON Schema 生成源**——MCP 协议交换
- **API 文档**

如果 SDK 类型和 schema 不一致，会有"运行时校验通过但类型不对"的隐患。**Assert 编译期断言**强制对齐——任何一边变化另一边没跟上，编译就报错。

### 6.3 适用场景

任何对外暴露 JSON 协议的 boundary——hook output、SDK params、config schema、MCP messages。**用 zod 一处定义，多处 derive**——而不是 TS 类型 + 单独 JSON Schema 文件 + 单独 validator function 三处维护。

## 7. 原则 6：type-first 设计——先建模错误再实现

### 7.1 现象

`PluginError` 30+ 种 type，IMPLEMENTATION STATUS 注释明说"当前生产用 2 种，10+ 种规划中"。

### 7.2 为什么

把"将来可能发生的错误"**提前用类型表达**：

1. 错误的字段精确（exitCode / signal / timeoutMs 各自带最有信息量的字段）
2. UI 渲染逻辑能 **forward-compat**——`getPluginErrorMessage` 把所有 type 处理掉，新加 type 强制更新 formatter
3. 重构有路标——`pluginLoader.ts` TODO 注释指向"这里产生 generic-error，应改成 git-auth-failed"

### 7.3 适用场景

任何**错误信息很重要**的系统——CLI / API server / 开发工具。错误不是兜底的 `string`，而是**第一公民**。先建好 schema，慢慢实现。

## 8. 原则 7：跨受众分字段——人 vs 模型 vs 持久化

### 8.1 现象

```
Command.description       // 给人看（typeahead）
Command.whenToUse        // 给模型看（system prompt skill_listing）

Message.isMeta           // 给人看？（不）模型看？（看）
Message.isVisibleInTranscriptOnly  // 给人看？（看）模型？（不）
Message.isVirtual        // 不持久（不进 transcript）
```

### 8.2 为什么这么细

人和模型对信息的**偏好和容量都不同**：

- 人的 description 要 1 行短
- 模型的 whenToUse 可以多行详细
- 持久化的 conversation 不必含 isVirtual 临时占位

如果把"消息内容"和"展示给谁"耦合在一起（比如只用 `content: string`），三方都不爽。

### 8.3 适用场景

任何"输出有多个受众"的系统。**人 / 模型 / 系统 / 持久化**经常要分别建模——不要假设它们想要的一样。

## 9. 原则 8：immutable + state-as-snapshot

### 9.1 现象

- AppState 用 `DeepImmutable` 包裹
- ToolPermissionContext 全 readonly
- updates 通过 `setAppState((prev) => next)` 函数式更新
- speculation state 用 `{ current: ... }` ref 模式避免 spread 复制

### 9.2 为什么

immutability 让以下变简单：

- React re-render 只检查 ref 相等（O(1) 而不是 O(n)）
- conversation recovery / time-travel debugging 只是保存 state 历史
- 多 reader 不会 race

但**不强求 100%**——`tasks: { [agentId]: TaskState }` 因为 TaskState 含 function 类型，被显式排除在 DeepImmutable 之外。**承认现实，best-effort**。

### 9.3 适用场景

任何带 React UI 或需要 recovery 的状态系统。学 Redux / Zustand 那一套——但允许少量 mutable escape hatch。

## 10. 原则 9：epoch counter 触发 effect

### 10.1 现象

```ts
// AppState
mcp: { ..., pluginReconnectKey: number }   // /reload-plugins 时 +1
authVersion: number                         // login/logout 时 +1
```

值本身没语义，**变化**有语义。React effect 把它列为 dep，值变就 re-run。

### 10.2 为什么不用 boolean / 事件总线

Boolean toggle 容易丢——如果先变 true 再变 false（再变 true），中间变化可能错过。Counter 永远递增，每次 +1 都唯一对应一次"事件"。

事件总线（pub/sub）更复杂——counter 是它的极简实现，借助 React 的 dep 监听机制。

### 10.3 适用场景

React 项目里"状态本身没变但需要重做某事"的场景——常用于：

- 重连
- 重新 fetch
- 刷新缓存

## 11. 原则 10：callback as protocol（不是 promise）

### 11.1 现象

```ts
// LocalJSXCommand
type LocalJSXCommandOnDone = (
  result?: string,
  options?: { display?, shouldQuery?, metaMessages?, nextInput?, submitNextInput? },
) => void

// Tool
onProgress?: ToolCallProgress<P>           // 多次调

// SetAppState
setAppState: (f: (prev: AppState) => AppState) => void  // updater function
```

### 11.2 为什么不一律用 promise / async iterator

- **多次回调**：onProgress 不止一次，promise 不擅长
- **UI 驱动**：onDone 由用户点按钮触发，不是函数返回——promise resolve 时机不对
- **协议丰富**：onDone 多个可选 options，函数签名表达力强
- **同步 + 异步混合**：setAppState updater function 可同步、可异步

callback API **更原始但更灵活**。在合适场景比 promise 更自然。

### 11.3 适用场景

任何"产生多次结果"或"由外部事件 trigger 完成"的接口。**不要 force everything into Promises**。

## 12. 原则 11：巨型 context 做信封

### 12.1 现象

```
ToolUseContext (Tool.ts:158-300):  50+ 字段
AppState     (AppStateStore.ts):   95+ 字段
Tool 接口    (Tool.ts:362-695):    45+ 字段
```

### 12.2 为什么不分拆成多个小对象

实际系统里"运行环境"包含**很多正交的能力**——log / state / abort / progress / commands / messages / agentId / fileLimits / permissionContext / ...

如果分成 10 个小对象传参，每个 tool / 每个组件都要接 10 个参数——签名爆炸。或者用 6-7 层 context provider——又很难追踪谁读了什么。

巨型 context 用一个对象承载所有——**承认现实**。每个消费方按需读字段，TypeScript 类型保证只能访问声明的字段。

### 12.3 适用场景

任何"运行环境复杂、有几十个独立能力"的系统。比如 web 框架的 request context、game engine 的 game state context、agent 的 tool execution context。

**反向不该用**：如果 context 字段只有 5-10 个、每个都被广泛使用——那分拆更清晰。

## 13. 原则 12：细粒度的 prompt cache 优化

### 13.1 现象

```
relevant_memories.header           // 预计算冻结，避免渲染时调 Date.now()
ToolUseContext.renderedSystemPrompt // fork 时冻结父 prompt 字节
ContentReplacementState              // tool result 长度膨胀时持久化外存
```

每条都是为了**保证相同语义在不同 turn 产生相同字节**——这是 prompt cache 命中率的硬要求。

### 13.2 为什么这么"卷"

Anthropic API 的 prompt cache 按 prefix 命中——如果 system prompt 字节有任何细微变化，从那点开始全部 cache miss。一个长 conversation 可能有几万 token 的 prefix，一次 miss 多花几十毫秒 + 几美分。

每个细节都是 **"渲染输出冻结" 的实例**：渲染层不能调 Date.now()、不能算"几天前"、不能 spread 大数组——一切让字节稳定。

### 13.3 适用场景

任何用 Anthropic / 其它有 prompt cache 的 LLM 服务的系统。**性能优化的 90% 来自这里**——不是模型选 vs 工具选。

## 15. 最终一段：写自己的 agent CLI 时怎么用

如果你要写一个类似 Claude Code 的 agent 工具，本系列建议的"最小起步集"：

### 15.1 第一周

- 定义 **Command 模型**（discriminated union + 可见性独立维度）
- 定义 **Tool 接口**（接受巨型 context、返回 ToolResult）
- 定义 **Message 模型**（user / assistant / system + isMeta 等可见性）

### 15.2 第二周

- 添加 **Permission 模型**（rules + decisions + reasons）
- 添加 **AppState** 单一全局 state
- 把 Tool 和 Permission 联起来（tool.checkPermissions 返回 PermissionResult）

### 15.3 第三周

- 添加 **Hook 模型**（事件 + 特化 schema）
- 把 Hook 和 Permission / Tool 联起来

### 15.4 第四周

- 添加 **Plugin 模型**（type-first 错误集 + LoadedPlugin）

### 15.5 关键 reflexes

- 想加 boolean？先想"和现有字段维度是否相同"
- 想用 string 兜底错误？先想"这个错误有几种状态值得区分"
- 想 promise？先想"这是单结果还是多次回调"
- 想拆 store？先想"跨子系统依赖多吗、recovery 复杂吗"
- 渲染时算时间？先想"明天再渲染会不会变字节"

每一条都是 claude-code 团队踩过坑学到的——**继承经验比模仿代码更值钱**。

## 16. 这一系列结束

恭喜——你完整走完了 7 个核心 model + 1 篇地图 + 1 篇哲学，共 9 篇。

如果带走一个总印象，应该是：**复杂的 agent CLI 不是设计灾难——只要每个决策维度被显式建模、每条边界被类型表达、每种错误被 first-class 处理**。

claude-code 的代码不"优雅"——但它**真实**。每个看似冗余的字段、每个看似过度的 union 分支，背后都有一个具体场景、一次踩坑、一项需求。**完美抽象在生产系统里不存在**——只有"诚实建模 + 持续重构"。

下次你打开一个大型 TS 项目源码，希望这 9 篇能让你**看懂为什么这么写**——而不是被吓退。
