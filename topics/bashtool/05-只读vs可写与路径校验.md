# 05 只读 vs 可写 + 路径校验

> 两个 ~1500 行的文件做一件事：**区分"无副作用的命令"和"会改/读敏感东西的命令"**。本篇拆 `readOnlyValidation.ts` 1990 行 + `pathValidation.ts` 1303 行的双重过滤。

## 5.1 为什么需要"只读" 概念

permission 决策的兜底（`bashPermissions.ts:1154-1163`）：

```ts
// 7. Check read-only rules
if (BashTool.isReadOnly(input)) {
  return {
    behavior: 'allow',
    updatedInput: input,
    decisionReason: { type: 'other', reason: 'Read-only command is allowed' },
  }
}
```

只读命令默认 allow——不弹窗、不打扰用户。这是 BashTool 的"低摩擦体验"基础：

- `ls`、`cat`、`grep`、`find` 这些没副作用的命令直接放行；
- 用户不需要为每条 `git status` 点确认；
- 模型可以高频探索代码库。

但**只读判定必须严格**——一旦判错（把"看起来只读但实际能写"当成只读）就完全绕过权限。所以 `readOnlyValidation` 是 1990 行的庞然大物。

## 5.3 COMMAND_ALLOWLIST —— flag 级别的命令配置

`readOnlyValidation.ts:128+` 是个庞大的 `COMMAND_ALLOWLIST` Record：

```ts
const COMMAND_ALLOWLIST: Record<string, CommandConfig> = {
  xargs: {
    safeFlags: {
      '-I': 'string',
      '--replace': 'string',
      '-n': 'number',
      '--max-args': 'number',
      // ... etc
    },
    additionalCommandIsDangerousCallback: (raw, args) => { ... },
  },
  fd: { safeFlags: FD_SAFE_FLAGS, ... },
  rg: { safeFlags: RIPGREP_READ_ONLY_COMMANDS, ... },
  // ... 几十个命令
}
```

每个命令配置：

```ts
type CommandConfig = {
  safeFlags: Record<string, FlagArgType>
  regex?: RegExp
  additionalCommandIsDangerousCallback?: (raw: string, args: string[]) => boolean
  respectsDoubleDash?: boolean
}

type FlagArgType = 'none' | 'string' | 'number' | 'optional-string'
```

每个 flag 都标了**它要不要参数、参数是什么类型**。这让 validator 能精确解析 argv。

### 例：FD_SAFE_FLAGS 的设计

```ts
const FD_SAFE_FLAGS: Record<string, FlagArgType> = {
  '-h': 'none',
  '--help': 'none',
  // ... 各种安全 flag

  // SECURITY: -x/--exec and -X/--exec-batch are deliberately excluded —
  // they execute arbitrary commands for each search result.
  // (-x 和 -X 不在白名单 → fd -x ... 会被判非只读)

  // SECURITY: -l/--list-details EXCLUDED — internally executes `ls` as subprocess
  // (same pathway as --exec-batch). PATH hijacking risk if malicious `ls` is on PATH.

  '-L': 'none',           // --follow
  '-d': 'number',         // --max-depth
  '-t': 'string',         // --type
  '-E': 'string',         // --exclude
  // ...
}
```

**deliberately excluded** 标记的 flag：
- `fd -x` / `fd --exec`：对每个搜索结果执行命令 → 完全不安全；
- `fd -l` / `fd --list-details`：内部 spawn `ls` → 受 PATH 污染影响。

`fd -l` 被排除是个非常细的判断——它"看起来只读"但实际触发 subprocess，可被 PATH hijacking。

## 5.4 validateFlags —— 通用 flag 解析

`utils/shell/readOnlyCommandValidation.ts` 里的 `validateFlags` 是通用 flag 解析器。它根据 `CommandConfig.safeFlags` 检查命令行：

```
for arg in argv:
  if arg starts with '-':
    if arg in safeFlags:
      if safeFlags[arg] === 'string' or 'number':
        consume next arg as value
      // else 'none', no value to consume
    else:
      return UNSAFE  // 未识别的 flag = 不安全
  else:
    // 位置参数 - 不检查 flag 但要给 path validation 处理
```

**fail-closed**：任何不在白名单的 flag → 直接判定不安全。新版本工具加了新 flag → Claude Code 默认不认 = 不放行。

## 5.5 commandHasAnyCd / commandWritesToGitInternalPaths —— 复合命令分析

`readOnlyValidation.ts` 里还有专门处理 git 攻击向量的逻辑。

### 攻击 1：`cd /malicious/dir && git status` —— 沙箱逃逸

注释（`readOnlyValidation.ts:1914-1923`）：

```ts
// SECURITY: Block compound commands that have both cd AND git
// This prevents sandbox escape via: cd /malicious/dir && git status
// where the malicious directory contains fake git hooks that execute arbitrary code.
if (compoundCommandHasCd && hasGitCommand) {
  return {
    behavior: 'passthrough',
    message: 'Compound commands with cd and git require permission checks for enhanced security',
  }
}
```

`git status` 默认是只读命令。但如果先 `cd` 到攻击者控制的目录，那个目录里有 `.git/hooks/post-status` 之类的 hook → `git status` 触发 hook → **任意代码执行**。

修复：**任何含 `cd` 的复合命令 + git 子命令** → 强制走 permission prompt。

### 攻击 2：bare repo 探测 —— 沙箱逃逸

注释（`readOnlyValidation.ts:1925-1935`）：

```ts
// SECURITY: Block git commands if the current directory looks like a bare/exploited git repo
// This prevents sandbox escape when an attacker has:
// 1. Deleted .git/HEAD to invalidate the normal git directory
// 2. Created hooks/pre-commit or other git-internal files in the current directory
// Git would then treat the cwd as the git directory and execute malicious hooks.
if (hasGitCommand && isCurrentDirectoryBareGitRepo()) { ... }
```

攻击者把当前目录构造成"看起来像 bare git repo"（删 `.git/HEAD`、加 `hooks/pre-commit`）→ git 把 cwd 当 `$GIT_DIR` → 触发 hook。

修复：检测到当前目录像 bare repo → 拒绝任何 git 命令。

### 攻击 3：先写 git 内部文件再跑 git

注释（`readOnlyValidation.ts:1937-1948`）：

```ts
// SECURITY: Block compound commands that write to git-internal paths AND run git
// Example attack: mkdir -p hooks && echo 'malicious' > hooks/pre-commit && git status
if (hasGitCommand && commandWritesToGitInternalPaths(command)) { ... }
```

复合命令里**先创建** git 内部路径（hooks/objects/refs/HEAD）**再跑** git → 任意代码执行。

修复：扫描复合命令的所有 subcommand，看有没有写 git 内部路径的；如果有 + git 命令 → 拒绝。

### 攻击 4：竞态 —— cwd 在评估时和执行时不同

注释（`readOnlyValidation.ts:1950-1964`）：

```ts
// SECURITY: Only auto-allow git commands as read-only if we're in the original cwd
// (which is protected by sandbox denyWrite) or if sandbox is disabled (attack is moot).
// Race condition: a sandboxed command can create bare repo files in a subdirectory,
// and a backgrounded git command (e.g. sleep 10 && git status) would pass the
// isCurrentDirectoryBareGitRepo() check at evaluation time before the files exist.
if (
  hasGitCommand &&
  SandboxManager.isSandboxingEnabled() &&
  getCwd() !== getOriginalCwd()
) { return { behavior: 'passthrough', ... } }
```

竞态攻击：
1. 评估时 cwd 是 `/project`，`isCurrentDirectoryBareGitRepo()` 返回 false → 放行；
2. 命令 `sleep 10 && git status` 启动，sleep 期间另一个命令在 `/project/sub/` 创建了 bare repo 文件；
3. 10 秒后 git status 执行，假设 cwd 是 `/project/sub/` → 触发恶意 hook。

修复：sandbox 启用 + cwd 不在 originalCwd → 拒绝（origCwd 受 sandbox denyWrite 保护，不可能被构造成 bare repo）。

这是个非常细的**TOCTOU（time-of-check / time-of-use）**漏洞修复。

## 5.6 pathValidation.ts —— 路径级拦截

`pathValidation.ts:27-63` 定义了 `PathCommand`——需要做路径校验的命令清单：

```ts
export type PathCommand =
  | 'cd' | 'ls' | 'find' | 'mkdir' | 'touch' | 'rm' | 'rmdir' | 'mv' | 'cp'
  | 'cat' | 'head' | 'tail' | 'sort' | 'uniq' | 'wc' | 'cut' | 'paste'
  | 'column' | 'tr' | 'file' | 'stat' | 'diff' | 'awk' | 'strings'
  | 'hexdump' | 'od' | 'base64' | 'nl' | 'grep' | 'rg' | 'sed' | 'git'
  | 'jq' | 'sha256sum' | 'sha1sum' | 'md5sum'
```

35 个常见 unix 命令。每个都有路径参数，每个的路径需要校验。

### PATH_EXTRACTORS —— 命令到路径提取器的映射

`pathValidation.ts:190` 的 `PATH_EXTRACTORS` 是个 Record，每个命令一个**提取函数**：

```ts
export const PATH_EXTRACTORS: Record<PathCommand, (args: string[]) => string[]> = {
  ls: (args) => filterOutFlags(args),
  cat: (args) => filterOutFlags(args),
  // ...
  grep: (args) => parsePatternCommand(args, GREP_FLAGS_WITH_ARGS, ['.']),
  // ...
}
```

每种命令有自己的 argv 结构——`grep pattern file file file` 第一个非 flag 是 pattern 不是路径；`find ./dir -name xxx` 第一个非 flag 是路径但后面的 flag 也带路径；`mv src dst` 两个路径角色不同。

每个 extractor 知道自己命令的语义，返回路径列表。

### COMMAND_OPERATION_TYPE —— 读 vs 写

`pathValidation.ts:552`：

```ts
export const COMMAND_OPERATION_TYPE: Record<PathCommand, FileOperationType> = {
  cd: 'read',
  ls: 'read',
  cat: 'read',
  mkdir: 'write',
  touch: 'write',
  rm: 'write',
  mv: 'write',
  cp: 'write',
  cat: 'read',
  // ...
}
```

每个命令是读还是写。这影响**路径校验走 readAllowed 还是 writeAllowed**——sandbox 的读限制和写限制是分开的。

## 5.7 filterOutFlags —— `--` 末尾标志符的正确处理

`pathValidation.ts:126-139`：

```ts
function filterOutFlags(args: string[]): string[] {
  const result: string[] = []
  let afterDoubleDash = false
  for (const arg of args) {
    if (afterDoubleDash) {
      result.push(arg)
    } else if (arg === '--') {
      afterDoubleDash = true
    } else if (!arg?.startsWith('-')) {
      result.push(arg)
    }
  }
  return result
}
```

注释（`pathValidation.ts:110-124`）描述了一个真实漏洞：

> Most commands (rm, cat, touch, etc.) stop parsing options at `--` and treat ALL subsequent arguments as positional, even if they start with `-`. Naive `!arg.startsWith('-')` filtering drops these, causing path validation to be silently skipped for attack payloads like:
>
>   `rm -- -/../.claude/settings.local.json`
>
> Here `-/../.claude/settings.local.json` starts with `-` so the naive filter drops it, validation sees zero paths, returns passthrough, and the file is deleted without a prompt. With `--` handling, the path IS extracted and validated.

具体攻击：

```bash
rm -- -/../.claude/settings.local.json
```

- `-/.../settings.local.json` 是合法 unix 文件名（以 `-` 开头）；
- `rm --` 之后的所有参数都当路径处理（POSIX 标准）；
- 朴素的 `!arg.startsWith('-')` 过滤 → 把它当 flag 丢掉；
- path validation 看到 0 个路径 → passthrough；
- rm 真正执行 → 删除了 settings 文件。

修复：识别 `--` 标志符，之后所有参数都当路径。

## 5.8 checkDangerousRemovalPaths —— rm 路径黑名单

`pathValidation.ts:65-108`：

```ts
function checkDangerousRemovalPaths(
  command: 'rm' | 'rmdir',
  args: string[],
  cwd: string,
): PermissionResult {
  const extractor = PATH_EXTRACTORS[command]
  const paths = extractor(args)

  for (const path of paths) {
    const cleanPath = expandTilde(path.replace(/^['"]|['"]$/g, ''))
    const absolutePath = isAbsolute(cleanPath)
      ? cleanPath
      : resolve(cwd, cleanPath)

    if (isDangerousRemovalPath(absolutePath)) {
      return {
        behavior: 'ask',
        message: `Dangerous ${command} operation detected: '${absolutePath}'\n\nThis command would remove a critical system directory. This requires explicit approval and cannot be auto-allowed by permission rules.`,
        decisionReason: { ... },
        suggestions: [],  // 不提供 suggestion - 不鼓励用户保存危险命令
      }
    }
  }

  return { behavior: 'passthrough', ... }
}
```

`isDangerousRemovalPath`（在 `utils/permissions/pathValidation.ts`）是个黑名单：`/`、`/usr`、`/etc`、`/var`、`/bin`、`~`、`~/.ssh`、`~/.aws`、`~/.config` 等。

**关键：cannot be auto-allowed by permission rules**——这条规则**优先于**用户配置的 allow 规则。即使用户配了 `Bash(rm -rf:*)`（不太可能但万一），也无法用 `rm -rf /` 通过。

注意 **不检查 symlink 解析后的路径**：

```
NOTE: We check the path WITHOUT resolving symlinks, because dangerous paths
like /tmp should be caught even though /tmp is a symlink to /private/tmp on macOS
```

macOS 上 `/tmp` 是 `/private/tmp` 的 symlink。检查 symlink 解析后的路径会让 `/tmp` 不在黑名单（变成 `/private/tmp`）→ 漏过。所以保留原始路径。

和 [04 permission 决策](./04-permission决策核心.md) 的 `stripSafeWrappers` 配对，但**操作 argv[] 而不是字符串**。注释明确（在 bashPermissions.ts:544-553）：

> SECURITY: keep in sync with checkSemantics wrapper-strip (ast.ts ~:1990-2080) AND stripWrappersFromArgv (pathValidation.ts ~:1260). Previously this pattern REQUIRED `-n N`; checkSemantics already handled bare `nice` and legacy `-N`. Asymmetry meant checkSemantics exposed the wrapped command to semantic checks but deny-rule matching and the cd+git gate saw the wrapper name.

**三个独立函数必须保持同步**：
- `bashPermissions.ts:stripSafeWrappers`（字符串级）
- `pathValidation.ts:stripWrappersFromArgv`（argv 级）
- `ast.ts:checkSemantics` 的 wrapper-strip（AST 级）

PR #21503 修过它们的不对称——`nice rm -rf /` 被 deny 规则识别为 `Bash(rm:*)` 命中 deny，但 cd+git gate 看到 wrapper name `nice`，gate 漏检。修复要求三个函数都按一致方式剥 wrapper。

这是工业代码中**多处实现必须同步**的典型痛点——每加一种 wrapper 要同时改 3 处，加新 wrapper 时容易遗漏。

## 5.10 checkPathConstraints —— 顶层路径校验

`pathValidation.ts:1013` 的 `checkPathConstraints` 是 `bashPermissions.ts:1106-1119` 调用的入口。简化逻辑：

```ts
export function checkPathConstraints(
  input,
  cwd,
  toolPermissionContext,
  compoundCommandHasCd,
  astRedirects,
  astCommands,
): PermissionResult {
  // 1. 拆复合命令为子命令列表
  const subcommands = astCommands ?? splitCommand_DEPRECATED(input.command).map(s => parseCommand(s))

  // 2. 提取每个子命令的路径 + 操作类型
  for (const subcmd of subcommands) {
    const baseCmd = subcmd.argv[0]
    if (!(baseCmd in PATH_EXTRACTORS)) continue  // 不在 PathCommand 列表

    const paths = PATH_EXTRACTORS[baseCmd](subcmd.argv.slice(1))
    const opType = COMMAND_OPERATION_TYPE[baseCmd]

    // 3. 对每个路径做校验
    for (const path of paths) {
      // - rm/rmdir 特殊：checkDangerousRemovalPaths
      // - 检查 path 是否在 sandbox 允许列表
      // - 检查 path 是否在 .claude 配置目录
      // - 检查 path 是否在 workingDirectories
    }
  }

  // 4. 检查重定向目标
  for (const redirect of astRedirects ?? []) {
    if (redirect.op in ['>', '>>', '>&', '&>', '&>>', '>|']) {
      // 写重定向 → 校验 redirect.target
      validatePath(redirect.target, 'write', ...)
    }
  }
}
```

3 层校验：

1. **PathCommand 级**：对每个识别的命令提取路径；
2. **重定向级**：`cmd > /etc/passwd` 即使 cmd 是 echo 也要拦；
3. **复合命令逐 subcommand**：`ls && rm -rf /` 拆开后第 2 段独立校验。

## 5.11 几个隐性设计判断

### 1. 用 allowlist 而不是 deny 列表

`COMMAND_ALLOWLIST` 只列**已知安全的 flag**，遇到新 flag 默认不安全。这种 **allowlist-only** 设计意味着：

- 工具升级加了新 flag → Claude Code 不认 → 默认走 ask；
- 不会因为"漏写一条 deny"留下未知 attack surface；
- 维护成本：每加一个工具或一个新 flag 都要更新清单。

这是经典的 **fail-closed 思路**——和 02 篇的 tree-sitter allowlist 完全同款。

### 2. 多处 PR # / HackerOne 引用

注释里 PR #21503 / HackerOne #3543050 / "naive filter drops it" 等等——每条都对应真实漏洞或重构。这条工程文化和 04 篇完全一致：**漏洞编号即代码注释**。

### 3. rm 危险路径**无法被规则覆盖**

`checkDangerousRemovalPaths` 注释 "**cannot be auto-allowed by permission rules**"。这是一个**硬规则**——即使用户的 allow 规则覆盖了，依然 ask。这种"用户规则之上的元规则"是高风险操作的兜底防线。

### 4. `--` POSIX 标志的正确处理

`filterOutFlags` 的 `--` 处理是个**5 行代码、防一类完整攻击**的典型——`rm -- -/../...` 这种攻击不靠 `--` 处理就完全绕过。这种**协议层细节**容易被忽略，但攻击者会精确利用。

### 5. symlink 不解析以保护黑名单

`isDangerousRemovalPath` 用 raw 路径而非 realpath——这避免 `/tmp → /private/tmp` 这类 symlink 让黑名单失效。

### 6. 三处 wrapper-strip 必须同步

`bashPermissions / pathValidation / ast.ts` 各有一套 wrapper 剥离逻辑。这种代码重复是个**已知 tech debt**——任何"添加新 wrapper 类型"的 PR 必须改 3 处，漏掉就引入不对称漏洞（如 PR #21503 修的那种）。

工业代码里这种"必须同步的兄弟函数"很常见。理想是抽出共享 helper，但 BashTool 的三处由于上下文不同（字符串 vs argv vs AST 节点）难以完全统一。

### 7. TOCTOU 漏洞修复

竞态修复（`getCwd() !== getOriginalCwd()` 时拒绝 git 命令）是个非常细的安全考虑——sandbox 启用后，**评估时 cwd 安全 ≠ 执行时 cwd 安全**。

这种 TOCTOU 思维是从系统安全工程移植到 LLM agent 工程的——很少见，但很有价值。

## 5.12 小结

- 两个文件 ~3300 行做"区分只读 vs 可写"和"路径黑/白名单"；
- `COMMAND_ALLOWLIST` 用 flag 级别的 allowlist——遇到新 flag 默认不安全（fail-closed）；
- 多个 git 攻击向量被显式拦截：cd+git 复合、bare repo 探测、写 git 内部文件、TOCTOU 竞态；
- `checkDangerousRemovalPaths` 用**不解析 symlink** 的原始路径检查 rm 危险目标，且**无法被用户规则覆盖**；
- `filterOutFlags` 的 POSIX `--` 处理防一类完整攻击（5 行代码挡 `rm -- -/../...`）；
- `stripWrappersFromArgv` / `stripSafeWrappers` / `ast.ts:checkSemantics` 三处必须同步——已知 tech debt；
- 每条规则都来自真实漏洞修复——注释里有 PR # / HackerOne 引用。
