# 07 - 工具继承与隔离机制

## 三个独立的问题

子代理"看到的世界"由三件正交的事决定：

1. **工具数组**：模型能调用哪些 tool（API `tools[]` 数组的内容）
2. **fork 隔离**：子代理的 conversation messages 是从零开始还是继承父对话
3. **worktree 隔离**：子代理的文件系统视图是父 cwd 还是独立 git worktree

可以两两正交组合。一个 fork + worktree 的子代理会继承父对话历史 + 独立文件视图；一个普通 subagent + worktree 是从零对话 + 独立文件视图。

## 工具数组的两条计算路径

`runAgent.ts:500-502`：

```typescript
const resolvedTools = useExactTools
  ? availableTools                                              // fork: 父的完整 tool pool
  : resolveAgentTools(agentDefinition, availableTools, isAsync).resolvedTools  // 普通：过滤
```

- **fork 路径**：直接用 `AgentTool.tsx` 传进来的 `toolUseContext.options.tools`——父对话的完整工具数组。目的是 cache-identical。
- **普通路径**：从 `availableTools` 出发，按 agent 定义的 `tools` 白名单和 `disallowedTools` 黑名单过滤。

## availableTools 是怎么来的

`AgentTool.tsx:573-577` 在 spawn 时**重新组装**子代理可见工具池：

```typescript
const workerPermissionContext = {
  ...appState.toolPermissionContext,
  mode: selectedAgent.permissionMode ?? 'acceptEdits'
}
const workerTools = assembleToolPool(workerPermissionContext, appState.mcp.tools)
```

注释（`AgentTool.tsx:568-572`）：

> Assemble the worker's tool pool independently of the parent's. Workers always get their tools from assembleToolPool with their own permission mode, so they aren't affected by the parent's tool restrictions.

也就是说：子代理的"原始工具池"不是父代理的工具池，而是用子代理自己的 permission mode 重算一次。`assembleToolPool` 在 `src/tools.ts`，按 permission mode 决定哪些工具进入（Plan 模式下排除 Edit/Write/Bash 的写命令等）。

这一层隔离很关键：父代理在 Plan 模式不能 Edit，但 spawn 出去的子代理（permissionMode 默认 `acceptEdits`）可以 Edit。"子代理跳出 Plan 限制"是设计意图，不是 bug——Plan 模式是给主代理"先规划再实施"用的，spawn 干活的子代理本来就要实施。

## resolveAgentTools 的过滤链

`agentToolUtils.ts:122-216` 是普通路径的过滤函数。流程：

```text
availableTools (来自 assembleToolPool)
        ↓
[1] filterToolsForAgent
    ├── 所有 mcp__ 工具 pass through
    ├── 命中 ALL_AGENT_DISALLOWED_TOOLS → drop
    ├── 非 built-in 且命中 CUSTOM_AGENT_DISALLOWED_TOOLS → drop
    ├── isAsync 且不在 ASYNC_AGENT_ALLOWED_TOOLS → drop（in-process teammate 例外）
    └── 否则 keep
        ↓
filteredAvailableTools
        ↓
[2] 应用 disallowedTools
    └── 按 agent 定义的 disallowedTools 移除（去除 permissionRule 前缀后的 toolName）
        ↓
allowedAvailableTools
        ↓
[3] 应用 tools（白名单）
    ├── 不写 / 写 ['*']：返回 allowedAvailableTools（即拒后剩下的全集）
    └── 显式数组：按 toolSpec 逐个查表
        ├── 找到 → 加入 resolved + validTools
        └── 找不到 → invalidTools
        ↓
resolvedTools
```

注意 `tools: ['*']` 在源码里被解析成 `hasWildcard = true`——不是字面字符串 `*`，而是"通配模式"。`generalPurposeAgent` 用 `tools: ['*']` 就是这个意思。

### ALL_AGENT_DISALLOWED_TOOLS

来自 `src/constants/tools.ts`。这些工具**任何 subagent 都不能用**，无论 built-in 还是 custom：

- 通常包含：`SkillTool`（子代理不能再触发 skill）、`ToolSearchTool`（子代理工具池已固定，不需要再 search）、某些 plan mode 内部工具等

### CUSTOM_AGENT_DISALLOWED_TOOLS

custom（非 built-in）agent 额外禁用的工具：

- 通常包含一些"内部 only"的工具，比如某些 SDK 通信工具

### ASYNC_AGENT_ALLOWED_TOOLS

async agent 允许的**白名单**（不在内的全禁掉）：

- 通常包含基础读写工具，禁用 `AskUserQuestion`（async agent 无法弹 UI 问用户）

例外：in-process teammate 即使 async 也允许 AgentTool 和 IN_PROCESS_TEAMMATE_ALLOWED_TOOLS（让 teammate 能 spawn sync 子代理 + 协调任务列表）。

## allowedTools 在 agent 工具规范中的特殊含义

`agentToolUtils.ts:186-204`：

```typescript
for (const toolSpec of agentTools) {
  const { toolName, ruleContent } = permissionRuleValueFromString(toolSpec)

  // 特殊：Agent 工具的 spec 可携带 allowedAgentTypes
  if (toolName === AGENT_TOOL_NAME) {
    if (ruleContent) {
      // 解析逗号分隔的 agent types: "worker, researcher" → ["worker", "researcher"]
      allowedAgentTypes = ruleContent.split(',').map(s => s.trim())
    }
    if (!isMainThread) {
      validTools.push(toolSpec)
      continue  // 子代理 Agent 工具被 filterToolsForAgent 移除，跳过解析
    }
    // 主线程时 fall through 走常规
  }

  const tool = availableToolMap.get(toolName)
  if (tool) {
    validTools.push(toolSpec)
    if (!resolvedToolsSet.has(tool)) {
      resolved.push(tool)
      resolvedToolsSet.add(tool)
    }
  } else {
    invalidTools.push(toolSpec)
  }
}
```

agent frontmatter 里能写：

```yaml
tools: Read, Edit, Agent(worker, researcher)
```

`Agent(worker, researcher)` 的语法表示"这个 agent 可以 spawn worker 和 researcher 类型的子代理，不能 spawn 其它"。`allowedAgentTypes` 跟着传到子代理的 `toolUseContext.options.agentDefinitions.allowedAgentTypes`，最终影响 `AgentTool.prompt()` 渲染时只列允许的类型。

## 父代理工具池 vs 子代理工具池：一个例子

设父代理在 `plan` permissionMode，可见工具：

```text
parentTools = [Read, Glob, Grep, FileRead, WebFetch, Agent, ExitPlanMode]
              ─ Edit / Write / Bash / NotebookEdit 被 plan 模式排除
```

父代理 spawn 一个 `general-purpose`（`tools: ['*']`, `permissionMode` 未指定 → acceptEdits）：

```text
workerPermissionContext.mode = 'acceptEdits'
workerTools = assembleToolPool(workerPermissionContext, mcpTools)
            = [Read, Glob, Grep, FileRead, FileEdit, FileWrite, Bash, NotebookEdit, Agent, ...]
            ─ acceptEdits 模式比 plan 模式开放，所以 Edit/Write/Bash 都在

filteredAvailableTools (filterToolsForAgent 后)
  drop ALL_AGENT_DISALLOWED_TOOLS（如 SkillTool）
  drop CUSTOM_AGENT_DISALLOWED_TOOLS（仅 custom agent）
  general-purpose 是 built-in, 跳过 custom 过滤
  isAsync 默认 false, 跳过 ASYNC 过滤
  → [Read, Glob, Grep, FileRead, FileEdit, FileWrite, Bash, NotebookEdit, Agent, ...]

应用 disallowedTools (general-purpose 没写) → 不变

应用 tools (['*']) → hasWildcard=true → 等于上一步

最终 resolvedTools = [Read, Glob, Grep, FileRead, FileEdit, FileWrite, Bash, NotebookEdit, Agent, ...]
```

父代理在 plan 模式不能 Edit，但 spawn 的 general-purpose 子代理能 Edit——这就是设计意图。

再看 spawn `Explore`：

```text
Explore.tools 未定义（继承）
Explore.disallowedTools = [Agent, ExitPlanMode, Edit, Write, NotebookEdit]
Explore.permissionMode 未指定 → acceptEdits

workerTools 同上 (acceptEdits 起算)

filteredAvailableTools 同上 (built-in)

应用 disallowedTools = [Agent, ExitPlanMode, Edit, Write, NotebookEdit] → 去掉这 5 个

应用 tools (未定义) → hasWildcard=true → 剩下的全集

最终 resolvedTools = [Read, Glob, Grep, FileRead, Bash, ...]
                       ↑ FileEdit / FileWrite / NotebookEdit 被 disallow 砍掉
```

注意 Explore 的 `disallowedTools` 写的是常量名 `FILE_EDIT_TOOL_NAME` = `'Edit'`，对应 tool 的 `name` 字段。`permissionRuleValueFromString` 还允许带模式（如 `'Bash(npm install:*)'`）的精细规则——agentToolUtils 解析时提取 `toolName` 用于"是否 disallow"判断，`ruleContent` 在 Agent 工具的场景下另作他用。

## fork 隔离机制详解

### 触发条件

```typescript
// AgentTool.tsx:322
const effectiveType = subagent_type ?? (isForkSubagentEnabled() ? undefined : GENERAL_PURPOSE_AGENT.agentType)
const isForkPath = effectiveType === undefined
```

`subagent_type` 省略 + `isForkSubagentEnabled()` 为 true → fork 路径。否则省略 → general-purpose。

`isForkSubagentEnabled()` 要求：

- `feature('FORK_SUBAGENT')` 开启
- 不在 coordinator mode
- 不在 non-interactive session

### FORK_AGENT 合成定义

`forkSubagent.ts:60-71`：

```typescript
export const FORK_AGENT = {
  agentType: FORK_SUBAGENT_TYPE,     // 'fork'
  whenToUse: 'Implicit fork — inherits full conversation context. ...',
  tools: ['*'],
  maxTurns: 200,
  model: 'inherit',
  permissionMode: 'bubble',
  source: 'built-in',
  baseDir: 'built-in',
  getSystemPrompt: () => '',          // 实际不调用：用父的 renderedSystemPrompt
} satisfies BuiltInAgentDefinition
```

注释：FORK_AGENT **不注册**在 `builtInAgents`——它不出现在 agent 列表里，只在 `subagent_type` 省略时才触发。`tools: ['*'] + useExactTools` 意味着旁路 `resolveAgentTools`，直接用父的工具数组。

### messages 继承的实现

`forkSubagent.ts:107-169` 的 `buildForkedMessages`：

```text
输入：
  parent assistantMessage（含全部 tool_use blocks）
  directive（fork 的指令字符串）

输出：
  [
    {
      role: 'assistant',
      content: [
        ...parent.content,    // text + thinking + 所有 tool_use 块原样
      ]
    },
    {
      role: 'user',
      content: [
        { type: 'tool_result', tool_use_id: a.id, content: [{type:'text', text: 'Fork started — processing in background'}] },
        { type: 'tool_result', tool_use_id: b.id, content: [{type:'text', text: 'Fork started — processing in background'}] },
        ... // 每个 parent tool_use 都配一个 placeholder result
        { type: 'text', text: buildChildMessage(directive) },
      ]
    }
  ]
```

`buildChildMessage` 把 directive 包装在 `<fork-boilerplate>` 标签里 + `<fork-directive>` 标签里（见 02 篇）。

`AgentTool.tsx:512` 之后 push 进 promptMessages：

```typescript
promptMessages = buildForkedMessages(prompt, assistantMessage)
```

`runAgent.ts:370-373` 把 `forkContextMessages`（父对话历史）和 promptMessages 拼起来：

```typescript
const contextMessages: Message[] = forkContextMessages
  ? filterIncompleteToolCalls(forkContextMessages)
  : []
const initialMessages: Message[] = [...contextMessages, ...promptMessages]
```

最终 fork 子代理的 messages 是：

```text
[
  ...父对话 history,                    // forkContextMessages
  父最后的 assistantMessage 副本,        // promptMessages[0]
  用户角色的 placeholder + directive,   // promptMessages[1]
]
```

filterIncompleteToolCalls 是关键的清理步骤：父对话里可能有 tool_use 没对应 tool_result（比如当前 fork 这个 tool_use 还没回结果），这种 orphan 在 API 上会 400。所以过滤掉所有"无 result 的 tool_use 块所在的 assistant message"。

### 递归 fork 守卫

```typescript
// AgentTool.tsx:332
if (toolUseContext.options.querySource === `agent:builtin:${FORK_AGENT.agentType}` || isInForkChild(toolUseContext.messages)) {
  throw new Error('Fork is not available inside a forked worker. ...')
}
```

两道线：

1. **querySource 主线**：fork 子代理的 `toolUseContext.options.querySource` 被设成 `'agent:builtin:fork'`（`runAgent.ts:694`）。检查这个等于查"我现在是不是 fork 子代理"。autocompact 不会重写 context.options，所以这条很稳。
2. **message scan 备用**：`isInForkChild()` 扫 messages 看有没有 `<fork-boilerplate>` 标签。autocompact 可能压缩/重写 message，所以这是兜底。

为什么 fork 子代理不能再 fork？因为 fork 的语义是"父对话的另一条分支"，"分支的分支"会让 mailbox 树形结构爆炸，且没有有意义的 cache 共享路径。

### fork 的 worktree 提示

```typescript
// AgentTool.tsx:598-602
if (isForkPath && worktreeInfo) {
  promptMessages.push(createUserMessage({
    content: buildWorktreeNotice(getCwd(), worktreeInfo.worktreePath)
  }))
}
```

fork + worktree 组合时，给子代理追加一条 user message：

```text
You've inherited the conversation context above from a parent agent working in <parentCwd>. You are operating in an isolated git worktree at <worktreeCwd> — same repository, same relative file structure, separate working copy. Paths in the inherited context refer to the parent's working directory; translate them to your worktree root. Re-read files before editing if the parent may have modified them since they appear in the context. Your changes stay in this worktree and will not affect the parent's files.
```

让子代理知道"上下文里的路径是父 cwd，但你在 worktree——读文件前先按 worktree 路径重读，避免读到 stale 内容"。

## worktree 隔离机制

### 触发与创建

`AgentTool.tsx:589-602`：

```typescript
const earlyAgentId = createAgentId()

let worktreeInfo: {
  worktreePath: string
  worktreeBranch?: string
  headCommit?: string
  gitRoot?: string
  hookBased?: boolean
} | null = null
if (effectiveIsolation === 'worktree') {
  const slug = `agent-${earlyAgentId.slice(0, 8)}`
  worktreeInfo = await createAgentWorktree(slug)
}
```

`createAgentWorktree`（`src/utils/worktree.ts:902`）执行 `git worktree add` 创建临时工作树：

- 路径通常是 `<gitRoot>/.claude/worktrees/agent-<slug>/`
- 分支名是 `claude-agent-<slug>` 之类
- 记录 headCommit 用于后续判定"有没有改动"

### cwd 切换

```typescript
// AgentTool.tsx:640-641
const cwdOverridePath = cwd ?? worktreeInfo?.worktreePath
const wrapWithCwd = <T,>(fn: () => T): T =>
  cwdOverridePath ? runWithCwdOverride(cwdOverridePath, fn) : fn()
```

`runWithCwdOverride`（`src/utils/cwd.ts`）用 AsyncLocalStorage 设置 cwd 覆盖。所有读 `getCwd()` 的代码——FileRead、FileEdit、Bash 的 cwd、git 命令——都在 worktree 内执行。

注意：是 AsyncLocalStorage，不是 `process.chdir`。process 的真实 cwd 没变，只有看 `getCwd()` 的代码被影响。这避免了多个子代理同时切 process cwd 的竞态。

### 清理决策

`AgentTool.tsx:644-685`：

```typescript
const cleanupWorktreeIfNeeded = async (): Promise<{ worktreePath?: string; worktreeBranch?: string }> => {
  if (!worktreeInfo) return {}
  const { worktreePath, worktreeBranch, headCommit, gitRoot, hookBased } = worktreeInfo
  worktreeInfo = null  // idempotent

  if (hookBased) {
    // Hook-based worktree 始终保留（无法检测 VCS 变更）
    logForDebugging(`Hook-based agent worktree kept at: ${worktreePath}`)
    return { worktreePath }
  }
  if (headCommit) {
    const changed = await hasWorktreeChanges(worktreePath, headCommit)
    if (!changed) {
      await removeAgentWorktree(worktreePath, worktreeBranch, gitRoot)
      // 清掉 metadata.worktreePath，避免 resume 时指向不存在的目录
      void writeAgentMetadata(asAgentId(earlyAgentId), {
        agentType: selectedAgent.agentType,
        description,
      }).catch(...)
      return {}
    }
  }
  logForDebugging(`Agent worktree has changes, keeping: ${worktreePath}`)
  return { worktreePath, worktreeBranch }
}
```

策略：

- 子代理结束时 `hasWorktreeChanges(worktreePath, headCommit)` 检查有没有改动。
- **无改动** → `removeAgentWorktree` 删 worktree + 删分支，metadata 也清掉。"试探性 spawn 不留痕"。
- **有改动** → 保留 worktree，把 worktreePath 和 worktreeBranch 写到 `tool_result.content` 末尾让父代理知道。
- **hook-based** 一律保留（不知道有没有改）。

这种"按需保留"是 worktree 模式的灵魂——绝大多数 spawn 是试探性的，无改动时自动清理；少数确实改了东西的会保留，给后续 review / merge / discard 用。

### 父代理拿到的回填

```text
[子代理的输出 content blocks]

worktreePath: /Users/.../.claude/worktrees/agent-7f8e9012/
worktreeBranch: claude-agent-7f8e9012
```


## fork × worktree 矩阵

| fork? | worktree? | 含义 |
|-------|-----------|------|
| No  | No  | 普通子代理：从零开始的对话 + 父 cwd |
| No  | Yes | 普通子代理 + 独立文件视图：典型"派人去 sandbox 试一下" |
| Yes | No  | fork 子代理：继承对话 + 父 cwd：典型"分叉一条思路接着研究" |
| Yes | Yes | fork + sandbox：继承对话 + 独立文件：典型"分叉一条思路 + 沙箱实施" |

四种组合各有用途，源码全支持。fork + worktree 时额外追加 `buildWorktreeNotice` 提示。

## 容易踩的点

1. **子代理 spawn 时父的 permission mode 不影响子的工具池**：子代理用自己的 `permissionMode ?? 'acceptEdits'` 重新算 workerTools。
2. **`tools: ['*']` 不是字面通配符**：源码识别成 `hasWildcard = true`，等同于"不写 tools 字段"。
3. **`disallowedTools` 在 `tools` 之前应用**：先按 disallowedTools 砍掉，再按 tools 选取。`tools: [A]` + `disallowedTools: [A]` = 空。
4. **fork 子代理保留 `Agent` 工具但通过 querySource 守卫禁再 fork**：是为了 cache 一致。如果想"递归 fork 一层"，源码层面拒绝。
5. **worktree 是 AsyncLocalStorage 切 cwd 不是 process.chdir**：同进程并发子代理可以各自跑在不同 worktree，互不影响。
6. **worktree 清理只看 git diff vs headCommit**：未追踪文件（gitignore 的、`.env` 之类）也会被算成"有改动"——所以子代理跑测试可能创建临时文件让 worktree 被保留。
7. **`hook-based` worktree 始终保留**：源码识别到 worktree 是通过 PreCompactHook 之类创建的（非 git worktree add），无法可靠检测改动，保守保留。
8. **`isolation: "remote"` 不创建 worktree**：remote 走 CCR，自己有 sandbox，不需要本地 worktree。`effectiveIsolation === 'remote'` 时直接 return 不到 worktree 分支。
